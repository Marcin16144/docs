Interactive rebase - przepisywanie historii

git rebase -i to potezne narzedzie do edycji historii commitow. Pozwala laczyc, dzielic, zmieniac kolejnosc i edytowac commity. Standardowy use case to czyszczenie historii feature branch przed mergem.

# Edycja ostatnich 5 commitow
git rebase -i HEAD~5

# Otwiera edytor:
pick abc1234 feat: add login form
pick def5678 fix: typo in login
pick ghi9012 fix: another typo
pick jkl3456 fix: yet another typo
pick mno7890 feat: add validation

# Komendy dostepne:
# pick   - uzyj commit jak jest
# reword - uzyj, zmien wiadomosc
# edit   - uzyj, zatrzymaj na edycje (split, amend)
# squash - polacz z poprzednim, edytuj wiadomosc obu
# fixup  - jak squash, ale wiadomosc fixupa odrzucona
# drop   - usun commit
# exec   - wykonaj komende powloki
# break  - zatrzymaj sie tutaj

# Po edycji - typowe sprzatanie:
pick abc1234 feat: add login form
fixup def5678 fix: typo in login
fixup ghi9012 fix: another typo
fixup jkl3456 fix: yet another typo
reword mno7890 feat: add login validation

Squash - laczenie commitow

# Przyklad - chcemy z 5 commitow zrobic 2

git rebase -i HEAD~5

# Edytor:
pick abc1234 feat: add login form
squash def5678 fix: typo in login
squash ghi9012 fix: another typo
pick jkl3456 feat: add validation
squash mno7890 fix: validation edge case

# Po zapisie - Git otworzy drugi edytor z polaczonymi wiadomosciami:
# Edit message for the first commit:
feat: add login form
fix: typo in login
fix: another typo

# Zostaw wlasciwa wiadomosc, np:
feat: add complete login form

# Powtorka dla drugiego squasha
feat: add validation

Edit - splitting commita

# Stary commit zawiera za duzo zmian, chcemy go podzielic
git rebase -i HEAD~3

pick abc1234 feat: add login form
edit def5678 feat: add EVERYTHING (auth + ui + api)   # zbyt duzy
pick ghi9012 fix: typo

# Git zatrzyma sie na commit def5678
# Reset do stanu sprzed commita
git reset HEAD^

# Teraz pliki sa unstaged - mozemy commitowac stopniowo
git add src/auth/
git commit -m "feat: add authentication backend"

git add src/ui/
git commit -m "feat: add login UI"

git add src/api/
git commit -m "feat: add API endpoints"

# Kontynuuj rebase
git rebase --continue

Autosquash - elegancki workflow

# Zamiast pamiętac ktory commit poprawiamy, mozna oznaczyc commit jako fixup

# Wlacz autosquash domyslnie
git config --global rebase.autosquash true

# Workflow - ostatni commit ma blad
git commit -m "feat: add user list"

# Znajdujesz blad, naprawiasz
echo "fix" > file.js

# Commit z fixup wskazujacym hash do poprawienia
git commit --fixup=abc1234

# Albo jeszcze lepiej - z hashem skroconym
git add .
git commit --fixup=HEAD~2

# Pozniej, przed PR, automatyczny rebase
git rebase -i --autosquash HEAD~10
# fixup commity sa AUTOMATYCZNIE wstawione w odpowiednie miejsca

git reflog - bezpiecznik na bledy

reflog (reference log) to lokalna historia wszystkich zmian HEAD. Pokazuje wszystko co kiedykolwiek robiles - nawet usuniete commity. Jest twoim ratunkiem przy katastrofalnych pomylkach.

# Pokaz historie HEAD
git reflog

# Przyklad wyjscia:
# abc1234 HEAD@{0}: reset: moving to HEAD~3
# def5678 HEAD@{1}: commit: feat: important feature
# ghi9012 HEAD@{2}: pull: Fast-forward
# jkl3456 HEAD@{3}: checkout: moving from main to feature

# Reflog konkretnej galezi
git reflog show feature/login

# UWAGA: reflog jest LOKALNY - nie udostepnia sie z push'em
# Domyslnie wpisy wygasaja po 90 dniach

Recovery scenariuszy

# SCENARIUSZ 1: Niechcaco zrobiles git reset --hard
git reset --hard abc1234       # ups!

git reflog
# def5678 HEAD@{1}: commit: feat: important feature
# abc1234 HEAD@{0}: reset: moving to HEAD~3

git reset --hard def5678       # przywrocone!

# SCENARIUSZ 2: Usunieta galaz
git branch -D feature/important   # ups!

git reflog
# Znajdz ostatni commit z tej galezi
# abc1234 HEAD@{5}: commit: WIP on feature/important

git checkout -b feature/important abc1234

# SCENARIUSZ 3: Niechcaco zrobiles rebase i sa konflikty/blędy
git rebase main      # poszlo zle
git rebase --abort   # wraca do stanu przed rebase

# Lub jak juz po rebase:
git reflog
# Znajdz wpis "rebase: " - ten ostatni przed nim to stan przed
git reset --hard HEAD@{8}

git bisect - znajdowanie bugow

bisect uzywa wyszukiwania binarnego do znalezienia commita, ktory wprowadzil blad. Przy 1000 commitach znajdziesz winowajce w 10 krokach.

# Zaczynamy bisect
git bisect start

# Oznaczamy biezacy commit jako zly (bug obecny)
git bisect bad

# Oznaczamy stary commit jako dobry (wszystko dzialalo)
git bisect good v1.0.0
# lub konkretny hash
git bisect good abc1234

# Git automatycznie checkout commit w polowie
# Testujemy aplikacje

# Jesli bug obecny:
git bisect bad

# Jesli OK:
git bisect good

# Jesli commit nie da sie przetestowac (np. nie kompiluje):
git bisect skip

# Powtarzaj az Git wyswietli "first bad commit":
# abc1234 is the first bad commit
# commit abc1234
# Author: ...
# Date:   ...
#     feat: refactor payment service

# Sprzatanie po skonczeniu
git bisect reset

Automatyczny bisect ze skryptem

# Skrypt zwraca exit code:
# 0       - dobry commit
# 1-127   - zly commit (poza 125)
# 125     - skip
# 128+    - przerwij bisect

# Plik test-bug.sh:
#!/bin/bash
npm test -- --grep "specific test"

# Uruchom bisect z automatyzacja
git bisect start HEAD v1.0.0
git bisect run ./test-bug.sh

# Git sam wykona kroki i znajdzie bad commit

git worktree - wiele galezi w roznych katalogach

worktree pozwala miec wiele galezi wycheckoutowanych w roznych katalogach jednoczesnie. Idealne gdy chcesz rownolegle pracowac nad feature i hotfixem bez stashowania.

# Lista istniejacych worktrees
git worktree list

# Stworz nowy worktree dla istniejacej galezi
git worktree add ../projekt-hotfix hotfix/critical

# Stworz nowy worktree z nowa galezia
git worktree add -b feature/login ../projekt-login

# Z konkretnego commita
git worktree add ../projekt-old v1.0.0

# Praca:
cd ../projekt-hotfix
# Edytuj, commituj, pushuj
git push

cd ../projekt-login
# Pracuj w izolacji - to jest osobny katalog z osobnym working tree

# Po skonczeniu - usun worktree
git worktree remove ../projekt-hotfix

# Wymus jesli sa niezacommitowane zmiany
git worktree remove --force ../projekt-hotfix

# Sprzatanie nieaktualnych referencji (po manual delete katalogu)
git worktree prune
Worktree use cases:
  • Pilny hotfix bez przerywania pracy nad feature
  • Testowanie dwoch wersji aplikacji obok siebie
  • Code review PR bez stashowania wlasnych zmian
  • Build i deploy starej wersji bez ruszania biezacej

Submodules - repo w repo

Submodule to sposob na zaglebienie jednego repozytorium git wewnatrz drugiego. Glowne repo trzyma referencje do konkretnego commita w submodule. Uzywane gdy musisz zalezec od konkretnej wersji innego repo.

# Dodanie submodule
git submodule add https://github.com/user/library.git libs/library

# Po dodaniu w main repo pojawia sie:
# - .gitmodules (konfiguracja)
# - libs/library/ (zaglebione repo, ale to wskaznik do commita)

git status
# new file:   .gitmodules
# new file:   libs/library

git commit -m "Add library submodule"

# Klonowanie repo z submodulami
git clone --recurse-submodules https://github.com/user/main-repo.git

# Lub jesli juz sklonowales bez --recurse:
git submodule init
git submodule update

# Krocej - od Git 2.13:
git submodule update --init --recursive

# Aktualizacja submodulow do najnowszej wersji
cd libs/library
git pull origin main
cd ../..
git add libs/library
git commit -m "Update library submodule"

# Aktualizacja wszystkich submodulow w jednej komendzie
git submodule update --remote --merge

# Status submodulow
git submodule status

# Wykonanie komendy w kazdym submodule
git submodule foreach 'git checkout main'

Sparse-checkout - czesciowe klonowanie

W ogromnych monorepo czesto nie potrzebujesz wszystkich plikow. Sparse-checkout pozwala wycheckoutowac tylko wybrane katalogi.

# Inicjalizacja sparse-checkout (Git 2.25+)
git clone --no-checkout https://github.com/big/monorepo.git
cd monorepo

# Wlaczenie sparse-checkout (cone mode - prostszy)
git sparse-checkout init --cone

# Wybor katalogow
git sparse-checkout set apps/web libs/shared

# Sprawdzenie konfiguracji
git sparse-checkout list

# Checkout
git checkout main

# W working tree masz tylko apps/web i libs/shared
# Pozostale katalogi nie zajmuja miejsca

# Dodanie kolejnego katalogu
git sparse-checkout add libs/utils

# Wylaczenie
git sparse-checkout disable

Partial clone - jeszcze efektywniej

# Klon bez blobow (tylko historia commitow)
git clone --filter=blob:none https://github.com/big/repo.git

# Bloby pobierane sa on-demand przy checkout

# Albo bez plikow > 100MB
git clone --filter=blob:limit=100m https://github.com/big/repo.git

# Treeless - jeszcze mniej (tylko commit objects)
git clone --filter=tree:0 https://github.com/big/repo.git

# Polaczenie z sparse-checkout daje minimalny working set

Git LFS - duze pliki

Git LFS (Large File Storage) zastepuje duze pliki binarne wskaznikami. Same pliki sa hostowane na osobnym serwerze. Niezbedne dla repo z grafika, modelami ML, video.

# Instalacja
sudo apt install git-lfs

# Inicjalizacja w repo (jednorazowo)
git lfs install

# Trackowanie typow plikow
git lfs track "*.psd"
git lfs track "*.zip"
git lfs track "*.mp4"
git lfs track "models/*.bin"

# Tworzy/aktualizuje .gitattributes
git add .gitattributes
git commit -m "Configure Git LFS"

# Standardowy workflow - LFS dziala transparentnie
git add design.psd
git commit -m "Add design"
git push

# Lista plikow LFS
git lfs ls-files

# Sprawdzenie statusu
git lfs status

# Migracja istniejacych plikow do LFS (UWAGA - zmienia historie!)
git lfs migrate import --include="*.zip"

# Limity LFS:
# GitHub: 1GB free, max 2GB per file
# GitLab: 10GB free
# Bitbucket: 1GB free

Git hooks

Hooks to skrypty wywolywane automatycznie przy roznych zdarzeniach Git. Sa w katalogu .git/hooks/ - przyklady z koncowka .sample. Aby aktywowac, usun rozszerzenie i nadaj uprawnienia wykonywania.

HookKiedyTypowe uzycie
pre-commitPrzed wykonaniem commitaLint, formatowanie, testy
commit-msgPo wpisaniu commit messageWalidacja Conventional Commits
pre-pushPrzed pushemPelne testy, build
post-commitPo commiciePowiadomienia, statystyki
pre-rebasePrzed rebasemOstrzezenie przed niebezpiecznym rebase
post-mergePo mergeAuto-instalacja zaleznosci

Przyklad pre-commit

#!/bin/bash
# .git/hooks/pre-commit

# Lint Pythona
files=$(git diff --cached --name-only --diff-filter=ACM | grep '\.py$')
if [ -n "$files" ]; then
    echo "Running flake8..."
    flake8 $files || exit 1

    echo "Running black..."
    black --check $files || {
        echo "Run 'black .' to fix formatting"
        exit 1
    }
fi

# Lint JavaScript
files=$(git diff --cached --name-only --diff-filter=ACM | grep -E '\.(js|ts|jsx|tsx)$')
if [ -n "$files" ]; then
    npx eslint $files || exit 1
fi

# Sprawdz brak debuggerow
if git diff --cached | grep -E '(debugger|console\.log|binding\.pry)'; then
    echo "Found debug statements in commit!"
    exit 1
fi

exit 0

Husky - hooks dla projektow Node.js

# Instalacja
npm install --save-dev husky lint-staged

# Inicjalizacja
npx husky init

# package.json
{
  "scripts": {
    "prepare": "husky"
  },
  "lint-staged": {
    "*.{js,ts,jsx,tsx}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{css,scss,md}": [
      "prettier --write"
    ]
  }
}

# .husky/pre-commit
npx lint-staged

# .husky/commit-msg
npx --no -- commitlint --edit $1

# .husky/pre-push
npm test

Pre-commit framework (uniwersalny)

# Instalacja
pip install pre-commit
# lub: brew install pre-commit

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
        args: ['--maxkb=500']
      - id: detect-private-key

  - repo: https://github.com/psf/black
    rev: 24.1.0
    hooks:
      - id: black

  - repo: https://github.com/pycqa/flake8
    rev: 7.0.0
    hooks:
      - id: flake8

# Instalacja hookow
pre-commit install
pre-commit install --hook-type commit-msg

# Uruchomienie recznie
pre-commit run --all-files
Inne zaawansowane techniki:
  • git blame - kto zmienil dana linie i kiedy
  • git log -S "kod" - znajdz commit dodajacy/usuwajacy konkretny tekst
  • git filter-branch / git filter-repo - masowa edycja historii
  • git replace - zastapienie commita bez przepisywania historii
  • git notes - dodawanie metadanych do commitow bez modyfikacji
  • git archive - eksport zawartosci jako tarball/zip
