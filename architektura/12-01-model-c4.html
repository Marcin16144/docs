Model C4

Cztery poziomy abstrakcji architektury — Context, Containers, Components, Code — i Structurizr DSL.

Cztery poziomy

L1: System Context  — "Jak system wpisuje sie w swiat?"
L2: Container       — "Z jakich czesci sklada sie system?"
L3: Component       — "Jak wyglada wnetrze kontenera?"
L4: Code            — "Jak wyglada kod?" (rzadko uzywany)

Poziom 1: System Context

System jako czarna skrzynka w kontekscie uzytkownikow i systemow zewnetrznych.

┌─────────────┐
│   Klient    │
└──────┬──────┘
       │ uzywa
       ▼
┌──────────────┐     ┌───────────────┐
│   System     │────→│ Stripe        │
│  E-commerce  │     │ (platnosci)   │
└──────┬───────┘     └───────────────┘
       │ emaile
       ▼
┌──────────────┐
│  SendGrid    │
└──────────────┘

Kiedy: poczatek projektu, onboarding, rozmowy z biznesem.

Poziom 2: Container

Wnetrze systemu — oddzielne deployable units: aplikacje, bazy, kolejki.

┌────────────────────────────────────────────┐
│            System E-commerce                │
│                                             │
│  Frontend ──→ API ──→ PostgreSQL           │
│  (React)     (Node.js)                     │
│               │                             │
│               ├──→ Redis (cache)           │
│               └──→ RabbitMQ (kolejka)      │
│                       │                     │
│                    Worker (background jobs) │
└────────────────────────────────────────────┘

Kiedy: planowanie architektury, decyzje technologiczne, dokumentacja dla zespolu.

Poziom 3: Component

Wnetrze jednego kontenera — moduly, serwisy, kontrolery.

┌───────────────────────────────────────┐
│           API Container                │
│                                        │
│  Auth Middleware                       │
│       ↓                                │
│  Order Controller (/api/orders)        │
│       ↓                                │
│  Order Service (logika biznesowa)      │
│       │           │           │        │
│  Order Repo   Payment GW   Email      │
│       ↓          ↓          Sender    │
│  PostgreSQL   Stripe        ↓         │
│                           SendGrid     │
└───────────────────────────────────────┘

Kiedy: planowanie funkcjonalnosci, code review architektury modulu.

Poziom 4: Code

Klasy, interfejsy, UML — rzadko tworzony recznie. Generowany automatycznie z kodu. Jesli potrzebujesz diagramu kodu — moze kod jest za skomplikowany.

Structurizr DSL

Diagramy C4 jako kod — wersjonowanie w Git, automatyczne generowanie.

workspace "E-commerce" {
  model {
    customer = person "Klient" "Kupuje produkty"

    ecommerce = softwareSystem "E-commerce" {
      frontend = container "Frontend" "React SPA" "TypeScript"
      api = container "API" "REST API" "Node.js / Express" {
        orderController = component "Order Controller"
        orderService = component "Order Service"
        orderRepo = component "Order Repository"
      }
      database = container "Database" "PostgreSQL" "" "database"
      cache = container "Cache" "Redis"
    }

    stripe = softwareSystem "Stripe" "Platnosci" "external"

    customer -> frontend "Przegladarka"
    frontend -> api "HTTPS / JSON"
    api -> database "SQL"
    api -> cache "Redis protocol"
    api -> stripe "HTTPS"
  }

  views {
    systemContext ecommerce "Context" {
      include *
      autoLayout
    }
    container ecommerce "Containers" {
      include *
      autoLayout
    }
  }
}

Kluczowe wnioski

  1. 4 poziomy abstrakcji — od panoramy do detalu
  2. Context (L1) dla interesariuszy — kto, co, z czym sie laczy
  3. Container (L2) dla zespolu — decyzje technologiczne
  4. Component (L3) dla developerow — wnetrze kontenera
  5. Code (L4) rzadko potrzebny — generuj automatycznie
  6. Structurizr DSL — diagram-as-code, wersjonowanie w Git
  7. Aktualizuj — nieaktualny diagram gorszy niz brak diagramu
