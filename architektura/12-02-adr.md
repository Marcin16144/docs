# Architecture Decision Records (ADR)

## Czym jest ADR?

Architecture Decision Record to krotki dokument opisujacy jedna konkretna decyzje architektoniczna. ADR odpowiada na pytanie: "Dlaczego wybralismy to rozwiazanie, a nie inne?" — i zachowuje kontekst decyzji dla przyszlych zespolow.

## Dlaczego ADR?

```
Bez ADR:
  Developer: "Dlaczego uzywamy MongoDB zamiast PostgreSQL?"
  Zespol: "Nie wiem, ktos tak zdecydowal 2 lata temu"
  Developer: "Moze zmienmy?"
  → Powtarzanie tych samych dyskusji
  → Brak kontekstu dlaczego

Z ADR:
  Developer: "Dlaczego uzywamy MongoDB?"
  → Czyta ADR-007: "Wybor bazy danych dla katalogu produktow"
  → Kontekst, alternatywy, uzasadnienie, konsekwencje
  → Swiadoma decyzja czy zmieniac czy nie
```

## Struktura ADR

### Szablon podstawowy (Michael Nygard)

```markdown
# ADR-001: Tytul decyzji

## Status
Zaakceptowany | Zaproponowany | Wycofany | Zastapiony przez ADR-XXX

## Kontekst
Jaka sytuacja/problem wymagal podjecia decyzji?
Jakie ograniczenia i wymagania istnialy?

## Decyzja
Co zdecydowalismy?

## Konsekwencje
Jakie sa pozytywne i negatywne skutki tej decyzji?
```

## Przyklady ADR

### Przyklad 1: Wybor bazy danych

```markdown
# ADR-007: PostgreSQL jako glowna baza danych

## Status
Zaakceptowany

## Data
2025-01-20

## Kontekst
Budujemy system e-commerce, ktory musi obslugiwac:
- Transakcje finansowe (zamowienia, platnosci)
- Relacje miedzy uzytkownikami, zamowieniami i produktami
- Wyszukiwanie produktow (full-text search)
- Elastyczny schemat dla atrybutow produktow

Zespol ma doswiadczenie z PostgreSQL i MongoDB.
Budzet nie pozwala na managed services premium.

## Rozwazone opcje

### PostgreSQL
- Zalety: ACID, relacje, JSONB, full-text search, darmowy
- Wady: Skalowanie horyzontalne trudniejsze

### MongoDB
- Zalety: Elastyczny schemat, horyzontalne skalowanie
- Wady: Brak ACID miedzy kolekcjami, JOIN-y drogie

### MySQL
- Zalety: Prosty, popularny
- Wady: Slabsze typy danych, brak JSONB, slabszy full-text

## Decyzja
Wybralismy PostgreSQL, poniewaz:
1. ACID jest krytyczne dla transakcji finansowych
2. JSONB rozwiazuje potrzebe elastycznego schematu
3. Wbudowany full-text search eliminuje potrzebe Elasticsearch
4. Zespol ma doswiadczenie z PostgreSQL

## Konsekwencje

### Pozytywne
- Jedna baza zamiast dwoch (PostgreSQL + Elasticsearch)
- Silne gwarancje spojnosci dla transakcji
- Duzy ekosystem narzedzi (pgAdmin, Flyway)

### Negatywne
- Skalowanie horyzontalne bedzie wymagalo Citus lub read replicas
- Full-text search PostgreSQL moze byc niewystarczajacy
  przy duzym wolumenie (rozwazymy Elasticsearch w przyszlosci)

## Uczestnicy
Jan Kowalski (Tech Lead), Anna Nowak (Backend), Tomek Zielinski (DBA)
```

### Przyklad 2: Wybor strategii komunikacji

```markdown
# ADR-012: Asynchroniczna komunikacja miedzy serwisami przez RabbitMQ

## Status
Zaakceptowany

## Data
2025-02-10

## Kontekst
System e-commerce ma 5 serwisow: Orders, Payments,
Inventory, Notifications, Analytics. Potrzebujemy
niezawodnej komunikacji miedzy nimi.

Wymagania:
- Utrata wiadomosci jest niedopuszczalna (platnosci)
- Serwisy musza byc niezalezne (loose coupling)
- Opoznienie dostarczenia < 1s dla wiekszosci przypadkow

## Rozwazone opcje

### REST (synchroniczny)
- Proste, znane zespolowi
- Problem: tight coupling, kaskadowe awarie

### RabbitMQ
- Dojrzaly, niezawodny, wsparcie dla roznych wzorcow
- Srednia zlozonosc operacyjna

### Apache Kafka
- Event streaming, replayability, wysoka przepustowosc
- Wysoka zlozonosc operacyjna, overengineering dla naszej skali

## Decyzja
RabbitMQ — niezawodna dostawa wiadomosci bez zlozonosci Kafki.

## Konsekwencje

### Pozytywne
- Loose coupling miedzy serwisami
- Odpornosc na chwilowe awarie (wiadomosci w kolejce)
- Eventual consistency wystarczy dla naszych przypadkow

### Negatywne
- Brak replayability (w przeciwienstwie do Kafki)
- Dodatkowa infrastruktura do utrzymania
- Zespol musi nauczyc sie asynchronicznych wzorcow
```

## Cykl zycia ADR

```
1. PROPOSED (zaproponowany)
   → Autor pisze ADR, otwiera PR
   → Dyskusja w zespole

2. ACCEPTED (zaakceptowany)
   → Zespol zgadza sie z decyzja
   → PR zmergowany

3. DEPRECATED (wycofany)
   → Decyzja przestala byc aktualna
   → Ale kontekst jest nadal wartosciowy

4. SUPERSEDED (zastapiony)
   → Nowy ADR zastepuje ten
   → Link do nowego: "Zastapiony przez ADR-025"
```

```
ADR-007: PostgreSQL jako baza danych
  Status: Zastapiony przez ADR-025
  
ADR-025: Migracja z PostgreSQL do CockroachDB
  Status: Zaakceptowany
  Kontekst: "ADR-007 zaklada wertykalne skalowanie,
  ale osiagnelismy limit jednego serwera..."
```

## Narzedzia

### adr-tools (CLI)

```bash
# Instalacja
brew install adr-tools

# Inicjalizacja
adr init doc/architecture/decisions

# Nowy ADR
adr new "Wybor frameworka frontendowego"
# → Tworzy: doc/architecture/decisions/0001-wybor-frameworka.md

# Nowy ADR zastepujacy stary
adr new -s 3 "Migracja z React do Next.js"
# → Tworzy nowy ADR i aktualizuje status ADR-003

# Lista ADR
adr list

# Generowanie spisu tresci
adr generate toc
```

### log4brains

Web UI do przegladania ADR — generuje statyczna strone z historii decyzji:

```bash
# Instalacja
npm install -g log4brains

# Inicjalizacja
log4brains init

# Nowy ADR
log4brains adr new "Wybor message brokera"

# Podglad lokalny
log4brains preview

# Budowanie statycznej strony
log4brains build
# → out/ (deploy na GitHub Pages)
```

## Proces review ADR

```
1. Autor tworzy ADR jako PR (Pull Request)
   - Wypelnia szablon
   - Status: Proposed

2. Zespol reviewuje PR
   - Komentarze, pytania, sugestie
   - Czy kontekst jest kompletny?
   - Czy alternatywy sa uczciwie porownane?
   - Czy konsekwencje sa realistyczne?

3. Decyzja zespolu
   - Akceptacja → merge, status: Accepted
   - Odrzucenie → zamkniecie PR z komentarzem
   - Zmiana → aktualizacja ADR, kolejna runda review

4. Implementacja
   - ADR jest referencja podczas implementacji
   - Link do ADR w kodzie/ticketach
```

## Dobre praktyki

1. **Jeden ADR = jedna decyzja** — nie mieszaj wielu decyzji w jednym dokumencie
2. **Krotkie i konkretne** — 1-2 strony, nie esej
3. **Pisz kontekst jak dla kogos, kto dolacza za rok** — nie zakladaj wiedzy
4. **Uczciwie opisuj alternatywy** — wady i zalety kazdej opcji
5. **Konsekwencje = trade-offs** — kazda decyzja ma cene
6. **ADR jest niemutowalne** — nie edytuj zaakceptowanych, tworzz nowe (supersede)
7. **Linkuj ADR w kodzie** — komentarze: "// patrz ADR-007"
8. **Review jak kod** — PR, dyskusja, merge

## Kiedy pisac ADR?

### Pisz gdy:
- Wybierasz technologie (baza, framework, jezyk)
- Zmieniasz architekture (monolit → mikroserwisy)
- Decyzja ma dlugoterminowe konsekwencje
- Decyzja jest kontrowersyjna lub trudna
- Decyzja wplywa na wiele zespolow

### Nie pisz gdy:
- Decyzja jest trywialna (formatowanie kodu, nazwa zmiennej)
- Decyzja jest odwracalna w minuty
- Standard branzy (HTTPS zamiast HTTP)

## Kluczowe wnioski

1. **ADR zachowuje kontekst decyzji** — "dlaczego" jest wazniejsze niz "co"
2. **Szablon Nygarda** wystarcza na poczatek — kontekst, decyzja, konsekwencje
3. **Cykl zycia** — proposed → accepted → deprecated/superseded
4. **adr-tools lub log4brains** — automatyzacja tworzenia i przegladania
5. **Review jak kod** — PR, dyskusja, merge
6. **Niemutowalne** — nie edytuj starych, tworzz nowe zastepujace
7. **Linkuj w kodzie** — ADR zyje blisko decyzji, nie w zapomnianym wiki
