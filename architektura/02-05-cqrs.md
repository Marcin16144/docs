# CQRS — Command Query Responsibility Segregation

## Czym jest CQRS?

CQRS to wzorzec architektoniczny polegający na **rozdzieleniu modelu odczytu (Query) od modelu zapisu (Command)**. Zamiast jednego modelu obsługującego zarówno odczyt, jak i zapis, tworzymy dwa niezależne modele, z których każdy jest zoptymalizowany pod kątem swojego zadania.

```
Tradycyjne podejście (CRUD):

┌─────────┐     ┌──────────────┐     ┌──────┐
│ Klient  │────►│  Jeden model │────►│  BD  │
│         │◄────│  (CRUD)      │◄────│      │
└─────────┘     └──────────────┘     └──────┘

CQRS:

┌─────────┐  Command  ┌──────────────┐     ┌─────────┐
│ Klient  │──────────►│ Write Model  │────►│ Write   │
│         │           └──────────────┘     │ Store   │
│         │                                └────┬────┘
│         │                                     │ sync
│         │  Query    ┌──────────────┐     ┌────▼────┐
│         │◄──────────│ Read Model   │◄────│ Read    │
└─────────┘           └──────────────┘     │ Store   │
                                           └─────────┘
```

## Dlaczego CQRS?

### Problem jednego modelu
W typowej aplikacji CRUD jeden model musi obsłużyć:
- Walidację i reguły biznesowe (zapis)
- Złożone zapytania raportowe (odczyt)
- Wyszukiwanie pełnotekstowe (odczyt)
- Agregacje i statystyki (odczyt)

To prowadzi do kompromisów — model jest zbyt złożony dla zapisu i zbyt wolny dla odczytu.

### Asymetria odczyt/zapis
W większości systemów:
```
Odczyty:  ████████████████████████ 90%
Zapisy:   ████                     10%

Wymagania odczytu:           Wymagania zapisu:
- Szybkość                   - Walidacja
- Denormalizacja             - Reguły biznesowe
- Wiele widoków              - Spójność transakcyjna
- Stronicowanie              - Audyt
- Cache-friendly             - Idempotentność
```

## Command Model (strona zapisu)

### Struktura komendy

```typescript
// Komenda = intencja zmiany stanu
interface CreateOrderCommand {
    type: "CreateOrder";
    customerId: string;
    items: Array<{
        productId: string;
        quantity: number;
    }>;
    shippingAddress: Address;
}

// Command Handler = logika biznesowa
class CreateOrderHandler {
    constructor(
        private readonly orderRepo: OrderRepository,
        private readonly inventory: InventoryService,
        private readonly eventBus: EventBus
    ) {}

    async handle(cmd: CreateOrderCommand): Promise<OrderId> {
        // 1. Walidacja biznesowa
        await this.inventory.checkAvailability(cmd.items);

        // 2. Utworzenie agregatu
        const order = Order.create(
            cmd.customerId,
            cmd.items,
            cmd.shippingAddress
        );

        // 3. Zapis
        await this.orderRepo.save(order);

        // 4. Publikacja zdarzeń
        await this.eventBus.publish(order.domainEvents);

        return order.id;
    }
}
```

### Walidacja komend

```
Komenda → [Walidacja strukturalna] → [Walidacja biznesowa] → [Wykonanie]
              (format danych)          (reguły domeny)        (zapis)

Poziomy walidacji:
1. Strukturalna: czy pola są wypełnione, typy poprawne?
2. Biznesowa:    czy klient istnieje? czy produkt jest dostępny?
3. Autoryzacja:  czy użytkownik ma prawo wykonać tę operację?
```

## Query Model (strona odczytu)

### Projekcje — zdenormalizowane widoki

```
Write Model (znormalizowany):     Read Model (zdenormalizowany):
                                  
┌──────────┐ ┌──────────┐        ┌─────────────────────────┐
│ orders   │ │ users    │        │ order_view              │
│ ──────── │ │ ──────── │   ──►  │ ────────────────────── │
│ id       │ │ id       │        │ order_id               │
│ user_id  │ │ name     │        │ customer_name          │
│ total    │ │ email    │        │ customer_email         │
│ status   │ │          │        │ total                  │
└──────────┘ └──────────┘        │ status                 │
┌──────────┐                     │ items_count            │
│order_items│                    │ items_json             │
│ ──────── │                     │ created_at             │
│ order_id │                     │ shipping_address       │
│ product  │                     └─────────────────────────┘
│ quantity │                     
│ price    │                     Jedna tabela = jeden widok
└──────────┘                     Bez JOINów!
```

### Implementacja projekcji

```typescript
// Projekcja nasłuchuje na zdarzenia i aktualizuje Read Model
class OrderProjection {
    constructor(private readonly readDb: ReadDatabase) {}

    async onOrderCreated(event: OrderCreated): Promise<void> {
        await this.readDb.insert("order_views", {
            order_id: event.orderId,
            customer_name: event.customerName,
            status: "created",
            total: event.total,
            items_count: event.items.length,
            items_json: JSON.stringify(event.items),
            created_at: event.timestamp
        });
    }

    async onOrderShipped(event: OrderShipped): Promise<void> {
        await this.readDb.update("order_views",
            { order_id: event.orderId },
            {
                status: "shipped",
                shipped_at: event.timestamp,
                tracking_number: event.trackingNumber
            }
        );
    }
}

// Query Handler — prosty odczyt bez logiki biznesowej
class GetOrderQueryHandler {
    constructor(private readonly readDb: ReadDatabase) {}

    async handle(query: GetOrderQuery): Promise<OrderView> {
        return this.readDb.findOne("order_views", {
            order_id: query.orderId
        });
    }
}
```

## Synchronizacja modeli

### Synchroniczna (natychmiastowa)
```
Command → Write DB → [Synchronous Update] → Read DB
                          │
                    W tej samej transakcji
                    (strong consistency)
```
Proste, ale ogranicza skalowanie.

### Asynchroniczna (zdarzeniowa)
```
Command → Write DB → [Event Published] → Message Broker → [Projection] → Read DB
                                              │
                                     Eventual consistency
                                     (opóźnienie ms-s)
```
Skalowalne, ale wymaga obsługi eventual consistency.

### Porównanie strategii synchronizacji

| Aspekt | Synchroniczna | Asynchroniczna |
|--------|--------------|----------------|
| Spójność | Natychmiastowa | Eventual |
| Wydajność | Niższa (jedna transakcja) | Wyższa (osobne procesy) |
| Złożoność | Niższa | Wyższa |
| Skalowalność | Ograniczona | Wysoka |
| Niezawodność | Zapis i projekcja powiązane | Niezależne |

## CQRS + Event Sourcing

Naturalne połączenie — Event Store jako źródło prawdy, projekcje jako modele odczytu:

```
┌─────────┐  Command   ┌──────────────┐
│ Klient  │───────────►│   Command    │
│         │            │   Handler    │
│         │            └──────┬───────┘
│         │                   │ append event
│         │            ┌──────▼───────┐
│         │            │  Event Store │ (źródło prawdy)
│         │            └──────┬───────┘
│         │                   │ events
│         │            ┌──────▼───────┐
│         │            │  Projection  │
│         │            │  Builder     │
│         │            └──────┬───────┘
│         │  Query     ┌──────▼───────┐
│         │◄───────────│  Read Model  │
└─────────┘            │(SQL/Elastic/ │
                       │ Redis/Mongo) │
                       └──────────────┘
```

### Wiele Read Models z jednego Event Store

```
Event Store (jedno źródło zdarzeń):
│
├──► Projekcja 1: Lista zamówień (PostgreSQL)
│    → Widok tabeli z paginacją
│
├──► Projekcja 2: Wyszukiwarka (Elasticsearch)
│    → Full-text search, filtry, facety
│
├──► Projekcja 3: Dashboard (Redis)
│    → Statystyki w czasie rzeczywistym
│
└──► Projekcja 4: Raportowanie (ClickHouse)
     → Agregacje, wykresy, eksporty
```

## Wzorce implementacji

### Mediator Pattern (MediatR)

```csharp
// Rejestracja handlera
services.AddMediatR(cfg => 
    cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));

// Command
public record CreateOrderCommand(
    string CustomerId,
    List<OrderItemDto> Items
) : IRequest<OrderId>;

// Handler
public class CreateOrderHandler 
    : IRequestHandler<CreateOrderCommand, OrderId>
{
    public async Task<OrderId> Handle(
        CreateOrderCommand request,
        CancellationToken ct)
    {
        var order = Order.Create(request.CustomerId, request.Items);
        await _repository.Save(order);
        return order.Id;
    }
}

// Query
public record GetOrderQuery(string OrderId) 
    : IRequest<OrderView>;

// Controller
[HttpPost]
public async Task<ActionResult> Create(CreateOrderRequest req) {
    var id = await _mediator.Send(new CreateOrderCommand(
        req.CustomerId, req.Items));
    return CreatedAtAction(nameof(Get), new { id }, null);
}

[HttpGet("{id}")]
public async Task<OrderView> Get(string id) {
    return await _mediator.Send(new GetOrderQuery(id));
}
```

### Pipeline Behaviors (Cross-cutting concerns)

```csharp
// Walidacja automatyczna dla każdej komendy
public class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public async Task<TResponse> Handle(TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken ct)
    {
        var failures = _validators
            .Select(v => v.Validate(request))
            .SelectMany(r => r.Errors)
            .Where(f => f != null)
            .ToList();

        if (failures.Any())
            throw new ValidationException(failures);

        return await next();
    }
}
```

## Kiedy stosować CQRS?

### Idealny dla:
- Systemów z asymetrią odczyt/zapis
- Złożonych widoków raportowych
- Wymagań pełnotekstowego wyszukiwania
- Systemów z wieloma modelami odczytu
- Aplikacji event-driven z Event Sourcing

### Nie stosować gdy:
- Proste CRUD bez złożonej logiki
- Mały zespół bez doświadczenia
- Aplikacja z symetrycznym odczytem/zapisem
- Wymaganie natychmiastowej spójności jest krytyczne

## Zalety i wady

### Zalety
- Niezależna optymalizacja odczytu i zapisu
- Skalowalność — osobne skalowanie modeli
- Wiele widoków z jednego źródła danych
- Lepsze separation of concerns
- Naturalnie współgra z Event Sourcing

### Wady
- Zwiększona złożoność kodu i infrastruktury
- Eventual consistency (przy async synchronizacji)
- Więcej kodu do utrzymania (dwa modele)
- Duplikacja danych
- Wymaga dyscypliny zespołu

## Podsumowanie

CQRS to wzorzec, który **rozwiązuje realny problem asymetrii odczytu i zapisu**. Nie jest uniwersalnym rozwiązaniem — stosuj go tam, gdzie jeden model nie wystarcza. Najlepiej sprawdza się w połączeniu z Event Sourcing i architekturą event-driven, ale można go wdrożyć również samodzielnie z synchroniczną projekcją.
