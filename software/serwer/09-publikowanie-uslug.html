Publikowanie uslug do Internetu

Reverse proxy, DMZ, WAF i nowoczesne podejscia zero trust dla bezpiecznej publikacji aplikacji.

Architektura reverse proxy

Bezposrednie wystawienie serwera aplikacyjnego do Internetu jest niebezpieczne. Standardowy wzorzec to umieszczenie reverse proxy/WAF w warstwie publicznej, ktory terminuje TLS, filtruje ruch i przekazuje do backendu w sieci wewnetrznej.

Schemat ruchu:

Klient (Internet) -> CDN/WAF (Cloudflare/Azure FD) -> Firewall zewnetrzny -> Reverse Proxy (DMZ) -> Firewall wewnetrzny -> Serwer aplikacji (LAN) -> Baza danych

Zalety reverse proxy

  • Ukrycie topologii wewnetrznej (klient nie zna IP backendu)
  • SSL termination - centralne zarzadzanie certyfikatami
  • Load balancing miedzy wieloma instancjami backendu
  • Caching odpowiedzi statycznych
  • Compression (gzip, brotli)
  • WAF - filtrowanie ruchu HTTP wg regul OWASP
  • Rate limiting i ochrona przed L7 DDoS

Two-firewall DMZ pattern

Klasyczny wzorzec DMZ wykorzystuje dwa firewalle (najlepiej od roznych producentow), miedzy ktorymi znajduje sie strefa zdemilitaryzowana. Reverse proxy znajduje sie w DMZ.

Reverse proxy w IIS+ARR

# Instalacja modulow
# 1. URL Rewrite Module
# 2. Application Request Routing (ARR)

# Wlaczenie proxy globalnie (powershell appcmd)
& "$env:windir\system32\inetsrv\appcmd.exe" set config `
  -section:system.webServer/proxy /enabled:"True" /commit:apphost

# Routing /api/ do backendu
& "$env:windir\system32\inetsrv\appcmd.exe" set config `
  "Default Web Site" -section:system.webServer/rewrite/rules `
  /+"[name='ApiProxy',stopProcessing='True']" /commit:apphost

Web Application Firewall (WAF)

WAF analizuje ruch HTTP/HTTPS na warstwie L7 (aplikacyjnej) i blokuje zlosliwe requesty. Najczestszy ruleset to OWASP Core Rule Set (CRS) obejmujacy najpopularniejsze ataki.

XSS (Cross-Site Scripting)Filtrowanie <script>, javascript:, on*=
RCE (Remote Code Execution)Blokowanie cmd= , powershell, /bin/sh

SSRFBlokowanie wywolan do 169.254.169.254 (metadata)

Direct Access - przestarzaly

Direct Access byl Microsoftowa technologia zdalnego dostepu (zawsze on, IPv6/IPSec) wprowadzona w Server 2008 R2. Wspierany do konca Server 2022.

Status: Direct Access jest deprecated w Windows Server 2025 - Microsoft rekomenduje migracje do Always On VPN (klient VPN z IKEv2 + RADIUS) lub modeli Zero Trust (Azure AD App Proxy, Cloudflare Access, Tailscale, Twingate).

Always On VPN

Nastepca DirectAccess - VPN klient skonfigurowany przez ProfileXML lub Intune, dziala na zwyklym kliencie Windows 10/11 + Server VPN/RAS lub appliances trzeciej strony.

  • Device tunnel - laczy maszyne przed logowaniem (pre-logon), umozliwia pobranie GPO, certyfikatow
  • User tunnel - po logowaniu, ruch uzytkownika
  • IKEv2 + EAP-TLS (certyfikaty) lub PEAP-MSCHAPv2 (haslo + MFA)
  • Conditional Access integration via Azure AD

Azure AD Application Proxy (Entra App Proxy)

Bardzo nowoczesne podejscie zero trust. Connector Application Proxy instalowany w sieci wewnetrznej nawiazuje wychodzace polaczenie do Azure - aplikacja webowa publikowana z lokalnego serwera bez otwierania zadnych portow inbound w firewallu.

# Architektura Application Proxy
# Client (internet) -> login.microsoftonline.com -> Azure AD App Proxy
#                                                          |
#                                  outbound TLS (port 443) | (HTTPS)
#                                                          v
#                                      App Proxy Connector (LAN)
#                                                          |
#                                                          v
#                                  Internal app server (np. IIS)

Zalety Application Proxy

  • Brak inbound rules - tylko outbound 443 (zwykle juz dozwolony)
  • Pre-authentication w Azure AD - tylko zalogowani uzytkownicy widza aplikacje
  • Conditional Access (MFA, location, device compliance, risk-based)
  • Brak DMZ - aplikacja zostaje w prywatnej sieci
  • Single Sign-On (Kerberos Constrained Delegation, headers, SAML)

Modern publishing checklist

  • Aplikacja wystawiona przez WAF (np. Cloudflare, Azure Front Door)
  • Certyfikat SSL od zaufanego CA (Let's Encrypt, DigiCert)
  • HTTP/2 i HTTP/3 (QUIC) wlaczone
  • HSTS header z preload
  • CSP (Content Security Policy) dla aplikacji web
  • Pre-authentication przed dotarciem ruchu do aplikacji (zero trust)
  • Logging na poziomie WAF + aplikacji do SIEM
  • Rate limiting na poziomie WAF
  • Geo-blocking dla regionow nieobslugiwanych biznesowo
  • Bot management (CAPTCHA, fingerprinting)
  • Regularne testy penetracyjne aplikacji
