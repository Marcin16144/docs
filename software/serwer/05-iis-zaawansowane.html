URL Rewrite Module

URL Rewrite jest najwazniejszym rozszerzeniem IIS. Pozwala na manipulacje adresami URL przy uzyciu reguly regex - przekierowania, rewrite, blokady, kanonizacja, reverse proxy. Po instalacji modul widoczny w IIS Manager pod pozycja URL Rewrite na poziomie strony.

<!-- web.config: wymuszenie HTTPS -->
<rewrite>
  <rules>
    <rule name="HTTPS Redirect" stopProcessing="true">
      <match url=".*" />
      <conditions>
        <add input="{HTTPS}" pattern="^OFF$" />
      </conditions>
      <action type="Redirect" url="https://{HTTP_HOST}/{R:0}"
              redirectType="Permanent" />
    </rule>
  </rules>
</rewrite>

Conditions i back-references

Conditions pozwalaja sprawdzac dodatkowe warunki przed wykonaniem akcji - naglowki, parametry serwera, properties pliku. Back-references {R:N} odwoluja sie do grup regex z match, {C:N} z conditions.

<rule name="Block Old Browsers">
  <match url=".*" />
  <conditions logicalGrouping="MatchAny">
    <add input="{HTTP_USER_AGENT}" pattern="MSIE [1-9]\." />
    <add input="{HTTP_USER_AGENT}" pattern="Trident/[1-6]" />
  </conditions>
  <action type="CustomResponse" statusCode="426"
          statusReason="Upgrade Required"
          statusDescription="Prosimy o aktualizacje przegladarki" />
</rule>

Application Request Routing (ARR)

ARR to rozszerzenie firmy Microsoft zamieniajace IIS w pelnoprawny reverse proxy i load balancer. ARR + URL Rewrite to standard dla publikowania aplikacji backend (Node.js, Python, .NET Core, Java) zza IIS.

# Instalacja przez Web Platform Installer lub bezposrednio
# https://www.iis.net/downloads/microsoft/application-request-routing

# Wlaczenie reverse proxy globalnie:
# IIS Manager -> Server -> Application Request Routing Cache
# -> Server Proxy Settings -> Enable Proxy

Reverse proxy do backendu Node.js

<!-- web.config: routing /api/ do Node na 127.0.0.1:3000 -->
<configuration>
  <system.webServer>
    <rewrite>
      <rules>
        <rule name="API Reverse Proxy" stopProcessing="true">
          <match url="^api/(.*)" />
          <action type="Rewrite"
                  url="http://127.0.0.1:3000/{R:1}"
                  logRewrittenUrl="true" />
          <serverVariables>
            <set name="HTTP_X_FORWARDED_FOR" value="{REMOTE_ADDR}" />
            <set name="HTTP_X_FORWARDED_PROTO" value="{CACHE_URL:1}" />
            <set name="HTTP_X_REAL_IP" value="{REMOTE_ADDR}" />
          </serverVariables>
        </rule>
      </rules>
    </rewrite>
  </system.webServer>
</configuration>

HTTP_X_FORWARDED_*: Bez ustawienia tych naglowkow aplikacja backend zobaczy IP IIS-a (127.0.0.1) zamiast realnego klienta. W ARR -> Server Proxy Settings nalezy wlaczyc Reverse rewrite host in response headers dla poprawnej obslugi przekierowan z backendu.

FastCGI dla PHP

PHP w IIS uruchamiany jest przez FastCGI Module. Microsoft rekomenduje NTS (Non-Thread Safe) buildy 64-bit z windows.php.net. PHP Manager for IIS dostarcza GUI do konfiguracji.

# Instalacja CGI feature
Install-WindowsFeature -Name Web-CGI

# Rejestracja PHP w FastCGI
appcmd.exe set config /section:system.webServer/fastCgi `
  /+"[fullPath='C:\PHP\php-cgi.exe']"

# Mapowanie rozszerzenia .php do handlera
appcmd.exe set config /section:system.webServer/handlers `
  /+"[name='PHP_via_FastCGI',path='*.php',verb='*',
       modules='FastCgiModule',scriptProcessor='C:\PHP\php-cgi.exe',
       resourceType='File']"

ASP.NET Core hosting

ASP.NET Core moze byc hostowany w IIS przez aspNetCoreModuleV2. Modul wspiera dwa modele: in-process (szybszy, w-procesie w3wp) i out-of-process (proxy do osobnego procesu Kestrel).

<!-- web.config aplikacji ASP.NET Core -->
<configuration>
  <system.webServer>
    <handlers>
      <add name="aspNetCore" path="*" verb="*"
           modules="AspNetCoreModuleV2" resourceType="Unspecified" />
    </handlers>
    <aspNetCore processPath="dotnet"
                arguments=".\MyApp.dll"
                stdoutLogEnabled="false"
                stdoutLogFile=".\logs\stdout"
                hostingModel="inprocess" />
  </system.webServer>
</configuration>

Wildcard Application Pools

Przy hostingu masowym (shared hosting) opcjonalne jest tworzenie osobnego App Pool dla kazdej witryny. Wildcard application pool wykorzystuje jeden pool dla wielu witryn z izolacja przez identity.

# Hot scenario: setting 1 pool per site za pomoca PowerShell
Import-Module WebAdministration
Get-ChildItem IIS:\Sites | ForEach-Object {
    $poolName = "AppPool-$($_.Name)"
    if (-not (Test-Path "IIS:\AppPools\$poolName")) {
        New-WebAppPool -Name $poolName
        Set-ItemProperty "IIS:\AppPools\$poolName" `
                         -Name "managedRuntimeVersion" -Value "v4.0"
    }
    Set-ItemProperty "IIS:\Sites\$($_.Name)" `
                     -Name "applicationPool" -Value $poolName
}

Application Initialization

Application Initialization Module rozwiazuje problem cold start - po recyclingu lub pierwszym requescie aplikacja moze startowac wolno. Modul preloaduje aplikacje przed pierwszym requestem od klienta.

<applicationInitialization
    doAppInitAfterRestart="true"
    skipManagedModules="false">
    <add initializationPage="/health" />
    <add initializationPage="/api/v1/warmup" />
</applicationInitialization>
  • Application Pool ustawic na AlwaysRunning
  • Site preload (preloadEnabled=true) wymusza warmup
  • idleTimeout w app pool najlepiej ustawic na 0 (brak idle shutdown)

Best practices

  • Reverse proxy w IIS = ARR + URL Rewrite (nie polegac wylacznie na samym URL Rewrite)
  • SSL terminacja na IIS, w sieci wewnetrznej HTTP do backendu (lub e2e TLS gdy compliance wymaga)
  • Compression (Static + Dynamic) wlaczone na poziomie serwera
  • HTTP/2 i HTTP/3 (QUIC) wlaczone w Server 2025
  • Failed Request Tracing dla debugowania problemow z URL Rewrite
  • ARR Cache moze cachowac responses z backendu - ustawiac ostroznie (cache poisoning)
