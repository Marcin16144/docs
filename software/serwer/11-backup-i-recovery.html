Backup i recovery

Strategie kopii zapasowych, narzedzia natywne, chmura i odtwarzanie po awarii.

Zasada 3-2-1

Kanon backupu mowi: 3 kopie danych w 2 roznych mediach, 1 kopia offsite. Wspolczesne rozszerzenie 3-2-1-1-0 dodaje: 1 kopia immutable/offline, 0 bledow w testach restore.

ElementCelPrzyklad
3 kopieTolerowanie utraty pojedynczych nosnikowProdukcja + backup lokalny + backup chmurowy
2 mediaRoznorodnosc technologii (uszkodzenie nie dotyczy obu)Dysk + tasma, dysk + chmura
1 offsiteOchrona przed katastrofa fizyczna (pozar, powodz)Inny budynek, region chmury
1 immutable/offlineOchrona przed ransomwareWORM disk, air-gapped tape
0 bledowRegularne testy odtwarzaniaMesieczny test restore

RTO vs RPO

RTO (Recovery Time Objective) - maksymalny dopuszczalny czas niedostepnosci (kiedy uslugi musza wrocic).

RPO (Recovery Point Objective) - maksymalna dopuszczalna utrata danych (jak czesto trzeba robic backup).

KlasaRTORPOStrategia
Mission-critical< 15 min< 5 minHA cluster + sync replication, hot standby
Business-critical< 4 h< 1 hAsync replication, quick restore from snapshot
Important< 24 h< 24 hDaily backup, off-site copy
Non-critical< 7 dni< 7 dniWeekly backup, archive storage

Windows Server Backup

Wbudowane narzedzie WSB (Windows Server Backup) i jego CLI wbadmin daje podstawowe mozliwosci backupu - System State, Bare-Metal Recovery, Volume, File-level. Dziala dobrze dla pojedynczych serwerow i malych srodowisk.

# Instalacja Windows Server Backup
Install-WindowsFeature Windows-Server-Backup

# Backup System State (zawiera AD, registry, IIS metabase, COM+, certificates)
wbadmin start systemstatebackup -backupTarget:F: -quiet

# Backup pelny (Bare Metal Recovery)
wbadmin start backup -backupTarget:F: `
                     -include:C:,D: `
                     -allCritical `
                     -systemstate `
                     -vssFull `
                     -quiet

# Pobranie historii backupow
wbadmin get versions

# Restore na poziomie pliku
wbadmin start recovery -version:01/15/2025-22:00 `
                        -itemType:File `
                        -items:C:\Data `
                        -recoveryTarget:E:\Restore `
                        -overwrite:CreateCopy

Volume Shadow Copy Service (VSS)

VSS to mechanizm Windows umozliwiajacy spojny backup plikow w uzyciu (otwarte przez aplikacje). Backup tools wywoluja VSS, ktore tworza "writers" specyficzne dla aplikacji (SQL, Exchange, Hyper-V, AD).

# Lista VSS writers (kazdy = aplikacja wspierajaca consistent snapshot)
vssadmin list writers

# Lista shadow storage
vssadmin list shadowstorage

# Wlaczenie Previous Versions na woluminie (uzytkownicy moga przywracac sami)
# Konfiguracja przez File Explorer -> Properties -> Shadow Copies -> Enable

# Tworzenie shadow copy z PowerShell
$shadow = (Get-WmiObject -List Win32_ShadowCopy).Create("C:\", "ClientAccessible")

Azure Backup

Managed cloud backup od Microsoftu. Agent Microsoft Azure Recovery Services Agent (MARS) instalowany na serwerze backupuje pliki/foldery/system state do Recovery Services Vault w Azure.

Skladniki Azure Backup

KomponentZastosowanie
MARS AgentProsty backup plikow + System State z on-prem
MABS (Microsoft Azure Backup Server)Backup wielu serwerow z lokalnego serwera (DPM bez SCDPM license)
Azure Backup Server System Center DPMPelne System Center DPM z replikacja do Azure
Azure VM BackupSnapshot VM w Azure (agent VM Extension)
Azure Backup Vault StorageGeo-redundant storage, immutable, soft delete
# Rejestracja MARS agent w vault (po instalacji msi)
Start-OBRegistration

# Konfiguracja policy backupu
$policy = New-OBPolicy
$schedule = New-OBSchedule -DaysOfWeek Monday,Wednesday,Friday `
                            -TimesOfDay "22:00"
$retention = New-OBRetentionPolicy -RetentionDays 30

Add-OBSchedule  -Policy $policy -Schedule $schedule
Add-OBRetentionPolicy -Policy $policy -RetentionPolicy $retention

# Folder do backupu
$source = New-OBFileSpec -FileSpec "C:\Data"
Add-OBFileSpec -Policy $policy -FileSpec $source

# Wdrozenie polityki
Set-OBPolicy -Policy $policy

Backupowanie Active Directory

Dla DC krytyczne sa: System State backup (zawiera baze NTDS.dit, SYSVOL, registry, IIS metabase). Minimum dwa kontrolery domeny + dzienny System State backup z retencja co najmniej 60 dni.

# Backup System State na DC (target nie moze byc na woluminie systemowym)
wbadmin start systemstatebackup -backupTarget:E: -quiet

# Tombstone Lifetime - kontrola "starosci" backupu
# Domyslnie 180 dni - backup musi byc nowszy by byl uzyteczny
Get-ADObject -Identity "CN=Directory Service,CN=Windows NT,CN=Services,$((Get-ADRootDSE).configurationNamingContext)" `
             -Properties tombstoneLifetime

# Authoritative restore (przywrocenie usunietego OU)
# Boot DC w trybie Directory Services Restore Mode (DSRM)
# Uruchomic ntdsutil
ntdsutil
    activate instance ntds
    authoritative restore
    restore subtree "OU=Sales,DC=contoso,DC=local"
    quit
    quit

AD Recycle Bin

Wbudowany "kosz" dla obiektow AD - umozliwia odzyskanie usunietego obiektu z pelnym zachowaniem atrybutow. Aktywowany raz, wlaczony forever.

# Wlaczenie AD Recycle Bin (raz, na zawsze - nie da sie wylaczyc)
Enable-ADOptionalFeature -Identity "Recycle Bin Feature" `
                          -Scope ForestOrConfigurationSet `
                          -Target "contoso.local"

# Restoreowanie usunietego uzytkownika
Get-ADObject -Filter 'isDeleted -eq $true -and SamAccountName -eq "jkowalski"' `
             -IncludeDeletedObjects |
    Restore-ADObject

Backup IIS

# Konfiguracja IIS (applicationHost.config)
$dest = "D:\Backups\IIS\$(Get-Date -Format 'yyyy-MM-dd')"
New-Item -Path $dest -ItemType Directory -Force

# Backup applicationHost + redirection.config + administration.config
Copy-Item "$env:windir\System32\inetsrv\config\applicationHost.config" $dest
Copy-Item "$env:windir\System32\inetsrv\config\redirection.config" $dest
Copy-Item "$env:windir\System32\inetsrv\config\administration.config" $dest

# Eksport konfiguracji site/pool
& "$env:windir\System32\inetsrv\appcmd.exe" list sites /xml > $dest\sites.xml
& "$env:windir\System32\inetsrv\appcmd.exe" list apppools /xml > $dest\apppools.xml

# Eksport certyfikatow (z prywatnym kluczem)
Get-ChildItem Cert:\LocalMachine\My | ForEach-Object {
    $thumb = $_.Thumbprint
    Export-PfxCertificate -Cert $_ `
                          -FilePath "$dest\cert-$thumb.pfx" `
                          -Password (ConvertTo-SecureString "BackupPassword!" -AsPlainText -Force)
}

Disaster Recovery Plan

Backup to nie DR. DR plan to dokument opisujacy jak organizacja kontynuuje dzialanie po katastrofie - role, kolejnosc odtwarzania, RTO/RPO per system, kontakty, alternatywne lokalizacje.

Elementy planu DR

  • Business Impact Analysis (BIA) - klasyfikacja systemow wg krytycznosci
  • Recovery Sequence - kolejnosc odtwarzania (np. AD -> DNS -> SQL -> aplikacje)
  • Personel i role - kto co robi, dane kontaktowe (off-hours)
  • Dokumentacja runbookow - krok po kroku procedury restore
  • Komunikacja - status page, mail/SMS broadcasting
  • Alternatywna lokalizacja - cold/warm/hot site, region DR w chmurze
  • Tabletop exercises - regularne cwiczenia teoretyczne
  • DR drill - rzeczywiste cwiczenie z odtwarzaniem (raz na pol roku)

Test restoreu - kluczowy

Backup ktory nigdy nie byl testowany nie istnieje. Najczestsze problemy to: brak dostepu do tasm/dyskow, niewiadome haslo do encryption, niekompletny System State, brak wymaganych komponentow do odzyskania (Recovery Services Vault credentials, MARS passphrase).

  • Test restore co najmniej raz na miesiac dla krytycznych systemow
  • Restore nie do produkcji - osobna VM/dysk testowy
  • Test odtwarzania z najstarszego dostepnego backupu (sprawdza retencje)
  • Dokumentowanie kazdego testu - czas, wynik, problemy
  • Test pelnego DR (przelaczenie do site DR) raz na rok

Ochrona przed ransomware

  • Immutable backups - WORM (Write Once Read Many) lub Locked policy w cloud
  • Air-gapped backups - tasma odlaczona, offline storage
  • Multi-Factor Authentication dla dostepu do konsoli backupu
  • Soft delete + recycle bin w Recovery Services Vault (Azure - 14 dni domyslnie)
  • Separate credentials dla backupu (nie domain admin)
  • Monitoring zmian wzorcow backup (gwaltowne zwiekszenie compression ratio = encryption)
