Zarzadzanie uprawnieniami

RBAC, JEA, PAM/PIM i Tier Model - kompletna kontrola dostepu do administracji.

RBAC - Role-Based Access Control

RBAC zaklada przyznawanie uprawnien do roli, nie pojedynczego uzytkownika. Uzytkownik dostaje role, role ma uprawnienia. Latwe do audytu, latwe do odbierania (usuwa sie z roli, nie odbiera kazdego uprawnienia z osobna).

Zasady projektowania RBAC

  • Least privilege - minimum uprawnien wymaganych do pracy
  • Separation of duties - krytyczne operacje wymagaja dwoch osob (np. tworca konta != approver)
  • Role mining - identyfikacja rol na podstawie obecnych uprawnien
  • Role explosion antipattern - zbyt wiele rol = trudne zarzadzanie
  • Attribute-Based (ABAC) jako rozszerzenie - dodatkowe atrybuty (czas, lokalizacja, device compliance)

Tier Model (Enterprise Access Model)

Microsoft promuje model warstw rozdzielajacy konta wg poziomu wrazliwosci zasobow. Konta jednego tieru nie loguja sie na nizszych poziomach - eliminuje to ryzyko ruchu lateralnego (atakujacy z compromised stacji nie moze uzyskac credentials Domain Admina).

Trzy warstwy

TierAktywaKonta administracyjneReguly
Tier 0Domain Controllers, ADCS, ADFS, Azure AD Connect, hypervisors hostujace DC, PAM/PAWDomain Admin, Enterprise Admin, Schema AdminKonta Tier 0 loguja sie TYLKO na Tier 0. Krytyczne aktywa - mozliwy pelny take-over domeny
Tier 1Servery aplikacyjne, baz danych, plikow, IIS, Exchange, SQLServer Admin, App Admin, DBAKonta Tier 1 NIE loguja sie na DC ani na stacje robocze
Tier 2Stacje robocze, laptopy, drukarkiHelpdesk, Workstation AdminKonta Tier 2 NIE loguja sie na serwery ani DC

Rule of three: Admin powinien miec trzy konta:
1) zwykle konto uzytkownika (poczta, dokumenty, browsing) - codzienna praca,
2) konto Tier 1/2 admin do operacji administracyjnych na serwerach/stacjach,
3) konto Tier 0 admin (jezeli zarzadza DC) - logowanie wylacznie z PAW (Privileged Access Workstation).

Implementacja Tier Model

# Strukturalizacja OU
OU=Tiers
   OU=Tier0   - DCs, ADCS, ADFS hosts
   OU=Tier1   - servery aplikacyjne
   OU=Tier2   - stacje robocze
   OU=Admins
      OU=Tier0Admins
      OU=Tier1Admins
      OU=Tier2Admins

# GPO: User Rights Assignment - "Deny logon"
# GPO link na Tier0:
#   "Deny logon as a service" / "interactively" -> Tier1Admins, Tier2Admins
# GPO link na Tier1:
#   "Deny logon as a service" / "interactively" -> Tier0Admins, Tier2Admins
# GPO link na Tier2:
#   "Deny logon as a service" / "interactively" -> Tier0Admins, Tier1Admins

Just Enough Administration (JEA)

JEA pozwala tworzyc ograniczone PowerShell endpoints wystawiajace wybrane cmdlety dla okreslonych grup. Uzytkownik widzi tylko zatwierdzone polecenia, nie dostaje pelnego dostepu do systemu.

Skladniki JEA

SkladnikOpis
Role Capability File (.psrc)Co dany rola moze zrobic - lista cmdletow, modulow
Session Configuration File (.pssc)Konfiguracja sesji - virtual account, role mapping
JEA EndpointWinRM listener z polityka session config
Virtual AccountKonto tworzone na czas sesji - admin uprawnienia bez stalego konta

Przyklad - JEA dla helpdesku (restart uslug)

# 1. Role Capability - co rola moze zrobic
$rolePath = "C:\Program Files\WindowsPowerShell\Modules\HelpdeskJEA\1.0.0\RoleCapabilities"
New-Item -Path $rolePath -ItemType Directory -Force

New-PSRoleCapabilityFile -Path "$rolePath\HelpdeskRole.psrc" `
    -VisibleCmdlets @(
        @{ Name = "Restart-Service"; Parameters = @{ Name = "Name"; ValidateSet = "Spooler","wuauserv","BITS" } },
        "Get-Service",
        "Get-Process",
        "Get-EventLog"
    ) `
    -VisibleFunctions @() `
    -VisibleAliases  @() `
    -VisibleExternalCommands @()

# 2. Session Configuration
New-PSSessionConfigurationFile -Path "C:\JEA\HelpdeskEndpoint.pssc" `
    -SessionType RestrictedRemoteServer `
    -RunAsVirtualAccount `
    -TranscriptDirectory "C:\JEA\Transcripts" `
    -RoleDefinitions @{
        "CONTOSO\Helpdesk-T1" = @{ RoleCapabilities = "HelpdeskRole" }
    }

# 3. Rejestracja endpointu
Register-PSSessionConfiguration -Name "JEA-Helpdesk" `
    -Path "C:\JEA\HelpdeskEndpoint.pssc" `
    -Force

# 4. Uzycie przez helpdesk
Enter-PSSession -ComputerName SRV-APP01 -ConfigurationName "JEA-Helpdesk"
# Helpdesk widzi tylko: Restart-Service (Spooler|wuauserv|BITS), Get-Service, Get-Process, Get-EventLog
# Wszystko innne: "The term 'X' is not recognized..."

Privileged Identity Management (PIM)

PIM to chmurowa funkcja Microsoft Entra ID (Azure AD) pozwalajaca aktywowac role tylko gdy potrzeba. Zamiast permanentnego Domain Admin, uzytkownik aktywuje role na okreslony czas (np. 4 godziny) z dodatkowa autoryzacja (MFA, justification, approval workflow).

Cechy PIM

  • Just-in-Time access - role aktywne tylko podczas wykonywania zadania
  • MFA required przed aktywacja
  • Approval workflow - inny administrator musi zatwierdzic
  • Time-bound - automatyczna deaktywacja po N godzinach
  • Justification - uzytkownik podaje powod aktywacji (audit trail)
  • Access reviews - okresowy przeglad uprawnien (czy nadal potrzebne)
  • Audit logs - kto, kiedy, dlaczego, na jak dlugo

Wymagania: Microsoft Entra ID P2 (P1 nie wystarczy) lub Microsoft 365 E5. Cena: ok. 9 USD/uzytkownik/miesiac.

Konfiguracja PIM

  1. Entra ID Portal -> Privileged Identity Management
  2. Azure AD Roles -> Roles -> wybor roli (np. Global Administrator)
  3. Add assignments -> user/group -> Eligible (zamiast Active)
  4. Settings:
    • Activation maximum duration: 4 hours
    • Require justification: Yes
    • Require MFA: Yes
    • Require approval: Yes (z listy approverow)
  5. Uzytkownik aktywuje role w "My roles" -> "Activate"

Microsoft Identity Manager (MIM)

MIM to on-premises platforma do zarzadzania tozsamoscia. Wspiera scenariusze identity lifecycle (joiner-mover-leaver), self-service password reset, group management, certificate management. Nastepca FIM 2010.

  • Synchronizacja miedzy systemami HR i AD
  • Workflow approval dla zmian uprawnien
  • MIM Privileged Access Management - bastion forest dla Tier 0
  • Self-service portal

MIM PAM (bastion forest)

MIM PAM tworzy osobny las administracyjny ("bastion forest") z relacja zaufania do produkcyjnego. Konta admina istnieja tylko w bastion - logowanie do produkcji wymaga aktywacji shadow account z czasowym SID history.

Privileged Access Workstation (PAW)

PAW to dedykowana stacja robocza dla administratorow Tier 0/1 - tylko do administracji, oddzielona od codziennej pracy.

  • Czysta instalacja Windows 11 Enterprise
  • BitLocker, Secure Boot, TPM 2.0, Credential Guard, Application Control (WDAC)
  • Brak dostepu do Internetu / poczty / Office
  • Brak USB (Group Policy denial)
  • Tylko aplikacje administracyjne (RSAT, MMC, PowerShell ISE)
  • Logowanie tylko Smart Card / FIDO2
  • Monitorowanie zwiekszone (Defender for Endpoint, Sysmon)

Best practices

  • Tier model - rozdzielenie kont admina, nigdy mieszanie tierow
  • Trzy konta dla admina (uzytkownik, T1/T2 admin, T0 admin)
  • JEA dla helpdesku/operatorow zamiast Local Admin
  • PIM dla rol Azure - eligible, nie active
  • PAW dla T0 admina - dedykowana stacja
  • Smart Card / FIDO2 dla wszystkich admin accounts (no password)
  • Service accounts gMSA zamiast domain user accounts
  • LAPS (Local Administrator Password Solution) - unikalne hasla local admin per maszyna
  • Quarterly access review - czy nadal potrzebne
  • Off-boarding checklist - automatyczna deaktywacja konta po wyjsciu
