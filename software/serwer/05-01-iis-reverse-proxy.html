IIS jako Reverse Proxy (ARR)

Application Request Routing + URL Rewrite - publikowanie aplikacji backend zza IIS.

Application Request Routing (ARR)

ARR jest oficjalnym rozszerzeniem Microsoftu zamieniajacym IIS w pelnoprawny reverse proxy z load balancing, health checking i cachingiem. Wymaga URL Rewrite Module jako fundamentu.

Instalacja

# Wymagania
# 1. URL Rewrite Module (wczesniej)
# 2. Application Request Routing 3.0+

# Pobranie z https://www.iis.net/downloads/microsoft/application-request-routing
# Lub przez Web Platform Installer:
& "$env:ProgramFiles\Microsoft\Web Platform Installer\WebpiCmd.exe" `
    /Install /Products:UrlRewrite2,ARRv3_0 /AcceptEula

# Po instalacji w IIS Manager pojawia sie:
# - Server -> "Application Request Routing Cache"
# - Server -> "URL Rewrite"
# - Web Farms (nowy node w lewym panelu)

Wlaczenie globalnego proxy

# Wlaczenie reverse proxy na poziomie serwera
& "$env:windir\system32\inetsrv\appcmd.exe" set config `
    -section:system.webServer/proxy `
    /enabled:"True" `
    /preserveHostHeader:"True" `
    /reverseRewriteHostInResponseHeaders:"True" `
    /commit:apphost

# Lub przez IIS Manager:
# Server -> Application Request Routing Cache -> Server Proxy Settings
# [x] Enable proxy
# [x] Preserve client IP in HTTP_X_FORWARDED_FOR
# [x] Reverse rewrite host in response headers

Reguly URL Rewrite dla reverse proxy

Routing po sciezce - mikroserwisy

Typowa architektura: IIS na frontu, kilka backendow obslugujacych rozne sciezki URL.

<configuration>
  <system.webServer>
    <rewrite>
      <rules>

        <!-- /api/* -> Node.js na 127.0.0.1:3000 -->
        <rule name="API Proxy" stopProcessing="true">
          <match url="^api/(.*)" />
          <action type="Rewrite"
                  url="http://127.0.0.1:3000/api/{R:1}" />
          <serverVariables>
            <set name="HTTP_X_FORWARDED_FOR"   value="{REMOTE_ADDR}" />
            <set name="HTTP_X_FORWARDED_PROTO" value="{CACHE_URL:1}" />
            <set name="HTTP_X_FORWARDED_HOST"  value="{HTTP_HOST}" />
            <set name="HTTP_X_REAL_IP"         value="{REMOTE_ADDR}" />
          </serverVariables>
        </rule>

        <!-- /app/* -> .NET Core na 127.0.0.1:5000 -->
        <rule name="DotNet Proxy" stopProcessing="true">
          <match url="^app/(.*)" />
          <action type="Rewrite"
                  url="http://127.0.0.1:5000/{R:1}" />
          <serverVariables>
            <set name="HTTP_X_FORWARDED_FOR"   value="{REMOTE_ADDR}" />
            <set name="HTTP_X_FORWARDED_PROTO" value="https" />
          </serverVariables>
        </rule>

        <!-- /python/* -> gunicorn na 127.0.0.1:8000 -->
        <rule name="Python Proxy" stopProcessing="true">
          <match url="^python/(.*)" />
          <action type="Rewrite"
                  url="http://127.0.0.1:8000/{R:1}" />
        </rule>

        <!-- Pliki statyczne serwowane przez IIS (nie proxy) -->
        <rule name="Static" stopProcessing="true">
          <match url="^(static|assets|images)/(.*)" />
          <action type="None" />
        </rule>

      </rules>

      <outboundRules>
        <!-- Przepisanie naglowka Location w odpowiedzi -->
        <rule name="Rewrite Location Header" preCondition="IsRedirection">
          <match serverVariable="RESPONSE_Location"
                 pattern="^http://127\.0\.0\.1:[0-9]+/(.*)" />
          <action type="Rewrite" value="https://{HTTP_HOST}/{R:1}" />
        </rule>
        <preConditions>
          <preCondition name="IsRedirection">
            <add input="{RESPONSE_STATUS}" pattern="3[0-9]{{2}}" />
          </preCondition>
        </preConditions>
      </outboundRules>
    </rewrite>
  </system.webServer>
</configuration>

X-Forwarded-* headers: Bez ustawienia tych naglowkow aplikacja backend zobaczy IP IIS (127.0.0.1) zamiast realnego klienta. To samo dotyczy schematu (HTTP/HTTPS) i hosta. Wszystkie nowoczesne frameworki (Express, ASP.NET Core, Flask) wspieraja te naglowki - nalezy je tylko skonfigurowac (np. app.set('trust proxy', true) w Express).

Web Farm - load balancing

ARR pozwala zdefiniowac Web Farm - grupe backendow, miedzy ktorymi rozdziela ruch wedlug wybranej polityki.

<webFarms>
  <webFarm name="MyApp-Backend" enabled="true">
    <server address="10.0.1.10" enabled="true">
      <applicationRequestRouting weight="100" />
    </server>
    <server address="10.0.1.11" enabled="true">
      <applicationRequestRouting weight="100" />
    </server>
    <server address="10.0.1.12" enabled="true">
      <applicationRequestRouting weight="50" />  <!-- mniej ruchu -->
    </server>

    <applicationRequestRouting>
      <!-- Round robin / weighted / least requests -->
      <loadBalancing algorithm="WeightedRoundRobin" />

      <!-- Sticky sessions na podstawie cookie ARRAffinity -->
      <affinity useCookie="true"
                cookieName="ARRAffinity"
                timeout="00:30:00" />

      <!-- Health check -->
      <healthCheck url="http://_Server_/health"
                   interval="00:00:30"
                   timeout="00:00:10"
                   responseMatch="OK" />

      <protocol>
        <cache enabled="false" />
        <timeout connectionTimeout="00:01:00"
                  responseHeaderTimeout="00:01:00" />
      </protocol>
    </applicationRequestRouting>
  </webFarm>
</webFarms>

Algorytmy load balancing

AlgorytmCharakterystyka

Weighted Total TrafficPer ilosc wyslanych bajtow
Least Current RequestDo serwera z najmniejsza liczba aktywnych requestow
Least Response TimeDo najszybszego (na podstawie srednich czasow)

Health checks

ARR co N sekund sprawdza endpoint na backendzie. Jezeli backend odpowiada bledem (lub timeout) X razy z rzedu, zostaje wyrzucony z farmy. Po pomyslnych Y sprawdzeniach wraca.

  • URL: dedykowany endpoint /health, /healthz, /api/v1/ping
  • Interval: 30 sekund (czesciej = wiecej overheadu, rzadziej = wolne wykrywanie)
  • Timeout: 5-10 sekund
  • Response match: regex na zawartosc odpowiedzi (np. "OK" lub "healthy")
  • Backend powinien sprawdzac swoje zaleznosci (DB, cache, API zewnetrzne) - "deep health check"

Sticky sessions (affinity)

Niektore aplikacje przechowuja state w pamieci procesu (in-memory session). Sticky session zapewnia, ze ten sam klient trafia zawsze do tego samego backendu. ARR wstrzykuje cookie ARRAffinity z ID serwera.

Anty-pattern: Sticky sessions nie rozwiazuja problemu, tylko go ukrywaja. Lepsza praktyka: stateless aplikacje + zewnetrzny store sesji (Redis, SQL Server, distributed cache). Sticky tylko jako tymczasowy workaround.

SSL termination

Standardowo ARR terminuje TLS na froncie i komunikuje sie z backendem przez czysty HTTP w wewnetrznej sieci. To zmniejsza obciazenie CPU backendow i centralizuje zarzadzanie certyfikatami.

<!-- IIS na froncie: HTTPS na 443, certyfikat zaufany przez przegladarki -->
<rule name="ToBackend">
  <match url=".*" />
  <action type="Rewrite" url="http://10.0.1.10/{R:0}" />
  <serverVariables>
    <!-- Backend wie, ze klient byl po HTTPS -->
    <set name="HTTP_X_FORWARDED_PROTO" value="https" />
  </serverVariables>
</rule>

End-to-end encryption

Dla scenariuszy compliance (PCI DSS, HIPAA) wymagane jest TLS od klienta do backendu - bez plain HTTP w sieci wewnetrznej. ARR moze proxy do HTTPS, walidacja certyfikatu konfigurowana per server.

Use cases

Mikroserwisy za jedna domena

https://api.contoso.com/users/*    -> users-service:8001
https://api.contoso.com/orders/*   -> orders-service:8002
https://api.contoso.com/payments/* -> payments-service:8003
https://api.contoso.com/static/*   -> serwowane bezposrednio przez IIS

Legacy + nowoczesna aplikacja w jednej domenie

https://app.contoso.com/      -> nowy SPA React (static + API call do /api)
https://app.contoso.com/api/  -> .NET Core 8 backend
https://app.contoso.com/admin -> legacy ASP.NET WebForms (ten sam IIS, inny site)

Cache statycznych odpowiedzi

<!-- Cache responses /api/products/* na 5 minut -->
<applicationRequestRouting>
  <cache enabled="true">
    <cacheControlRules>
      <add path="/api/products/*"
           cacheControl="max-age=300, public" />
    </cacheControlRules>
  </cache>
</applicationRequestRouting>

Best practices

  • X-Forwarded-* zawsze ustawione - reverse rewrite host headers w ARR Server Settings
  • Connection timeout do backendu krotszy niz timeout klienta (zeby blad propagowal sie szybko)
  • Health check endpoint na kazdym backendzie - sprawdzajacy zaleznosci
  • Logging zawiera URL po rewrite (logRewrittenUrl) dla diagnostyki
  • Stateless aplikacje + zewnetrzny session store zamiast sticky sessions
  • SSL termination na ARR + opcjonalne re-encrypt do backendu
  • Backendy zwiazane do 127.0.0.1 / sieci wewnetrznej, nigdy do publicznego IP
  • Failed Request Tracing wlaczone na czas debugowania
