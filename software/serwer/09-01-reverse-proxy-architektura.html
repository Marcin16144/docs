Architektura reverse proxy dla uslug publicznych

DMZ, two-firewall pattern, SSL termination i izolacja backendu - kompletny design.

Po co reverse proxy

Bezposrednie wystawienie serwera aplikacyjnego do Internetu jest bardzo niebezpieczne. Reverse proxy w warstwie publicznej chroni backend, terminuje TLS, filtruje ruch i dystrybuuje obciazenie.

FunkcjaDlaczego wazne
Ukrycie topologiiKlient nie widzi adresow IP backendu - utrudnione skanowanie
SSL terminationCentralne zarzadzanie certyfikatami, obciazenie CPU TLS na proxy
WAFFiltrowanie SQL injection, XSS, RCE przed dotarciem do aplikacji
Load balancingRozdzielenie ruchu miedzy wiele instancji backendu
CachingCachowanie odpowiedzi statycznych - oszczedzenie backendu
Rate limitingOchrona L7 przed DDoS i scraperami

Header manipulationX-Frame-Options, CSP, HSTS dodawane centralnie
Path-based routingRozdzielenie /api -> backend1, /app -> backend2

Two-firewall DMZ pattern

Klasyczny i wciaz aktualny wzorzec. Dwa firewalle (najlepiej od roznych producentow) tworza miedzy soba strefe zdemilitaryzowana (DMZ). Reverse proxy znajduje sie w DMZ.

Architektura:

           Internet
              |
              v
     +----------------+
     | External       |  Firewall #1 (perimeter, idealnie inny producent)
     | Firewall (FW1) |  - tylko 80/443 in -> DMZ
     +-------+--------+
             |
             v
     +----------------------------+
     |          DMZ                |
     |   - Reverse proxy (IIS+ARR  |  Strefa zdemilitaryzowana
     |     lub Nginx)              |  - hosty publicznie dostepne
     |   - WAF (opcjonalnie)       |  - brak ruchu inicjowanego do LAN
     |   - Public DNS              |
     |   - Mail relay              |
     +-------+--------------------+
             |
             v
     +----------------+
     | Internal       |  Firewall #2 (segment internal)
     | Firewall (FW2) |  - tylko proxy -> konkretne porty backendu
     +-------+--------+
             |
             v
     +----------------------------+
     |   Internal LAN              |
     |   - App servers             |  Backend - chroniony
     |   - Database                |  - brak ekspozycji do Internetu
     |   - AD / file servers       |
     +-----------------------------+

Reguly firewallowe

FirewallDirectionSourceDestinationPortAkcja
FW1 (External)InboundAnyDMZ-Proxy80, 443Allow
FW1 (External)InboundAnyAnyAnyDeny (default)
FW1 (External)OutboundDMZInternet53, 80, 443 (limited)Allow (updates, OCSP)
FW2 (Internal)InboundDMZ-ProxyBackend-App8080 (specific)Allow
FW2 (Internal)InboundDMZLANAnyDeny (default)
FW2 (Internal)OutboundLANDMZAnyDeny (chyba ze inicjowane z LAN)

Zlota zasada: Z DMZ nigdy nie powinno byc inicjowanego ruchu do LAN. Backend serwery laczy sie z DMZ proxy tylko w odpowiedzi na requesty (sesje juz nawiazane). Po kompromitacji proxy atakujacy nie ma jak dostac sie do LAN.

Implementacja DMZ proxy - opcje

IIS + ARR (Application Request Routing)

Microsoft stack - dobre dla srodowisk juz uzywajacych Windows Server.

  • Wbudowane w Windows, dobrze zintegrowane z AD
  • URL Rewrite + ARR daje pelne mozliwosci reverse proxy
  • Web Farms z load balancing i health checks
  • Zarzadzanie przez IIS Manager (GUI) lub PowerShell

Nginx

Najpopularniejszy reverse proxy w swiecie open source. Dziala tez na Windows ale natywnie na Linux.

  • Bardzo wysoka wydajnosc (event-driven, asynchroniczny)
  • Bogata ekosfera modulow (Lua, OpenResty)
  • Konfiguracja w plikach .conf - infrastrukturalne jako kod
  • Free + komercyjny Nginx Plus z dodatkowymi funkcjami
# Przyklad konfiguracji Nginx jako reverse proxy
server {
    listen 443 ssl http2;
    server_name app.contoso.com;

    ssl_certificate     /etc/ssl/certs/contoso.crt;
    ssl_certificate_key /etc/ssl/private/contoso.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;

    location /api/ {
        proxy_pass         http://10.10.1.10:8080;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://10.10.1.20:80;
    }
}

HAProxy

Klasyk load balancingu, popularny w wysokoprzepustowych srodowiskach. Lepszy dla TCP/L4 niz Nginx, w L7 porownywalny.

Cloudflare / Azure Front Door / AWS CloudFront

Cloud-based reverse proxy + CDN + WAF - eliminuje koniecznosc utrzymywania wlasnego DMZ proxy. Najnowoczesniejsze podejscie dla wielu organizacji.

SSL termination

Trzy wzorce obsługi TLS w reverse proxy:

WzorzecOpisPlusyMinusy
SSL TerminationTLS terminowane na proxy, plain HTTP do backenduMniejsze obciazenie backendu, latwe debugowaniePlain HTTP w sieci wewnetrznej (compliance ryzyko)
SSL Re-encryptionTLS terminowane na proxy + nowe TLS do backenduEnd-to-end encryption, mozliwa inspekcjaDodatkowy CPU, dwa certyfikaty
SSL PassthroughTLS przechodzi przez proxy bez deszyfrowania (TCP relay)True E2E, brak modyfikacjiBrak L7 features (WAF, headers, caching)

Rekomendacja: Dla wiekszosci aplikacji - SSL Termination. Dla compliance (PCI DSS, HIPAA) - SSL Re-encryption. SSL Passthrough tylko gdy aplikacja wymaga end-to-end (np. mTLS, custom protocols).

X-Forwarded-* headers

Kluczowe naglowki przekazujace informacje o orginalnym kliencie:

HeaderCo zawieraPrzyklad
X-Forwarded-ForLancuch IP klienta + posrednikow203.0.113.5, 198.51.100.1
X-Forwarded-ProtoSchemat orginalny (http/https)https
X-Forwarded-HostOrginalny Host headerapp.contoso.com
X-Real-IPIP najblizszego klienta (single value)203.0.113.5
Forwarded (RFC 7239)Standardowy zamiast X-* prefixedfor=203.0.113.5;proto=https

Konfiguracja backendu: Aplikacja musi jawnie ufac X-Forwarded-* headers. W przeciwnym razie atakujacy moze podszywac sie pod inny IP. Frameworki:
- Express: app.set('trust proxy', '127.0.0.1')
- ASP.NET Core: app.UseForwardedHeaders() z whitelist proxy IPs
- Flask: ProxyFix(app.wsgi_app, x_for=1, x_proto=1)
- IIS: ServerVariables w URL Rewrite

Bezpieczenstwo zarzadzania

  • Mgmt VLAN - dedykowana siec do zarzadzania DMZ proxy (RDP, SSH, monitoring)
  • Bastion host / Jump server - obowiazkowe wejscie przez bastion, NIE bezposrednio
  • IP whitelist - tylko adresy IP adminow moga sie laczyc do mgmt portow
  • MFA - drugi czynnik dla logowania (Smart Card, FIDO2, TOTP)
  • Logging mgmt sessions - PowerShell transcription, sudo logi, RDP session recording
  • JIT access - Azure Bastion, AWS SSM Session Manager (no SSH/RDP exposed)

Multi-region / High Availability

WzorzecOpis
Active-Passive (single region)2 proxy + VRRP/keepalived/Failover Cluster - automatyczne przelaczenie
Active-Active (single region)2+ proxy za load balancerem (ELB, ALB, AKS Ingress)
Active-Active (multi-region)Geographic routing przez Azure Traffic Manager / AWS Route53 / CloudFront
Anycast (CDN)Cloudflare / Akamai - jednolity adres IP rozproszony globalnie

Logging i monitoring

  • Access logs proxy zawieraja: czas, IP klienta, request, response code, czas, User-Agent
  • Wysylac do centralnego SIEM (logi proxy = pierwsza linia detekcji)
  • Health check endpoints - dedicated /health na backendzie
  • Synthetic monitoring - co 30s test z roznych regionow (np. UptimeRobot, Pingdom, Datadog Synthetics)
  • Alarmy: response time > X, error rate > Y%, traffic spike
  • Dashboard z metrics: requests/sec, latency, error rate, backend status

Antywzorce

AntywzorzecProblem
Reverse proxy w wewnetrznej sieci, brak DMZBrak izolacji - kompromitacja proxy = LAN compromise
Aplikacja backend bezposrednio po IP w InternecieBrak ochrony, latwy do skanowania
Self-signed cert na DMZ (publiczny)Klienci dostaja warning, atak MITM mozliwy
Mgmt RDP z Internetu (3389 open)Brute force / RDP exploits (BlueKeep)
Brak X-Forwarded-* lub backend ufa wszystkimIP spoofing - logi pokazuja IP proxy zamiast klienta
Wszystkie aplikacje w jednej puli/serwerzeCrash jednej = padaja pozostale
Backend ma routing default gateway przez InternetCompromise -> backend moze egress do C2

Best practices

  • Two-firewall DMZ z reverse proxy w warstwie publicznej
  • Firewall #1 i #2 od roznych producentow (defense in depth)
  • SSL termination na proxy + opcjonalne re-encryption do backendu
  • X-Forwarded-* zawsze ustawiane, backend ufa tylko proxy IP
  • WAF przed lub na proxy (mod_security, Cloudflare, Azure App Gateway WAF)
  • Mgmt VLAN + bastion host + MFA
  • Health checks z deep checks zaleznosci backendu
  • Logging do SIEM, alarmy na anomalie
  • HA: minimum 2 proxy active-passive lub active-active
  • Regularne testy DR (przelaczenie do drugiego site)
