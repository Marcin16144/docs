Monitoring i troubleshooting

Komendy diagnostyczne, packet capture, monitoring tools, typowe problemy i rozwiazania

Podstawowe komendy diagnostyczne

ping

Najprostszy test - czy host odpowiada (ICMP Echo Request/Reply). Mierzy RTT i packet loss.

# Linux/macOS:
ping 1.1.1.1                       # nieskonczone, Ctrl+C konczy
ping -c 4 1.1.1.1                  # 4 pakiety
ping -i 0.2 1.1.1.1                # interwal 0.2 sekundy
ping -s 1472 1.1.1.1               # rozmiar payload (test MTU)
ping -M do -s 1472 1.1.1.1         # don't fragment

# Windows:
ping 1.1.1.1                       # 4 pakiety domyslnie
ping -t 1.1.1.1                    # nieskonczone
ping -n 100 1.1.1.1                # 100 pakietow
ping -l 1472 1.1.1.1               # rozmiar pakietu

# Output (Linux):
PING 1.1.1.1 (1.1.1.1) 56(84) bytes of data.
64 bytes from 1.1.1.1: icmp_seq=1 ttl=58 time=8.21 ms
--- 1.1.1.1 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3005ms
rtt min/avg/max/mdev = 8.156/8.337/8.547/0.165 ms

traceroute / tracert

Pokazuje droge pakietow przez kolejne routery. Wysyla pakiety z rosnacym TTL i zbiera ICMP Time Exceeded.

# Linux:
traceroute -n 8.8.8.8              # -n = bez DNS resolution
traceroute -I 8.8.8.8              # ICMP zamiast UDP
traceroute -T 8.8.8.8              # TCP probe
traceroute -p 443 -T 8.8.8.8       # TCP do portu 443

# Windows:
tracert 8.8.8.8
tracert -d 8.8.8.8                 # bez DNS

# Output:
traceroute to 8.8.8.8 (8.8.8.8), 30 hops max, 60 byte packets
 1  192.168.1.1   1.234 ms   0.987 ms   0.876 ms
 2  10.50.1.1     5.432 ms   5.123 ms   5.234 ms
 3  79.96.x.x     8.123 ms   8.234 ms   8.345 ms
 4  *  *  *                        # nie odpowiada (filtruje ICMP)
 5  8.8.8.8       8.567 ms   8.456 ms   8.345 ms

mtr - My TraceRoute

Ciagle traceroute z statystykami per hop. Najlepsze narzedzie do diagnostyki packet loss.

# Linux:
mtr 8.8.8.8                        # interaktywny
mtr -r -c 100 8.8.8.8              # raport po 100 cyklach
mtr -nrwc 100 8.8.8.8              # raport, bez DNS, wide format

dig / nslookup

DNS lookup tools.

# dig - swiss army knife DNS:
dig example.com                    # podstawowy A lookup
dig +short example.com             # tylko adresy
dig MX example.com                 # rekord MX
dig AAAA example.com               # IPv6
dig @1.1.1.1 example.com           # konkretny resolver
dig +trace example.com             # od root przez TLD do authoritative
dig -x 8.8.8.8                     # reverse DNS
dig +noall +answer example.com     # tylko answer section

# nslookup (cross-platform):
nslookup example.com
nslookup example.com 1.1.1.1
nslookup -type=MX example.com

# host (uproszczone):
host example.com
host -t TXT example.com

nmap - skanowanie portow

# Domyslne skanowanie 1000 najpopularniejszych portow:
nmap example.com

# Konkretne porty:
nmap -p 22,80,443 example.com
nmap -p 1-1000 example.com         # zakres
nmap -p- example.com               # wszystkie 65535

# Skan calej podsieci:
nmap 192.168.1.0/24

# Service detection (-sV):
nmap -sV -p 22,80,443 example.com

# OS detection (-O):
sudo nmap -O example.com

# Aggressive (vse wymienione + traceroute + scripts):
sudo nmap -A example.com

# Skan UDP (powolny):
sudo nmap -sU -p 53,123,161 example.com

# Stealth (SYN scan, half-open):
sudo nmap -sS example.com

# Skripty NSE - wykrywanie podatnosci:
nmap --script vuln example.com
nmap --script ssl-enum-ciphers -p 443 example.com

nc / netcat - swiss army knife

# Test TCP polaczenia:
nc -v example.com 443
# Connection to example.com 443 port [tcp/https] succeeded!

# Listen mode (sluchaj na porcie):
nc -lvp 8080

# Send file:
# Strona odbierajaca:
nc -lvp 8080 > received.bin
# Strona wysylajaca:
nc receiver.host 8080 < file.bin

# UDP:
nc -u host 53

# Quick HTTP request:
echo -e "GET / HTTP/1.1\r\nHost: example.com\r\n\r\n" | nc example.com 80

# Banner grabbing:
nc -v ssh.host 22

ss / netstat

Wyswietlanie polaczen i listening socketow. ss jest nowsze i szybsze niz netstat.

# ss (preferred):
ss -tulpn                          # TCP/UDP listening z procesami i numerami
ss -tn state established           # aktywne TCP polaczenia
ss -t                              # tylko TCP
ss -u                              # tylko UDP
ss -l                              # listening
ss -p                              # process info
ss -n                              # numeric (no DNS resolution)
ss -i                              # extended info (cwnd, rtt)
ss -s                              # summary (statystyki)

# Konkretny port:
ss -tn dport = :443
ss -tn sport = :22

# netstat (legacy, dziala wszedzie):
netstat -tulpn                     # Linux
netstat -an                        # Windows
netstat -an | findstr LISTENING    # Windows: tylko sluchajace

lsof -i

# Co uzywa portu 80?
sudo lsof -i :80

# Co uzywa portow w zakresie?
sudo lsof -i :1-1024

# Wszystkie network connections procesu:
sudo lsof -p 12345 -i

# Tylko TCP listening:
sudo lsof -i TCP -s TCP:LISTEN

iperf3 - test bandwidth

# Server side:
iperf3 -s

# Client side:
iperf3 -c server.host
iperf3 -c server.host -t 30        # 30 sekund
iperf3 -c server.host -P 4         # 4 paralelne strumienie
iperf3 -c server.host -R           # reverse (server -> client)
iperf3 -c server.host -u           # UDP
iperf3 -c server.host -u -b 1G     # UDP 1 Gbps target

# Output (typowy gigabit):
[ ID] Interval           Transfer     Bitrate
[  5]  0.00-10.00 sec   1.10 GBytes   946 Mbits/sec  sender
[  5]  0.00-10.00 sec   1.10 GBytes   945 Mbits/sec  receiver

curl / wget

# curl - testowanie HTTP:
curl -v https://example.com        # verbose - widac TLS handshake
curl -I https://example.com        # tylko headers (HEAD request)
curl -L https://example.com        # follow redirects
curl --resolve example.com:443:1.2.3.4 https://example.com   # custom DNS
curl -k https://self-signed.com    # ignoruj cert (insecure)

# Mierzenie czasu:
curl -w "@curl-format.txt" -o /dev/null -s https://example.com
# format: time_namelookup, time_connect, time_appconnect, time_total

# wget - download:
wget https://example.com/file.zip
wget -c https://example.com/file.zip   # continue resume
wget -r -np https://example.com/dir/    # recursive, no parent

Packet capture

tcpdump

Klasyczny CLI do capturowania pakietow. Bardzo mocny, BPF filter syntax.

# Najprostsze - na interface eth0:
sudo tcpdump -i eth0

# Z DNS i numerami portow:
sudo tcpdump -i eth0 -nn

# Konkretny host:
sudo tcpdump -i eth0 host 1.2.3.4

# Konkretny port:
sudo tcpdump -i eth0 port 443
sudo tcpdump -i eth0 'tcp port 80'

# Kombinacje BPF:
sudo tcpdump -i eth0 'host 1.2.3.4 and port 80'
sudo tcpdump -i eth0 'src host 1.2.3.4 or dst host 5.6.7.8'
sudo tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn) != 0'   # SYN packets

# Zapis do pliku PCAP:
sudo tcpdump -i eth0 -w capture.pcap

# Czytanie z pliku:
tcpdump -r capture.pcap

# Hex + ASCII:
sudo tcpdump -i eth0 -A port 80
sudo tcpdump -i eth0 -X port 80    # hex + ascii

# ICMP traffic:
sudo tcpdump -i eth0 icmp

# Limit pakietow:
sudo tcpdump -i eth0 -c 100        # zatrzymaj po 100

Wireshark

GUI do analizy ruchu. Zaznajamia ze sie z protokolami, dekoduje setki z nich. Niezbedne narzedzie diagnostyki.

Filter examples

# Display filters (rozne od capture filters!):
ip.addr == 192.168.1.10
tcp.port == 443
http.request.method == "POST"
dns.qry.name == "example.com"
tcp.flags.syn == 1 and tcp.flags.ack == 0    # SYN tylko
tcp.analysis.retransmission                  # retransmisje
ssl.handshake.type == 1                      # ClientHello
http.response.code == 500

tshark - Wireshark CLI

# Capture na interface:
sudo tshark -i eth0

# Z filterem:
sudo tshark -i eth0 -f "port 443"

# Display filter (-Y):
sudo tshark -i eth0 -Y "http.request"

# Specific fields:
sudo tshark -i eth0 -T fields -e ip.src -e ip.dst -e http.host

# Read pcap:
tshark -r capture.pcap -Y "dns"

SNMP - Simple Network Management Protocol

SNMP od 1988 - standardowy protokol pollowania urzadzen sieciowych. UDP 161 (queries) / 162 (traps). MIB (Management Information Base) opisuje co mozna pytac.

WersjaBezpieczenstwoStatus
SNMPv1Plain text community stringLegacy, NIE w produkcji
SNMPv2cPlain text community stringNadal popularny niestety
SNMPv3Authentication + encryptionZalecane
# snmpwalk - dump wszystkich OID:
snmpwalk -v 2c -c public 192.168.1.1
snmpwalk -v 2c -c public 192.168.1.1 1.3.6.1.2.1.1   # System group

# Konkretne OID:
snmpget -v 2c -c public 192.168.1.1 sysDescr.0
snmpget -v 2c -c public 192.168.1.1 ifInOctets.1

# SNMPv3 z auth+priv:
snmpwalk -v 3 -u myuser -l authPriv \
  -a SHA -A "authpassword" \
  -x AES -X "privpassword" \
  192.168.1.1

NetFlow / IPFIX / sFlow

Protokoly do zbierania statystyk ruchu. Routery wysylaja sample lub flow records do collectora.

  • NetFlow v5/v9 - Cisco, najczesciej spotykany
  • IPFIX (RFC 7011) - IETF standard, oparty na NetFlow v9
  • sFlow - sample-based (np. 1 z 1000 pakietow), wsparcie wielu producentow
  • Kolektory: nfdump/nfsen, ntopng, FlowMon, Plixer

Najczestsze problemy + rozwiazania

"Brak internetu"

# Krok 1: link layer
ip link show eth0                  # czy interface UP?
ethtool eth0                       # negocjacja link, predkosc

# Krok 2: IP
ip addr show eth0                  # czy ma adres IP?
ip route show                      # czy jest default gateway?

# Krok 3: gateway
ping 192.168.1.1                   # local gateway

# Krok 4: ISP / WAN
ping 8.8.8.8                       # publiczny IP
ping 1.1.1.1                       # alternatywny

# Krok 5: DNS
ping google.com                    # DNS resolution + osiagalnosc
nslookup google.com 1.1.1.1        # explicit resolver

# Diagnoza:
# - ping 192.168.1.1 OK, 8.8.8.8 FAIL  -> problem ISP/gateway
# - ping 8.8.8.8 OK, ping google.com FAIL -> problem DNS
# - wszystko OK ale strona nie ladowuje  -> firewall, MTU, routing

"Wolny internet"

  • Speedtest: porownaj z deklaracja ISP. Jesli np. 50/10 zamiast 1000/100 - problem fizyczny lub kontrakt
  • Ping i jitter: wysokie warto. -> congestion lub problemy WAN
  • MTU issues: ping -M do -s 1472 8.8.8.8 - jesli niedaje, zmniejsz MTU
  • Sprawdz CPU routera: czesto bottleneck - tani router nie obsluzy 1 Gbps z NAT/QoS/VPN
  • WiFi vs ethernet: jesli WiFi wolniejsze, znajdz mniej zatkany kanal

"Port zablokowany"

# Test z zewnatrz:
nc -v your.public.ip 8080
# Connection refused = port closed
# Operation timed out = filtered (firewall)
# Connection succeeded = port open

# Sprawdz kolejno:
1. Aplikacja nasluchuje?    -> ss -tlnp | grep :8080
2. Lokalny firewall?         -> iptables -L -n / ufw status
3. NAT na routerze?          -> port forwarding skonfigurowany?
4. ISP filtruje port?        -> niektore ISP blokuja port 25, 80, 443 dla home users
5. CGNAT?                    -> jesli IP zaczyna sie 100.64-127, masz CGNAT i nie masz publicznego IP

"Cannot reach server"

mtr -rwc 50 server.host
# Patrz w ktorym hopie packet loss zaczyna sie. To routing problem na tej trasie.

# Test alternatywna trasa:
# - przez VPN
# - przez mobile network
# - z innego DNS

"DNS nie resolvuje"

# Test z roznymi resolverami:
dig @1.1.1.1 example.com
dig @8.8.8.8 example.com
dig @9.9.9.9 example.com

# Jesli wszystkie failuje - problem z domena (NXDOMAIN)
# Jesli tylko twoj resolver - cache problem lub MITM

# Flush DNS cache:
sudo systemd-resolve --flush-caches    # Linux systemd
sudo killall -HUP mDNSResponder        # macOS
ipconfig /flushdns                     # Windows

# Sprawdz konfiguracje resolvera:
cat /etc/resolv.conf                   # Linux
scutil --dns                           # macOS
ipconfig /all                          # Windows
