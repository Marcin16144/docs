Co to jest TLS

TLS (Transport Layer Security) to nastepca SSL (Secure Sockets Layer). Zapewnia trzy rzeczy: poufnosc (szyfrowanie), integralnosc (kontrola modyfikacji) i autentykacje (potwierdzenie tozsamosci serwera). Stosowany w HTTPS, SMTP-TLS, IMAPS, FTPS, OpenVPN i wielu innych.

Lancuch zaufania

Certyfikat lisciasty (leaf, end-entity) podpisany jest przez certyfikat posredni (intermediate), ktory podpisany jest przez root CA. Root CA jest w zaufanym magazynie systemu/przegladarki.

Root CA (self-signed, w trust store przegladarki/OS)
  |
  +-- Intermediate CA (wystawiony przez Root)
        |
        +-- Leaf certificate (wystawiony przez Intermediate, dla example.com)

# W praktyce serwer wysyla bundle:
# leaf cert + intermediate cert(s)
# (root jest po stronie klienta)

Wildcard vs SAN

Wildcard certificate

Cert z CN/SAN *.example.com chroni wszystkie subdomeny pierwszego poziomu (api.example.com, www.example.com). NIE pokrywa apex (samej example.com - trzeba osobno) ani a.b.example.com.

SAN (Subject Alternative Names)

Cert moze zawierac wiele konkretnych nazw, np. example.com, www.example.com, mail.example.com. Lista do 100-250 SAN typowo.

# Wildcard - wymaga DNS-01 challenge w Let's Encrypt:
*.example.com    # api, www, mail
example.com      # apex - NIE pokryty wildcard, dodaj osobno

# Multi-SAN cert:
example.com
www.example.com
api.example.com
admin.example.com
shop.example.com

ACME - automatyzacja certyfikatow

ACME (Automated Certificate Management Environment, RFC 8555) to protokol uzywany przez Let's Encrypt i innych. Klient ACME automatycznie zamawia, weryfikuje i odnawia certyfikaty.

Wyzwania ACME

ChallengeMechanizmUzycie
HTTP-01Plik na serwerze pod /.well-known/acme-challenge/Domyslne, latwe na public web
DNS-01Rekord TXT _acme-challenge.example.comWildcard certs, internal services
TLS-ALPN-01Specjalny TLS handshake na porcie 443Gdy port 80 niedostepny

Klienci ACME

  • certbot - oficjalny Python klient EFF, najpopularniejszy
  • acme.sh - bash, najlzejszy, masa pluginow DNS
  • lego - Go, modulowy
  • Caddy - HTTP serwer z auto-HTTPS wbudowanym
  • Traefik - reverse proxy z auto cert
  • cert-manager - dla Kubernetes

certbot - przyklady

# Standalone (otwiera port 80 sam):
sudo certbot certonly --standalone -d example.com -d www.example.com

# Webroot (uzywa istniejacego serwera):
sudo certbot certonly --webroot -w /var/www/html -d example.com

# Nginx plugin (auto-konfiguracja):
sudo certbot --nginx -d example.com

# Apache plugin:
sudo certbot --apache -d example.com

# Wildcard (DNS-01 z Cloudflare):
sudo certbot certonly --dns-cloudflare \
  --dns-cloudflare-credentials ~/.cf.ini \
  -d example.com -d "*.example.com"

# Renewal (automatyczne via cron/systemd timer):
sudo certbot renew --dry-run
sudo certbot renew

# Lista certyfikatow:
sudo certbot certificates

# Usuniecie:
sudo certbot delete --cert-name example.com

acme.sh - przyklady

# Instalacja:
curl https://get.acme.sh | sh

# Standalone:
acme.sh --issue --standalone -d example.com

# DNS API (Cloudflare):
export CF_Token="xxx"
export CF_Account_ID="xxx"
acme.sh --issue --dns dns_cf -d example.com -d "*.example.com"

# Instalacja cert do nginx (po wystawieniu):
acme.sh --install-cert -d example.com \
  --key-file /etc/nginx/ssl/example.com.key \
  --fullchain-file /etc/nginx/ssl/example.com.cer \
  --reloadcmd "systemctl reload nginx"

Caddy - auto HTTPS w 5 liniach

# Caddyfile
example.com {
    reverse_proxy localhost:8080
}

# Caddy automatycznie:
# 1. Wystawi cert z Let's Encrypt
# 2. Skonfiguruje HTTPS (port 443)
# 3. Przekierowuje HTTP -> HTTPS
# 4. Odnowi cert przed wygasnieciem

OCSP - Online Certificate Status Protocol

OCSP pozwala sprawdzic czy cert nie zostal odwolany. Klient pyta serwer OCSP CA o status certu serwera.

OCSP Stapling

Serwer sam regularnie pobiera podpisana odpowiedz OCSP od CA i dolacza ja do TLS handshake. Klient nie musi pytac CA - lepiej dla wydajnosci i prywatnosci.

# Nginx OCSP stapling:
ssl_stapling on;
ssl_stapling_verify on;
ssl_trusted_certificate /etc/ssl/chain.pem;
resolver 1.1.1.1 valid=300s;
resolver_timeout 5s;

CRL (Certificate Revocation List)

CRL to lista odwolanych certyfikatow publikowana przez CA. Klient pobiera caly plik. Bardziej archiczne niz OCSP - nie skaluje sie dobrze.

Certificate Transparency

Certificate Transparency (RFC 6962) wymaga aby wszystkie publicznie zaufane CA logowaly wystawione certyfikaty do publicznych logow CT. Daje przejrzystosc - mozna sprawdzic czy ktos wystawil cert dla naszej domeny.

# Sprawdzenie cert dla domeny przez CT:
# https://crt.sh/?q=example.com

# CLI z curl:
curl -s "https://crt.sh/?q=example.com&output=json" | jq

Cipher suites - wspolczesne

Cipher suite to kombinacja: key exchange + authentication + bulk cipher + MAC. TLS 1.3 znacznie uproscil cipher suites.

TLS 1.3 - tylko 5 cipher suites

TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_CCM_SHA256
TLS_AES_128_CCM_8_SHA256

# AES-GCM - hardware accelerated (AES-NI), preferowany na x86/ARM modern
# ChaCha20-Poly1305 - software-friendly, lepszy na slabsze CPU mobile

TLS 1.2 - bezpieczne cipher suites

# Polec ECDHE (forward secrecy) + AEAD (GCM/CCM):
ECDHE-ECDSA-AES256-GCM-SHA384
ECDHE-RSA-AES256-GCM-SHA384
ECDHE-ECDSA-CHACHA20-POLY1305
ECDHE-RSA-CHACHA20-POLY1305
ECDHE-ECDSA-AES128-GCM-SHA256
ECDHE-RSA-AES128-GCM-SHA256

# UNIKAJ:
- RC4, DES, 3DES (slabe)
- MD5, SHA1 (zlamane)
- CBC bez ETM (BEAST, Lucky13)
- RSA key exchange (brak forward secrecy)

Forward secrecy (PFS)

Perfect Forward Secrecy zapewnia ze nawet jesli klucz prywatny serwera zostanie skradziony, stare nagrane sesje nie beda mogly byc odszyfrowane. Wymaga ECDHE/DHE key exchange (zamiast RSA).

HSTS - HTTP Strict Transport Security

HSTS (RFC 6797) mowi przegladarce "uzywaj HTTPS dla tej domeny przez X sekund". Zapobiega downgrade attacks.

# Nginx:
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;

# Apache:
Header always set Strict-Transport-Security "max-age=63072000; includeSubDomains; preload"

# Preload list:
# https://hstspreload.org/
# Po dodaniu - przegladarki zawsze HTTPS, nawet pierwszy raz

Komendy openssl

# Wygeneruj klucz prywatny RSA:
openssl genrsa -out example.com.key 2048

# Wygeneruj klucz ECDSA:
openssl ecparam -genkey -name prime256v1 -out example.com.key

# Stworz CSR (Certificate Signing Request):
openssl req -new -key example.com.key -out example.com.csr \
  -subj "/CN=example.com/O=My Company/C=PL"

# Podejrzyj cert:
openssl x509 -in cert.pem -text -noout

# Sprawdz lancuch zaufania:
openssl s_client -connect example.com:443 -servername example.com -showcerts

# Sprawdz validity:
openssl x509 -in cert.pem -dates -noout

# Self-signed cert (rozwoj):
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout key.pem -out cert.pem \
  -subj "/CN=localhost"

# Konwersja formatow:
openssl x509 -in cert.pem -out cert.der -outform DER  # PEM -> DER
openssl pkcs12 -export -in cert.pem -inkey key.pem -out cert.pfx  # PEM -> PFX

# Test polaczenia TLS:
openssl s_client -connect example.com:443 -tls1_3
openssl s_client -connect example.com:443 -tls1_2

# Sprawdz wszystkie cipher suites serwera:
nmap --script ssl-enum-ciphers -p 443 example.com

Certificate pinning

HPKP (HTTP Public Key Pinning) byl mechanizmem przypinania konkretnego klucza w przegladarce. Deprecated w 2018 - zbyt latwo bylo "zabic" wlasna domene zlym pinem (DoS na siebie). Obecnie zastapiony Certificate Transparency.

Best practices 2026: Let's Encrypt + Caddy/Traefik dla auto-HTTPS, TLS 1.3 only (lub TLS 1.2 z fallback), ECDSA P-256 key, OCSP stapling, HSTS z preload, monitoring CT przez crt.sh, A+ na ssllabs.com.
