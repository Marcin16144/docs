Protokoly transportowe TCP, UDP, ICMP

Warstwa transportowa internetu - jak dziala niezawodne i szybkie przekazywanie danych

TCP - Transmission Control Protocol

TCP (RFC 9293) zapewnia niezawodna, uporzadkowana, polaczeniowa transmisje strumieniowa. To najczesciej uzywany protokol w internecie - HTTP, SSH, FTP, SMTP, IMAP wszystkie pracuja na TCP.

Cechy TCP

  • Reliable - kazdy bajt potwierdzany ACK; brak ACK = retransmisja
  • Ordered - dane dostarczane w kolejnosci wysylania (sequence numbers)
  • Connection-oriented - sesja musi byc nawiazana (handshake) i zakonczona (FIN)
  • Flow control - sliding window kontroluje ile danych mozna wyslac przed ACK
  • Congestion control - reaguje na zatory w sieci, zwalnia transmisje
  • Stream-based - aplikacja widzi ciagly strumien bajtow, nie pakiety

3-way handshake

# Nawiazanie polaczenia TCP:
Klient                                Serwer
  |                                      |
  | -------- SYN (seq=100) -----------> |   1. Klient: "chce sie polaczyc"
  |                                      |
  | <----- SYN-ACK (seq=500, ack=101) -- |   2. Serwer: "OK, ja tez"
  |                                      |
  | -------- ACK (seq=101, ack=501) ----> |   3. Klient: "OK, zaczynamy"
  |                                      |
  |                                      |
  | === Connection ESTABLISHED === |

Zakonczenie polaczenia (4-way)

# Graceful close (FIN):
Klient                                Serwer
  | -------- FIN -------------> |   "skonczylem wysylac"
  | <-------- ACK ------------- |   "OK"
  | <-------- FIN ------------- |   "ja tez skonczylem"
  | -------- ACK -------------> |   "OK, zegnaj"

# Lub abrupt close (RST):
  | -------- RST -------------> |   "polaczenie ASAP zerwij"

Sliding window i flow control

Kazda strona ogasza receive window - ile danych moze przyjac. Nadawca nie wysyla wiecej niz to okno. Window scaling (RFC 7323) pozwala oknom > 64 KB az do 1 GB.

# Linux - parametry TCP window:
sysctl net.core.rmem_max        # max receive buffer
sysctl net.ipv4.tcp_rmem        # min/default/max receive buffers
sysctl net.ipv4.tcp_wmem        # min/default/max send buffers
sysctl net.ipv4.tcp_window_scaling   # zwykle 1 (enabled)

# Sprawdzenie aktywnych window:
ss -i                            # extended info per socket

Congestion control - Reno, Cubic, BBR

AlgorytmRokCharakterystyka
Reno / NewReno1990Klasyczny - wolny start + AIMD (Additive Increase, Multiplicative Decrease)
CUBIC2008Default w Linuksie - krzywa szescienna, lepiej w high-bandwidth
BBR (Bottleneck Bandwidth and RTT)2016Google - mierzy rzeczywista przepustowosc i RTT, nie czeka na pakiety zgubione
BBRv2/v32020+Ulepszone wersje BBR, fairness do CUBIC
# Linux - zmiana algorytmu congestion control:
sysctl net.ipv4.tcp_congestion_control       # check current
sudo sysctl -w net.ipv4.tcp_congestion_control=bbr
echo "net.ipv4.tcp_congestion_control=bbr" | sudo tee -a /etc/sysctl.conf

# Dostepne algorytmy:
sysctl net.ipv4.tcp_available_congestion_control

MSS - Maximum Segment Size

MSS to maksymalny rozmiar TCP payload (bez headerow). Zwykle MTU - IP header - TCP header = 1500 - 20 - 20 = 1460 bajtow dla Ethernet. Dla VPN/MPLS zmniejsza sie o overhead.

UDP - User Datagram Protocol

UDP (RFC 768) jest minimalistyczny: connectionless, bez gwarancji dostarczenia, bez kolejnosci. Header tylko 8 bajtow vs 20+ TCP. Dlatego jest szybki i ma mniejszy overhead.

# Header UDP (8 bajtow):
| Source Port (16) | Dest Port (16) |
| Length (16)      | Checksum (16)  |
| ............ Data ............... |

Kiedy uzywac UDP

  • DNS - krotkie zapytania, retransmisja na poziomie aplikacji
  • VoIP (RTP) - opozniony pakiet jest gorszy niz zgubiony
  • Video streaming - mozna sobie pozwolic na klatke ubytek
  • Gaming online - liczy sie low latency, nie 100% packet delivery
  • NTP - synchronizacja czasu
  • DHCP - broadcast, brak sesji
  • SNMP - lekkie zapytania monitoringowe
  • WireGuard, QUIC - VPN i HTTP/3 buduja niezawodnosc na UDP

ICMP - Internet Control Message Protocol

ICMP (RFC 792) to protokol "metadanych" warstwy network. Sluzy do diagnostyki, raportowania bledow, kontroli ruchu. NIE jest TCP ani UDP - dziala bezposrednio na IP.

ICMPv6 i NDP

W IPv6 ICMP rozszerzono: NDP (Neighbor Discovery Protocol) zastapil ARP. NDP korzysta z multicastu zamiast broadcastu (ktorego nie ma w IPv6).

  • RS (Router Solicitation) - klient pyta routery
  • RA (Router Advertisement) - router oglasza prefiks i konfiguracje
  • NS (Neighbor Solicitation) - odpowiednik ARP request
  • NA (Neighbor Advertisement) - odpowiednik ARP reply

QUIC - Quick UDP Internet Connections

QUIC (RFC 9000) to nowoczesny protokol transportowy zbudowany na UDP. Bazuje na nim HTTP/3. Stworzony przez Google w 2012, standaryzowany w 2021 przez IETF.

Zalety QUIC

  • 0-RTT handshake - przy ponownym polaczeniu zero round-trip time
  • Multiplexing bez head-of-line blocking - kazdy stream niezalezny (w przeciwienstwie do HTTP/2 nad TCP)
  • Wbudowane TLS 1.3 - szyfrowanie obowiazkowe
  • Connection migration - przelaczenie z WiFi na 5G bez restartu sesji
  • User-space implementation - latwiej rozwijac niz zmieniac kernel TCP

Port forwarding i NAT traversal

Aby aplikacja na komputerze za NAT byla dostepna z internetu, trzeba skonfigurowac port forwarding na routerze. Dla aplikacji P2P (np. WebRTC) stosuje sie automatyczne metody.

  • UPnP (Universal Plug and Play) - aplikacja prosi router o otwarcie portu (czesto niebezpieczne, wylaczane w firmach)
  • NAT-PMP / PCP - alternatywa Apple/IETF, prostsza i bezpieczniejsza
  • STUN (Session Traversal Utilities for NAT) - dowiaduje sie publicznego IP/portu
  • TURN (Traversal Using Relays around NAT) - relay gdy bezposrednie polaczenie niemozliwe
  • ICE (Interactive Connectivity Establishment) - lacznie probuje wszystkie metody

Zlote zasada - TCP gdy potrzebujesz niezawodnosci (HTTP, baza danych, plik), UDP gdy potrzebujesz szybkosci i mozesz tolerowac straty (gry, voip, dns), QUIC gdy potrzebujesz obu (HTTP/3).
