Prompty dla CMS plugin-based

Core CMS + dodawanie rozszerzen jako pluginy — od projektowania API po dystrybucje.

Dlaczego plugin architecture?

Tradycyjny CMS: wszystko wbudowane, customizacja = forking core.

Plugin-based CMS: maly stabilny core + funkcje jako pluginy, marketplace, niezalezny lifecycle.

Koncepty:

  1. Hooks (actions/filters) — punkty rozszerzen w core
  2. Service Container — DI rejestrowane przez pluginy
  3. Event Bus — pub/sub dla pluginow (luzny coupling)
  4. Plugin Manifest — metadata (version, dependencies, hooks)
  5. Public API — stabilne interfejsy zachowywane przez core
  6. Lifecycle hooks — install, activate, deactivate, uninstall

KROK 2: Definicja Plugin API

ZADANIE: Zaprojektuj Plugin API (kontrakt core ↔ plugin).

1. INTERFEJS PluginInterface
   - Lifecycle: install(), uninstall(), activate(), deactivate()
   - Metadata: getName(), getVersion(), getDependencies()
   - Permissions: getRequiredPermissions()

2. PLUGIN MANIFEST (plugin.yaml)
   - name, version, author, license
   - core_version_constraint (^2.0)
   - dependencies (other plugins)
   - permissions (db.write, http.outbound...)
   - hooks (ktore rejestruje)

3. HOOK SYSTEM
   - Action hooks: void, side effects
   - Filter hooks: zwracaja zmodyfikowana wartosc
   - Priority (0-100, lower = first)

4. EXTENSION POINTS
   - Admin menu items
   - Routes (frontend + admin)
   - Twig templates / template overrides
   - CLI commands
   - Database migrations (per plugin schema)

5. EVENTS (oficjalne wydarzenia core)
   - Article: BeforePublish, AfterPublish, BeforeDelete
   - User: AfterRegister, AfterLogin
   - System: PluginActivated, PluginDeactivated

Output: Markdown z PHP interfejsami i przykladowym manifest.

KROK 3: Plugin Manager (core component)

PLIK: src/Core/Plugin/PluginManager.php

ZADANIE: Implementuj PluginManager — serce systemu pluginow.

ODPOWIEDZIALNOSCI:
1. Discovery — skanowanie folderu plugins/ dla plugin.yaml
2. Validation — sprawdzanie manifestu (semver, dependencies, signature)
3. Loading — kolejnosc wg dependency graph (topological sort)
4. Lifecycle — install/activate/deactivate/uninstall
5. Permission check — czy plugin ma uprawnienia do operacji
6. Health check — czy plugin nie crashuje
7. Dependency resolution — graph + cycle detection
8. State management — ktory plugin jest active w DB

WYMAGANIA:
- Lazy loading — plugin tylko gdy potrzebny
- Cached registry (Redis/file)
- Atomic operations — install/uninstall jako transakcja
- Rollback — gdy install fails

INTERFEJS:
class PluginManager {
    public function discover(): array;
    public function install(string $pluginId): InstallResult;
    public function activate(string $pluginId): void;
    public function deactivate(string $pluginId): void;
    public function uninstall(string $pluginId): void;
    public function getActive(): array;
    public function isCompatible(Plugin $plugin): bool;
}

KROK 4: Hook System

ZADANIE: Implementuj hook system inspirowany WordPress (actions + filters).

WYMAGANIA:

1. ACTION HOOKS (void, side effects)
   $hooks->doAction('article.published', $article);

   Plugin rejestruje:
   $hooks->addAction('article.published',
       [$emailNotifier, 'send'], priority: 10);

2. FILTER HOOKS (zwracaja zmodyfikowana wartosc)
   $title = $hooks->applyFilter('article.title', $rawTitle);

3. PRIORITY (0-100, lower = wczesniej)

4. NAMESPACING ('system.article.published', 'plugin.seo.metaTags')

5. WILDCARD: 'article.*' lapie wszystkie article events

6. PERFORMANCE
   - Skompilowany registry
   - Brak refleksji w runtime
   - Lazy listeners

7. INTEGRACJA Z SYMFONY EVENTS
   - HookManager wraps EventDispatcher

Przykladowa implementacja Plugin main class

final class SeoPlugin extends AbstractPlugin
{
    public function getName(): string { return 'seo-plugin'; }
    public function getVersion(): string { return '1.2.0'; }

    public function install(InstallContext $ctx): void
    {
        $ctx->migrate(__DIR__ . '/../migrations');
        $ctx->settings()->setDefaults([
            'sitemap_enabled' => true,
            'meta_title_suffix' => ' | {site_name}',
        ]);
        $ctx->scheduleJob('seo:sitemap:regenerate', '@daily');
    }

    public function activate(ActivateContext $ctx): void
    {
        $ctx->hooks()->addAction(
            'article.published',
            [SitemapInvalidator::class, 'invalidate'],
            priority: 10
        );

        $ctx->hooks()->addFilter(
            'article.title',
            [TitleEnhancer::class, 'addSuffix'],
            priority: 20
        );

        $ctx->menu()->addAdminMenuItem([
            'label' => 'SEO',
            'icon' => 'search',
            'route' => 'seo_admin_dashboard',
        ]);
    }

    public function getDependencies(): array
    {
        return ['cms-core' => '^2.0'];
    }

    public function getRequiredPermissions(): array
    {
        return ['db.write', 'admin.menu', 'cache.write'];
    }
}

Wzorce architektoniczne

Wzorzec 1: Service Locator + Tags (Symfony native)

// Plugin rejestruje:
$services->set(SeoMetaProvider::class)
    ->tag('seo.meta_provider', ['priority' => 10]);

// Core uzywa:
foreach ($container->findTaggedServices('seo.meta_provider') as $p) {
    $p->provide($article);
}

Plus: Symfony-native, dobre dla DI. Minus: wymaga znajomosci DI tags.

Wzorzec 2: Event-driven (najluzniejszy coupling)

// Core emit:
$dispatcher->dispatch(new ArticlePublished($article));

// Plugin listen (Symfony attributes):
#[AsEventListener(event: ArticlePublished::class)]
class SitemapInvalidator {
    public function __invoke(ArticlePublished $event): void {
        $this->cache->delete('sitemap');
    }
}

Wzorzec 4: Hybrid (rekomendowany)

  • Service Tags dla: providers, processors (silnie typed)
  • Events dla: side effects (notifications, cache invalidation)
  • Hooks (filters) dla: modyfikacji wartosci (jak WP)
  • Plugin Interface dla: lifecycle (install/uninstall)

Bezpieczenstwo plugin systems

Threat model

  1. Malicious plugin — instalujesz, kradnie dane
  2. Vulnerable plugin — exploit przez plugin (SQLi, XSS)
  3. Plugin conflict — psuje inne pluginy lub core
  4. Performance attack — plugin spowalnia hot path
  5. Privilege escalation — plugin uzyskuje wiecej uprawnien
  6. Supply chain attack — wstrzykniecie zlego kodu w update

Mitigations

  1. Code signing — Composer + GPG keys, verify signature
  2. Permission system — manifest deklaruje, runtime enforce
  3. Sandboxing — PHP fpm pool per plugin, filesystem chroot
  4. Static analysis on install — PHPStan, Psalm taint
  5. Runtime isolation — DB schema separate, fs dir, sessions
  6. Audit log — wszystkie plugin actions
  7. Update strategy — auto-patch only, major needs approval

   - Browse marketplace (lista, search, filter, ratings)

   - Show progress
   - Rollback if fails

4. SECURITY
   - Code signing (composer + GPG)
   - Permission prompt
   - Static analysis on install
   - Vendor reputation

5. UPDATE MANAGEMENT
   - Check updates daily (cron)
   - Notify admin
   - Semver-aware (major = manual, patch = auto)

Czego LLM czesto zle robi

Tight coupling core ↔ plugin

// Zle: core wie o konkretnym pluginie
if ($pluginManager->isActive('seo-plugin')) {
    $title = $container->get('seo.title_enhancer')->enhance($title);
}

// Dobrze: hook system, plugin sam sie podpina
$title = $hooks->applyFilter('article.title', $title);

Brak permission system

LLM domyslnie nie mysli o uprawnieniach. Zawsze pytaj: "Jakie permissions powinien miec plugin? Czy core wymusza ich respect?"

Brak BC compatibility planu

"Co sie dzieje gdy core zmienia API w wersji 3.0? Stare pluginy nadal dzialaja? Pluginy must-update? Migration tool dla plugin developers?"
