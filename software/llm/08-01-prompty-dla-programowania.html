Prompty dla programowania i architektury

Z przykladami budowy CMS w PHP — jak podzielic prace, od czego zaczac, jak iteracyjnie pracowac z LLM.

Filozofia: programowanie z LLM ≠ chat

LLM jako para programisty wymaga innego podejscia niz ChatGPT-konwersacja:

Chat:                              Programowanie z LLM:
- "Wyjasnij rekurencje"            - Specyfikacja → projekt → kod → testy → review
- Jeden prompt, jedna odpowiedz    - Lancuch promptow, iteracja
- Tekstowa odpowiedz               - Pliki, struktury, testy
- Brak kontekstu projektu          - Pelny kontekst (codebase, konwencje)

Zasada #1: Im bardziej zlozone zadanie, tym bardziej dziel prace na fazy zamiast jednego mega-promptu.

4-fazowy model promptowania dla developmentu

FAZA 1: ANALIZA (Discovery) — Zrozumienie problemu, wymagan. Output: spec, user stories, edge cases
FAZA 2: PROJEKT (Design) — Architektura, struktura plikow, schema DB. Output: diagramy, ADR, interfejsy
FAZA 3: KOD (Implementation) — Implementacja krok po kroku. Output: pliki, testy, dokumentacja
FAZA 4: REVIEW (Quality) — Bezpieczenstwo, wydajnosc, refactor. Output: poprawki, optymalizacje

FAZA 1: Analiza i wymagania

Cel: wydobyc z LLM pelne zrozumienie problemu zanim zaczniesz pisac kod.

Template — Discovery prompt

ROLA: Jestes senior software architectem z 15-letnim doswiadczeniem
w budowaniu systemow CMS w PHP.

KONTEKST:
Buduje CMS dla sredniej wielkosci portalu (~50k uzytkownikow/dzien).
Wymagania:
- Multi-author publishing
- SEO optimization
- Multi-language (PL/EN)
- Performance < 200ms TTFB
- Komentarze i moderacja

ZADANIE: Przeprowadz analize wymagan:

1. Zadaj 5-10 pytan ktore pomoga doprecyzowac wymagania
2. Zidentyfikuj nietypowe edge cases ktore moga umknac
3. Wskaz ryzyka techniczne dla tej skali
4. Zaproponuj 3 alternatywne podejscia (np. headless vs tradycyjny)
   z analiza trade-offs

NIE pisz jeszcze kodu. Skupiamy sie na zrozumieniu.

Dlaczego to dziala: rola ustawia oczekiwania jakosci, kontekst daje istotne ograniczenia, strukturalne zadanie zamiast "napisz CMS", "NIE pisz kodu" wymusza fazowosc.

Edge cases ktore znajdzie LLM dla CMS:

  • Co przy konfliktach edycji (2 autorow edytuje ten sam artykul)?
  • Cache invalidation przy publikacji
  • Rollback po bledzie w workflow
  • GDPR przy komentarzach (anonymous + IP)
  • Filename sanitization (XSS w mediach)

Iteruj: pierwszy szkic to nie final. Zadawaj pytania:

  • "Dlaczego tu wybrales X zamiast Y?"
  • "Jak ten design zachowa sie przy 10x obciazeniu?"
  • "Gdzie tu sa single points of failure?"

FAZA 3: Implementacja

Anty-pattern: "Napisz caly CMS w PHP"

LLM wygeneruje 500 linii kiepskiego kodu. NIE rob tego.

Pattern: Iteracyjne male kroki

KROK 1: "Implementuj klase Article (aggregate root) zgodnie z architektura.
         Tylko ta klasa, z testami PHPUnit."

KROK 2: "Implementuj ArticleRepository (interface) i jej Doctrine impl."

KROK 3: "Implementuj PublishArticleCommand + Handler. Tylko logika."

KROK 4: "Dodaj HTTP controller dla POST /api/articles/{id}/publish."

KROK 5: "Dodaj integration test dla pelnego flow publikacji."

Template — Implementation prompt

KONTEKST: [link do architektury z fazy 2]

PLIK: src/Domain/Article/Article.php

ZADANIE: Implementuj klase Article jako aggregate root.

WYMAGANIA:
- PHP 8.3, strict_types
- Readonly properties tam gdzie mozliwe
- Wszystkie metody mutacji rzucaja DomainException jesli invariant naruszony
- Emituj Domain Events (ArticlePublished, ArticleEdited)
- Nie zna szczegolow persystencji (Doctrine itp.)

REGULY BIZNESOWE:
- Mozna publikowac tylko Article w stanie DRAFT
- Tytul: 5-200 znakow
- Edycja resetuje publishedAt do null jesli zmiana > 50% tresci
- Po archiwizacji nie mozna juz edytowac

DOSTARCZ:
1. Plik Article.php (z komentarzami WHY, nie WHAT)
2. Plik ArticleStatus.php (enum)
3. Plik ArticleId.php (value object)
4. Pliki domain events
5. Test PHPUnit z 100% coverage scenariuszy biznesowych

Przyklad output PHP

<?php
declare(strict_types=1);

namespace App\Domain\Article;

use App\Domain\Article\Event\ArticlePublished;
use App\Domain\Shared\AggregateRoot;

final class Article extends AggregateRoot
{
    private string $title;
    private string $content;
    private ArticleStatus $status;
    private ?\DateTimeImmutable $publishedAt = null;

    private function __construct(
        public readonly ArticleId $id,
        public readonly AuthorId $authorId,
        public readonly \DateTimeImmutable $createdAt,
    ) {}

    public static function create(
        ArticleId $id,
        string $title,
        AuthorId $authorId,
    ): self {
        self::assertTitleLength($title);
        $article = new self($id, $authorId, new \DateTimeImmutable());
        $article->title = $title;
        $article->content = '';
        $article->status = ArticleStatus::Draft;
        return $article;
    }

    public function publish(\DateTimeImmutable $now): void
    {
        if ($this->status !== ArticleStatus::Draft) {
            throw new \DomainException(
                'Only draft articles can be published'
            );
        }

        $this->status = ArticleStatus::Published;
        $this->publishedAt = $now;

        $this->recordEvent(new ArticlePublished(
            $this->id, $this->authorId, $now
        ));
    }

    private static function assertTitleLength(string $title): void
    {
        $len = mb_strlen($title);
        if ($len < 5 || $len > 200) {
            throw new \DomainException("Title must be 5-200 chars");
        }
    }
}

Patterns dla efektywnej implementacji

Pattern: "Show me X first"

"Zanim napiszesz kod, pokaz:
1. Lista plikow ktore utworzysz
2. Krotka odpowiedz jak kazdy plik wpisuje sie w architekture
3. Czy sa dependencies na inne klasy ktore nie istnieja?

Czekaj na moje OK przed pisaniem kodu."

Pattern: "Test-first"

"Najpierw napisz testy (PHPUnit) dla scenariuszy:
- Tworzenie article z poprawnym tytulem (happy path)
- Title za krotki / za dlugi → DomainException
- Publish DRAFT → status = PUBLISHED, event emitted
- Publish PUBLISHED → DomainException

Pokaz testy. Po mojej akceptacji napisz implementacje."

Pattern: Constraint-driven

"Przy implementacji TRZYMAJ SIE zasad:
- NIE uzywaj static methods (poza named constructors)
- NIE uzywaj global state
- NIE uzywaj zmiennych mutable poza klasa
- KAZDA publiczna metoda ma test
- KAZDY public param ma type hint
- Komentarze tylko WHY, nigdy WHAT"

FAZA 4: Review i refactor

LLM jako niezalezny reviewer — czesto widzi rzeczy ktorych autor nie widzi.

Template — Review prompt

ROLA: Senior PHP engineer specjalizujacy sie w bezpieczenstwie aplikacji.

KOD DO REVIEW: [wklej kod]

ZADANIE: Code review pod katem:

1. BEZPIECZENSTWO
   - SQL injection
   - XSS (output escaping)
   - CSRF
   - File upload vulnerabilities
   - Path traversal
   - Authentication/authorization
   - Sekrety w kodzie

2. WYDAJNOSC
   - N+1 queries
   - Brakujace indeksy DB
   - Cache opportunities
   - Memory leaks (dlugie procesy)

3. JAKOSC KODU
   - SOLID violations
   - Code smells
   - Duplikacja
   - Nieczytelne nazwy

DLA KAZDEGO PROBLEMU:
- Severity: Critical / High / Medium / Low
- Linia / fragment kodu
- Wyjasnienie problemu
- Konkretna propozycja fix-a (kod)

Specjalistyczne review prompty

Security review

"Sprawdz ten kod pod katem OWASP Top 10 2021. Dla kazdego znalezionego problemu pokaz exploit (proof of concept) i fix."

Database review

"Przeanalizuj schema MySQL pod katem: brakujace indeksy (na podstawie typowych queries), niewlasciwe typy kolumn, mozliwosci partycjonowania, czy tabele sa w 3NF?"

Kompletny workflow: budowa CMS w PHP od zera

Krok 1: Discovery (1 prompt)

"Pomoz mi zaplanowac CMS dla portalu newsowego.
Skala: 50k unique/day, 10 autorow, 100 artykulow/tydzien.

Zadaj 10 pytan przed projektowaniem. Czekaj na odpowiedzi."

Krok 2: ADR (1 prompt)

"Na bazie odpowiedzi, wygeneruj 5 ADR dla kluczowych decyzji:
- Framework (custom vs Symfony vs Laravel)
- Database (MySQL vs Postgres)
- Cache (Redis vs Memcached)
- Search (DB vs Elasticsearch vs Meilisearch)
- Frontend (server-rendered vs SPA vs hybrid)

Format: ADR z kontekstem, decyzja i konsekwencjami."

Krok 3: Architektura (1 prompt)

"Na podstawie ADR-ow wygeneruj:
1. C4 diagram (Context, Container) w Mermaid
2. Strukture katalogow (PSR-4)
3. Schema bazy danych (10-15 tabel)
4. Liste bounded contexts (Article, User, Comment, Media...)"

Krok 4: Implementacja per Bounded Context (wiele promptow)

"Zacznij od bounded context Article. Implementuj:
1. Aggregate Article + value objects
2. Repository interface
3. Domain events
4. Doctrine implementation repository
5. PHPUnit tests

Po kazdym pliku — pokaz go i czekaj na review."

Krok 5: Application layer (CQRS)

"Application layer dla Article. Use cases:
- CreateArticleCommand + Handler
- PublishArticleCommand + Handler
- UpdateArticleCommand + Handler
- GetArticleQuery + Handler
- ListPublishedArticlesQuery + Handler

Wszystko z testami integracyjnymi (z prawdziwa baza via testcontainers)."

Krok 6: HTTP layer

"REST API:
POST   /api/articles
GET    /api/articles/{slug}
PATCH  /api/articles/{id}
POST   /api/articles/{id}/publish

Kazdy endpoint:
- Controller (cienki)

- Response format JSON:API

Plus testy E2E (Behat lub PHPUnit)."

Krok 7: UI (frontend)

"Server-side rendered frontend z Twig:
- Layout
- Lista artykulow
- Detail artykulu z komentarzami
- Admin panel (lista, edit, publish)

Use Hotwire (Turbo + Stimulus) dla interactivity bez SPA."

Krok 8: DevOps

"Docker Compose dla dev:
- PHP 8.3 FPM
- Nginx
- MySQL 8
- Redis

Plus:

Najczestsze bledy promptowania

  • ✗ Mega-prompt: "Napisz caly CMS w PHP" → 2000 linii kiepskiego kodu
  • ✗ Brak kontekstu projektu: LLM nie wie co to za projekt, jakie konwencje
  • ✗ Tylko happy path: Brak edge cases, walidacji, testow bledow
  • ✗ Brak ograniczen: LLM moze uzyc dowolnego frameworka, dowolnej wersji PHP
  • ✗ Brak iteracji: Jeden prompt → akceptacja kodu bez pytan

Dobry prompt zawiera

  1. Role (Senior PHP architect)
  2. Kontekst (CMS, skala, stack)
  3. Konkretne zadanie (jeden plik, jedna funkcja)
  4. Constraints (PSR, strict_types, no static)
  5. Format output (kod + testy + komentarze WHY)
  6. Checkpoint (pokaz plan przed kodem)

System prompt dla CMS PHP project

Jestes senior PHP engineer pracujacym nad CMS dla sredniego portalu.

STACK:
- PHP 8.3 (strict types, readonly, enums)
- Symfony 7.x lub Laravel 11.x
- MySQL 8 / PostgreSQL 16
- Redis dla cache i kolejek
- Doctrine ORM
- PHPUnit + Pest dla testow
- PHPStan level 8

KONWENCJE:
- PSR-4 autoloading, PSR-12 code style
- Domain-Driven Design (Domain/Application/Infrastructure/UI)
- CQRS-light (osobne handlery dla command i query)
- Repository pattern z interface w Domain
- Domain Events dla side effects
- Testy: AAA pattern (Arrange-Act-Assert)

ZASADY:
- Nigdy nie uzywaj globals, $GLOBALS, statics
- Kazda publiczna metoda ma type hint i PHPDoc
- Komentarze WHY, nie WHAT
- 100% test coverage dla Domain layer
- Wszystkie SQL przez prepared statements
- Output zawsze escapowany (Twig auto-escape ON)

PRZY PISANIU KODU:
1. Najpierw pokaz plan (pliki, dependencies)
2. Potem testy (jako kontrakt)
3. Potem implementacja
4. Po kazdej fazie czekaj na review

PYTAJ jesli:
- Wymagania niejasne
- Moze byc wiele poprawnych rozwiazan
- Brakuje kontekstu (struktury istniejacego kodu)

"Wygeneruj:

"Bounded Context: Comment.

Praktyczne komendy dla Claude Code / Cursor

/security-audit-php

Przeprowadz security audit zmienionych plikow (git diff main).
Sprawdz:
- SQLi (czy sa przygotowane statements?)
- XSS (czy output escapowany w Twig/PHP?)
- Mass assignment
- File upload (rozszerzenia, MIME, path)
- Hardcoded secrets
- CSRF tokens

Output: lista problemow + fix-y.

/refactor-legacy-php

Refaktor legacy PHP na nowoczesny:
1. Dodaj declare(strict_types=1)
2. Type hints wszedzie
3. Readonly properties
4. Enum zamiast const
5. Dependency injection zamiast new
6. PHPUnit dla kazdej publicznej metody

Pokaz diff. Nie zmieniaj zachowania (testy musza passowac).

Czego unikac

  • ✗ Stare CMS (WordPress 5.x bez blokow) — security ryzyko, vendor lock
  • ✗ Custom framework "from scratch" — chyba ze research, nie produkcja
  • ✗ PHP < 8.1 — brakuje readonly, enums, fibers
  • ✗ MySQL < 8 — brakuje window functions, JSON improvements
  • ✗ Server-side templating bez auto-escape — XSS risk

Co warto zapamietac

  1. Faza > prompt — dziel prace, nie dawaj jednego mega-zadania
  2. Show plan first — niech LLM pokaze co zrobi przed kodem
  3. Test-first — testy jako kontrakt, potem implementacja
  4. Iteracja — pierwszy szkic to nie final
  5. Niezalezny review — LLM jako reviewer czesto widzi co przeoczyles
  6. Constraints — bez nich LLM uzyje "popularnych" rozwiazan
  7. Kontekst projektu — zawsze konwencje, stack, decyzje
  8. Komendy / templates — zapisz dobre prompty jako reusable
