Model proxy (router / cascade)

Lekki model-bramka: sam odpowiada na proste pytania, a trudne deleguje do wiekszych lub specjalistycznych modeli.

O co chodzi

Chcesz zbudowac model, ktory sam odpowiada na to, co umie, a gdy nie wie — odwoluje sie do innych modeli (wiekszych, specjalistycznych albo chmurowych). To klasyczny wzorzec zwany LLM router, model gateway albo cascade.

Najwazniejsza rzecz na start: model proxy to NIE jest model trenowany od zera. To warstwa orkiestracji (kilkadziesiat linii kodu) + opcjonalnie maly klasyfikator decydujacy o trasie. Nie potrzebujesz klastra GPU ani milionow dolarow — potrzebujesz dobrego mechanizmu "wiem, ze nie wiem".

            ┌──────────────────────┐
   pytanie  │   MODEL PROXY        │
 ──────────▶│  (maly, lokalny)     │
            └─────────┬────────────┘
                      │ ocena pewnosci
              ┌───────┴────────┐
        pewny │                │ niepewny / nie wie
              ▼                ▼
       ┌────────────┐   ┌──────────────────┐
       │ odpowiedz  │   │  ESKALACJA        │
       │ lokalnie   │   │  duzy / cloud /   │
       │ (tanio)    │   │  specjalista      │
       └────────────┘   └──────────────────┘

Terminologia — co to naprawde jest

Ludzie myla "model proxy" z MoE. To rozne rzeczy:

PojecieCo routujeGranularnoscGdzie zyje

Cascade (FrugalGPT)tani → drogi, sekwencyjnieper zapytaniewarstwa aplikacji

To, co opisujesz ("jak nie wie, pyta innych"), to cascade z bramka pewnosci — najprostszy i najtanszy wariant routera. MoE to cos zupelnie innego (routing wewnatrz jednego modelu) — nie myl tych dwoch.

Wzorce architektoniczne

A) Pre-routing (klasyfikuj → wybierz model PRZED generacja)

Lekki klasyfikator patrzy na pytanie i od razu kieruje je do wlasciwego modelu. Zero podwojnego kosztu, ale wymaga dobrego klasyfikatora.

pytanie → [router/klasyfikator] → wybor modelu → odpowiedz

B) Cascade / fallback (probuj tanio → eskaluj gdy niepewny)

Dokladnie Twoj scenariusz. Najpierw maly model, a jesli "nie wie" — wiekszy. Prosty, ale placisz za obie proby przy eskalacji.

pytanie → maly → pewny? → TAK: zwroc
                       └── NIE: → duzy → zwroc

C) Mixture of Agents (pytaj kilka, agreguj)

Kilka modeli odpowiada rownolegle, model-agregator scala. Najlepsza jakosc, najwyzszy koszt.

D) Verifier / judge

Maly model odpowiada, drugi model (lub ten sam) weryfikuje odpowiedz; jesli weryfikacja wypada zle → eskalacja.

Dla Twojego celu zacznij od B (cascade). Gdy zbierzesz dane z logow, doloz A (pre-routing), zeby uniknac podwojnego kosztu.

Sedno problemu: skad model wie, ze "nie wie"?

To jest cala trudnosc. LLM domyslnie brzmi pewnie nawet gdy halucynuje. Musisz dolozyc sygnal pewnosci. Metody (od najprostszej):

1. Self-evaluation (structured output) — najlatwiejsze

Kaz modelowi zwrocic JSON z polem confidence i instrukcja: "jesli nie znasz odpowiedzi, ustaw confidence < 0.5".

{"answer": "...", "confidence": 0.0-1.0, "domain": "..."}

Dziala zaskakujaco dobrze jako pierwsza bramka. Wada: model bywa przesadnie pewny (slaba kalibracja).

2. Logprobs / perplexity

Niska srednia prawdopodobienstwa tokenow = model "sie waha". Prog na perplexity → eskalacja. Wymaga modelu zwracajacego logprob-y (Ollama/llama.cpp potrafia).

3. Self-consistency (semantic entropy)

Sprobuj N razy z temperature>0. Jesli odpowiedzi sie rozjezdzaja → model nie wie → eskaluj. Drogie (N wywolan), ale najlepiej koreluje z halucynacjami (Nature 2024, "semantic entropy").

4. Heurystyki

Wykrycie fraz typu "nie jestem pewien", "nie mam informacji", wykrycie domeny poza zakresem (np. pytanie o swieze dane → cutoff), bardzo krotka/pusta odpowiedz.

5. Verifier model

Osobny (maly) model-sedzia ocenia odpowiedz: "Czy ta odpowiedz jest poprawna i kompletna? TAK/NIE".

Szczegoly mierzenia wiedzy modelu i kalibracji — patrz rozdzial 11-01 Weryfikacja wiedzy modelu. Pamietaj: surowe confidence bez kalibracji klamie — zawsze zwaliduj prog na realnych danych.

Implementacja krok po kroku (Ollama + fallback do chmury)

Pod Twoj sprzet (RTX 5060 8GB): proxy = maly model lokalny przez Ollama, eskalacja = wiekszy model w chmurze (lub wiekszy lokalny, jesli masz VRAM).

import json
import ollama                      # pip install ollama
from anthropic import Anthropic    # pip install anthropic

LOCAL_MODEL  = "llama3.2:3b"          # proxy / drzwi frontowe (maly, lokalny, darmowy)
REMOTE_MODEL = "claude-sonnet-4-6"    # eskalacja (duzy, platny)
CONF_THRESHOLD = 0.7

client = Anthropic()  # czyta ANTHROPIC_API_KEY ze srodowiska

SYSTEM = """Jestes asystentem-proxy. Odpowiadaj rzetelnie, ale TYLKO gdy jestes pewien.
Zwroc WYLACZNIE JSON: {"answer": "...", "confidence": 0.0-1.0, "domain": "..."}.
Jesli nie znasz odpowiedzi lub sie wahasz, ustaw confidence ponizej 0.5."""

def ask_local(question: str) -> dict:
    resp = ollama.chat(
        model=LOCAL_MODEL,
        messages=[{"role": "system", "content": SYSTEM},
                  {"role": "user",   "content": question}],
        format="json",                 # wymus poprawny JSON
        options={"temperature": 0},
    )
    return json.loads(resp["message"]["content"])

def ask_remote(question: str) -> str:
    msg = client.messages.create(
        model=REMOTE_MODEL,
        max_tokens=1024,
        messages=[{"role": "user", "content": question}],
    )
    return msg.content[0].text

def proxy(question: str) -> dict:
    local = ask_local(question)
    if local.get("confidence", 0) >= CONF_THRESHOLD:
        return {"source": LOCAL_MODEL, "answer": local["answer"]}
    # model "nie wie" — deleguj do wiekszego
    return {"source": REMOTE_MODEL, "answer": ask_remote(question)}

print(proxy("Ile to 2+2?"))                                  # → lokalny (pewny)
print(proxy("Udowodnij twierdzenie Godla o niezupelnosci"))  # → eskalacja

Wariant z self-consistency (gdy nie ufasz confidence)

from collections import Counter

def ask_local_consistent(question: str, n: int = 5) -> tuple[str, float]:
    answers = []
    for _ in range(n):
        r = ollama.chat(model=LOCAL_MODEL,
                        messages=[{"role": "user", "content": question}],
                        options={"temperature": 0.7})
        answers.append(r["message"]["content"].strip())
    top, count = Counter(answers).most_common(1)[0]
    return top, count / n          # zgodnosc jako pewnosc

answer, agreement = ask_local_consistent("Stolica Australii?")
if agreement < 0.6:               # odpowiedzi sie rozjechaly → nie wie
    answer = ask_remote("Stolica Australii?")

Trenowanie wlasnego routera "od zera" (opcjonalnie)

Jesli chcesz prawdziwy wlasny model-router (a nie heurystyke), wytrenuj maly klasyfikator decydujacy "zostan lokalnie vs eskaluj". To jest ta czesc, ktora realnie "tworzysz od podstaw".

Skad dane? Z logow wlasnego cascade'a: dla kazdego pytania zapisz, czy maly model wystarczyl (1) czy trzeba bylo eskalowac (0).

# pip install sentence-transformers scikit-learn
from sentence_transformers import SentenceTransformer
from sklearn.linear_model import LogisticRegression

emb = SentenceTransformer("all-MiniLM-L6-v2")     # maly, lokalny, darmowy

X = emb.encode([row["question"] for row in logs]) # logi z cascade'a
y = [row["local_was_enough"] for row in logs]      # 1 = zostan, 0 = eskaluj

router = LogisticRegression().fit(X, y)

def should_stay_local(question: str) -> bool:
    x = emb.encode([question])
    return router.predict_proba(x)[0][1] >= 0.5

To pre-router (wzorzec A): podejmuje decyzje bez uruchamiania duzego modelu → zero podwojnego kosztu. Gdy zbierzesz wiecej danych, mozesz zamienic regresje logistyczna na fine-tune malego BERT/DistilBERT albo malego LLM jako klasyfikatora.

Koszt i latencja — kompromisy

Sens cascade'a to oszczednosc: maly lokalny model lapie wiekszosc zapytan za darmo.

E[koszt] = p · c_lokalny + (1−p) · (c_lokalny + c_zdalny)
         = c_lokalny + (1−p) · c_zdalny        (przy eskalacji placisz OBA)

p          = odsetek zapytan obsluzonych lokalnie
c_lokalny  ≈ 0   (wlasny GPU, prad)
c_zdalny   = cena duzego modelu w chmurze
p (lapie lokalnie)Wzgledny koszt vs "wszystko w chmurze"
0%~100% (a nawet >100% przez podwojne wywolanie)
50%~50%
80%~20%
95%~5%

Im lepiej proxy lapie proste pytania, tym taniej. Ale cascade doklada latencje (sekwencyjne wywolania) i przy eskalacji placisz dwa razy — dlatego pre-routing (wzorzec A) bywa lepszy, gdy masz dobry klasyfikator.

Pulapki

  • Niekalibrowane confidence — model bywa pewny blednych odpowiedzi. Zwaliduj prog na realnym zbiorze testowym, nie zgaduj.
  • Podwojny koszt i latencja — eskalacja = dwie proby. Przy duzym ruchu przejdz na pre-routing.
  • Router drift — rozklad pytan sie zmienia; klasyfikator trzeba douczac.
  • Niespojnosc formatow — rozne modele zwracaja inaczej; ujednolicaj output po stronie proxy.
  • Bezpieczenstwo / prywatnosc — eskalacja wysyla dane do zewnetrznego API. Nie loguj sekretow i pilnuj, co opuszcza maszyne lokalna.
  • Pojedynczy punkt awarii — proxy to waskie gardlo; dodaj timeouty i twardy fallback.

Sciezka wdrozenia

1. Uruchom maly model lokalnie (Ollama: llama3.2:3b / qwen2.5:3b)
   ↓
2. Dodaj bramke pewnosci (structured output {answer, confidence})
   ↓
3. Eskalacja przy niskiej pewnosci → wiekszy model / chmura
   ↓
4. Owin to w LiteLLM (jednolite API + fallback przy bledzie)
   ↓
5. Loguj kazde zapytanie: pytanie, pewnosc, czy eskalowano, wynik
   ↓
6. Z logow wytrenuj pre-router (klasyfikator) → tnij podwojny koszt
   ↓
7. Skalibruj prog pod swoj budzet (koszt vs jakosc)
