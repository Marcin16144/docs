Context management i wskazowki

Jak nie przekraczac limitu kontekstu, redukowac koszty i utrzymywac jakosc odpowiedzi.

Czym jest context window?

Context window = maksymalna liczba tokenow ktore LLM moze przetworzyc w jednym wywolaniu. Obejmuje:

  • System prompt
  • Historia rozmowy (wszystkie poprzednie wiadomosci)
  • Aktualny prompt uzytkownika
  • Tools / function definitions
  • Aktualnie generowana odpowiedz (output tokens)
┌────────────────────────────────────────────────┐
│              CONTEXT WINDOW (200k)              │
├────────────────────────────────────────────────┤
│  System prompt           │  ~5k tokens          │
│  Tool definitions        │  ~2k tokens          │
│  Conversation history    │  ~50k tokens         │
│  Current user message    │  ~1k tokens          │
│  Output (max_tokens)     │  ~8k tokens          │
└──────────────────────────┴──────────────────────┘
                            Total: ~66k / 200k

Tokeny — jak liczyc

Regula kciuka:

  • 1 token ≈ 0.75 slowa w angielskim
  • 1 token ≈ 0.5 slowa w polskim (wiecej tokenizacji!)
  • 1 token ≈ 4 znaki w angielskim
  • 1 token ≈ 2-3 znaki w polskim
Tekst: "Hello world!" (12 znakow)
→ 3 tokeny: ["Hello", " world", "!"]

Tekst: "Czesc swiecie!" (14 znakow, polski)
→ 7 tokenow: ["Cze", "sc", " s", "wie", "cie", "!"]

Narzedzia: tiktoken (Python), anthropic-tokenizer, HF tokenizers, OpenAI Tokenizer playground, Anthropic Console.

Dlaczego context ma znaczenie?

1. Koszt rosnie liniowo

Claude Sonnet 4.6: $3 / 1M input tokens

Rozmowa 10k tokenow:    $0.03 per request
Rozmowa 100k tokenow:   $0.30 per request   (10x drozej!)
Rozmowa 200k tokenow:   $0.60 per request

Bez prompt caching: kazdy request platsz pelna cene.
Z prompt caching: cached tokens ~10% ceny → $0.003.

2. Latency rosnie z kontekstem

Time to First Token (TTFT) zalezy od dlugosci kontekstu:
- 10k tokens:  ~500ms
- 100k tokens: ~3s
- 200k tokens: ~8s

3. Quality DEGRADUJE z dlugim kontekstem

"Lost in the middle" — model gorzej znajduje informacje w srodku dlugiego kontekstu:

  • Top 10% kontekstu: ~95% accuracy
  • Srodek 50%: ~70% accuracy
  • Koniec 10%: ~85% accuracy (recency bias)

"Needle in a Haystack" benchmark testuje retrieval z dlugiego kontekstu. Modele 2026 sa coraz lepsze, ale problem nie zniknal.

4. Hallucinations rosna z kontekstem

Przy 100k+ tokenow modele zaczynaja mylic fakty, mieszac konteksty, halucynowac.

10 strategii zarzadzania kontekstem

1. Krotszy system prompt

ZLY system prompt (3000 slow):
"Jestes asystentem... [historia firmy] [lista produktow]
[wszystkie polityki zwrotu] [wszystkie cenniki]..."

DOBRY system prompt (300 slow):
"Jestes asystentem klienta firmy XYZ.
Twoje zadania: [3 punkty]
Twoje ograniczenia: [3 punkty]
W razie watpliwosci uzyj search_kb()."

+ Tool: search_kb(query) → zwraca relevantne fragmenty

Efekt: 90% redukcja kosztu, lepsze wyniki.

2. RAG zamiast wrzucania wszystkiego

ZLE:
prompt = full_knowledge_base + question  # 100k tokens

DOBRZE:
relevant_chunks = retrieve(question, top_k=5)  # 2k tokens
prompt = relevant_chunks + question  # 3k tokens

Oszczednosc: 30-100x mniej tokenow.

3. Prompt caching (kluczowe w 2026)

Anthropic, OpenAI, Google — 90% redukcja kosztu dla cached czesci.

# Anthropic prompt caching
client.messages.create(
    model="claude-opus-4-7",
    system=[
        {
            "type": "text",
            "text": LONG_SYSTEM_PROMPT,   # 5000 tokens
            "cache_control": {"type": "ephemeral"}
        },
        {
            "type": "text",
            "text": f"Context: {document}",  # 50k tokens
            "cache_control": {"type": "ephemeral"}
        }
    ],
    messages=[{"role": "user", "content": query}]
)

# Pierwszy request: full price (+25% cache write)
# Kolejne (w 5 min): cached parts sa 10% ceny

4. Kompaktowanie historii

def manage_conversation_context(messages, max_tokens=50_000):
    if total_tokens(messages) < max_tokens:
        return messages

    # Wymus podsumowanie starszych wiadomosci
    old = messages[:-10]  # zachowaj 10 ostatnich
    recent = messages[-10:]

    summary = llm.summarize(old)

    return [
        {"role": "system",
         "content": f"Earlier summary: {summary}"},
        *recent
    ]

Anatomia "context budget"

Budget thinking — planuj ile tokenow na co.

Total context budget: 100k tokens

Allocation:
├─ System prompt:           3k  (3%)
├─ Tool definitions:        1k  (1%)
├─ RAG retrieved docs:      8k  (8%)   ← top 5 chunks
├─ Conversation history:    20k (20%)  ← ostatnie 20 wymian
├─ Memory (long-term):      3k  (3%)   ← top 10 facts
├─ Current user message:    2k  (2%)
├─ Reserved for output:     8k  (8%)
└─ Buffer (safety):         55k (55%)  ← na nieoczekiwane

Hard limit per request: 45k actual usage.

Jak rozpoznac ze context jest problemem

Symptomy

  1. "Lost in the middle" — model nie odnajduje info ktore JEST w prompcie
  2. Zapomnienie instrukcji — model nie przestrzega system prompta po dlugiej rozmowie
  3. Halucynacje — zaczyna zmyslac fakty
  4. Wolny TTFT — > 5s do pierwszego tokenu
  5. Wysokie koszty — rachunek rosnie wykladniczo
  6. Errors "context_length_exceeded" — przekraczasz limit

Praktyczne wskazowki

1. Mierz tokeny przed wysylka

def safe_send(messages, max_context=180_000):
    enc = tiktoken.encoding_for_model("gpt-4o")
    total = sum(len(enc.encode(m["content"])) for m in messages)

    if total > max_context:
        raise ValueError(f"Too long: {total} > {max_context}")

    return llm.send(messages)

2. Loguj token usage

Wskazowki specyficzne per model

Claude (Anthropic)

Co dziala swietnie:

  • XML structure: <context>...</context> znacznie pomaga
  • "Long context" — 200k uzywaj smialo
  • Prompt caching — zawsze wlacz dla powtarzalnych czesci
  • Extended thinking — dla skomplikowanych zadan

Pulapki: Bez cache_control placisz pelna cene; extended thinking zjada output tokens.

GPT-5 / GPT-4o (OpenAI)

Co dziala: Markdown format, function calling vs structured output, prompt caching automatyczne (od 1024 tokens).

Pulapki: 128k limit (latwiej go przekroczyc niz 200k Claude); czasem ignoruje system prompt.

Gemini (Google)

Co dziala: 1-2M context = mozesz wrzucic caly codebase; multimodal native; swietny caching dla bardzo dlugich kontekstow.

Pulapki: "Lost in the middle" wciaz problem przy 1M; tendency do "lazy" przy duzym kontekscie.

Llama / Mistral / Qwen (open source)

Co dziala: self-host = nie ma kosztu per token; mozesz zwiekszyc kontekst (RoPE scaling).

Pulapki: wiekszosc trenowanych do 8-32k; KV cache zjada VRAM dramatycznie; quantization (Q4) zwieksza "lost in the middle".

Anti-patterns do unikania

"Wrzuce caly dokument"

# ZLE
response = llm.ask(f"Caly dokument: {entire_book}\n\nPytanie: ...")
# 500k tokenow = $$$$ + lost in middle

# DOBRZE
chunks = retrieve(question, top_k=5)
response = llm.ask(f"Relevant: {chunks}\n\nPytanie: ...")

"Jeszcze jeden few-shot"

Kazdy few-shot example = 200-500 tokenow. Po 10 examples masz 5k tokenow w kazdym requeście. Sprawdz czy wszystkie potrzebne — czesto 2-3 wystarcza.

Powtarzanie info

Zle: "Mow tylko po polsku" w system prompt + w kazdej wiadomosci + po kazdej odpowiedzi.

Dobrze: raz w system. Jesli model myli jezyki — zmien model lub fine-tune.

Brak garbage collection w historii

if len(messages) > 30:
    messages = compact_old_messages(messages, keep_recent=20)

Decyzja: long context vs RAG

Long context wygrywa gdy:

  • Dokument < 500k tokenow (mieszczy sie w 1M Gemini)
  • Zapytania wymagaja caloscowego zrozumienia
  • Niska liczba zapytan (< 100/dzien)
  • Zlozone reasoning po dokumencie
  • Aktualizacja dokumentu rzadka

RAG wygrywa gdy:

  • Korpus > 1M tokenow (TB tekstu)
  • Wysoka liczba zapytan (RAG dramatycznie tanszy)
  • Czeste aktualizacje
  • Wymagane cytowanie zrodel
  • Selektywne info wystarczy

Hybrid (zalecane w 2026):

1. Retrieval pobiera top-50 chunks
2. Long-context model (Gemini 1M) przetwarza wszystkie 50
3. Gemini decyduje co relevantne, generuje odpowiedz

Best of both worlds.

Praktyczny checklist

  • Czy potrzebuje wszystkich tych tokenow?
  • Czy system prompt jest zoptymalizowany?
  • Czy wlaczylem prompt caching dla stalych czesci?
  • Czy uzywam RAG zamiast wrzucac wszystko?
  • Czy historia rozmowy jest skompaktowana?
  • Czy mierze i loguje usage?
  • Czy testuje "needle in haystack" dla mojego use case?
  • Czy wybralem wlasciwy model (maly dla prostych task)?
  • Czy mam fallback gdy context exceeded?
  • Czy mam rate limits per user?

Praktyczne reguly kciuka

1. Cel: < 30% wykorzystania context window
   200k limit → trzymaj sie 60k typically

2. Cache hit rate > 70%
   Jesli nizszy → reorganizuj prompt structure

3. Output max_tokens: ustaw realistic limit
   Bez tego model moze gadac 8k tokenow niepotrzebnie

4. Token cost > $0.10 per request?
   Sprawdz czy potrzebujesz, czy mozesz zopt.

5. RAG > 5k tokens retrieved?
   Lepszy reranking, mniej top_k

6. History > 20 wiadomosci?
   Skompaktuj lub sliding window

7. System prompt > 1000 slow?
   Refaktor, uzyj tools zamiast info w prompcie

8. Latency > 3s?
   Skroc kontekst lub mniejszy model

10 najwazniejszych zasad

  1. Mierz tokeny — bez tego nic nie zmienisz
  2. Loguj koszt per request, per feature, per user
  3. Krotszy system prompt > dlugi monolit (rozbij na tools)
  4. Prompt caching — zawsze wlacz, 90% redukcja kosztu
  5. RAG zamiast wrzucania calego dokumentu
  6. Kompaktuj historie w dlugich rozmowach
  7. Mniejszy model dla prostych zadan (Haiku zamiast Opus)
  8. Stream output dla lepszego UX
  9. Test "needle in haystack" dla swojego use case
  10. Hard limits per user/feature zeby uniknac overspendingu
