XSS (Cross-Site Scripting)

XSS — atakujacy wstrzykuje skrypt JS do strony. React automatycznie escapuje wartosci w JSX, co eliminuje wiekszosc atakow.

// Bezpieczne — React escapuje
const userInput = '<script>alert("XSS")</script>';
return <div>{userInput}</div>;
// Render: <div>&lt;script&gt;alert("XSS")&lt;/script&gt;</div> — tekst, nie kod

// NIEBEZPIECZNE — pomija escape
return <div dangerouslySetInnerHTML={{ __html: userInput }} />;
// Skrypt zostanie wykonany!

Kiedy musisz uzyc dangerouslySetInnerHTML

Czasem (np. markdown, rich text z CMS) potrzebujesz HTML. Wtedy sanitize przed wlozeniem.

npm i isomorphic-dompurify

import DOMPurify from 'isomorphic-dompurify';

function Article({ html }) {
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: ['p', 'strong', 'em', 'a', 'ul', 'li', 'h2', 'h3', 'code'],
    ALLOWED_ATTR: ['href', 'title'],
  });
  return <article dangerouslySetInnerHTML={{ __html: clean }} />;
}

Inne zrodla XSS w React

  • href={url} z user-controlled URL — javascript:alert(1) URI dziala. Waliduj!
  • SVG w <img src> z user data — SVG moze zawierac <script>
  • Server-side rendering bez escape (manipulacja stringa — nie rob tego)
// Walidacja URL
function safeHref(url) {
  try {
    const u = new URL(url);
    if (['http:', 'https:', 'mailto:'].includes(u.protocol)) return url;
    return '#';
  } catch {
    return '#';
  }
}

<a href={safeHref(userUrl)}>Link</a>

Content Security Policy (CSP)

CSP to header HTTP, ktory mowi przegladarce co moze sie zaladowac. Druga linia obrony przeciw XSS.

// next.config.js
const cspHeader = `
  default-src 'self';
  script-src 'self' 'nonce-${nonce}' 'strict-dynamic';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  font-src 'self';
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  upgrade-insecure-requests;
`;

module.exports = {
  async headers() {
    return [{
      source: '/(.*)',
      headers: [
        { key: 'Content-Security-Policy', value: cspHeader.replace(/\n/g, ' ') },
        { key: 'X-Frame-Options', value: 'DENY' },
        { key: 'X-Content-Type-Options', value: 'nosniff' },
        { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
        { key: 'Permissions-Policy', value: 'camera=(), microphone=()' },
      ],
    }];
  },
};

BFF Pattern (Backend for Frontend)

Przeglad: dla SPA + zewnetrzne API, BFF (Next.js / Node) trzyma tokeny i posredniczy. Klient nigdy nie widzi access token. Standard 2026 dla bezpieczenstwa.

// app/api/proxy/route.ts (Next.js)
import { cookies } from 'next/headers';

export async function GET(req) {
  const cookieStore = await cookies();
  const session = cookieStore.get('session')?.value;
  const tokens = await getTokens(session); // server-side store

  const r = await fetch('https://api.example.com/data', {
    headers: { Authorization: `Bearer ${tokens.accessToken}` },
  });

  return Response.json(await r.json());
}

NIE uzywaj localStorage dla tokenow

Powody

  • Kazdy XSS moze wykrasc token (localStorage.getItem('token'))
  • Brak automatic submission — trzeba reczne dolaczyc do requestu
  • Brak SameSite ochrony
  • Persystuje na zawsze — uzytkownik moze zostawic na publicznym kompie

Wlasciwa droga: httpOnly + Secure + SameSite=Lax cookie z BFF pattern.

// Zly — localStorage
localStorage.setItem('access_token', token);
fetch('/api', { headers: { Authorization: 'Bearer ' + localStorage.getItem('access_token') } });

// Dobry — httpOnly cookie set przez serwer
// Server response:
//   Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

// Klient po prostu fetchuje — cookie automatycznie
fetch('/api/data', { credentials: 'include' });

CSRF (Cross-Site Request Forgery)

CSRF — atakujaca strona zmusza przegladarke uzytkownika do wyslania requestu do twojej domeny (z auto-cookie).

Obrona

  • SameSite=Lax (default w nowoczesnych przegladarkach) — blokuje cross-site cookies dla niebezpiecznych metod
  • CSRF token — serwer generuje, klient dolacza w header lub form field
  • Double-submit cookie — cookie + header z ta sama wartoscia, atakujaca nie moze ustawic header
  • Origin/Referer check serwerowy
// Server — generuj token CSRF dla sesji
// W kazdym formularzu (lub fetch) dolaczaj

// Hidden input
<input type="hidden" name="_csrf" value={csrfToken} />

// fetch
fetch('/api/transfer', {
  method: 'POST',
  headers: { 'X-CSRF-Token': csrfToken, 'Content-Type': 'application/json' },
  credentials: 'include',
  body: JSON.stringify(data),
});

Server Actions — bezpieczenstwo

Server Actions (React 19 / Next.js) maja wbudowana ochrone CSRF (Origin check). ALE musisz pamietac:

'use server';

export async function deletePost(formData) {
  // 1. ZAWSZE sprawdz autoryzacje
  const session = await getSession();
  if (!session) throw new Error('Unauthorized');

  // 2. Waliduj input (Zod)
  const id = z.string().uuid().parse(formData.get('id'));

  // 3. Sprawdz uprawnienia (czy user moze usunac TEN post)
  const post = await db.posts.find(id);
  if (post.userId !== session.userId) throw new Error('Forbidden');

  // 4. Wykonaj
  await db.posts.delete(id);
  revalidatePath('/posts');
}

Server Action — zlote zasady

  • Auth zawsze pierwsza linia — nawet jesli przycisk widoczny tylko dla zalogowanych
  • Zod / Valibot — waliduj kazdy input
  • Authorization (RBAC) — nie tylko czy zalogowany, ale czy MOZE wykonac te akcje
  • Rate limiting — np. Upstash Ratelimit dla wywolan
  • Zwracaj generyczne bledy — nie ujawniaj szczegolow infrastruktury

Production checklist

  • HTTPS only (HSTS header)
  • CSP header skonfigurowany (testuj report-only przed enforce)
  • Security headers: X-Frame-Options, X-Content-Type-Options, Referrer-Policy
  • Cookies: httpOnly, Secure, SameSite
  • Brak tokenow w localStorage
  • Zod / Valibot na wejsciu Server Actions / API
  • Rate limiting (Upstash, Vercel)
  • Dependency scanning w CI (npm audit, Snyk, Dependabot)
  • Sentry / error tracking (uwaga na PII w breadcrumbs)
  • Brak sourcemaps publicznych (lub tylko do Sentry)
