Branching i merging w Git

Galezie, scalanie, rebase, cherry-pick, stash, konflikty

Czym jest galaz w Gitcie?

Galaz (branch) w Gitcie to po prostu wskaznik na konkretny commit. To nie jest kopia plikow ani osobny katalog. Tworzenie galezi w Gitcie jest bardzo tanie (tworzy sie tylko 41-bajtowy plik z hashem). Glowna galaz to zazwyczaj main (dawniej master).

Dlaczego galezie sa tak istotne?
  • Pozwalaja pracowac nad funkcjonalnosciami w izolacji
  • Umozliwiaja code review przed mergem
  • Pozwalaja na rownolegla prace wielu osob
  • Wspomagaja CI/CD - testy uruchamiane per branch

Tworzenie i przelaczanie galezi

Git oferuje dwa sposoby na zarzadzanie galeziami: starsze polecenie checkout (uniwersalne) oraz nowsze switch i restore (od Git 2.23, bardziej intuicyjne).

# Lista lokalnych galezi (gwiazdka oznacza biezaca)
git branch

# Lista wszystkich galezi (lokalne + zdalne)
git branch -a

# Lista zdalnych
git branch -r

# Lista z ostatnim commitem
git branch -v

# Tworzenie nowej galezi (bez przelaczenia)
git branch feature-login

# Tworzenie z konkretnego commita
git branch feature-fix abc1234

# Przelaczenie (stary sposob)
git checkout feature-login

# Tworzenie + przelaczenie (stary sposob)
git checkout -b feature-login

# NOWY skladniowo (zalecany od Git 2.23)
git switch feature-login
git switch -c feature-login        # tworzy + przelacza
git switch -c feature-fix main     # tworzy z main

# Powrot do poprzedniej galezi
git switch -

# Przelaczenie na zdalna galaz (pobranie z origin)
git switch feature-from-colleague

Cykl zycia galezi

# 1. Pobierz aktualny main
git switch main
git pull

# 2. Stworz galaz feature
git switch -c feature/login-form

# 3. Pracuj, commituj
echo "kod" > login.js
git add login.js
git commit -m "feat: add login form"

# 4. Wypchnij galaz na remote
git push -u origin feature/login-form
# -u ustawia tracking - nastepnie wystarczy 'git push'

# 5. Stworz Pull Request / Merge Request w GitHub/GitLab

# 6. Po review i merge - usun galaz
git switch main
git pull
git branch -d feature/login-form           # bezpieczne (sprawdza merge)
git branch -D feature/login-form           # FORCE delete

# 7. Usun zdalna galaz
git push origin --delete feature/login-form

# 8. Wyczysc nieaktualne refs zdalnych
git fetch --prune

Zmiana nazwy galezi

# Zmien nazwe biezacej galezi
git branch -m new-name

# Zmien nazwe konkretnej galezi
git branch -m old-name new-name

# Aktualizacja remote po zmianie nazwy
git push origin -u new-name
git push origin --delete old-name

Merge - scalanie galezi

Merge laczy zmiany z jednej galezi do drugiej. Git oferuje rozne strategie scalania w zaleznosci od historii commitow.

Fast-forward merge

Gdy galaz docelowa nie ma nowych commitow, ktorych nie ma w galezi zrodlowej, Git po prostu przesuwa wskaznik. Brak commitu merge.

git switch main
git merge feature/login-form

# Wynik (przed i po):
# Przed: main -> A -> B
#                 \-> C -> D (feature)
#
# Po:    main -> A -> B -> C -> D

3-way merge

Gdy obie galezie maja nowe commity od momentu rozejscia, Git tworzy nowy "merge commit" z dwoma rodzicami.

git switch main
git merge feature/login-form

# Wynik:
# Przed: main -> A -> B -> E -> F
#                 \-> C -> D (feature)
#
# Po:    main -> A -> B -> E -> F -> M (merge commit)
#                 \-> C -> D ----/

Wymuszenie merge commita (--no-ff)

# Zawsze tworz merge commit (zachowuje historie galezi)
git merge --no-ff feature/login-form

# Przydatne w GitFlow - widac jasno gdzie sie zaczyna i konczy feature

Squash merge

Polacz wszystkie commity z galezi w jeden, dodaj go do glownej galezi. GitHub i GitLab oferuja to jako opcje przy mergowaniu PR.

# Lokalnie
git switch main
git merge --squash feature/login-form
git commit -m "feat: implement login form"

# 10 commitow z feature staje sie 1 commitem na main
# Galaz feature pozostaje nienaruszona

Rebase

Rebase to alternatywa dla merge - zamiast tworzyc merge commit, "przenosi" commity z jednej galezi na koniec drugiej. Tworzy liniowa, czysta historie. Ale zmienia hashe commitow - wiec NIGDY nie rebasuj wypchnietych commitow na shared branch.

# Klasyczny use case - update feature z main
git switch feature/login-form
git fetch origin
git rebase origin/main

# Lub krocej z pull
git pull --rebase origin main

# Wynik:
# Przed: A -> B -> C -> D (main)
#         \-> E -> F (feature)
#
# Po rebase: A -> B -> C -> D (main)
#                          \-> E' -> F' (feature)
#
# Uwaga: E i F maja nowe hashe (E' i F')

Rebase interaktywny

Pozwala edytowac historie commitow przed wypchnieciem - laczyc, dzielic, zmieniac wiadomosci.

# Rebase ostatnich 4 commitow
git rebase -i HEAD~4

# Otwiera edytor:
# pick abc1234 feat: add login form
# pick def5678 fix: typo
# pick ghi9012 fix: another typo
# pick jkl3456 feat: add validation

# Komendy:
# pick   - uzyj commit jak jest
# reword - uzyj commit, zmien wiadomosc
# edit   - uzyj commit, zatrzymaj na edycje
# squash - polacz z poprzednim, edytuj wiadomosc
# fixup  - jak squash, ale bez wiadomosci
# drop   - usun commit

# Po edycji - zapisz i zamknij. Git wykona operacje.

Rozwiazywanie konfliktow przy rebase

# Podczas rebase moze sie pojawic konflikt
git rebase main
# CONFLICT (content): Merge conflict in src/app.js

# Rozwiaz konflikt w pliku
vim src/app.js

# Zaznacz jako rozwiazany
git add src/app.js

# Kontynuuj rebase
git rebase --continue

# Albo pomin obecny commit
git rebase --skip

# Albo przerwij i wroc do stanu przed rebase
git rebase --abort

Zlota zasada Gita:

Nigdy nie rebasuj galezi, ktora juz zostala udostepniona innym (wypchnieta i ktoś inny moze na niej pracować). Rebasing przepisuje historie - co dla wspoldzielonej galezi prowadzi do chaosu.

Cherry-pick

Cherry-pick pozwala wziac konkretny commit z jednej galezi i zaaplikowac go do innej. Przydatne np. przy hotfixach lub portowaniu poprawek.

# Pojedynczy commit
git switch main
git cherry-pick abc1234

# Wiele commitow
git cherry-pick abc1234 def5678 ghi9012

# Zakres (bez abc1234, do ghi9012 wlacznie)
git cherry-pick abc1234..ghi9012

# Zakres z abc1234 wlacznie
git cherry-pick abc1234^..ghi9012

# Bez automatycznego commitu (tylko zmiany w stage)
git cherry-pick --no-commit abc1234
# Mozesz teraz edytowac przed commitowaniem
git commit

# Z konfliktami - jak przy rebase
git cherry-pick --continue
git cherry-pick --abort
git cherry-pick --skip

Stash - tymczasowe schowki

Stash zapisuje niezatwierdzone zmiany w "skrytce" i czysci robocze drzewo. Przydatne gdy musisz szybko przelaczyc galaz bez commitowania niedokonczonej pracy.

# Schowaj zmiany (zarowno staged jak i unstaged)
git stash
git stash push -m "WIP: praca nad walidacja"

# Z untracked plikami
git stash -u
git stash --include-untracked

# Tylko konkretny plik
git stash push -m "tylko style" src/styles.css

# Lista skrytek
git stash list
# stash@{0}: WIP on main: ...
# stash@{1}: WIP on feature: ...

# Pokaz zawartosc skrytki
git stash show
git stash show -p stash@{1}        # pelny diff

# Przywroc i usun ze stack (LIFO)
git stash pop

# Przywroc, ale zostaw w stack
git stash apply
git stash apply stash@{2}

# Usun ze stack
git stash drop stash@{0}

# Usun wszystkie
git stash clear

# Stworz galaz ze stash (przydatne gdy zmiany sa duze)
git stash branch feature/wip-work stash@{0}

Konflikty - rozwiazywanie

Konflikty pojawiaja sie gdy dwa commity zmieniaja te sama linie. Git oznacza miejsca konfliktow specjalnymi markerami w pliku.

// src/app.js po konflikcie
function calculatePrice(item) {
<<<<<<< HEAD
    return item.price * 1.23;  // 23% VAT
=======
    return item.price * 1.08;  // 8% VAT
>>>>>>> feature/eu-tax
}

Markery wyjasnione:

  • <<<<<<< HEAD - poczatek wersji z biezacej galezi
  • ======= - separator
  • >>>>>>> branch-name - koniec wersji z dolaczanej galezi
# Po edycji pliku - usuwasz markery i zostawiasz wlasciwa wersje
function calculatePrice(item, country) {
    const rate = country === 'PL' ? 1.23 : 1.08;
    return item.price * rate;
}

# Zaznacz jako rozwiazany
git add src/app.js

# Kontynuuj merge/rebase
git commit                  # przy merge
git rebase --continue       # przy rebase

# Lub przerwij wszystko
git merge --abort
git rebase --abort

# Sprawdzenie ktore pliki maja konflikty
git status

# Diff z ich/nasza wersja
git diff --ours src/app.js
git diff --theirs src/app.js

git mergetool - graficzne rozwiazywanie

# Konfiguracja narzedzia
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait $MERGED'

# Albo meld (Linux)
git config --global merge.tool meld

# Uruchomienie
git mergetool

# Po rozwiazaniu git tworzy backup .orig - mozna usunac
git config --global mergetool.keepBackup false

Praktyczne wskazowki:
  • Jedna galaz = jeden cel (jeden feature, jeden bug fix)
  • Krotkie zycie galezi - merguj jak najszybciej
  • Regularnie aktualizuj feature branch z main (rebase lub merge)
  • Squash drobnych commitow przed pushem (czystsza historia)
  • Usuwaj galezie po merge (zarowno lokalnie jak i zdalnie)
