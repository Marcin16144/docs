Zdalne repozytoria

remote, fetch/pull/push, hosting, SSH, GPG signing, gh CLI

Czym jest "remote"?

Remote to nazwana referencja do zdalnego repozytorium. Domyslnie po klonowaniu masz jedno remote o nazwie origin, ktore wskazuje na URL z ktorego sklonowales kod. Repozytorium moze miec wiele remote'ow - przydatne przy pracy z forkami.

# Klonowanie repozytorium (tworzy origin automatycznie)
git clone https://github.com/uzytkownik/projekt.git
git clone git@github.com:uzytkownik/projekt.git

# Lista remote'ow
git remote
git remote -v        # z URL'ami

# Szczegoly konkretnego remote
git remote show origin

# Dodanie nowego remote
git remote add upstream https://github.com/oryginal/projekt.git

# Zmiana URL istniejacego remote
git remote set-url origin git@github.com:nowy-user/projekt.git

# Zmiana z HTTPS na SSH
git remote set-url origin git@github.com:uzytkownik/projekt.git

# Zmiana nazwy
git remote rename origin github

# Usuniecie
git remote remove upstream

Origin vs upstream - konwencja forkow

Przy pracy z forkami konwencja jest taka:

  • origin - twoj fork na GitHub
  • upstream - oryginalny projekt
# Sklonowales swoj fork
git clone git@github.com:moj-user/projekt.git
cd projekt

# Dodaj upstream wskazujacy na oryginal
git remote add upstream https://github.com/oryginal-user/projekt.git

# Pobierz zmiany z upstream
git fetch upstream

# Zmerguj zmiany z upstream/main do swojego main
git switch main
git merge upstream/main
# Lub: git pull upstream main

# Wypchnij zaktualizowany main do swojego forka
git push origin main

Fetch vs Pull

To jedna z najwazniejszych roznic w Gitcie:

Aspektgit fetchgit pull
Co robiTylko pobiera zmiany ze zdalnego repofetch + merge (lub rebase)
Modyfikuje plikiNIETAK
BezpieczenstwoBezpieczne zawszeMoze tworzyc konflikty
Kiedy uzywacSprawdzanie zmian, audytAktualizacja swojej galezi
# Fetch - tylko pobranie informacji o zmianach
git fetch                    # z origin
git fetch upstream           # z konkretnego remote
git fetch --all              # ze wszystkich remote'ow

# Sprawdz co sie zmienilo bez aplikowania
git log HEAD..origin/main --oneline
git diff HEAD origin/main

# Dopiero teraz mergujemy (jesli OK)
git merge origin/main

# Pull = fetch + merge
git pull
git pull origin main

# Pull z rebase (czystsza historia)
git pull --rebase
git pull --rebase origin main

# Skonfiguruj rebase domyslnie dla pull
git config --global pull.rebase true

# Albo "fast-forward only" - bezpieczniejsze
git config --global pull.ff only
# Wtedy pull failuje gdy nie ma fast-forward - musisz zdecydowac swiadomie

Push - wypychanie zmian

# Pierwszy push z ustawieniem trackingu
git push -u origin feature/login

# Po -u wystarczy zwykly push
git push

# Push wszystkich galezi
git push --all

# Push wraz z tagami
git push --tags
git push --follow-tags    # tylko anotowane tagi

# Push do innego remote
git push upstream main

# Force push - NIEBEZPIECZNE
git push --force
git push -f

# BEZPIECZNIEJSZE - failuje jesli ktos w miedzyczasie pushnal
git push --force-with-lease

# Wypchnij galaz pod inna nazwa
git push origin local-name:remote-name

# Usun zdalna galaz
git push origin --delete feature/old
git push origin :feature/old    # stara skladnia
Force push - krytyczne zasady:
  • NIGDY nie rob --force na shared branch (main, develop)
  • Zamiast --force uzywaj --force-with-lease
  • Force push jest dozwolony tylko na twojej osobistej feature branch
  • Po force push poinformuj zespol jesli ktos pracowal na tej galezi
  • Wiele firm blokuje force push do main przez branch protection

Tracking branches

Lokalna galaz moze "trackowac" zdalna galaz - dzieki temu git wie skad pullowac i gdzie pushowac.

# Status z informacja o trackingu
git status
# On branch main
# Your branch is up to date with 'origin/main'.

# Sprawdz tracking
git branch -vv

# Ustaw tracking dla biezacej galezi
git branch --set-upstream-to=origin/main

# Krocej
git branch -u origin/main

# Lub przy pierwszym pushu
git push -u origin main

# Pokaz tylko nieuploadowane commity
git log @{u}..

# Pokaz commity ktore sa na remote a nie ma u nas
git log ..@{u}

SSH keys - bezpieczne uwierzytelnianie

SSH to standardowy sposob na uwierzytelnianie do remote bez wpisywania hasla. Klucze ed25519 sa szybsze i bezpieczniejsze niz RSA.

# Sprawdz istniejace klucze
ls -la ~/.ssh/

# Wygeneruj nowy klucz ed25519
ssh-keygen -t ed25519 -C "kontakt@i4n.pl"

# Pliki domyslnie:
# ~/.ssh/id_ed25519       (prywatny - NIGDY nie udostepniaj)
# ~/.ssh/id_ed25519.pub   (publiczny - to wklejasz na GitHub)

# Wyswietl klucz publiczny
cat ~/.ssh/id_ed25519.pub

# Dodaj klucz do agenta SSH
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# Test polaczenia z GitHub
ssh -T git@github.com
# Hi username! You've successfully authenticated...

# Test z GitLab
ssh -T git@gitlab.com

Konfiguracja ~/.ssh/config dla wielu kont

# ~/.ssh/config
Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal

Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work

# Uzycie
git clone git@github-personal:user/repo.git
git clone git@github-work:company/repo.git

GPG signing commitow

Podpisywanie GPG potwierdza, ze commit pochodzi rzeczywiscie od ciebie. GitHub/GitLab pokazuja "Verified" dla podpisanych commitow.

# Sprawdz istniejace klucze GPG
gpg --list-secret-keys --keyid-format=long

# Wygeneruj nowy klucz GPG
gpg --full-generate-key
# Wybierz: RSA and RSA, 4096 bits, klucz nie wygasa
# Wpisz email zgodny z git config user.email

# Skopiuj klucz publiczny do GitHub
gpg --armor --export TWOJ_KEY_ID

# Skonfiguruj git
git config --global user.signingkey TWOJ_KEY_ID
git config --global commit.gpgsign true        # auto-sign wszystkie commity
git config --global tag.gpgsign true           # auto-sign tagi

# Recznie podpisz commit
git commit -S -m "feat: add feature"

# Podpisz tag
git tag -s v1.0.0 -m "Release 1.0.0"

# Sprawdz podpis
git log --show-signature

# DCO - Developer Certificate of Origin (alternatywa dla GPG)
git commit --signoff -m "feat: add feature"
# Dodaje "Signed-off-by: Name " na koncu wiadomosci

Workflow z forkami

Klasyczny workflow contribution do projektu open source:

# 1. Fork na GitHub (klikniecie w UI)

# 2. Sklonuj swoj fork
git clone git@github.com:moj-user/projekt.git
cd projekt

# 3. Dodaj oryginal jako upstream
git remote add upstream https://github.com/oryginal-user/projekt.git
git remote -v
# origin    git@github.com:moj-user/projekt.git (fetch)
# origin    git@github.com:moj-user/projekt.git (push)
# upstream  https://github.com/oryginal-user/projekt.git (fetch)
# upstream  https://github.com/oryginal-user/projekt.git (push)

# 4. Stworz feature branch
git switch -c feature/awesome-feature

# 5. Pracuj, commituj, pushuj
git push -u origin feature/awesome-feature

# 6. Stworz Pull Request na GitHub

# 7. Periodycznie synchronizuj fork z upstream
git switch main
git fetch upstream
git merge upstream/main
git push origin main

# 8. Po merge PR - usun lokalna i zdalna galaz
git switch main
git branch -d feature/awesome-feature
git push origin --delete feature/awesome-feature

gh CLI - GitHub z linii komend

gh to oficjalne CLI od GitHub. Pozwala wykonywac wiekszosc operacji bez opuszczania terminala.

# Instalacja na Ubuntu
sudo apt install gh

# Instalacja na macOS
brew install gh

# Logowanie (otworzy przegladarke z OAuth)
gh auth login

# Sprawdz status
gh auth status

# Klonuj repo (skrocone uzycie)
gh repo clone owner/repo

# Stworz nowe repo
gh repo create projekt --public --source=. --push

# Forkuj
gh repo fork owner/repo --clone

# Lista PR-ow
gh pr list
gh pr list --state closed
gh pr list --author @me

# Stworz PR (bazujac na biezacej galezi)
gh pr create --title "feat: nowa funkcja" --body "Opis zmian"

# PR template z editora
gh pr create --web

# Status PR
gh pr status

# Checkout PR (np. do code review)
gh pr checkout 123

# Komentarz pod PR
gh pr comment 123 --body "LGTM!"

# Merge PR
gh pr merge 123 --squash --delete-branch

# Issues
gh issue list
gh issue create --title "Bug" --body "Opis"
gh issue close 42

# Workflows / Actions
gh workflow list
gh workflow run deploy.yml
gh run list

# Releases
gh release create v1.0.0 --title "Version 1.0.0" --notes "Release notes"
gh release upload v1.0.0 ./binary.tar.gz

Conflict resolution dla zdalnych zmian

# Twoj push zostal odrzucony bo ktos pushnal w miedzyczasie
git push
# rejected - non-fast-forward

# Opcja 1: Pull z rebase (czystsza historia)
git pull --rebase
# Rozwiaz konflikty jesli sa
git add .
git rebase --continue
git push

# Opcja 2: Pull z merge
git pull
# Rozwiaz konflikty
git add .
git commit
git push

# Opcja 3: Force push (TYLKO osobiste branche!)
git push --force-with-lease
Najlepsze praktyki:
  • Zawsze uzywaj SSH (lub GitHub CLI) zamiast HTTPS z haslem
  • Wlacz GPG signing dla wszystkich commitow
  • Konfiguruj pull.rebase i pull.ff = only
  • Nigdy nie rob git push --force - tylko --force-with-lease
  • Branch protection dla main: require PR review, no direct push
  • 2FA na koncie GitHub/GitLab
  • Personal Access Token z minimalnymi scope'ami zamiast hasla
