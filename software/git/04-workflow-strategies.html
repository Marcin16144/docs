Po co strategia branchowania?

W zespolach pracujacych nad wspolnym repozytorium potrzebne sa jasne reguly: ktore branche maja zmiany, jak sa wprowadzane, kiedy releasujemy. Strategia eliminuje chaos i pozwala na powtarzalne procesy. Wybor zalezy od skali zespolu, czestotliwosci wydan i kultury organizacji.

GitFlow

GitFlow opisany przez Vincenta Driessena w 2010 roku to klasyczny model dla projektow z dlugim cyklem wydawniczym. Wykorzystuje pieć typow galezi.

GalazCelCykl zycia
master / mainTylko produkcyjny kod, kazdy commit ma tag wersjiWieczna
developIntegracja nowych funkcjonalnosci - nastepne wydanieWieczna
feature/*Nowa funkcjonalnoscKrotka, mergowana do develop
release/*Przygotowanie wydania (tylko bug fixy)Krotka, do main + develop
hotfix/*Pilna naprawa produkcjiKrotka, z main do main + develop

Workflow w GitFlow

# Inicjalizacja (jednorazowo)
git switch main
git switch -c develop
git push -u origin develop

# Nowa funkcjonalnosc - z develop
git switch develop
git pull
git switch -c feature/user-profile

# Praca, commity
git add .
git commit -m "feat: dodaj edycje profilu"

# Push i PR do develop
git push -u origin feature/user-profile
# Stworz PR feature/user-profile -> develop

# Po merge - usun feature branch
git branch -d feature/user-profile

# Przygotowanie wydania
git switch develop
git switch -c release/v1.5.0
# Tutaj tylko: bug fixy, aktualizacja CHANGELOG, version bump
# Nie dodawaj nowych feature'ow!

# Finalizacja release
git switch main
git merge --no-ff release/v1.5.0
git tag -a v1.5.0 -m "Release 1.5.0"
git switch develop
git merge --no-ff release/v1.5.0
git branch -d release/v1.5.0
git push origin main develop --tags

# Hotfix - pilna naprawa
git switch main
git switch -c hotfix/v1.5.1-security
# Naprawa
git commit -m "fix: critical security patch"
git switch main
git merge --no-ff hotfix/v1.5.1-security
git tag -a v1.5.1 -m "Hotfix 1.5.1"
git switch develop
git merge --no-ff hotfix/v1.5.1-security
git branch -d hotfix/v1.5.1-security
GitFlow - kiedy stosowac:
  • Klasyczne wydania wersji oprogramowania (np. desktopowe aplikacje)
  • Wymagane wsparcie wielu wersji jednoczesnie
  • Dlugie cykle releasowe (kilka tygodni do miesiecy)
  • Zespoly z dedykowanymi rolami (developer, release manager)
Wady:
  • Skomplikowany - duzo galezi do ogarniecia
  • Wolny proces - nie nadaje sie dla CI/CD i czestych deploymentow
  • Czeste konflikty miedzy develop a release
  • Nie pasuje do nowoczesnych SaaS / mikroserwisow

GitHub Flow

GitHub Flow to prosty, lekki model stworzony przez GitHub. Tylko jedna glowna galaz (main) i feature branche. Idealny dla aplikacji webowych z ciaglym deploymentem.

Reguly GitHub Flow

  1. Wszystko na main jest gotowe do deploy
  2. Stworz galaz z opisowa nazwa
  3. Commituj regularnie i pushuj na remote
  4. Otworz PR jak tylko jestes gotowy do dyskusji
  5. Merge dopiero po review i przejsciu CI
  6. Deployuj natychmiast po merge
# Workflow GitHub Flow
git switch main
git pull

# Feature branch
git switch -c add-search-feature

# Praca, commit, push
git commit -m "feat: implement search"
git push -u origin add-search-feature

# Po review i merge - deployment automatyczny przez CI/CD
# Galaz usunieta automatycznie

# Aktualizacja main
git switch main
git pull
git branch -d add-search-feature

GitLab Flow

GitLab Flow rozszerza GitHub Flow o galezie srodowiskowe. Dodaje branche dla kazdego srodowiska (staging, production), co umozliwia kontrole nad tym co zostaje wdrozone gdzie.

# Galezie:
# main          - rozwoj
# pre-production - testowe srodowisko
# production    - produkcja

# Workflow:
# 1. Feature -> main (PR + review)
# 2. main automatycznie deployowany na dev
# 3. Manualnie merguj main -> pre-production (deploy na staging)
# 4. Po testach merguj pre-production -> production (deploy na prod)

# Promocja kodu zawsze "w gore" - nigdy z powrotem
git switch pre-production
git merge main
git push

# Po testach
git switch production
git merge pre-production
git tag v1.5.0
git push --follow-tags

# Hotfix - bezposrednio z production
git switch production
git switch -c hotfix/critical
# Fix
# Cherry-pick / merge do main, pre-production i production

Trunk-Based Development

Trunk-Based Development to model najszybciej rosnacy w popularnosci. Wszyscy developerzy commituja do jednej glownej galezi (trunk/main). Feature branche istnieja krotko (1-2 dni max). Niedokonczone funkcje sa ukrywane pod feature flags.

Filozofia

  • Krotkie galezie (max 2 dni zycia)
  • Czeste integracje z trunk (wiele razy dziennie)
  • Feature flags dla niegotowych funkcji
  • Continuous Integration (CI) niezbedne
  • Wymagana automatyzacja testow
  • Release branche tworzone z trunk tylko dla stabilizacji
# Krotka galaz - po jednym dniu mergowana
git switch main
git pull
git switch -c quick-fix

# Praca - max kilka commitow
git commit -m "fix: button alignment"

# Push, PR, code review, merge - wszystko tego samego dnia
git push -u origin quick-fix

# Niegotowa funkcjonalnosc - pod feature flag
if (featureFlags.newCheckout) {
    return <NewCheckout />;
} else {
    return <OldCheckout />;
}

# Release branch tylko dla stabilizacji wersji
git switch main
git switch -c release/v2.0
# Tylko bug fixy, brak nowych funkcji
# Po wydaniu - branch usuwany lub trzymany dla wsparcia
Trunk-based - kiedy stosowac:
  • Aplikacje SaaS z continuous deployment
  • Mikroserwisy
  • Doswiadczone zespoly z silnym CI/CD
  • Kultura code review i feature flags
Wymagania:
  • Wysokie pokrycie testami automatycznymi
  • System feature flags (np. LaunchDarkly, Unleash, Flagsmith)
  • Szybki pipeline CI/CD (< 15 minut)
  • Branch protection (no direct push, required reviews)

Conventional Commits

Conventional Commits to specyfikacja standaryzujaca wiadomosci commitow. Pozwala automatycznie generowac CHANGELOG, okreslac wersje, integrowac z narzedziami CI/CD.

Format

<type>(<scope>): <subject>

<body>

<footer>
TypeZnaczenieSemVer impact
featNowa funkcjonalnoscMINOR
fixNaprawa bugaPATCH
docsTylko dokumentacjanone
styleFormatowanie, brak logikinone
refactorRefaktor bez zmian funkcjonalnoscinone
perfOptymalizacja wydajnosciPATCH
testDodawanie/zmiana testownone
buildSystem buildu, zaleznoscinone
ciKonfiguracja CI/CDnone
choreInne zadanianone
revertCofniecie commitavaries

Przyklady

# Prosta funkcjonalnosc
feat: dodaj logowanie przez Google OAuth

# Z zakresem (scope)
feat(auth): dodaj logowanie przez Google OAuth

# Naprawa buga
fix(api): rozwiaz null pointer w endpoint /users

# Breaking change - dwa sposoby:
# 1. Wykrzyknik po typie
feat!: usun deprecated endpoint /api/v1

# 2. Footer BREAKING CHANGE
feat(api): zmien strukture odpowiedzi /users

BREAKING CHANGE: pole 'name' zostalo zastapione przez 'firstName' i 'lastName'.
Klienci musza zaktualizowac kod parsujacy odpowiedz.

# Pelny przyklad
feat(payments): integracja z Stripe

Dodaje obsluge platnosci kartami przez Stripe Elements.
Wspierane sa karty Visa, Mastercard, Amex.
Implementuje 3D Secure dla transakcji powyzej 500 PLN.

Narzedzia wymuszajace standard

# commitlint - lint commit messages
npm install --save-dev @commitlint/cli @commitlint/config-conventional

# .commitlintrc.json
{
  "extends": ["@commitlint/config-conventional"]
}

# Husky - hook git
npm install --save-dev husky
npx husky init
echo 'npx --no -- commitlint --edit $1' > .husky/commit-msg

# Commitizen - interaktywny prompt
npm install --save-dev commitizen
npx commitizen init cz-conventional-changelog --save-dev --save-exact

# Uzycie
git cz   # zamiast git commit

Semantic Versioning (SemVer)

SemVer to standardowy schemat numerowania wersji: MAJOR.MINOR.PATCH (np. 2.5.3).

CyfraZwiekszamy gdyPrzyklad
MAJORBreaking changes (niekompatybilne API)1.5.3 -> 2.0.0
MINORNowe funkcje (kompatybilne wstecz)1.5.3 -> 1.6.0
PATCHBug fixy (kompatybilne wstecz)1.5.3 -> 1.5.4

Pre-release i metadata

# Pre-release
1.0.0-alpha
1.0.0-alpha.1
1.0.0-beta
1.0.0-rc.1

# Build metadata
1.0.0+20260507
1.0.0-beta+exp.sha.5114f85

# W praktyce
git tag -a v1.5.0-beta.1 -m "Beta 1 of 1.5.0"
git tag -a v1.5.0-rc.1 -m "RC 1"
git tag -a v1.5.0 -m "Stable 1.5.0"

Automatyzacja - semantic-release

# Na podstawie Conventional Commits automatycznie:
# - okresla nowa wersje (analizuje typy commitow)
# - tworzy CHANGELOG.md
# - tagi w gitcie
# - GitHub Release
# - publikuje na npm

# Instalacja
npm install --save-dev semantic-release

# .releaserc.json
{
  "branches": ["main"],
  "plugins": [
    "@semantic-release/commit-analyzer",
    "@semantic-release/release-notes-generator",
    "@semantic-release/changelog",
    "@semantic-release/npm",
    "@semantic-release/github",
    "@semantic-release/git"
  ]
}

# CI/CD wywoluje
npx semantic-release

Praktyczne rekomendacje:
  • Mala aplikacja webowa, jeden deploy - GitHub Flow
  • SaaS z testowym srodowiskiem - GitLab Flow
  • Mikroserwisy, doswiadczony zespol - Trunk-Based
  • Komercyjne oprogramowanie z wieloma wersjami - GitFlow
  • Open source library - GitHub Flow + SemVer + semantic-release
