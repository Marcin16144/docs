Bazy danych

Warstwa połączenia, migrator, modele, konwencja nazewnictwa

1. Warstwa połączenia (PDO)

Frontend ([index.php](../../index.php)) używa singletona PDO. Wybór silnika sterowany kluczem db.driver w configu — autoloader katalogu core/db/ wciąga plik on-demand.

Driver w configu Klasa Plik Wymagane pola configu
mysql MySqlDriver core/db/MySqlDriver.php host, port, database, username, password, charset
pgsql PgSqlDriver core/db/PgSqlDriver.php host, port, database, username, password
sqlite SqliteDriver core/db/SqliteDriver.php database (ścieżka lub :memory:)

2. Komponenty modułowe

Każdy komponent żyje w app/<Pascal>/, wykrywany przez ComponentDiscovery. Appdb jest bazą każdego projektu; CMS/Shop — opcjonalne nadbudowy.

Appdb baza

Application Main — autentykacja, sesje, log aplikacji.

  • Slug: appdb
  • Tabele: users (Use), logs (Log)
  • Log z wersją: LogAppVersion ← Core\Version::current()
  • Tracking: <tenant>_migrations_appdb

Cms opcjonalny

CMS — strony, kategorie, media.

  • Slug: cms
  • Tabele: pages
  • Prefix kolumn: Pag
  • Tracking: <tenant>_migrations_cms

Shop opcjonalny

Sklep — produkty, zamówienia, koszyk.

  • Slug: shop
  • Tabele: (pusty — szablon)
  • Prefix kolumn: (TBD)
  • Tracking: <tenant>_migrations_shop

3. Warstwa migracji

Migrator nie startuje przy żądaniach frontendu. Wyzwalany przy loginie do admin/ oraz z CLI bin/migrate. Lock-pliki w var/schema-lock/ trzymają fingerprint nazw plików migracji — gdy zgodny ze stanem dysku, runner pomija zapytania SQL.

Wyzwalacz

  • → Login do /admin/
  • → php bin/migrate <k> migrations:migrate
→

MigrationRunner::runPending()

  • 1. ComponentDiscovery → lista komponentów
  • 2. SchemaLock fingerprint vs disk
  • 3. Jeśli rozjazd → migracja w transakcji
  • 4. Aktualizacja lock-pliku

5. Modele tabel — deklaratywne źródło prawdy

Każda tabela ma model w app/<Komponent>/Models/<Entity>Model.php. Każda kolumna to jedna linia w columns() — łatwo zaremować, dodać, zmienić indeks. Migracja CREATE jest cienka i woła $model->createTableSql().

final class UsersModel extends TableModel { public function entity(): string { return 'users'; } public function columnPrefix(): string { return 'Use'; } public function columns(): array { return [ // ── Kolumny bazowe (wymagane wg konwencji) ── Column::guid('ID')->primaryKey(), Column::dateTime('DateTime')->default('CURRENT_TIMESTAMP'), Column::autoInc('IDAuto')->uniqueKey('idauto'), // ── Kolumny biznesowe ── Column::varchar('Login', 64)->uniqueKey('login'), Column::varchar('Password', 255), Column::varchar('Email', 190)->nullable()->uniqueKey('email'), Column::tinyInt('IsActive')->default(1), // Column::varchar('Phone', 32)->nullable(), ← łatwo dodać / zaremować ]; } }

6. Cykl życia modelu po wdrożeniu

SytuacjaDziałanie
CREATEMigracja używa createTableSql() z modelu
+ kolumna1) Dodaj linię w modelu. 2) Nowa migracja ALTER z ALTER TABLE ADD COLUMN
– kolumna1) Zaremuj linię. 2) Nowa migracja ALTER z DROP COLUMN
Zmiana typu1) Zmień w modelu. 2) Nowa migracja z MODIFY COLUMN
Zmiana indeksu1) Zmień uniqueKey/indexKey lub indexes(). 2) Migracja DROP INDEX + ADD UNIQUE KEY

7. Konwencja nazewnictwa

Prefix tabeli = atrybut tenanta (jeden klient / aplikacja / domena). Prefix kolumn = 3–5 znaków PascalCase, per tabela.

Element Konwencja Przykład
Nazwa tabeli <tenant>_<entity> def_users, kl1_pages
Primary key <C>ID CHAR(36) GUID (generowany w aplikacji) UseID, PagID
Znacznik utworzenia <C>DateTime DATETIME DEFAULT CURRENT_TIMESTAMP UseDateTime
Auto-increment <C>IDAuto INT UNSIGNED, UNIQUE (nie PK) UseIDAuto
Znacznik modyfikacji (opcjonalnie) <C>Modified DATETIME NULL ON UPDATE CURRENT_TIMESTAMP UseModified
Unique index uniq_<tabela>_<cel> uniq_def_users_login
Zwykły indeks idx_<tabela>_<cel> idx_def_pages_parent
Foreign key fk_<tabela>_<kolumna> fk_def_pages_authorid
Tabela metadanych migratora <tenant>_migrations_<slug> def_migrations_appdb
