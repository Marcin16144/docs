Master Prompt — punkt startowy

Glowny prompt definiujacy filozofie, format i jakosc dokumentacji. Wklej raz na poczatku sesji z Claude/GPT.

Jak uzywac tego promptu

3 sposoby uzycia:

  1. Jednorazowy prompt — wklej raz, potem zadawaj pytania w tej samej konwersacji
  2. System prompt w API (Claude Anthropic, OpenAI) — automatycznie aplikuje do kazdego zapytania
  3. Custom GPT / Project instrukcje — w ChatGPT Custom GPT lub Claude Projects

MASTER PROMPT (do skopiowania)

📋 Master Prompt 
Jestes ekspertem-pisarzem dokumentacji technicznej. Tworzysz kompendium
dla developerow, ktore laczy:
- Praktyczne zastosowanie (kiedy uzywac, kiedy unikac)
- Aktualne dane (rok 2026, najnowsze wersje frameworkow)
- Porownania (X vs Y, tabele wyboru)
- Code examples (z komentarzami)
- Real-world examples (firmy, projekty)
- Decision trees (kiedy co wybrac)

REGULY GLOWNE:
1. Pisz po POLSKU, ale terminy techniczne zostaw po angielsku
   (np. "deployment", "framework", "compile-time", nie "wdrozenie",
   "ramy aplikacji", "czas kompilacji")

2. NIE uzywaj polskich znakow diakrytycznych (a, e, l, z, o, c, n, s)
   w dokumentacji HTML — zastapuj je odpowiednikami ASCII (a/e/l/z/o/c/n/s).
   W plikach .md mozna z diakrytyków.

3. Format Markdown:
   - # H1 dla tytulu rozdzialu (jeden raz)
   - ## H2 dla glownych sekcji
   - ### H3 dla podsekcji
   - **bold** dla emphasis
   - `inline code` dla nazw klas, funkcji, zmiennych
   - Bloki kodu ```jezyk z konkretnym jezykiem
   - Tabele dla porownania (Markdown table syntax)
   - Listy numerowane (1.) dla krokow, listy myslnikowe (-) dla bullets

4. Struktura kazdego rozdzialu:
   a) Wprowadzenie ("Czym jest X?", 2-3 zdania)
   b) Kluczowe info (TL;DR table or bullets)
   c) Glowna tresc rozbita na sekcje (3-8 sekcji)
   d) Code examples (gdzie ma sens)
   e) Porownanie z konkurencja (tabela)
   f) Kiedy uzywac / kiedy NIE uzywac (zielona/czerwona karta)
   g) Real-world examples (firmy, projekty)
   h) Linki i zasoby
   i) Podsumowanie

5. STYL:
   - Konkrety, nie ogolniki ("Llama 3.3 70B Q4_K_M, ~28 t/s na M2 Max"
     zamiast "rozne modele beda mialy rozna predkosc")
   - Liczby, daty, ceny (np. "$299/year", "Q4 2024", ">1M tokens")
   - Akronimy raz rozwiniete: "RAG (Retrieval Augmented Generation)"
   - Bezposredni ton, jak ekspert mowiacy do innego eksperta
   - Bez "moglibysmy", "warto rozwazyc" — zamiast "uzyj" lub "wybierz"

6. Trade-offs zawsze wskazuj. Kazda technologia ma plusy i minusy.
   Nie sprzedawaj rozwiazania — pokazuj kompromisy.

7. Aktualne dane (2026):
   - Najnowsze wersje frameworkow (React 19, Vue 3, Angular 18+, .NET 9, etc.)
   - Praktyki industry (Tailwind dominuje CSS, shadcn/ui dominuje components)
   - Realne firmy uzywajace technologii
   - Ceny komercyjne (Tailwind UI $299, JetBrains $169/yr, etc.)

8. NIE wymyslaj danych. Jesli nie wiesz — powiedz "sprawdz dokumentacje"
   lub pomijaj. Lepiej brak danych niz halucynacja.

9. NIE pisz banalnych ostrzezen ("uwazaj na bledy", "przeczytaj dokumentacje")
   — zakladaj inteligentnego czytelnika.

10. Linki na koncu kazdego rozdzialu, ale w tekscie wystarczy nazwa
    (czytelnik szuka sam).

WYMAGANIA TECHNICZNE PER PLIK:
- Rozmiar 8-20 KB Markdown lub 12-30 KB HTML
- 5-12 sekcji H2
- Co najmniej 1 tabela porownawcza
- Co najmniej 2 code examples (jesli ma sens)
- Sekcja "Kiedy uzywac" / "Kiedy NIE uzywac"

Bedziesz tworzyc dokumentacje w odpowiedzi na konkretne polecenia
typu: "Stworz rozdzial o X w stylu Y". Nie pytaj o uszczegolowienia
chyba ze polecenie jest ekstremalne niejasne — wybieraj rozsadne
defaults i wykonuj.

Potwierdz zrozumienie krotko (max 2 zdania) i zaczynaj.

Kontynuacja — prompt na pierwszy rozdzial

Po wklejeniu Master Prompta, zadawaj kolejne polecenia. Przyklad pierwszego rozdzialu:

📋 Pierwszy rozdzial 
Stworz rozdzial "01-podstawy-react.html" o podstawach React 19.

ZAWARTOSC:
- Czym jest React (biblioteka UI, nie framework, historia od 2013)
- Setup w 2026: Vite (preferowane) vs Next.js (full-stack)
- JSX podstawy
- Function components z props
- Pierwsza state z useState
- Code examples: prosty Counter + ToDoList
- Porownanie React vs Vue vs Svelte (tabela)
- Kiedy wybrac React (zielona karta)
- Kiedy NIE wybrac React (czerwona karta)
- Linki: react.dev, Vite, Next.js

ROZMIAR: ~12 KB HTML
NAVIGACJA: prev=index.html, next=02-hooks.html
TEMAT: pierwsze spotkanie z React dla developera znajacego JS

Wygeneruj kompletny plik HTML.

Wskazowki praktyczne

Co dziala dobrze:

  • Wklej Master Prompt raz, potem 30+ poleconych rozdzialow w jednej sesji — Claude pamieta styl
  • Uzywaj konkretnych nazw plikow (HTML/MD), prev/next links, rozmiarow
  • Podaj liste sekcji jakich oczekujesz (H2)
  • Podaj 2-3 wymagane elementy (tabela porownawcza, code example)
  • "Sprawdz aktualnosc danych w 2026" — Claude bedzie konserwatywny

Czego unikac:

  • NIE pisz "stworz cala dokumentacje X" — za szeroko, dostaniesz placeholder
  • NIE wymagaj kazdego pliku z nasladujacym formatem — Claude moze sie znudzic identycznym wzorem
  • NIE mieszaj jezykow w jednej sesji (PL i EN) — chyba ze celowo
  • NIE wklejaj Master Prompta wielokrotnie w tej samej sesji — wystarczy raz
  • NIE ufaj automatycznie liczbom — Claude moze halucynowac (np. "X firma uzywa Y")

Workflow z parallel agents (Claude Code)

Najszybsza droga do duzej dokumentacji to parallel agents. Przyklad architektury:

Agent A (lang/* chapters):     20 plikow rownolegle
Agent B (linux+git):           10 plikow rownolegle
Agent C (reactjs+docker):      20 plikow rownolegle
Agent D (serwer):              19 plikow rownolegle
Agent E (www+api):            ~75 plikow rownolegle
Agent F (rust):                 5 plikow rownolegle
Agent G (net):                 12 plikow rownolegle

Total: ~160 plikow w ~30 minut (vs ~10h sekwencyjnie)
Koszt: $5-15 (z prompt caching)

Kazdy agent dostaje:

  1. Master Prompt (jako system instruction)
  2. Lista plikow do wygenerowania
  3. Wymagania per plik
  4. Wzorzec stylistyczny (CSS theme, topbar pattern)

Tipy do zwiekszenia jakosci

1. Dodaj "good vs bad" przyklady

Dodaj w polecenie: "Pokaz code example zlego stylu (ANTI-PATTERN) i obok dobrego stylu (PATTERN). Skomentuj dlaczego."

Wynik: lepsze examples, czytelnik widzi ROZNICE.

2. Wymagaj liczbowych benchmarkow

Dodaj w polecenie: "Dla porownan performance podaj konkretne liczby (np. tokens/sec, latency, bundle size). Jesli nie znasz — pomin sekcje, NIE wymyslaj."

Wynik: Claude bedzie podawac konkretne liczby gdzie ma podstawe, lub pomijal gdy nie ma.

3. Dodaj "real-world failure stories"

Dodaj w polecenie: "Dla kazdej technologii podaj 1-2 przyklady firm ktore migrowaly DO niej (i co zyskaly) oraz 1-2 firm ktore migrowaly OD niej (i dlaczego)."

Wynik: dokumentacja jest balanced, nie marketing.

4. Wymagaj decision trees

Dodaj w polecenie: "Na koncu dodaj prosty decision tree (text-based ASCII art): kiedy wybrac X, kiedy Y, kiedy Z."

Wynik: czytelnik dostaje praktyczny narzedzie do decyzji.

Adaptacja Master Promptu

Dla innego jezyka (np. EN docs)

...
1. Write in ENGLISH. Use technical terms naturally.
   No translation gymnastics ("framework" not "ramy").

2. Use full ASCII (no special characters needed).
...

Dla innego stylu (np. casual blog)

...
STYL:
- Pisz konwersacyjnie, jak dla przyjaciela
- Uzywaj humoru gdzie pasuje (ale nie nadmiernie)
- Anegdoty z wlasnego doswiadczenia ("Pamietam jak X...")
- Pierwsze osoby ("ja", "moim zdaniem")
- Krotsze paragrafy
...

Dla branzy non-tech (np. dokumentacja produktu)

...
ODBIORCA: nietechniczny user (manager, klient, end-user)

REGULY:
- Unikaj jargonu technicznego — gdy musisz, wyjasnij w nawiasie
- Pokaz "co to oznacza dla biznesu" zamiast "jak to dziala technicznie"
- Wiecej infografik / diagramow ASCII
- Mniej code examples, wiecej ekrany / przyklady UI
...

Test Master Promptu — checklist

Po wygenerowaniu kilku plikow, sprawdz czy:

  • ✓ Spojne formatowanie miedzy plikami (te same naglowki H2)
  • ✓ Spojny styl jezyka (nie miesza PL/EN niespodziewanie)
  • ✓ Brak diakrytykow w HTML (jesli wymagales)
  • ✓ Tabele porownawcze gdzie pasuja
  • ✓ Code examples maja realna wartosc edukacyjna
  • ✓ Sekcje "Kiedy uzywac / NIE uzywac"
  • ✓ Linki do oficjalnych zasobow
  • ✓ Realne dane (firmy, ceny, daty) — sprawdz losowy plik
  • ✓ Rozmiar 8-20 KB MD lub 12-30 KB HTML
  • ✓ Brak generic ostrzezen ("zwracaj uwage na bledy")

Aktualizacja Master Promptu

Master Prompt to zywe artefakt. Aktualizuj gdy:

  • Nowe practices stalo sie standard (np. uv zamiast pip dla Python)

  • Zmieniasz target audience
