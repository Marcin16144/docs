10. Prompty per styl narracji i tone of voice

Praktyczne tipy, real-world examples, decision trees, comparison tables, struktura rozdzialu, anti-patterns w dokumentacji.

Filozofia stylu dokumentacji

Dobra dokumentacja techniczna jest jak rozmowa z senior inzynierem przy kawie: konkrety, przyklady, otwarte mowienie o trade-offs, brak korpo-tonu. Czytelnik to nie student — to kolega ktory chce odpowiedzi w 5 minut.

Prompt: Praktyczne tipy

Prompt — Practical tips 
Pisz dokumentacje w stylu "praktyczne tipy". REGULY:

1. Kazda rada ma byc DZIALAJACA.
   Zle: "uzywaj nowoczesnych narzedzi"
   Dobrze: "Uzyj uv zamiast pip — instalacja paczek 10x szybsza,
   resolver napisany w Rust"

2. Kazdy fakt ma liczby / wersje / daty.
   Zle: "duze projekty maja problem z bundlem"
   Dobrze: "Bundle ponad 250 KB gzipped degradacja LCP o ~1s
   na 3G — Google Search Console wykluczy z indexu"

3. Pisz "Co zrobic" zamiast "co rozwazyc".
   Zle: "warto rozwazyc indexowanie kolumny"
   Dobrze: "Dodaj index na user_id (CREATE INDEX ...). Query
   z 800ms -> 5ms, pamiec +20%"

4. Kazdy tip jako numerowana lista lub krotka sekcja H3.
   Czytelnik scanuje, nie czyta linearnie.

5. Zlap blad / pulapke ZANIM ja popelnia. Nie po fakcie.
   Zle: "jesli masz problem X, sprobuj Y"
   Dobrze: "Uwaga: jesli ustawisz X=true bez Y, dostaniesz Z.
   Zawsze ustawiaj oba razem"

Prompt: Real-world examples

Prompt — Real-world 
Dla kazdej technologii podaj REAL-WORLD examples z firm.

WZORZEC:
"Migrowali DO X: [Firma A, rok], [Firma B, rok]. Co zyskali:
[konkret]. Co stracili: [konkret]."
"Migrowali OD X: [Firma C, rok], dlaczego: [konkret]"

PRZYKLADY:
- Stripe -> Ruby on Rails monolith do dzis (2024+), $50B valuation,
  decyzja techniczna tegoroczna nie zmiana
- Twitter -> Scala+JVM 2010, kosztowne, w 2022 czesciowo back to Rails
- Amazon Prime Video 2023 -> z microservices DO monolitu, 90%
  cost reduction (slynny case)
- Shopify -> modular monolith zamiast microservices, "majestic monolith"
- Pinterest -> Postgres skalowalne do petabajtow

NIE WYMYSLAJ. Jesli nie znasz, napisz "(potwierdz w infrastrukturze
[firma])". Lepiej brak example niz halucynacja.

KAZDY ROZDZIAL: 2-4 real-world cases. Prawdziwe nazwy firm,
prawdziwe daty migracji, prawdziwe rezultaty.

Prompt: Decision trees

Prompt — Decision trees 
Dodawaj decision trees na koncu rozdzialow gdzie sa wybory technologiczne.

WZORZEC ASCII art:
+------+--------------------------------+
| Pytanie kluczowe?                     |
+- TAK: technologia A
+- NIE: idz dalej
   +- Drugie pytanie?
      +- TAK: technologia B
      +- NIE: technologia C

PRZYKLAD:
Database for new project?
+- < 100k MAU, prosta domena: PostgreSQL (sql + jsonb wystarczy)
+- > 100k MAU lub time-series: PostgreSQL + Timescale
+- Document-heavy, schema dynamiczna: MongoDB
+- Real-time analytics: ClickHouse
+- Graph relationships: Neo4j lub Postgres + cypher extension
+- Scale-out > 10TB: CockroachDB lub Spanner

REGULY:
- Max 4-5 galezi (dluzszy = nieczytelny)
- Pytania binarne (TAK/NIE) lub categoryczne
- Konczyl konkretem (nazwa technologii), nie "rozwaz"
- ASCII art z + i - (nie unicode box drawing)

Prompt: Comparison tables

Prompt — Comparison tables 
Porownania zawsze w tabelach. REGULY:

1. Pierwsza kolumna: nazwa technologii.
2. Kazda kolejna kolumna: jeden konkretny atrybut.
3. Atrybuty MIERZALNE (cena, rozmiar, latency), nie subiektywne
   (popularnosc, jakosc).
4. Ostatnia kolumna: "Sweet spot" (kiedy uzywac).
5. 3-8 wierszy (wiecej = nieczytelne).

PRZYKLAD ZLY:
| Tool | Quality | Speed | Popular |
| A    | Good    | Fast  | Yes     |

PRZYKLAD DOBRY:
| Tool | Bundle (gzip) | Build (5k pliki) | Sweet spot |
| Vite | 4 KB runtime  | 320 ms           | SPA, dev experience |
| esbuild | 0 (bundler) | 80 ms          | Library bundling, CLI |

UWAGA NA:
- Liczby konkretne (320 ms, $19/user/mo, 4.2 MB)
- Nie miesz "good/medium/bad" w tabeli (subiektywne)
- Daj date pomiaru ("benchmarki Q1 2026")

Prompt: Kiedy uzywac / Kiedy NIE uzywac

Prompt — When to use 
Kazda technologia/wzorzec MUSI miec sekcje "Kiedy uzywac" i
"Kiedy NIE uzywac". Stosuj cards green / red.

WZORZEC GREEN (kiedy uzywac):
- 3-5 konkretnych scenariuszy
- Per-scenariusz: "jesli X, to Y daje Z" (warunek + benefit)
- Z liczbami / daty / wersje gdzie mozna

PRZYKLAD:
"Kiedy wybrac PostgreSQL:
- Domena z relacjami (>5 powiazanych tabel) — joins na PG sa szybkie
- Potrzeba ACID transactions — 100% zgodne (vs MongoDB compromises)
- JSONB dla document-style + relacje — tylko PG ma to dobrze
- Skalowanie do 10TB single instance — bez problemow"

WZORZEC RED (kiedy NIE uzywac):
- 3-5 anti-scenarios (kiedy ZLY wybor)
- Skierowane do specific use case
- Pokaz alternatywe

PRZYKLAD:
"Kiedy NIE PostgreSQL:
- Sub-millisecond pure key-value -> Redis / DragonflyDB
- 100k+ writes/sec time-series -> ClickHouse / TimescaleDB
- Multi-region active-active -> CockroachDB / Spanner
- Schema-less heavy + flexible queries -> MongoDB
- Graph traversal heavy -> Neo4j"

Struktura idealnego rozdzialu

  1. Intro (50-150 slow) — czym jest temat, dla kogo, kiedy aktualne
  2. TL;DR table — najwazniejsze fakty w 5-8 wierszach
  3. Sekcje merytoryczne (5-10) — kazda 200-500 slow + code/example
  4. Tabela porownawcza — z konkurencja / alternatywami
  5. Real-world examples — 2-4 firmy/projekty
  6. Kiedy uzywac (green card) — 3-5 scenariuszy
  7. Kiedy NIE uzywac (red card) — 3-5 anti-scenariuszy
  8. Decision tree — ASCII art
  9. Linki — oficjalne docs, github, blog post key
  10. Podsumowanie — 2-3 zdania, what's next

Reguly stylistyczne

Konkrety zamiast ogolnikow

Zle: "rozne modele beda mialy rozna predkosc"
Dobrze: "Llama 3.3 70B Q4_K_M generuje ~28 t/s na M2 Max, ~95 t/s na A100 80GB"

Liczby, daty, wersje

Bez liczb dokumentacja jest opowiadaniem. "Tailwind 4 oxide engine napisany w Rust, 10x szybszy build (16ms vs 160ms na medium projekt)" zamiast "szybszy".

Bezposredni ton

"Uzyj useEffect dla side effects" zamiast "Mozna by rozwazyc wykorzystanie useEffect". Czytelnik chce dyrektywy nie waterfall.

Akronimy raz rozwiniete

"RAG (Retrieval Augmented Generation) ulepszyl..." potem juz tylko "RAG". Bez rozwijania = barbarzynstwo. Z rozwijaniem za kazdym razem = uzytownik mysli ze to nowe.

Unikaj waterfall

Zle: "Aplikacje nowoczesne charakteryzuja sie pewnymi cechami ktore mozna scharakteryzowac jako..."
Dobrze: "Apka 2026 = SSR + Islands + Edge runtime + RSC"

NIE wymyslaj danych

"Microsoft uzywa Y" — czy na pewno wiesz? Jesli nie, napisz "duze enterprise" lub omijaj. Halucynacja w docs niszczy zaufanie permanentnie.
