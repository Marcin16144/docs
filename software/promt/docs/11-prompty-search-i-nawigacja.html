11. Prompty per search i nawigacja

Generowanie main index, drzewa nawigacji, client-side search, breadcrumbs, prev/next links, cross-references.

Filozofia nawigacji

Bez search dokumentacja 200 plikow jest nieuzywalna. Bez breadcrumbs czytelnik gubi sie po 3 klikach. Nawigacja musi byc spojna na kazdej stronie (topbar) + predictable (prev/next).

Prompt: Generowanie main index.html

Prompt — Main index 
Stworz glowny index.html dla calej dokumentacji (D:/docs/index.html).

STRUKTURA:
- Topbar minimalny (tylko tytul "Dokumentacja", brak breadcrumb)
- H1 z gradient text "Dokumentacja techniczna"
- Sekcja "Search" (input z client-side search, opisana w prompt 2)
- Drzewo kategorii (12 glownych) z .breadcrumb pattern:
  * 01 — Jezyki (ikona, krotka opis, link)
  * 02 — Frontend
  * 03 — Backend
  * 04 — Devops
  * 05 — LLM/AI
  * 06 — Audio/VST
  * 07 — Architektura
  * 08 — Narzedzia
  * 09 — Prompty (meta)
  * itd.

KAZDA KATEGORIA:
<li>
  <a href="kategoria/index.html">
    <span class="num">NN</span>
    <span class="title">Nazwa</span>
    <span class="meta">X plikow, ~Y godzin</span>
    <span class="desc">Krotki opis 1 zdanie</span>
  </a>
</li>

DODAJ:
- Sekcja "Recently updated" (top 5 ostatnio zmienionych)
- Sekcja "Most read" (jesli masz analitykę)
- Footer z linkiem do GitHub source

ROZMIAR: 8-15 KB

Prompt: Client-side search (vanilla JS + JSON index)

Prompt — Client search 
Stworz client-side search dla statycznej dokumentacji (vanilla JS,
zero dependencies, zadnego buildera).

ARCHITEKTURA:
1. Build-time: parser przechodzi przez .html files,
   ekstraktuje H1/H2/H3, pierwsze 200 slow tekstu, generuje
   search-index.json (~ 50-200 KB dla 200 plikow)

2. Run-time: search.js laduje search-index.json przy pierwszym
   interakcji (lazy load), index w pamieci

3. Search algorithm: simple substring + tokenization
   (split na bialych znakach, lowercase), score
   za pomocy MiniSearch lub Fuse.js (CDN, zero deps)

4. UI: input fixed-top z dropdown wynikami (max 10),
   ESC closes, ARROW UP/DOWN navigates, ENTER opens

5. Highlight matching tokens w wynikach

CODE EXAMPLE: pelny generator (Node.js) + pelny search.js
(client) + integration w <head>

ALTERNATIVES:
- Pagefind (best-in-class static search, Rust-built, zero JS deps)
- DocSearch (Algolia, free dla OSS docs)
- Lunr.js (battle-tested, larger bundle)
- MiniSearch (lightweight 7KB)

REKOMENDACJA: Pagefind dla nowych projektow (najlepszy DX
2024-2026), MiniSearch jako vanilla JS embedded.

Prompt: Breadcrumbs pattern

Prompt — Breadcrumbs 
Generuj breadcrumbs spojnie w calej dokumentacji.

DWA WZORCE:

1) .breadcrumb (pionowa lista, tylko na index pages):
<ul class="breadcrumb">
  <li><a href="01-podstawy.html">
    <span class="num">01</span>
    <span class="title">Podstawy</span>
    <span class="meta">~15 min</span>
  </a></li>
  ...
</ul>

CSS:
.breadcrumb{list-style:none;padding:0}
.breadcrumb li{margin:8px 0}
.breadcrumb a{display:flex;gap:16px;padding:14px 18px;
  background:var(--surface);border-radius:8px;
  border-left:3px solid var(--accent);text-decoration:none;
  color:var(--text)}
.breadcrumb a:hover{background:var(--code-bg);transform:translateX(4px)}
.breadcrumb .num{color:var(--accent);font-weight:600;
  min-width:32px}
.breadcrumb .title{flex:1;font-weight:500}
.breadcrumb .meta{color:var(--text-muted);font-size:.85rem}

2) .topbar (sticky, na podstronach):
<div class="topbar">
  <a href="../../index.html">Glowna</a>
  <span class="sep">/</span>
  <a href="../index.html">Kategoria</a>
  <span class="sep">/</span>
  <span class="title">Nazwa biezacej strony</span>
</div>

UWAGA: ostatni element to TEKST (nie link) — biezaca strona.
Sticky pozwala na szybki powrot.

Prompt: Auto-generowanie nav-bottom prev/next

Prompt — Nav-bottom prev/next 
Generuj nav-bottom (prev/next) automatycznie na podstawie
nazewnictwa plikow.

KONWENCJA:
NN-temat.html w kazdej kategorii, gdzie NN to numer porzadku.

ALGORYTM (build-time script):
1. Lista wszystkich .html w kategorii, sort alphabetic.
2. Dla pliku NN-temat.html:
   - prev = NN-1 file (lub index.html jesli NN=01)
   - next = NN+1 file (lub null/inny link jesli ostatni)
3. Inject <div class="nav-bottom"> przed </div></body>

PYTHON SCRIPT (przyklad):
import os, re
files = sorted(f for f in os.listdir('docs') if f.endswith('.html'))
for i, f in enumerate(files):
    prev = files[i-1] if i > 0 else 'index.html'
    nxt = files[i+1] if i < len(files)-1 else None
    # ... inject nav-bottom

WZORZEC HTML:
<div class="nav-bottom">
  <a href="PREV_FILE">&larr; PREV_TITLE</a>
  <a href="NEXT_FILE">NEXT_TITLE &rarr;</a>
</div>

CSS:
.nav-bottom{display:flex;justify-content:space-between;
  margin-top:60px;padding-top:24px;border-top:1px solid var(--border)}
.nav-bottom a{color:var(--accent);text-decoration:none;font-size:.9rem}

EDGE CASE: ostatni plik nie ma "next", uzyj link do parent
("Wroc do indeksu &rarr;").

Prompt: Linkowanie miedzy rozdzialami (cross-references)

Prompt — Cross-references 
Twoze cross-references miedzy rozdzialami konsekwentnie.

WZORCE:

1) "See also" sekcja na koncu rozdzialu:
<h2>Powiazane tematy</h2>
<ul>
  <li><a href="../docker/index.html">Docker</a> — runtime kontenerow</li>
  <li><a href="../linux/05-firewall.html">Firewall (Linux)</a> — security warstwa</li>
</ul>

2) Inline link w tekscie (sparingly):
"Dla szczegolow setup zobacz <a href="../docker/02-dockerfile.html">
Dockerfile</a>."

3) Sidebar "powiazane" (na wieksze strony):
<aside class="related">
  <h3>Powiazane</h3>
  <a href="...">Link 1</a>
  <a href="...">Link 2</a>
</aside>

REGULY:
- Max 5 cross-refs na rozdzial (wiecej = noise)
- Tylko relevant (czytelnik bedzie chcial po przeczytaniu)
- Z krotkim opisem ("Docker — runtime"), nie sam link
- Wzgledne sciezki (../kategoria/plik.html)
- NIGDY absolute (file:///D:/docs/...)

ANTI-PATTERN: link do innej strony bez wyjasnienia ("zobacz tez X")

Rekomendacja architektury

Maly site (<50 stron)

MiniSearch z embedded JSON index w <script> tag. Zero requests, zero dependencies. Bundle ~10 KB total.

Sredni site (50-500 stron)

Pagefind — build CLI generuje shardowany index, lazy load chunkow per query. Najnowoczesniejsze rozwiazanie 2024-2026, recommended dla wiekszosci.

Duzy site (500+ stron)

Algolia DocSearch (free dla OSS), albo self-hosted Typesense / Meilisearch. Real-time indexing, faceted search, analytics.

Anti-patterns nawigacji

Brak prev/next

Czytelnik konczy rozdzial i nie wie co dalej. Wraca do index. Frustracja. Zawsze prev/next na dole rozdzialu.

Nieaktualne breadcrumbs

"Glowna / Frontend / React" gdy faktycznie jesteamy w "Vue". Build-time scripts to sprawdzaja, ale ludzie copy-paste robia bledy. Auto-generuj.

Search ktory wymaga full reload

Klikasz wynik -> ladowanie 3s. Source: typowe Lunr.js setup. Lekarstwo: fetch + render preview w panel zamiast nawigacji.

Linki absolutne zamiast wzglednych

file:///D:/docs/... dziala lokalnie, nie dziala po deploy na webserver. Zawsze ../kategoria/plik.html.

Workflow: dodanie nowego rozdzialu

  1. Stworz NN-temat.html (kopiuj wzorzec z 01)
  2. Update kategoria-index.html — dodaj wpis w .breadcrumb
  3. Update PREV pliku (NN-1) — zmien link "next" na nowy plik
  4. Update NEXT pliku (NN+1) — zmien link "prev" na nowy plik
  5. Re-build search index (Pagefind: pagefind --site docs)
  6. Test linkow (broken-link-checker, lychee)
  7. Commit + push
