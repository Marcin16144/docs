06. Prompty per architektura i paterny

Wzorce architektoniczne, DDD, CQRS, Clean Architecture, communication patterns, SOLID, GoF.

Filozofia rozdzialow architektonicznych

Architektura to kompromisy, nie best practices. Kazdy wzorzec ma cene. Zamiast "uzywaj microservices" — "kiedy ich rzeczywiscie potrzebujesz, kiedy NIE". Decision trees dominuja. Real-world przypadki z firm (kto migrowa, dlaczego).

Anti-patterns

Distributed monolith

Microservices ktore nie sa niezalezne — zmiana w jednym wymusza redeployment innych. Zlosliwosc gorsza niz monolit (network latency + sztywne sprzezenie).

Anemic domain model

Klasy z samymi properties bez logiki, cala logika w "Service" klasach. Procedural code ubrany w OOP. DDD lekarstwo: rich domain model z metodami biznesowymi w entities/aggregates.

God class / God service

Jedna klasa robi wszystko. SRP violation. Najprostsze drogi powstawania: dodawanie metod gdy "logiczne miejsce" gubi sie. Refactor przez extract class.

Premature microservices

Zacznij od monolitu / modular monolith. Mikroserwisy gdy wymusza skalowanie, niezalezne deploys lub roznorodnosc tech stack. Nie "bo modne".

Decision tree — wzorzec architektoniczny

Liczba inzynierow?
+- 1-5: Monolit (klasyczny lub modular)
+- 5-50: Modular Monolith (preferowane) lub microservices (jesli musisz)
+- 50+: Microservices (z ostroznoscia)

Domena biznesowa zlozona (>20 entities, complex rules)?
+- Tak: DDD tactical patterns + Clean Architecture
+- Nie: Prosta 2-3 warstwowa app (Controller-Service-Repository)

Wymagany audit trail / undo / rebuild state?
+- Tak: Event Sourcing
+- Nie: Stan w DB

Asymetryczny load (czesty read, rzadki write)?
+- Tak: CQRS (oddziel read i write models)
+- Nie: Single model

Real-time updates do klienta?
+- WebSocket / SignalR (full-duplex)
+- SSE (server-to-client only, prostszy)

Communication miedzy serwisami?
+- Synchroniczne CRUD: REST / gRPC
+- Asynchroniczne events: Kafka / RabbitMQ / NATS
+- Browser-friendly: REST / GraphQL
