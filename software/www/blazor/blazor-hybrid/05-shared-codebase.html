Shared codebase Blazor Hybrid

RazorClassLibrary, conditional compilation, platform-specific implementations, MVVM

Cel: jeden kod — wiele platform

Pisanie aplikacji Blazor Server + WASM + MAUI z osobnymi codebases to ogromna duplikacja. Idealnie 80-90% kodu (komponenty UI, biznes-logic, models) ma byc wspolne, a tylko 10-20% (specyficzne dla platformy) per app.

Architektura solution

MyApp.sln
├── MyApp.Shared/              # Class library (modele, DTOs, interfaces)
├── MyApp.Components/          # RazorClassLibrary (Blazor komponenty)
├── MyApp.BusinessLogic/       # Class library (services, validators)
├── MyApp.Web.Server/          # ASP.NET Core (Blazor Server / United)
├── MyApp.Web.Client/          # Blazor WASM (interactive)
├── MyApp.Maui/                # Blazor MAUI (mobile + desktop)
├── MyApp.Wpf/                 # Blazor WPF (Windows desktop)
└── MyApp.Tests/               # Unit + integration tests

Conditional compilation (#if)

Aby ten sam kod sluzyl w wielu projektach, ale rozni sie w detalach — uzywasz preprocessor directives.

public class FileService
{
    public string GetPath(string filename)
    {
#if MAUI
        return Path.Combine(FileSystem.AppDataDirectory, filename);
#elif WINDOWS_DESKTOP
        return Path.Combine(
            Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
            "MyApp", filename);
#else
        return filename;
#endif
    }
}

W .csproj:

<PropertyGroup Condition="'$(TargetFramework)' == 'net9.0-android' OR '$(TargetFramework)' == 'net9.0-ios'">
  <DefineConstants>$(DefineConstants);MAUI</DefineConstants>
</PropertyGroup>

Interface-based abstraction

Czystszy pattern niz #if — wszedzie interfejsem, implementacja per platforma.

// Shared
public interface IStorageService
{
    Task SaveAsync(string key, string value);
    Task<string?> LoadAsync(string key);
}
// Web (WASM/Server)
public class WebStorageService : IStorageService
{
    private readonly ILocalStorageService localStorage;

    public Task SaveAsync(string key, string value) => localStorage.SetItemAsync(key, value);
    public Task<string?> LoadAsync(string key) => localStorage.GetItemAsync<string>(key);
}
// MAUI
public class MauiStorageService : IStorageService
{
    public Task SaveAsync(string key, string value) => Preferences.Default.Set(key, value);
    public Task<string?> LoadAsync(string key) => Task.FromResult(Preferences.Default.Get(key, ""));
}

MVVM patterns dla hybrid

MVVM (Model-View-ViewModel) pozwala oddzielic logike UI od widoku — widok moze byc Blazor (.razor), XAML lub inny.

// ViewModel (shared)
public partial class ProductListViewModel : ObservableObject
{
    [ObservableProperty]
    private List<Product> products = new();

    [ObservableProperty]
    private bool isLoading;

    [RelayCommand]
    private async Task LoadAsync()
    {
        IsLoading = true;
        try
        {
            Products = await api.GetAllAsync();
        }
        finally
        {
            IsLoading = false;
        }
    }
}
// View w Blazor
@inject ProductListViewModel ViewModel

@if (ViewModel.IsLoading)
{
    <p>Ladowanie...</p>
}
else
{
    <ul>
    @foreach (var p in ViewModel.Products)
    {
        <li>@p.Name</li>
    }
    </ul>
}

<button @onclick="ViewModel.LoadCommand.ExecuteAsync">Odswiez</button>

Pakiet CommunityToolkit.Mvvm generuje boilerplate (PropertyChanged, RelayCommand) automatycznie.

Sharing JS

// MyApp.Components/wwwroot/js/helpers.js
export function copyToClipboard(text) {
    return navigator.clipboard.writeText(text);
}
// W komponencie
@inject IJSRuntime JS

@code {
    private async Task Copy(string text)
    {
        var module = await JS.InvokeAsync<IJSObjectReference>(
            "import", "./_content/MyApp.Components/js/helpers.js");
        await module.InvokeVoidAsync("copyToClipboard", text);
    }
}

Dependency Injection patterns

Wspolny AddMyApp extension method:

// MyApp.Components/ServiceCollectionExtensions.cs
public static class ServiceCollectionExtensions
{
    public static IServiceCollection AddMyAppCore(this IServiceCollection services)
    {
        services.AddScoped<IProductService, ProductService>();
        services.AddScoped<ICartService, CartService>();
        services.AddSingleton<ProductCache>();
        return services;
    }
}
// W kazdej aplikacji
services.AddMyAppCore();
services.AddSingleton<IStorageService, WebStorageService>(); // platform-specific

Testowanie wspolnego kodu

Reuse testow dla calej logic. Komponenty Blazor mozna testowac z bUnit:

// MyApp.Tests
[Test]
public void ProductCard_Renders()
{
    using var ctx = new TestContext();
    ctx.Services.AddSingleton<IProductService, FakeProductService>();

    var cut = ctx.RenderComponent<ProductCard>(ps => ps
        .Add(p => p.Product, new Product { Name = "Test", Price = 99 })
    );

    cut.Find("h3").TextContent.Should().Be("Test");
    cut.Find(".price").TextContent.Should().Contain("99");
}

Common pitfalls

  • Tight coupling do platform APIs — uzywaj zawsze interface
  • JS Interop w shared lib — nie dziala w MAUI tak samo jak w WASM
  • Routing — @page w shared lib dziala, ale moze konfliktowac z aplikacja-specific routes
  • Auth — AuthenticationStateProvider rozni sie miedzy WASM, Server, MAUI
  • HttpClient — w MAUI default zachowanie cookies inne niz w WASM

Werdykt

Najlepsza strategia 2026: RazorClassLibrary + interface-based DI. Stworz fundament jako class library, implementuj platform-specific services per app. Reuse ~85% kodu, w tym wszystkie komponenty UI. Dodatkowo MVVM z CommunityToolkit.Mvvm dla view-models.
