Wydajnosc Blazor Server

Latency budget, render batching, JS interop minimalization, prerendering

Gdzie tracimy czas?

W Blazor Server kazda interakcja UI jest round-tripem przez SignalR. Czas na klik to:

FazaCzas (typowy)
Klik — klient wysyla event0 ms
Network up20-100 ms (zalezne od lokalizacji)
Server processing (event handler)1-10 ms
Render diff calculation1-5 ms
Network down (diff)20-100 ms
Client DOM patch1-5 ms
Total~50-220 ms

Latency budget

Dla "feel of native", interakcja powinna konczyc sie w 100 ms. To znaczy:

  • Server EU + klient EU: 50-80 ms (dobra)
  • Server US + klient EU: 150-200 ms (granica)
  • Server US + klient Asia: 300+ ms (zla)

Stad rekomendacja: serwer w tym samym regionie co uzytkownicy. Geo-routing dla globalnej publicznosci.

Render batching

Blazor inteligentnie laczy multiple StateHasChanged w jeden render. Mozesz to wymusic:

private async Task LoadAndUpdate()
{
    isLoading = true;
    StateHasChanged(); // pokaz spinner

    var data = await api.LoadAsync();

    isLoading = false;
    items = data;
    // automatyczny re-render po await
}

Manualne kontrolowanie ShouldRender

private string oldValue = "";

protected override bool ShouldRender()
{
    if (currentValue == oldValue) return false; // skip render
    oldValue = currentValue;
    return true;
}

Virtualization — duze listy

Dla list 100+ items uzywaj <Virtualize>:

<Virtualize Items="@products" Context="product" ItemSize="50" OverscanCount="3">
    <ProductRow Product="@product" />
</Virtualize>

Renderuje tylko widoczne wiersze. 10000 wierszy — renderuje ~20.

Z server-side data

<Virtualize ItemsProvider="LoadItems" Context="item">
    <ItemTemplate>
        <ProductRow Product="@item" />
    </ItemTemplate>
    <Placeholder>
        <p>Ladowanie...</p>
    </Placeholder>
</Virtualize>

@code {
    private async ValueTask<ItemsProviderResult<Product>> LoadItems(ItemsProviderRequest req)
    {
        var items = await api.GetPagedAsync(req.StartIndex, req.Count);
        var total = await api.GetTotalCountAsync();
        return new ItemsProviderResult<Product>(items, total);
    }
}

Minimalizacja JS interop

Kazdy JS.InvokeAsync w Blazor Server to oddzielny round trip przez SignalR. Drogie dla loop:

// ZLE: 100 round-tripow
foreach (var item in items)
{
    await JS.InvokeVoidAsync("doSomething", item);
}

// DOBRZE: jeden batch
await JS.InvokeVoidAsync("doManyThings", items.ToArray());

Prerendering — szybsze pierwsze ladowanie

W Blazor United (.NET 8/9) komponenty mozna prerenderowac — serwer wysyla kompletny HTML, dopiero potem hydratuje. To poprawia LCP i SEO.

<Counter @rendermode="@(new InteractiveServerRenderMode(prerender: true))" />

Persistent state

Aby uniknac double-fetch po prerender:

@inject PersistentComponentState State

@code {
    private List<Product>? products;

    protected override async Task OnInitializedAsync()
    {
        if (!State.TryTakeFromJson<List<Product>>("products", out products))
            products = await api.GetAllAsync();

        State.RegisterOnPersisting(() =>
        {
            State.PersistAsJson("products", products);
            return Task.CompletedTask;
        });
    }
}

Database — oszczedzaj zapytania

Po renderze komponentu, kazdy refresh wywoluje OnInitialized... Jesli dolaczasz EF Core, mozesz zalac DB.

Wzor — cache w-pamieci dla wybranych zapytan

builder.Services.AddMemoryCache();

// Service
public async Task<List<Category>> GetCategoriesAsync()
{
    return await cache.GetOrCreateAsync("categories", async entry =>
    {
        entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(15);
        return await db.Categories.ToListAsync();
    }) ?? new();
}

Connection: WebSocket vs Long Polling

WebSocket jest 5-10x szybszy niz long polling. Upewnij sie ze:

  • HTTPS dziala (WebSocket nad ssl =wss)
  • Reverse proxy nie psuje upgrade headers
  • Firewall nie blokuje WebSocket (port 443 OK na ogol)

Best practices summary

  • Server jak najblizej uzytkownikow
  • WebSocket aktywny (sprawdz w prod)
  • Virtualize dla list 100+
  • Cache zapytan, ktore sie nie zmieniaja czesto
  • Batchuj JS interop calls
  • Profile w devtools / Application Insights
  • Limity circuit memory
  • HTTP/2 (lub HTTP/3) dla statycznych zasobow
  • Brotli/Gzip compression dla CSS/JS

Cel performansowy

Aplikacja Blazor Server z lokalnym serwerem powinna miec:

  • First render: <500 ms
  • Klik latency p50: <80 ms
  • Klik latency p95: <200 ms
  • Memory per circuit: <5 MB
  • 0 JS errors w devtools
