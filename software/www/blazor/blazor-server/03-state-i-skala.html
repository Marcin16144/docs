State i skala Blazor Server

Sticky sessions, Azure SignalR Service, Redis backplane, scaling out

Problem skalowania

Blazor Server jest stateful — circuit z wszystkimi danymi uzytkownika zyje na jednym konkretnym serwerze. To stwarza wyzwania dla skali:

  • Nie mozesz po prostu rownowazyc uzytkownikow round-robin (ten sam user musi wracac na ten sam serwer)
  • Pamiec rosnie liniowo z liczba uzytkownikow
  • Restart serwera = utrata stanu wszystkich aktywnych circuits
  • Disconnect = bledne UX dla wszystkich uzytkownikow tej maszyny

Sticky sessions

Sticky session (session affinity) — load balancer kieruje requesty od tego samego klienta zawsze na ten sam backend. To jest obowiazkowe dla Blazor Server scaled out.

Nginx

upstream blazor_app {
    ip_hash;  # sticky based on IP
    server backend1.example.com;
    server backend2.example.com;
    server backend3.example.com;
}

server {
    listen 443 ssl;
    server_name app.example.com;

    location / {
        proxy_pass http://blazor_app;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_cache_bypass $http_upgrade;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

Azure App Service

Domyslnie Azure App Service uzywa ARRAffinity cookie dla session affinity. Wlaczone domyslnie, ale mozesz zweryfikowac:

az webapp update --client-affinity-enabled true --name myapp

Kubernetes

apiVersion: v1
kind: Service
spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800

Azure SignalR Service

Managed SignalR od Microsoftu. Odciaza serwer aplikacji od trzymania WebSocket connections — backbone do hostowania, ale sam circuit i state nadal zyja na app server.

// Program.cs
builder.Services.AddSignalR()
    .AddAzureSignalR(builder.Configuration["Azure:SignalR:ConnectionString"]);

builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents();

Korzysci

  • Auto-scaling do milionow polaczen
  • Globalne polaczenie (CDN-like dla SignalR)
  • App server moze sie restartowac — SignalR Service trzyma queue
  • Rozliczanie per "unit" (~1000 polaczen / unit)

Redis backplane

Alternatywa dla Azure SignalR — uzywanie Redis do publish/subscribe miedzy serwerami SignalR. Wymaga sticky sessions (Redis NIE rozwiazuje problemu state per circuit).

builder.Services.AddSignalR()
    .AddStackExchangeRedis(builder.Configuration["Redis:ConnectionString"]);

Uzytek: gdy masz wlasna Redis na infra i nie chcesz placic za Azure SignalR.

Scaling out scenarios

Scenario 1: Mala aplikacja (do 1000 users)

  • Pojedynczy serwer (np. Azure App Service S1)
  • Brak scaling out potrzebny
  • ~4 GB RAM wystarczy

Scenario 2: Srednia (1000-10000 users)

  • 2-4 instancje aplikacji
  • Sticky sessions wymagane
  • Azure SignalR Service zalecane (lub Redis backplane)
  • Database za connection pool

Scenario 3: Duza (10000+ users)

  • Premium SignalR Service
  • Wieloregionalne deployment z geo-routing
  • Specjalna optymalizacja memory per circuit
  • Pre-warming, blue-green deployment
  • Rozwazenie migracji wybranych komponentow do WASM (mniej obciazenia serwera)

Optymalizacja memory

OwningComponentBase dla DbContext

@inherits OwningComponentBase<AppDbContext>

@code {
    protected override async Task OnInitializedAsync()
    {
        // Service rozpoczyna scope dedykowany dla tego komponentu
        var data = await Service.Products.ToListAsync();
    }
}

Komponent ma wlasny scope DI, dispose przy unmount — eliminuje long-lived DbContext per circuit (memory leak risk).

Virtualization dla list

<Virtualize Items="@products" Context="product" ItemSize="50">
    <ProductRow Product="@product" />
</Virtualize>

Renderuje tylko widoczne wiersze — oszczedza pamiec na duzych listach (10000+ items).

Lazy loading komponentow

@if (showAdvanced)
{
    <AdvancedSettings />
}

Nie tworz drzewa zanim go uzytkownik nie zazada.

Hostowanie wieloregionalne

Dla globalnej publicznosci najlepiej miec serwery w wielu regionach. Klient laczy z najblizszym — Traffic Manager / Front Door routuje na podstawie geo lub latency.

app.example.com (Front Door / Traffic Manager)
  +-- eu.app.example.com -> serwer w Amsterdam
  +-- us.app.example.com -> serwer w Virginia
  +-- asia.app.example.com -> serwer w Singapore

Wada: kazdy region ma wlasna baze (replication delay) lub jedna globalna baza (cross-region latency).

Werdykt

Blazor Server skaluje sie ladnie do kilku tysiecy uzytkownikow z Azure SignalR Service. Powyzej 10000 musisz powaznie zastanowic sie, czy nie lepiej Blazor WASM (autonomiczny klient) lub Blazor United (mix per komponent). Public-facing duza aplikacja czesto lepiej dziala w WASM.
