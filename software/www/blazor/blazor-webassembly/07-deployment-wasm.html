Deployment Blazor WASM

Static hosting (Azure SWA, Netlify, Vercel, S3+CloudFront), CDN, kompresja, environment

Kluczowa zaleta WASM — static hosting

Blazor WASM po publish to statyczne pliki. Mozesz hostowac go na dowolnym hostingu, ktory podaje pliki HTML/JS/WASM. Nie potrzeba serwera .NET, nie ma sticky sessions, brak persistent connections.

Publishing

# Standardowa publikacja
dotnet publish -c Release -o publish

# Wynik: publish/wwwroot zawiera caly content do hosting
ls publish/wwwroot/
# index.html
# _framework/    (mono runtime, dlls)
# css/
# js/
# manifest.json
# service-worker.js

Azure Static Web Apps

Najszybszy wybor dla Blazor WASM — tier free, integracja z GitHub Actions, custom domains, identity providers.

Setup z Azure Portal

  1. Create resource -> Static Web App
  2. Polacz z GitHub repo
  3. Wybierz "Blazor" preset
  4. Build: app_location=/, output=wwwroot
  5. Azure auto-tworzy GitHub Action

GitHub Action workflow

name: Azure Static Web Apps CI/CD

on:
  push:
    branches: [main]

jobs:
  build_and_deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          submodules: true
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '9.0'
      - run: dotnet publish -c Release -o release
      - uses: Azure/static-web-apps-deploy@v1
        with:
          azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
          repo_token: ${{ secrets.GITHUB_TOKEN }}
          action: "upload"
          app_location: "/"
          api_location: ""
          output_location: "release/wwwroot"

staticwebapp.config.json

{
  "navigationFallback": {
    "rewrite": "/index.html",
    "exclude": ["/_framework/*", "/css/*", "/js/*"]
  },
  "globalHeaders": {
    "Cache-Control": "no-cache, no-store, must-revalidate"
  },
  "routes": [
    {
      "route": "/_framework/*",
      "headers": {
        "Cache-Control": "public, max-age=31536000, immutable"
      }
    }
  ],
  "mimeTypes": {
    ".wasm": "application/wasm",
    ".dll": "application/octet-stream"
  }
}

Netlify

Najpopularniejszy darmowy hosting dla statycznych SPA.

netlify.toml

[build]
  command = "dotnet publish -c Release -o output"
  publish = "output/wwwroot"

[build.environment]
  DOTNET_VERSION = "9.0"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

[[headers]]
  for = "/_framework/*"
    [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

[[headers]]
  for = "/index.html"
    [headers.values]
    Cache-Control = "no-cache, no-store, must-revalidate"

AWS S3 + CloudFront

S3 bucket setup

aws s3 mb s3://my-blazor-app
aws s3 sync publish/wwwroot/ s3://my-blazor-app/ --delete
aws s3 website s3://my-blazor-app/ --index-document index.html --error-document index.html

CloudFront distribution

  1. Origin: S3 bucket (use OAC, nie public access)
  2. Behaviors:
    • /_framework/* -> cache 1 year
    • /* -> cache none, redirect 404 to index.html
  3. Viewer protocol: HTTPS only (redirect HTTP)
  4. HTTP/2 i HTTP/3 enabled
  5. Compression: enabled (auto-brotli)

CloudFront Function dla SPA fallback

function handler(event) {
    var request = event.request;
    var uri = request.uri;

    // Czy request to plik (.dll, .wasm, .png, etc.)?
    if (uri.includes('.')) return request;

    // Inaczej -> index.html
    request.uri = '/index.html';
    return request;
}

GitHub Pages

Mozliwy, ale wymaga workaround dla SPA routing (nie ma server-side fallback).

# .github/workflows/deploy.yml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
      - run: dotnet publish -c Release -o publish
      - run: cp publish/wwwroot/index.html publish/wwwroot/404.html # SPA fallback
      - run: |
          # Update base href
          sed -i 's|<base href="/"|<base href="/${{ github.event.repository.name }}/"|g' \
            publish/wwwroot/index.html
      - uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./publish/wwwroot

Cloudflare Pages

Darmowy, szybki, CDN globalny. Build automatycznie z GitHub.

# Build settings
Framework: None
Build command: dotnet publish -c Release -o output
Build output directory: output/wwwroot
Environment variables:
  DOTNET_VERSION = 9.0

Wlasny nginx / Apache

nginx

server {
    listen 443 ssl http2;
    server_name app.example.com;
    root /var/www/myapp/wwwroot;

    # MIME types dla WASM
    types {
        application/wasm wasm;
        application/octet-stream dll pdb;
        text/cache-manifest manifest;
    }

    # SPA fallback
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Cache framework agressywnie
    location /_framework/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        gzip_static on;
        brotli_static on;
    }

    # Index.html bez cache
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # Brotli i gzip
    gzip on;
    gzip_types application/wasm application/octet-stream text/css application/javascript;

    brotli on;
    brotli_types application/wasm application/octet-stream text/css application/javascript;
    brotli_comp_level 11;
}

Compression headers

Blazor publish generuje pliki .gz i .br. Server musi je serwowac kiedy klient wspiera (Accept-Encoding header).

Cache strategy — szczegoly

PlikCache header
index.htmlno-cache
service-worker.jsno-cache
_framework/*.dll, *.wasmmax-age=31536000, immutable
_framework/blazor.boot.jsonno-cache (zmienia sie z deployem)
css/*.css, js/*.jsmax-age=86400
manifest.jsonmax-age=86400

appsettings.json files

Po publish wszystkie pliki appsettings.*.json ida do wwwroot. Dla rozdzielenia env w prod, nadpisz przy build:

# GitHub Actions
- run: |
    cp environments/prod/appsettings.json publish/wwwroot/
    dotnet publish -c Release -o publish

Pre-deployment checklist

  • HTTPS only (z HSTS)
  • SPA fallback na 404 -> index.html
  • Cache headers prawidlowo (immutable dla _framework)
  • Brotli/Gzip wlaczone
  • MIME type .wasm = application/wasm
  • CSP header (jesli mozliwe)
  • Manifest.json link w head
  • Apple-touch-icon dla iOS
  • Open Graph metadata dla SEO
  • Health check endpoint w API

Monitoring

Aplikacja WASM zyje w przegladarce — trudniej monitorowac niz server. Opcje:

  • Application Insights — client-side telemetry przez JS SDK
  • Sentry — error tracking z source maps
  • LogRocket / FullStory — session replay
  • Real User Monitoring (RUM) — Cloudflare, Datadog
// js
window.appInsights = new ApplicationInsights({
    config: { instrumentationKey: 'KEY' }
});
appInsights.loadAppInsights();
appInsights.trackPageView();
