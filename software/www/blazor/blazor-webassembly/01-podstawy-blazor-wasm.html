Podstawy Blazor WebAssembly

WebAssembly basics, .NET runtime w przegladarce, hosting statyczny

Czym jest WebAssembly?

WebAssembly (WASM) to standard przegladarkowy — binarny format kodu wykonywany w sandboxie obok JavaScript. Powstal z myslen o jezykach takich jak C, C++, Rust — ale .NET runtime tez dziala w WASM.

Architektura Blazor WASM

W Blazor WebAssembly:

  1. Przegladarka pobiera mono runtime (~2 MB skompresowane)
  2. Runtime startuje i ladowa pliki .dll z aplikacji
  3. Aplikacja wykonuje sie cala w przegladarce — brak serwera potrzebnego po starcie
  4. HTTP calls ida do dowolnego API (CORS-aware)
  5. UI updates sa lokalne — brak round-tripow

Plusy i minusy

Plusy

  • Aplikacja jest statyczna — hostuj na CDN, S3, Netlify, GitHub Pages
  • Niska latencja (UI lokalne)
  • Dziala offline (po pobraniu)
  • Skaluje sie do milionow uzytkownikow (brak serwera state)
  • Brak wymagan WebSocket / sticky sessions
  • Pelny C# w przegladarce — LINQ, Tasks, JsonSerializer

Minusy

  • Duzy bundle — runtime ~2 MB + dlls (typowo 4-8 MB total skompresowane)
  • Wolniejsze pierwsze ladowanie niz Blazor Server
  • Kod aplikacji idzie do klienta — wrazliwa logika musi byc w API
  • Wolniejsza wykonanie niz natywne JS (~2-5x dla typowych operacji)
  • Brak dostepu do server-only API (musisz stworzyc REST API)

Program.cs (WASM)

var builder = WebAssemblyHostBuilder.CreateDefault(args);
builder.RootComponents.Add<App>("#app");
builder.RootComponents.Add<HeadOutlet>("head::after");

builder.Services.AddScoped(sp => new HttpClient
{
    BaseAddress = new Uri(builder.HostEnvironment.BaseAddress)
});

await builder.Build().RunAsync();

Hosting

Statyczny hosting

Po publish dostajesz folder wwwroot ze wszystkim potrzebnym. Mozesz wgrac na:

  • Azure Static Web Apps (free tier)
  • Netlify (free)
  • Vercel
  • GitHub Pages (z workaround dla SPA)
  • AWS S3 + CloudFront
  • Cloudflare Pages
  • Wlasny nginx / Apache / IIS
dotnet publish -c Release -o publish
# Upload publish/wwwroot na CDN/S3/Netlify

nginx config

server {
    listen 443 ssl;
    server_name app.example.com;
    root /var/www/myapp/wwwroot;

    location / {
        try_files $uri $uri/ /index.html;
    }

    # Cache .dll, .wasm
    location ~* \.(dll|wasm|pdb|js|css)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        gzip_static on;
    }

    # MIME types
    types {
        application/wasm wasm;
        application/octet-stream dll;
    }
}

Pierwsze ladowanie — co sie dzieje

  1. Przegladarka pobiera index.html (~5 KB)
  2. Pobiera blazor.webassembly.js (~80 KB)
  3. Pobiera dotnet.wasm i dotnet.runtime.js (~2 MB)
  4. Pobiera dlls aplikacji (~5-10 MB skompresowane)
  5. Mono runtime startuje, JIT kompiluje, aplikacja wystartowala

Total typowo: 3-10 sekund na slabym mobile, 1-2 sekundy na desktop.

Komunikacja z API

// Service
public class ProductService
{
    private readonly HttpClient http;

    public ProductService(HttpClient http)
    {
        this.http = http;
    }

    public async Task<List<Product>> GetAllAsync()
    {
        return await http.GetFromJsonAsync<List<Product>>("api/products") ?? new();
    }

    public async Task<Product> CreateAsync(Product product)
    {
        var res = await http.PostAsJsonAsync("api/products", product);
        return await res.Content.ReadFromJsonAsync<Product>() ?? product;
    }
}

Hosted vs standalone

ModeCharakterystyka

StandaloneSam WASM client, API jest gdzie indziej (Node.js, Python, etc).

PWA — Progressive Web App

Blazor WASM ma wbudowany support dla PWA:

dotnet new blazorwasm --pwa

Generuje service-worker.js, manifest.json — aplikacja moze byc instalowana, dziala offline.

Kiedy wybrac Blazor WASM?

  • Public-facing aplikacje (mobile, masowi uzytkownicy)
  • Aplikacje, ktore musza dzialac offline
  • Hosting na CDN / static hosting (taniej niz server)
  • Multi-region distribution
  • Wysoka odpornosc na disconnects
  • Aplikacje typu SPA z ciezka interaktywnoscia (drawing apps, editors)

Kiedy NIE wybrac WASM?

  • Pierwsze ladowanie ma byc <1s — uzyj Blazor Server lub United
  • Wymagana ochrona kodu — cala logika idzie do klienta
  • Wymaga real-time push z servera — uzyj SignalR client
  • Heavy compute — WASM jest 2-5x wolniejszy niz natywne

Tipy dla rozpoczecia

  • Zaczynaj od --hosted jesli backend tez piszesz w .NET
  • Wlacz Brotli compression w hostingu (3x mniejsze pliki)
  • Cache headers immutable dla .dll i .wasm
  • Cache busting przez ?v={version} dla index.html
  • Service worker dla offline — setup PWA
