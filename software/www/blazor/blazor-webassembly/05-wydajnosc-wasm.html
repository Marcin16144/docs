SIMD — Single Instruction Multiple Data

WASM od 2021 wspiera SIMD — rownolegle operacje wektorowe na 128-bit lanes. Idealne dla matematyki wektorowej, image processing, kryptografii.

<PropertyGroup>
  <WasmEnableSIMD>true</WasmEnableSIMD>
</PropertyGroup>
using System.Numerics;

public static Vector<float> FastSum(float[] a, float[] b)
{
    var va = new Vector<float>(a);
    var vb = new Vector<float>(b);
    return va + vb; // SIMD pod spodem
}

Daje 2-4x speedup dla mathematic-heavy kodu. Wymaga przegladarki z SIMD support (Chrome 91+, Firefox 89+, Safari 16+).

Multi-threading (Web Workers)

WASM od Webo Workers moze uzywac wielu watkow. Standardowe Tasks oraz System.Threading.Thread beda dzialac w workerach.

<PropertyGroup>
  <WasmEnableThreads>true</WasmEnableThreads>
</PropertyGroup>

Wymagania (z powodu Spectre/Meltdown mitigations):

  • Strona musi byc cross-origin isolated
  • Headery: Cross-Origin-Embedder-Policy: require-corp, Cross-Origin-Opener-Policy: same-origin
  • Wymaga HTTPS
// nginx
add_header Cross-Origin-Embedder-Policy require-corp;
add_header Cross-Origin-Opener-Policy same-origin;
// Uzycie watkow w C#
var task = Task.Run(() =>
{
    return ComputeHeavyJob(data);
});

await task; // wykonane na osobnym watku/workerze

Memory management

GC pressure

WASM ma swojego GC (mono GC), ktory pauzuje aplikacje. Aby unikac:

  • Reuse buforow zamiast tworzyc nowe (np. ArrayPool<T>)
  • Uzywaj Span<T> dla rozkroju tablic bez alokacji
  • Streamuj duze pliki zamiast trzymac w pamieci
  • Dispose IDisposable w odpowiednim czasie
// Zle: alokuje na kazdym wywolaniu
public string Format(int[] numbers)
{
    var sb = new StringBuilder();
    foreach (var n in numbers) sb.AppendLine(n.ToString());
    return sb.ToString();
}

// Lepiej: uzyj zerowej alokacji
public void FormatToWriter(int[] numbers, TextWriter writer)
{
    Span<char> buffer = stackalloc char[16];
    foreach (var n in numbers)
    {
        n.TryFormat(buffer, out var written);
        writer.Write(buffer.Slice(0, written));
        writer.WriteLine();
    }
}

Memory limits

Mono runtime w przegladarce ma limit ~2 GB heap. Dla wiekszosci aplikacji to duzo, ale operuj na duzych datasets z streamingiem.

Virtualization dla list

<Virtualize Items="@products" Context="product" ItemSize="50">
    <ProductRow Product="@product" />
</Virtualize>

Renderuje tylko widoczne wiersze. Dla 10000 wierszy 10x szybsze niz pelny render.

Reduce render frequency

// W rapidnym Timer pobieraniu danych:
private System.Timers.Timer? timer;
private DateTime lastRender = DateTime.MinValue;

protected override void OnInitialized()
{
    timer = new System.Timers.Timer(50); // co 50 ms
    timer.Elapsed += async (s, e) =>
    {
        UpdateData();

        // Limit do max 10 fps
        if (DateTime.UtcNow - lastRender > TimeSpan.FromMilliseconds(100))
        {
            lastRender = DateTime.UtcNow;
            await InvokeAsync(StateHasChanged);
        }
    };
    timer.Start();
}

HttpClient pooling

Reuse HttpClient instances — nie twórz nowego HttpClient na kazda operacje.

// Zle
var client = new HttpClient(); // alokuje, slow
var data = await client.GetStringAsync("api/...");

// Dobrze
@inject HttpClient Http
var data = await Http.GetStringAsync("api/...");

Optymalizacja JSON

System.Text.Json jest szybki, ale mozesz go jeszcze poprawic:

// 1. Source-generated serializers (no reflection, AOT-friendly)
[JsonSerializable(typeof(Product))]
[JsonSerializable(typeof(List<Product>))]
internal partial class AppJsonContext : JsonSerializerContext { }

// 2. Uzycie
var products = JsonSerializer.Deserialize(json, AppJsonContext.Default.ListProduct);

Lazy loading komponentow

Komponenty i assemblies dla nich pobierane na zadanie:

<ItemGroup>
  <BlazorWebAssemblyLazyLoad Include="Charts.dll" />
</ItemGroup>
// Routes.razor
<Router AppAssembly="@typeof(App).Assembly"
        OnNavigateAsync="OnNavigateAsync"
        AdditionalAssemblies="@lazyLoadedAssemblies">
</Router>

@code {
    private List<Assembly> lazyLoadedAssemblies = new();

    private async Task OnNavigateAsync(NavigationContext args)
    {
        if (args.Path.StartsWith("charts"))
        {
            var assemblies = await Loader.LoadAssembliesAsync(new[] { "Charts.dll" });
            lazyLoadedAssemblies.AddRange(assemblies);
        }
    }
}

Best practices summary

  • Wlaczone PublishTrimmed
  • Brotli compression
  • Cache headers immutable
  • Virtualize dla list 100+
  • HttpClient z DI (nie new)
  • Source-generated JSON serializers
  • SIMD dla matematyki
  • Threading dla heavy compute (jesli serwujesz cross-origin isolated)
  • Lazy loading dla rzadko uzywanych feature
  • Profile w DevTools przed optymalizacja (premature opt = zlo)
