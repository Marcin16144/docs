Trimming — usuwanie nieuzywanego kodu

IL Trimmer (znany jako IL Linker) analizuje kod i usuwa niedostepne metody, klasy, assemblies. Wlaczone domyslnie w Release.

<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <TrimMode>link</TrimMode>
</PropertyGroup>

Typowo redukuje 3-5x. Uwaga: niektore biblioteki uzywaja reflection — trzeba dodac TrimmerRoot:

<ItemGroup>
  <TrimmerRootAssembly Include="MyLibrary" />
</ItemGroup>

Brotli compression

Brotli daje 20-30% lepsza kompresje niz Gzip dla tekstowych zasobow. Blazor publish generuje pliki .br obok .dll i .wasm:

publish/wwwroot/_framework/
  System.Text.Json.dll       (1.2 MB)
  System.Text.Json.dll.gz    (400 KB)
  System.Text.Json.dll.br    (320 KB)

Nginx

brotli on;
brotli_static on;
brotli_types application/wasm application/dll text/css application/javascript;
brotli_comp_level 11;

Lazy loading assemblies

Mozesz oznaczyc niektore assemblies jako lazy — pobiora sie dopiero przy navigacji do strony, ktora ich uzywa.

<ItemGroup>
  <BlazorWebAssemblyLazyLoad Include="HeavyFeature.Charts.dll" />
  <BlazorWebAssemblyLazyLoad Include="HeavyFeature.PdfGenerator.dll" />
</ItemGroup>
// W komponencie
@inject LazyAssemblyLoader Loader

@code {
    protected override async Task OnInitializedAsync()
    {
        var assemblies = await Loader.LoadAssembliesAsync(new[]
        {
            "HeavyFeature.Charts.dll",
            "HeavyFeature.PdfGenerator.dll"
        });
    }
}

Idealne dla feature-rich admin paneli, gdzie wiekszosc uzytkownikow nie odwiedza wszystkich sekcji.

AOT vs IL Linker (interpreted)

IL Linker (default)

  • Mono runtime interpretuje IL bytecode
  • Rozmiar: ~5-10 MB skompresowane
  • Szybkosc: bazowa — "OK" dla typowych aplikacji UI

AOT (Ahead-Of-Time)

  • Kompilacja IL do natywnego WASM przed uruchomieniem
  • Rozmiar: 5x wiekszy niz IL Linker (typowo 25 MB skompresowane)
  • Szybkosc: 2-10x szybsza dla CPU-bound zadan
  • Idealne dla heavy compute (gry, obliczenia, algorytmy)
  • Niewydajne dla typowych UI — tradeoff size/speed nie warto
<PropertyGroup>
  <RunAOTCompilation>true</RunAOTCompilation>
  <PublishTrimmed>true</PublishTrimmed>
</PropertyGroup>

Kiedy AOT?

  • Gry w przegladarce (engine, fizyka)
  • Obrobka grafiki / wideo
  • Algorytmy szyfrowania, kompresji
  • Heavy linear algebra
  • Symulacje, ML inference

Dla typowej aplikacji biznesowej (CRUD, dashboard) NIE wlaczaj AOT — user czeka 5x dluzej na pierwsze ladowanie dla minimalnego ulepszenia UI.

Cache strategies

Cache busting

Pliki aplikacji maja immutable cache z hashed name. Tylko index.html i service-worker.js wymagaja krotkich cache.

# nginx
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}
location ~* \.(dll|wasm|pdb)$ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}

Service worker dla offline

// service-worker.published.js
self.addEventListener('install', e =>
{
    e.waitUntil(caches.open('blazor-cache').then(cache =>
        cache.addAll([
            '/',
            '/_framework/blazor.webassembly.js',
            // ... auto-generated lista
        ])
    ));
});

self.addEventListener('fetch', e =>
{
    e.respondWith(caches.match(e.request).then(r => r || fetch(e.request)));
});

Pre-rendering

W trybie hosted mozesz prerenderowac WASM aplikacje — serwer wysyla statyczny HTML, potem WASM "ozywia". Ulatwia LCP i SEO.

// Hosted Server Program.cs
app.MapFallbackToFile("index.html"); // standalone
// vs
app.MapRazorComponents<App>()
    .AddInteractiveWebAssemblyRenderMode(); // prerender

Practical optimization checklist

  • Wlaczone PublishTrimmed (default w Release)
  • Brotli compression na serwerze
  • Cache-Control immutable dla _framework
  • Lazy load duzych feature dlls (charts, PDF, etc.)
  • NIE wlaczaj AOT bez powodu
  • Usun nieuzywane NuGet packages
  • Bundle analyzer aby zidentyfikowac heavy deps
  • HTTP/2 lub HTTP/3 dla parallelnego pobierania plikow
  • CDN przed serwerem (CloudFlare, CloudFront)
