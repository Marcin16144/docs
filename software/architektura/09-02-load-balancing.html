Load Balancing

Algorytmy rozkladania ruchu, health checks, session affinity, L4 vs L7, auto-scaling.

L7 routing:
  /api/*     → backend-pool
  /static/*  → cdn-pool
  /ws/*      → websocket-pool

Algorytmy

Round Robin

Kolejne requesty do kolejnych serwerow w kolko. Prosty, rownomierny, ale nie uwzglednia obciazenia.

Weighted Round Robin

Serwer A: waga 5 (mocny)   → 50% ruchu
Serwer B: waga 3 (sredni)  → 30% ruchu
Serwer C: waga 2 (slaby)   → 20% ruchu

Least Connections

Request trafia do serwera z najmniejsza liczba aktywnych polaczen. Najlepszy algorytm ogolnego przeznaczenia.

IP Hash

Hash IP klienta determinuje serwer — ten sam klient zawsze trafia do tego samego serwera. Prosta session affinity.

Least Response Time

Request do serwera z najkrotszym srednim czasem odpowiedzi.

Health Checks

Passive — monitorowanie odpowiedzi

# Nginx — 3 bledy w 30s = serwer down
upstream backend {
  server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
  server 10.0.0.2:8080 max_fails=3 fail_timeout=30s;
}

Active — regularne zapytania

# HAProxy — sprawdzaj /healthz co 5s
backend app_servers
  option httpchk GET /healthz
  http-check expect status 200
  server srv1 10.0.0.1:8080 check inter 5s fall 3 rise 2
  server srv2 10.0.0.2:8080 check inter 5s fall 3 rise 2

# fall 3 = 3 bledy → down
# rise 2 = 2 sukcesy → zdrowy

Health Endpoint

app.get('/healthz', async (req, res) => {
  try {
    await db.query('SELECT 1');
    await redis.ping();
    res.status(200).json({
      status: 'healthy',
      uptime: process.uptime()
    });
  } catch (err) {
    res.status(503).json({
      status: 'unhealthy',
      error: err.message
    });
  }
});

Session Affinity

Problem: uzytkownik zalogowany na Serwerze A — nastepny request trafia do B (brak sesji).

Lepsze rozwiazanie: externalizacja sesji

# Zamiast sticky sessions — sesje w Redis
Klient → [LB] → Serwer A ──→ Redis (sesja)
                 Serwer B ──→ Redis (sesja)
                 Serwer C ──→ Redis (sesja)
# Kazdy serwer ma dostep do tej samej sesji
const session = require('express-session');
const RedisStore = require('connect-redis')(session);

app.use(session({
  store: new RedisStore({ client: redisClient }),
  secret: 'session-secret',
  resave: false,
  saveUninitialized: false,
  cookie: { secure: true, httpOnly: true }
}));

Konfiguracja Nginx

upstream backend {
  least_conn;
  server 10.0.0.1:8080 weight=5;
  server 10.0.0.2:8080 weight=3;
  server 10.0.0.3:8080 weight=2;
  server 10.0.0.4:8080 backup;
}

server {
  listen 443 ssl http2;
  server_name api.example.com;

  location /api/ {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For
      $proxy_add_x_forwarded_for;

    proxy_connect_timeout 5s;
    proxy_read_timeout 30s;
    proxy_next_upstream error timeout http_502 http_503;
    proxy_next_upstream_tries 2;
  }
}

Auto-scaling

Ruch rosnie → CPU > 70%
  → Auto-scaler dodaje instancje
  → LB dodaje je do puli
  → Health check OK → ruch kierowany

Ruch spada → CPU < 30%
  → Auto-scaler oznacza instancje jako "draining"
  → LB nie kieruje NOWYCH requestow
  → Czeka na zakonczenie istniejacych (30s)
  → Usuwa instancje

Connection draining — przed usunieciem instancji, dokoncz istniejace requesty. Zapobiega blednym odpowiedziom.

Kluczowe wnioski

  1. L7 dla HTTP (routing po URL) — L4 dla TCP/UDP (wydajnosc)
  2. Least Connections — najczesciej najlepszy algorytm ogolnego przeznaczenia
  3. Health checks sa obowiazkowe — active + passive
  4. Unikaj sticky sessions — externalizuj sesje do Redis
  5. Auto-scaling z LB = elastycznosc kosztowa i wydajnosciowa
  6. Connection draining zapobiega blednym odpowiedziom
  7. W chmurze uzywaj managed LB — mniej operacji
