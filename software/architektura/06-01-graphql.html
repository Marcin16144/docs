GraphQL

Jezyk zapytan do API, w ktorym klient definiuje dokladnie jakie dane chce otrzymac.

GraphQL vs REST — problem

REST — Over-fetching (za duzo danych):
GET /api/users/123
→ { id, name, email, address, phone, avatar, bio, settings... }
  (potrzebowales tylko name i email)

REST — Under-fetching (3 roundtripy):
GET /api/users/123
GET /api/users/123/orders
GET /api/orders/456/items

GraphQL — 1 request, dokladnie te pola:
query {
  user(id: "123") {
    name
    email
    orders(last: 5) {
      total
      items { name, price }
    }
  }
}

Schema Definition Language (SDL)

type User {
  id: ID!
  name: String!
  email: String!
  age: Int
  orders: [Order!]!
  role: Role!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
  createdAt: DateTime!
}

enum OrderStatus {
  PENDING
  PROCESSING
  SHIPPED
  DELIVERED
  CANCELLED
}

input CreateOrderInput {
  items: [OrderItemInput!]!
  shippingAddress: AddressInput!
}

Architektura serwera

Resolvers

const resolvers = {
  Query: {
    user: async (_, { id }, ctx) => {
      return ctx.dataSources.userAPI.getUser(id);
    }
  },
  Mutation: {
    createOrder: async (_, { input }, ctx) => {
      if (!ctx.currentUser)
        throw new AuthenticationError();
      return ctx.dataSources.orderAPI.create({
        userId: ctx.currentUser.id,
        ...input
      });
    }
  },
  // Field resolver — leniwe ladowanie
  User: {
    orders: (user, _, ctx) =>
      ctx.dataSources.orderAPI.getByUserId(user.id)
  }
};

DataLoader (problem N+1)

// Problem: 10 zamowien → 10 zapytan o uzytkownika
// Rozwiazanie: batch w jedno zapytanie

const userLoader = new DataLoader(async (ids) => {
  const users = await db.users.findByIds(ids);
  return ids.map(id =>
    users.find(u => u.id === id)
  );
});

// Resolver uzywa loadera
Order: {
  customer: (order) =>
    userLoader.load(order.customerId)
}

Bezpieczenstwo

1. Limitowanie glebokosci zapytan

// Zablokuj nieskonczone zagniezdzenie
const depthLimit = require('graphql-depth-limit');
const server = new ApolloServer({
  validationRules: [depthLimit(5)]
});

2. Query cost analysis

Przypisanie kosztu do pol — droga operacja (np. orders) ma wyzszy koszt. Limit calkowitego kosztu zapytania.

Kiedy stosowac?

Stosuj gdy:

  • Frontend potrzebuje elastycznych zapytan
  • Wiele zrodel danych do agregacji
  • Mobile + Web z roznymi wymaganiami
  • Czeste zmiany wymagan UI
  • Niezaleznosc frontendu od backendu

Nie stosuj gdy:

  • Proste CRUD API
  • File upload glowna funkcja
  • Potrzebujesz HTTP caching
  • Maly zespol / prosty projekt
  • Public API (REST latwiejszy)

Dobre praktyki

  1. Schema-first — zaprojektuj schema przed implementacja
  2. Nie mapuj 1:1 do bazy — schema to kontrakt, nie model
  3. Zawsze DataLoader — unikanie N+1
  4. Limituj zlozonosc — depth limit + cost analysis
  5. Monitoruj resolwery — wydajnosc per-field
  6. Ewoluuj schema — dodawaj, deprecjonuj, nie usuwaj
  7. Generuj typy — GraphQL Code Generator
