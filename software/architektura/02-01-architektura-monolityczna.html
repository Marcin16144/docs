Architektura monolityczna

Jedna aplikacja, jeden deployment, jeden proces — klasyczne podejscie, ktore wciaz ma swoje miejsce.

Czym jest monolit?

Architektura monolityczna to podejscie, w ktorym cala aplikacja jest budowana, wdrazana i skalowana jako jedna, spojna jednostka. Wszystkie funkcjonalnosci — od interfejsu uzytkownika, przez logike biznesowa, po dostep do danych — dzialaja w ramach jednego procesu.

Struktura typowego monolitu

Monolit jednowarstwowy (prosty)

Cala logika w jednym projekcie bez wyraznego podzialu na moduly:

  • src/
  • ├── controllers/
  • │ ├── OrderController.java
  • │ ├── UserController.java
  • │ └── PaymentController.java
  • ├── services/
  • │ ├── OrderService.java
  • │ ├── UserService.java
  • │ └── PaymentService.java
  • ├── repositories/
  • │ ├── OrderRepository.java
  • │ └── UserRepository.java
  • ├── models/
  • │ ├── Order.java
  • │ └── User.java
  • └── Application.java

Monolit modularny (strukturalny)

Podzial na moduly z wyraznymi granicami i odpowiedzialnosciami:

  • src/
  • ├── modules/
  • │ ├── orders/
  • │ │ ├── api/OrderController.java
  • │ │ ├── domain/Order.java
  • │ │ ├── service/OrderService.java
  • │ │ └── repository/OrderRepository.java
  • │ ├── users/
  • │ │ ├── api/UserController.java
  • │ │ ├── domain/User.java
  • │ │ └── service/UserService.java
  • │ └── payments/
  • │ ├── api/PaymentController.java
  • │ └── service/PaymentService.java
  • ├── shared/
  • │ ├── config/
  • │ └── utils/
  • └── Application.java

Modularyzacja wewnatrz monolitu

Zasady dobrej modularyzacji

  1. Wysoka spojnosc (high cohesion) — modul realizuje jedna odpowiedzialnosc
  2. Luzne powiazania (low coupling) — moduly komunikuja sie przez interfejsy
  3. Enkapsulacja — wewnetrzne szczegoly modulu sa ukryte
  4. Jawne zaleznosci — graf zaleznosci jest czytelny i jednokierunkowy

Egzekwowanie granic modulow

// Interfejs publiczny modulu zamowien
public interface OrderFacade {
    OrderDto createOrder(CreateOrderCommand cmd);
    OrderDto getOrder(OrderId id);
    List<OrderDto> getUserOrders(UserId userId);
}

// Implementacja ukryta w module
class OrderFacadeImpl implements OrderFacade {
    private final OrderRepository repository;
    private final OrderValidator validator;

    @Override
    public OrderDto createOrder(CreateOrderCommand cmd) {
        validator.validate(cmd);
        Order order = Order.create(cmd);
        repository.save(order);
        return OrderDto.from(order);
    }
}

Kiedy monolit to wlasciwy wybor?

Idealny dla

  • Malych zespolow (2-10 deweloperow)
  • MVP i prototypow — szybki time-to-market
  • Domen o niskiej zlozonosci
  • Ograniczonego budzetu — niski koszt infrastruktury
  • Poczatku nowego projektu — lepsza eksploracja domeny

Problematyczny dla

  • Duzych zespolow (50+ deweloperow)
  • Niezaleznego skalowania komponentow
  • Roznych cykli wdrozen modulow
  • Polyglot programming — rozne technologie
  • Ekstremalnej dostepnosci — fault isolation

Branch by Abstraction

  1. Utworz abstrakcje (interfejs) nad fragmentem do wydzielenia
  2. Zmien klientow, aby korzystali z abstrakcji
  3. Utworz nowa implementacje (mikroserwis)
  4. Przelacz abstrakcje na nowa implementacje
  5. Usun stara implementacje

Anty-wzorce monolitu

Big Ball of Mud

Brak wyraznej struktury — kazdy modul zalezy od kazdego. Zmiany wywoluja kaskade nieoczekiwanych efektow ubocznych. Kod staje sie nieutrzymywalny.

Distributed Monolith

Pozornie osobne serwisy, ale scisle powiazane — deploy wymaga jednoczesnego wdrozenia wielu serwisow. To najgorsze z dwoch swiatow: zlozonosc systemu rozproszonego plus sztywnosc monolitu.

Podsumowanie

Architektura monolityczna nie jest "przestarzala" ani "zla". To swiadomy wybor architektoniczny, ktory w wielu sytuacjach jest optymalny. Kluczem jest utrzymanie wewnetrznej modularyzacji, aby w przyszlosci migracja do innej architektury (jesli zajdzie taka potrzeba) byla wykonalna.
