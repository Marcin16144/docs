Serwowanie modeli i LLMOps

Gdzie i jak uruchomic model, ile to kosztuje, jak to monitorowac i zabezpieczyc — od malego GPU po wdrozenie produkcyjne.

Inferencja lokalna vs. API w chmurze

Pierwsza decyzja architektoniczna: czy hostujesz model sam, czy korzystasz z gotowego API. To kompromis miedzy kontrola/prywatnoscia a wygoda/jakoscia.

API w chmurze

  • Dostep do najlepszych modeli (Claude, GPT, Gemini) bez wlasnego sprzetu
  • Zero utrzymania, automatyczne skalowanie
  • Platnosc za tokeny — koszt rosnie z ruchem
  • Dane wychodza na zewnatrz (kwestia prywatnosci/compliance)
  • Zaleznosc od dostawcy i limitow

Inferencja lokalna / self-hosted

  • Pelna prywatnosc — dane nie opuszczaja srodowiska
  • Staly koszt sprzetu zamiast za-token
  • Brak limitow zewnetrznych, dzialanie offline
  • Wymaga GPU i utrzymania; modele zwykle slabsze niz topowe API
  • Ty odpowiadasz za skalowanie i dostepnosc

Czesty wybor 2026 to podejscie hybrydowe: lokalny model do prostych/wrazliwych zadan, API do najtrudniejszych (zob. router/kaskada nizej).

Kwantyzacja i wymagania VRAM

Kwantyzacja zmniejsza precyzje wag (np. z 16-bit do 4-bit), drastycznie obnizajac zapotrzebowanie na pamiec i przyspieszajac inferencje, kosztem niewielkiej utraty jakosci. To kluczowa technika, by uruchamiac modele na skromnym sprzecie.

FormatGdzieOpis
GGUFllama.cpp, Ollama, LM StudioStandard kwantyzacji dla inferencji lokalnej (CPU/GPU). Warianty Q4_K_M, Q5_K_M, Q6_K, Q8_0 — kompromis rozmiar/jakosc. Q4_K_M to popularny "sweet spot".
AWQvLLM, TGIKwantyzacja 4-bit zachowujaca wazne wagi (activation-aware); dobra jakosc na GPU.
GPTQvLLM, TGIPopularna kwantyzacja 4-bit po treningu (post-training).
FP8 / INT8vLLM, TensorRT-LLM8-bit na nowszych GPU — wieksza przepustowosc przy minimalnej stracie jakosci.

Szacowanie VRAM

Zgrubnie: pamiec na same wagi modelu to liczba parametrow × bajty na parametr. Do tego dochodzi cache KV (rosnie z dlugoscia kontekstu i liczba rownoleglych zapytan) oraz narzut.

VRAM_wagi ≈ parametry × bajty_na_param
  FP16  : 2 B/param   |  8B → ~16 GB
  INT8  : 1 B/param   |  8B → ~8 GB
  4-bit : ~0,5 B/param|  8B → ~4-5 GB
+ cache KV (kontekst × warstwy × batch) + narzut

Realia malego GPU (np. 8 GB VRAM)

Na karcie z 8 GB VRAM (typowy laptop z RTX) nie zmiescisz duzego modelu w FP16. Praktyczne podejscie:

  • Modele 7-9B w kwantyzacji 4-bit (GGUF Q4_K_M) mieszcza sie z zapasem na kontekst — to glowny target dla 8 GB.
  • Modele 12-14B bywaja na granicy — pomaga nizsza kwantyzacja i offload czesci warstw na CPU (llama.cpp/Ollama).
  • Krotszy kontekst zmniejsza cache KV — nie ustawiaj 32k, jesli wystarczy 4-8k.
  • Ollama / llama.cpp to naturalny wybor: automatyczny podzial warstw GPU/CPU, format GGUF, proste uruchomienie.
  • Gdy lokalny model nie wystarcza — eskaluj zapytanie do wiekszego modelu (kaskada, patrz nizej).

Batching i streaming

  • Continuous batching — serwer (vLLM, TGI, SGLang) laczy zapytania wielu uzytkownikow w locie, maksymalizujac wykorzystanie GPU i przepustowosc.
  • PagedAttention (vLLM) — efektywne zarzadzanie cache KV jak pamiecia stronicowana, mniej marnotrawstwa VRAM.
  • Streaming (SSE) — token po tokenie do klienta; drastycznie poprawia odczuwalna responsywnosc (liczy sie TTFT — czas do pierwszego tokenu). Patrz 06 — Komunikacja i integracja (Server-Sent Events).

Koszty i latencja

Kluczowe metryki wydajnosci serwowania:

  • TTFT (Time To First Token) — jak szybko zaczyna sie odpowiedz; zalezy m.in. od dlugosci promptu (faza prefill).
  • TPOT / tok/s — tempo generacji kolejnych tokenow (faza decode).
  • Przepustowosc — laczna liczba tokenow/s przy wielu zapytaniach (rosnie z batchingiem).
  • Koszt na 1000 tokenow (API) lub koszt GPU/godz. (self-host).

Jak obnizac koszty i latencje: krotsze prompty (mniej kontekstu), mniejszy/kwantyzowany model do prostych zadan, cache promptow, batching, ograniczanie max_tokens, oraz router kierujacy ruch do najtanszego wystarczajacego modelu.

Cache promptow

Prompt caching ponownie wykorzystuje obliczenia dla powtarzalnego prefiksu promptu (np. dluga instrukcja systemowa, staly kontekst), zamiast liczyc je od nowa przy kazdym zapytaniu. Efekt: nizszy TTFT i nizszy koszt.

  • API: Anthropic, OpenAI i inni oferuja cache promptow (czesto z duza znizka na tokeny z cache).
  • Self-host: vLLM i SGLang robia automatyczne prefix caching wspoldzielonych prefiksow miedzy zapytaniami.
  • Dobra praktyka: umieszczaj stale tresci (system prompt, dokumenty) na poczatku promptu, a zmienne (pytanie) na koncu — by prefiks dalo sie cache'owac.

Obserwowalnosc (LLMOps)

LLM jest niedeterministyczny i kosztowny, wiec obserwowalnosc jest niezbedna — nie wystarcza klasyczne logi aplikacji.

  • Logi i tracing — pelne slady zapytan: prompt, odpowiedz, uzyte narzedzia, tokeny, koszt, latencja. Dla agentow — cala trajektoria krokow.
  • Narzedzia (2026): LangSmith, Langfuse (open-source), Helicone, Phoenix (Arize), Traceloop/OpenLLMetry. Coraz czesciej oparte o OpenTelemetry (semantyka GenAI), co spina je z reszta observability.
  • Ewaluacja jakosci — zbiory testowe pytan referencyjnych, metryki (faithfulness, trafnosc), "LLM-as-a-judge", testy regresji jakosci przy zmianie modelu/promptu. Narzedzia: Ragas, DeepEval, promptfoo, Evals.
  • Monitoring produkcyjny — koszt/uzytkownik, wskazniki odmow, sygnaly o halucynacjach, feedback uzytkownikow, dryf jakosci w czasie.

Bezpieczenstwo

  • Guardraile — walidacja wejscia i wyjscia: filtrowanie tresci niedozwolonych, wykrywanie danych wrazliwych (PII), wymuszanie formatu/schematu odpowiedzi. Narzedzia: Llama Guard, NeMo Guardrails, Guardrails AI, moderacja API.
  • Prompt injection — najpowazniejsze ryzyko aplikacji LLM (OWASP Top 10 for LLM). Traktuj kazda tresc z zewnatrz (dokumenty RAG, wynik narzedzi, wejscie uzytkownika) jako niezaufana; izoluj instrukcje systemowe od danych, nie pozwalaj danym sterowac akcjami.
  • Wyciek danych — uwazaj, co trafia do promptu i do logow; egzekwuj uprawnienia juz na poziomie retrievalu (filtrowanie metadanych w bazie wektorowej, 13-03).
  • Najmniejsze uprawnienia narzedzi i human-in-the-loop dla akcji wrazliwych (zob. 13-02 Agenty).
  • Rate limiting i kontrola kosztu — ochrona przed naduzyciem i "denial of wallet".

Wzorce wdrozen

Router modeli

Klasyfikator kieruje zapytanie do wlasciwego modelu wedlug trudnosci/kosztu: proste → maly/lokalny, trudne → duzy. Optymalizuje koszt przy zachowaniu jakosci.

Kaskada

Najpierw tanszy model; jesli niepewny lub wynik nie przejdzie walidacji — eskalacja do wiekszego. Maly model obsluguje wiekszosc ruchu.

Fallback

Gdy glowny model/dostawca jest niedostepny lub przekroczy limit — automatyczne przelaczenie na zapasowy (inny model, inny region, inny provider). Zwieksza dostepnosc.

Hybryda lokalne + chmura

Lokalny model (prywatnosc, koszt) dla wiekszosci zadan; API (jakosc) dla najtrudniejszych. Naturalne polaczenie routera/kaskady z fallbackiem.

Dla malego GPU to spojny scenariusz: lokalny model kwantyzowany na 8 GB VRAM jako pierwsza linia, a kaskada/fallback do wiekszego modelu (w LAN lub chmurze) tylko gdy lokalny jest niepewny. Mechanike decyzji "kiedy eskalowac" omawia 13-02.

Podsumowanie

Serwowanie LLM to inzynieria kompromisow: jakosc kontra koszt kontra latencja kontra prywatnosc. Wybierz model serwowania (lokalnie vs. API), dobierz silnik (vLLM dla produkcji GPU, Ollama/llama.cpp dla malego sprzetu), zastosuj kwantyzacje pod swoj budzet VRAM, wlacz batching, streaming i cache promptow dla wydajnosci, a od pierwszego dnia zadbaj o obserwowalnosc, ewaluacje i guardraile. Router, kaskada i fallback pozwalaja laczyc tani lokalny model z mocnym API — i sa szczegolnie sensowne, gdy dysponujesz tylko skromnym GPU.
