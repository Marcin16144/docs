# 06-03: gRPC — kompletny przewodnik

## Czym jest gRPC?

gRPC (gRPC Remote Procedure Calls) to nowoczesny, wydajny framework do komunikacji między serwisami, stworzony przez Google. Używa Protocol Buffers jako języka opisu interfejsu (IDL) i formatu serializacji, a HTTP/2 jako protokołu transportowego. gRPC umożliwia definiowanie serwisów i generowanie kodu klienta/serwera w wielu językach.

## Dlaczego gRPC?

### Porównanie z REST

| Cecha | REST | gRPC |
|-------|------|------|
| Format danych | JSON (tekstowy) | Protocol Buffers (binarny) |
| Protokół | HTTP/1.1 lub HTTP/2 | HTTP/2 (wymagany) |
| Kontrakt | OpenAPI (opcjonalny) | .proto (wymagany) |
| Generowanie kodu | Opcjonalne | Wbudowane |
| Streaming | Ograniczony | Natywny (4 typy) |
| Rozmiar wiadomości | Większy (~JSON) | Mniejszy (~10x mniej) |
| Szybkość serializacji | Wolniejsza | ~5-10x szybsza |
| Obsługa przeglądarek | Natywna | Wymaga gRPC-Web |
| Debugowanie | Proste (czytelny JSON) | Trudniejsze (binarny format) |
| Krzywa uczenia | Niższa | Wyższa |

## Protocol Buffers (Protobuf)

Protocol Buffers to mechanizm serializacji danych — binarny, wydajny, z silnym typowaniem.

### Definicja typów (.proto)

```protobuf
syntax = "proto3";

package ecommerce;

option go_package = "github.com/myapp/ecommerce";
option java_package = "com.myapp.ecommerce";

// Definicja wiadomości (message)
message User {
  int32 id = 1;              // numer pola (nie wartość!)
  string name = 2;
  string email = 3;
  UserRole role = 4;
  repeated Order orders = 5; // lista (powtarzalne pole)
  optional string phone = 6; // pole opcjonalne
  google.protobuf.Timestamp created_at = 7;
}

enum UserRole {
  USER_ROLE_UNSPECIFIED = 0; // zawsze 0 jako domyślna
  USER_ROLE_USER = 1;
  USER_ROLE_ADMIN = 2;
  USER_ROLE_MODERATOR = 3;
}

message Order {
  int32 id = 1;
  int32 user_id = 2;
  repeated OrderItem items = 3;
  double total = 4;
  OrderStatus status = 5;
}

message OrderItem {
  int32 product_id = 1;
  string product_name = 2;
  int32 quantity = 3;
  double price = 4;
}

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_PROCESSING = 2;
  ORDER_STATUS_SHIPPED = 3;
  ORDER_STATUS_DELIVERED = 4;
  ORDER_STATUS_CANCELLED = 5;
}
```

### Reguły numeracji pól

- Numery pól to identyfikatory binarne — **nigdy ich nie zmieniaj** po wdrożeniu
- Numery 1-15 zajmują 1 bajt (używaj dla częstych pól)
- Numery 16-2047 zajmują 2 bajty
- Usunięte pola oznacz jako `reserved` aby uniknąć ponownego użycia

```protobuf
message User {
  reserved 4, 8;               // zarezerwowane numery
  reserved "old_field_name";   // zarezerwowane nazwy
  int32 id = 1;
  string name = 2;
}
```

## Definicja serwisu

```protobuf
service UserService {
  // Unary RPC — request/response
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
  rpc CreateUser(CreateUserRequest) returns (CreateUserResponse);
  rpc UpdateUser(UpdateUserRequest) returns (UpdateUserResponse);
  rpc DeleteUser(DeleteUserRequest) returns (DeleteUserResponse);

  // Server streaming — serwer wysyła strumień
  rpc ListUsers(ListUsersRequest) returns (stream User);

  // Client streaming — klient wysyła strumień
  rpc UploadUserPhotos(stream UploadPhotoRequest) returns (UploadPhotoResponse);

  // Bidirectional streaming — oba kierunki
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}

message GetUserRequest {
  int32 id = 1;
}

message GetUserResponse {
  User user = 1;
}

message ListUsersRequest {
  int32 page_size = 1;
  string page_token = 2;
  string filter = 3;
}

message CreateUserRequest {
  string name = 1;
  string email = 2;
  UserRole role = 3;
}

message CreateUserResponse {
  User user = 1;
}
```

## Generowanie kodu

### Instalacja i użycie protoc

```bash
# Instalacja protoc (Protocol Buffer Compiler)
# Generowanie kodu Go
protoc --go_out=. --go-grpc_out=. proto/user.proto

# Generowanie kodu Python
protoc --python_out=. --grpc_python_out=. proto/user.proto

# Generowanie kodu C#
protoc --csharp_out=. --grpc_csharp_out=. proto/user.proto

# Generowanie kodu Java
protoc --java_out=. --grpc_java_out=. proto/user.proto
```

### Wygenerowany kod (Go — przykład)

```go
// Wygenerowany interfejs serwera
type UserServiceServer interface {
    GetUser(ctx context.Context, req *GetUserRequest) (*GetUserResponse, error)
    CreateUser(ctx context.Context, req *CreateUserRequest) (*CreateUserResponse, error)
    ListUsers(req *ListUsersRequest, stream UserService_ListUsersServer) error
    Chat(stream UserService_ChatServer) error
}

// Wygenerowany klient
type UserServiceClient interface {
    GetUser(ctx context.Context, in *GetUserRequest, opts ...grpc.CallOption) (*GetUserResponse, error)
    CreateUser(ctx context.Context, in *CreateUserRequest, opts ...grpc.CallOption) (*CreateUserResponse, error)
    ListUsers(ctx context.Context, in *ListUsersRequest, opts ...grpc.CallOption) (UserService_ListUsersClient, error)
    Chat(ctx context.Context, opts ...grpc.CallOption) (UserService_ChatClient, error)
}
```

## 4 typy komunikacji (streaming)

### 1. Unary RPC (Request-Response)

Najprostszy typ — klient wysyła jedno żądanie, serwer zwraca jedną odpowiedź.

```go
// Serwer
func (s *server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.GetUserResponse, error) {
    user, err := s.db.FindUser(req.Id)
    if err != nil {
        return nil, status.Errorf(codes.NotFound, "user %d not found", req.Id)
    }
    return &pb.GetUserResponse{User: user}, nil
}

// Klient
resp, err := client.GetUser(ctx, &pb.GetUserRequest{Id: 123})
if err != nil {
    log.Fatalf("GetUser failed: %v", err)
}
fmt.Println(resp.User.Name)
```

### 2. Server Streaming

Klient wysyła jedno żądanie, serwer odpowiada strumieniem wiadomości.

```go
// Serwer
func (s *server) ListUsers(req *pb.ListUsersRequest, stream pb.UserService_ListUsersServer) error {
    users, _ := s.db.GetAllUsers(req.Filter)
    for _, user := range users {
        if err := stream.Send(user); err != nil {
            return err
        }
    }
    return nil // koniec streamu
}

// Klient
stream, err := client.ListUsers(ctx, &pb.ListUsersRequest{Filter: "active"})
for {
    user, err := stream.Recv()
    if err == io.EOF {
        break // koniec streamu
    }
    if err != nil {
        log.Fatalf("ListUsers error: %v", err)
    }
    fmt.Println(user.Name)
}
```

### 3. Client Streaming

Klient wysyła strumień wiadomości, serwer odpowiada jedną odpowiedzią.

```go
// Serwer
func (s *server) UploadUserPhotos(stream pb.UserService_UploadUserPhotosServer) error {
    var totalSize int64
    for {
        photo, err := stream.Recv()
        if err == io.EOF {
            return stream.SendAndClose(&pb.UploadPhotoResponse{
                Count: totalSize,
                Message: "Upload complete",
            })
        }
        if err != nil {
            return err
        }
        totalSize += int64(len(photo.Data))
        s.storage.Save(photo)
    }
}

// Klient
stream, _ := client.UploadUserPhotos(ctx)
for _, photo := range photos {
    stream.Send(&pb.UploadPhotoRequest{Data: photo})
}
resp, _ := stream.CloseAndRecv()
fmt.Printf("Uploaded %d bytes\n", resp.Count)
```

### 4. Bidirectional Streaming

Oba kierunki jednocześnie — klient i serwer wysyłają strumienie niezależnie.

```go
// Serwer
func (s *server) Chat(stream pb.UserService_ChatServer) error {
    for {
        msg, err := stream.Recv()
        if err == io.EOF {
            return nil
        }
        if err != nil {
            return err
        }
        // Przetwórz wiadomość i odpowiedz
        response := processMessage(msg)
        if err := stream.Send(response); err != nil {
            return err
        }
    }
}

// Klient — odczyt i zapis w osobnych goroutines
stream, _ := client.Chat(ctx)

// Wysyłanie
go func() {
    for _, msg := range messages {
        stream.Send(msg)
    }
    stream.CloseSend()
}()

// Odbieranie
for {
    resp, err := stream.Recv()
    if err == io.EOF {
        break
    }
    fmt.Println(resp.Text)
}
```

## Deadlines i Timeouts

gRPC używa deadlines zamiast timeoutów — deadline to absolutny punkt w czasie.

```go
// Klient ustawia deadline
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

resp, err := client.GetUser(ctx, &pb.GetUserRequest{Id: 123})
if err != nil {
    st, ok := status.FromError(err)
    if ok && st.Code() == codes.DeadlineExceeded {
        log.Println("Timeout — serwer nie odpowiedzial w 5 sekund")
    }
}

// Serwer sprawdza deadline
func (s *server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.GetUserResponse, error) {
    if ctx.Err() == context.DeadlineExceeded {
        return nil, status.Error(codes.DeadlineExceeded, "deadline exceeded")
    }
    // ... logika
}
```

Deadline propaguje się w łańcuchu wywołań — jeśli serwis A wywołuje B z deadline 5s, serwis B zna pozostały czas.

## Metadata (nagłówki)

Metadata w gRPC to odpowiednik nagłówków HTTP — pary klucz-wartość.

```go
// Klient — wysyłanie metadata
md := metadata.New(map[string]string{
    "authorization": "Bearer token123",
    "x-request-id":  "abc-def-123",
})
ctx := metadata.NewOutgoingContext(context.Background(), md)
resp, err := client.GetUser(ctx, req)

// Serwer — odczyt metadata
func (s *server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.GetUserResponse, error) {
    md, ok := metadata.FromIncomingContext(ctx)
    if !ok {
        return nil, status.Error(codes.Unauthenticated, "no metadata")
    }
    token := md.Get("authorization")
    // walidacja tokenu...
}
```

## Obsługa błędów

gRPC definiuje zestaw standardowych kodów błędów:

| Kod | Nazwa | Użycie |
|-----|-------|--------|
| 0 | OK | Sukces |
| 1 | CANCELLED | Anulowane przez klienta |
| 2 | UNKNOWN | Nieznany błąd |
| 3 | INVALID_ARGUMENT | Niepoprawne argumenty (400) |
| 4 | DEADLINE_EXCEEDED | Timeout |
| 5 | NOT_FOUND | Zasób nie istnieje (404) |
| 6 | ALREADY_EXISTS | Zasób już istnieje (409) |
| 7 | PERMISSION_DENIED | Brak uprawnień (403) |
| 13 | INTERNAL | Błąd wewnętrzny (500) |
| 14 | UNAVAILABLE | Serwis niedostępny (503) |
| 16 | UNAUTHENTICATED | Brak uwierzytelnienia (401) |

### Użycie w kodzie

```go
import "google.golang.org/grpc/status"
import "google.golang.org/grpc/codes"

// Zwracanie błędu
func (s *server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.GetUserResponse, error) {
    user, err := s.db.FindUser(req.Id)
    if err == sql.ErrNoRows {
        return nil, status.Errorf(codes.NotFound,
            "uzytkownik o id %d nie istnieje", req.Id)
    }
    if err != nil {
        return nil, status.Errorf(codes.Internal,
            "blad bazy danych: %v", err)
    }
    return &pb.GetUserResponse{User: user}, nil
}

// Obsługa błędu po stronie klienta
resp, err := client.GetUser(ctx, req)
if err != nil {
    st, ok := status.FromError(err)
    if ok {
        switch st.Code() {
        case codes.NotFound:
            log.Printf("Nie znaleziono: %s", st.Message())
        case codes.InvalidArgument:
            log.Printf("Bledne dane: %s", st.Message())
        default:
            log.Printf("Blad gRPC [%s]: %s", st.Code(), st.Message())
        }
    }
}
```

## Load Balancing w gRPC

gRPC korzysta z długotrwałych połączeń HTTP/2, co komplikuje load balancing.

### Strategie

1. **Proxy-based (L7)** — load balancer terminuje połączenie gRPC i tworzy nowe do backendu. Envoy, Nginx, HAProxy.
2. **Client-side** — klient zna listę serwerów i sam rozdziela żądania. Wbudowane w gRPC (round-robin, pick-first).
3. **Look-aside (service discovery)** — klient odpytuje rejestr (Consul, etcd) i sam balansuje.

```go
// Client-side load balancing — round robin
conn, err := grpc.Dial(
    "dns:///myservice.default.svc.cluster.local:50051",
    grpc.WithDefaultServiceConfig(`{"loadBalancingConfig": [{"round_robin":{}}]}`),
)
```

### Dlaczego L4 load balancing nie działa?

HTTP/2 multipleksuje wiele żądań na jednym połączeniu TCP. Load balancer L4 (TCP) widzi jedno połączenie i kieruje cały ruch do jednego backendu. Potrzebny jest L7, który rozumie ramki HTTP/2.

## gRPC-Web

gRPC-Web umożliwia wywołania gRPC z przeglądarek, które nie obsługują natywnie HTTP/2 z trailerami.

### Architektura

```
Przeglądarka (gRPC-Web klient)
    |
    | HTTP/1.1 lub HTTP/2 (bez trailerów)
    v
Envoy Proxy (translacja)
    |
    | gRPC natywny (HTTP/2)
    v
gRPC Serwer
```

### Ograniczenia gRPC-Web

- Brak client streaming i bidirectional streaming
- Server streaming ograniczony (przez SSE lub WebSocket)
- Wymaga proxy (Envoy, grpc-web proxy)

## Kiedy używać gRPC vs REST?

### Używaj gRPC gdy:

- Komunikacja wewnętrzna między mikroserwisami
- Wymagana wysoka wydajność i niskie opóźnienia
- Potrzebujesz streamingu (np. dane w czasie rzeczywistym)
- Ścisły kontrakt API jest priorytetem
- Komunikacja polilotyczna (wiele języków programowania)
- Transfer dużych wolumenów danych

### Używaj REST gdy:

- API publiczne (klienci zewnętrzni)
- Aplikacje przeglądarkowe (bez proxy)
- Proste operacje CRUD
- Potrzebujesz łatwego debugowania (czytelny JSON)
- Zespół nie zna gRPC
- Caching HTTP jest krytyczny

### Podejście hybrydowe

```
Internet                    Wewnętrzna sieć
[Przeglądarka] → REST →  [API Gateway] → gRPC → [Serwis A]
[Mobile App]   → REST →  [API Gateway] → gRPC → [Serwis B]
                                        → gRPC → [Serwis C]
```

REST na zewnątrz (łatwość użycia), gRPC wewnątrz (wydajność).

## Dobre praktyki

1. **Projektuj API-first** — .proto file jest kontraktem, projektuj go świadomie
2. **Wersjonuj .proto pliki** — używaj package versioning (v1, v2)
3. **Nigdy nie zmieniaj numerów pól** — dodawaj nowe, stare oznacz jako reserved
4. **Ustawiaj deadlines** — zawsze, na każdym poziomie łańcucha
5. **Używaj interceptorów** — middleware dla logowania, auth, metryk
6. **Implementuj health checking** — standard gRPC Health Checking Protocol
7. **Monitoruj** — Prometheus + gRPC metrics (opóźnienia, błędy, throughput)
8. **Używaj reflection** — ułatwia debugging (grpcurl, grpc-tools)
