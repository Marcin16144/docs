Coupling i Cohesion

Niskie sprzezenie miedzy modulami, wysoka spojnosc wewnatrz — fundament dobrej architektury.

Definicje

Coupling (sprzezenie) — stopien, w jakim moduly zaleza od siebie. Im wyzsze, tym trudniejsza zmiana jednego modulu bez wplywu na inne.

Cohesion (spojnosc) — stopien, w jakim elementy wewnatrz modulu sa ze soba powiazane. Im wyzsza, tym bardziej modul skupia sie na jednym zadaniu.

Typy sprzezenia (od najgorszego)

1. Content Coupling — najgorsze

Modul bezposrednio odwoluje sie do wewnetrznych danych innego modulu.

// ZLE — bezposredni dostep do pol prywatnych
class OrderProcessor {
    process(cart: ShoppingCart): void {
        for (let i = 0; i < cart._items.length; i++) {
            cart._items[i]._price *= 0.9;
        }
        cart._totalCalculated = false;
    }
}

// DOBRZE — publiczne API
class OrderProcessor {
    process(cart: ShoppingCart): void {
        cart.applyDiscount(0.1);
    }
}

2. Common Coupling

Moduly dziela globalny stan (zmienne globalne, mutowalne singletony).

# ZLE — globalny stan dzielony miedzy modulami
_current_user = None

class AuthService:
    def login(self, username, password):
        global _current_user
        _current_user = self.db.find(username)

class OrderService:
    def create_order(self, items):
        global _current_user
        return Order(customer=_current_user, items=items)

# DOBRZE — jawne przekazywanie
class OrderService:
    def create_order(self, customer: Customer, items: list) -> Order:
        return Order(customer=customer, items=items)

3. Control Coupling

Modul przekazuje flage sterujaca logika innego modulu.

// ZLE — flagi steruja logika
class UserService {
    getUser(id: string, includeOrders: boolean,
            includeAddress: boolean,
            formatForAPI: boolean): any {
        const user = this.repo.find(id);
        if (includeOrders) { user.orders = this.orderRepo.find(id); }
        if (includeAddress) { user.address = this.addrRepo.find(id); }
        if (formatForAPI) { return this.formatForAPI(user); }
        return user;
    }
}

// DOBRZE — oddzielne metody
class UserService {
    getUser(id: string): User {
        return this.repo.find(id);
    }
    getUserWithOrders(id: string): UserWithOrders {
        const user = this.repo.find(id);
        const orders = this.orderRepo.find(id);
        return { ...user, orders };
    }
    getUserForAPI(id: string): UserDTO {
        return UserDTO.from(this.repo.find(id));
    }
}

4. Stamp Coupling

Modul otrzymuje wiecej danych niz potrzebuje.

// ZLE — caly User, ale potrzebne tylko email i name
function sendWelcomeEmail(user: User): void {
    mailer.send(user.email, `Witaj ${user.name}!`);
}

// DOBRZE — dokladnie to, co potrzebne
interface EmailRecipient {
    email: string;
    name: string;
}

function sendWelcomeEmail(recipient: EmailRecipient): void {
    mailer.send(recipient.email, `Witaj ${recipient.name}!`);
}

5. Data Coupling — najlepsze

// DOBRZE — proste parametry
function calculateTax(amount: number, taxRate: number): number {

}

function formatCurrency(amount: number, currency: string): string {
    return `${amount.toFixed(2)} ${currency}`;

1. Coincidental — najgorsza

class Utils {

2. Temporal — slaba

// ZLE — pogrupowane bo uruchamiaja sie jednoczesnie
class ApplicationStartup {
    initialize(): void {
        this.connectToDatabase();
        this.loadConfiguration();
        this.initializeCache();
        this.startMessageBroker();
        this.warmUpMLModels();

class Application {

        private db: DatabaseConnection,
        private config: ConfigLoader,

        private broker: MessageBroker

    async start(): Promise<void> {

        await this.broker.start();
    }

5. Functional — najlepsza

// Wszystko sluzy jednemu celowi: zarzadzanie koszykiem
class ShoppingCart {
    private items: CartItem[] = [];

    addItem(product: Product, quantity: number): void {
        const existing = this.findItem(product.id);
        if (existing) {
            existing.increaseQuantity(quantity);
        } else {
            this.items.push(new CartItem(product, quantity));
        }
    }

    removeItem(productId: string): void {
        this.items = this.items.filter(i => i.productId !== productId);
    }

    calculateTotal(): Money {
        return this.items.reduce(
            (sum, item) => sum.add(item.getSubtotal()),
            Money.zero()
        );
    }

    isEmpty(): boolean {
        return this.items.length === 0;
    }

    private findItem(id: string): CartItem | undefined {
        return this.items.find(i => i.productId === id);
    }
}

Praktyczna refaktoryzacja

Przed — niska spojnosc, wysokie sprzezenie

class ECommerceService:
    def __init__(self):
        self.db = MySQLConnection()
        self.mailer = SmtpClient()
        self.stripe = StripeAPI()
        self.redis = RedisClient()

    def place_order(self, user_id, cart_items):
        # walidacja, obliczenia, platnosc, zapis, cache, email
        # — szesc odpowiedzialnosci w jednej metodzie
        user = self.db.query("SELECT * FROM users ...")
        total = 0
        for item in cart_items:
            product = self.db.query("SELECT * FROM products ...")
            total += product[0]['price'] * item['quantity']
        tax = total * 0.23
        self.stripe.charge(user['card_token'], total + tax)
        self.db.execute("INSERT INTO orders ...")
        self.redis.delete(f"cart:{user_id}")
        self.mailer.send(user['email'], "Zamowienie", "...")

Po — wysoka spojnosc, niskie sprzezenie

class OrderService:
    """Orkiestracja zamowienia — jedna odpowiedzialnosc."""
    def __init__(self, validator, calculator, payments, repo, notifier):
        self.validator = validator
        self.calculator = calculator
        self.payments = payments
        self.repo = repo
        self.notifier = notifier

    def place_order(self, customer, items):
        self.validator.validate(customer, items)
        pricing = self.calculator.calculate(items)
        payment = self.payments.charge(customer, pricing.total)
        order = Order.create(customer, items, pricing, payment)
        self.repo.save(order)
        self.notifier.order_placed(order)
        return order

class PriceCalculator:
    """Tylko obliczenia cenowe."""
    def calculate(self, items) -> Pricing:
        subtotal = sum(i.price * i.quantity for i in items)
        discount = self.discount_svc.calculate(items)
        tax = self.tax_svc.calculate(subtotal - discount)
        return Pricing(subtotal, discount, tax)

class OrderValidator:
    """Tylko walidacja zamowienia."""
    def validate(self, customer, items):
        if not self.customer_repo.exists(customer.id):
            raise CustomerNotFoundError(customer.id)
        for item in items:
            if not self.inventory.is_available(item.product_id, item.qty):
                raise OutOfStockError(item.product_id)

Metryki

Afferent Coupling (Ca) — ile modulow zalezy ode mnie? Wysoki Ca = zmiana jest ryzykowna.

Efferent Coupling (Ce) — od ilu modulow ja zaleze? Wysoki Ce = modul jest kruchy.

Instability (I) = Ce / (Ca + Ce) — I=0 calkowicie stabilny, I=1 calkowicie niestabilny.

Wskazowki na co dzien

  • Klasa "Utils" to sygnal alarmowy — podziel na moduly tematyczne
  • Jesli zmiana w module A wymaga zmian w B, C, D — za wysokie sprzezenie
  • Jesli nazwa klasy wymaga "Manager", "Handler", "Utils" — za niska spojnosc
  • Cykliczne zaleznosci (A → B → C → A) — najgorszy rodzaj sprzezenia, eliminuj natychmiast
  • Interfejsy redukuja coupling — zalez od abstrakcji
  • Eventy/wiadomosci daja luzniejsze sprzezenie niz bezposrednie wywolania
