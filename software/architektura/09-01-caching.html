Cache-Aside (Lazy Loading)

Aplikacja zarzadza cachem recznie — sprawdza cache, przy miss czyta z bazy i zapisuje do cache.

async function getUser(userId) {
  // 1. Sprawdz cache
  const cached = await redis.get(`user:${userId}`);
  if (cached) return JSON.parse(cached);  // HIT

  // 2. MISS — czytaj z bazy
  const user = await db.users.findById(userId);

  // 3. Zapisz do cache
  await redis.set(`user:${userId}`,
    JSON.stringify(user), 'EX', 3600);
  return user;
}

Zalety: Prostota, cache ma tylko czytane dane. Wady: Pierwsze zapytanie wolne, mozliwa niespojnosc.

Read-Through

Cache sam pobiera dane z bazy przy miss — aplikacja zawsze czyta z cache.

const cache = new ReadThroughCache({
  store: redis,
  loader: async (key) => {
    const [type, id] = key.split(':');
    return db[type].findById(id);
  },
  ttl: 3600
});

const user = await cache.get('user:123');

Write-Through

Zapis idzie przez cache do bazy synchronicznie — cache jest zawsze aktualny.

Zapis: Aplikacja → Cache → Baza (synchronicznie)
Odczyt: Aplikacja → Cache (zawsze aktualny)

Zalety: Spojnosc cache-baza. Wady: Wyzsze latencje zapisu.

Write-Behind (Write-Back)

Zapis do cache natychmiast, zapis do bazy asynchronicznie z opoznieniem.

async function updateUser(userId, data) {
  // Natychmiastowy zapis do cache
  await redis.set(`user:${userId}`, JSON.stringify(data));

  // Dodaj do bufora (async flush do bazy co 5s)
  writeBuffer.push({ userId, data });
}

setInterval(async () => {
  if (writeBuffer.length === 0) return;
  const batch = writeBuffer.splice(0, writeBuffer.length);
  await db.users.bulkUpdate(batch);
}, 5000);

Zalety: Bardzo szybki zapis, batching. Wady: Ryzyko utraty danych przy awarii cache.

Strategie inwalidacji

TTL (Time-based)

const TTL = {
  userProfile: 3600,      // 1h — rzadko sie zmienia
  productList: 300,       // 5min
  searchResults: 60,      // 1min
  stockPrice: 5           // 5s — czesto sie zmienia
};

Event-based (aktywna inwalidacja)

async function updateUser(userId, data) {
  await db.users.update(userId, data);
  await redis.del(`user:${userId}`);
  await redis.del(`user-orders:${userId}`);

  // Pub/Sub — inwalidacja w wielu instancjach
  redis.publish('cache:invalidate', JSON.stringify({
    keys: [`user:${userId}`]
  }));
}

Cache Stampede

Problem: klucz wygasa, setki requestow jednoczesnie pytaja baze — przeciazenie.

Rozwiazanie: Locking (mutex)

async function getWithLock(key, loader, ttl) {
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const lockKey = `lock:${key}`;
  const acquired = await redis.set(
    lockKey, '1', 'NX', 'EX', 10
  );

  if (acquired) {
    const data = await loader();
    await redis.set(key, JSON.stringify(data), 'EX', ttl);
    await redis.del(lockKey);
    return data;
  } else {
    await sleep(100);
    return getWithLock(key, loader, ttl);  // retry
  }
}

Rozwiazanie: Probabilistic Early Refresh

Odswiezaj cache przed wygasnieciem — gdy TTL < 10%, odswiez w tle i zwroc stare dane.

Wzorce Redis

// String — proste klucz-wartosc
await redis.set('user:123', JSON.stringify(user), 'EX', 3600);

// Hash — struktura z polami
await redis.hset('user:123', {
  name: 'Jan', email: 'jan@ex.com', role: 'admin'
});
const all = await redis.hgetall('user:123');

// Sorted Set — ranking
await redis.zadd('leaderboard', 1500, 'player:1');
const top10 = await redis.zrevrange('leaderboard', 0, 9, 'WITHSCORES');

// Rate Limiting
async function rateLimit(key, max, windowSec) {
  const current = await redis.incr(key);
  if (current === 1) await redis.expire(key, windowSec);
  if (current > max) throw new RateLimitError();
  return { remaining: max - current };
}

CDN i Cache-Control

# Statyczne assety — dlugi cache + hash w nazwie
Cache-Control: public, max-age=31536000, immutable

# API responses — krotki cache
Cache-Control: public, max-age=60, s-maxage=300

# Prywatne dane — nie cachuj na CDN
Cache-Control: private, max-age=0, no-store

# Stale-while-revalidate
Cache-Control: public, max-age=60, stale-while-revalidate=300

Kluczowe wnioski

  1. Cache-aside to najpopularniejsza strategia — prosta i elastyczna
  2. Write-behind daje najszybsze zapisy, ale ryzyko utraty danych
  3. TTL to podstawa — zawsze ustawiaj czas wygasniecia
  4. Cache stampede to realny problem — locking lub early refresh
  5. CDN dla statycznych zasobow — latwa wygrana wydajnosciowa
  6. Redis to swiss army knife — cache, rate limiting, kolejki
  7. Inwalidacja jest najtrudniejsza — event-based dla krytycznych danych
