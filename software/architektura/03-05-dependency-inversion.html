Dependency Inversion Principle (DIP)

Moduly wysokiego poziomu nie powinny zalezec od modulow niskiego poziomu — oba powinny zalezec od abstrakcji.

Dwie reguly DIP

  1. Moduly wysokiego poziomu nie powinny zalezec od modulow niskiego poziomu — oba powinny zalezec od abstrakcji
  2. Abstrakcje nie powinny zalezec od szczegolow — szczegoly powinny zalezec od abstrakcji

Tradycyjnie logika biznesowa zalezala od infrastruktury (baza, siec). DIP odwraca ten kierunek — to szczegoly implementacyjne dostosowuja sie do abstrakcji definiowanych przez logike biznesowa.

Przyklad 1: Serwis zamowien

Zle — bezposrednie zaleznosci od infrastruktury

class MySQLDatabase {
    query(sql: string): any[] { /* MySQL */ }
    execute(sql: string): void { /* MySQL */ }
}

class SmtpEmailSender {
    send(to: string, subject: string, body: string): void { /* SMTP */ }
}

class StripePaymentGateway {
    charge(token: string, amount: number): PaymentResult { /* Stripe */ }
}

// OrderService BEZPOSREDNIO zalezy od MySQL, SMTP, Stripe
class OrderService {
    private db = new MySQLDatabase();
    private mailer = new SmtpEmailSender();
    private payments = new StripePaymentGateway();

    placeOrder(order: Order): void {
        this.payments.charge(order.cardToken, order.total);
        this.db.execute(`INSERT INTO orders VALUES (...)`);
        this.mailer.send(order.email, 'Zamowienie', '...');
    }
}

Dobrze — zaleznosc od abstrakcji

// Abstrakcje definiowane przez warstwe biznesowa
interface OrderRepository {
    save(order: Order): void;
    findById(id: string): Order;
}

interface PaymentGateway {
    charge(amount: Money, method: PaymentMethod): PaymentResult;
}

interface NotificationService {
    sendOrderConfirmation(order: Order): void;
}

// Logika biznesowa zalezy TYLKO od abstrakcji
class OrderService {
    constructor(
        private orders: OrderRepository,
        private payments: PaymentGateway,
        private notifications: NotificationService
    ) {}

    placeOrder(order: Order): OrderResult {
        const payment = this.payments.charge(
            order.total, order.paymentMethod
        );
        if (!payment.success) {
            return OrderResult.paymentFailed(payment.error);
        }
        order.markAsPaid(payment.transactionId);
        this.orders.save(order);
        this.notifications.sendOrderConfirmation(order);
        return OrderResult.success(order);
    }
}

// Infrastruktura implementuje abstrakcje
class PostgresOrderRepository implements OrderRepository {
    constructor(private pool: Pool) {}
    save(order: Order): void {
        this.pool.query(
            'INSERT INTO orders (id, total, status) VALUES ($1, $2, $3)',
            [order.id, order.total.amount, order.status]
        );
    }
    findById(id: string): Order {
        const row = this.pool.query('SELECT * FROM orders WHERE id=$1', [id]);
        return this.mapToOrder(row);
    }
}

class StripePaymentGateway implements PaymentGateway {
    charge(amount: Money, method: PaymentMethod): PaymentResult {
        const result = stripe.charges.create({
            amount: amount.toCents(),
            currency: amount.currency,
            source: method.token
        });
        return PaymentResult.from(result);
    }
}

Trzy formy Dependency Injection

// 1. Constructor Injection (najczesciej stosowana)
class OrderService {
    constructor(
        private repo: OrderRepository,
        private payments: PaymentGateway
    ) {}
}

// 2. Method Injection (zaleznosc potrzebna w jednej metodzie)
class ReportGenerator {
    generate(data: ReportData, formatter: ReportFormatter): string {
        return formatter.format(data);
    }
}

// 3. Property Injection (rzadko — trudne do kontrolowania)
class NotificationService {
    logger?: Logger;
    notify(message: string): void {
        this.logger?.log(`Wysylanie: ${message}`);
    }
}

Przyklad 2: DI Container (Python)

class Container:
    def __init__(self):
        self._factories = {}
        self._singletons = {}

    def register(self, interface, factory, singleton=False):
        self._factories[interface] = (factory, singleton)

    def resolve(self, interface):
        if interface in self._singletons:
            return self._singletons[interface]
        factory, is_singleton = self._factories[interface]
        instance = factory(self)
        if is_singleton:
            self._singletons[interface] = instance
        return instance

# Rejestracja
container = Container()
container.register(OrderRepository,
    lambda c: PostgresOrderRepository(db_pool), singleton=True)
container.register(PaymentGateway,
    lambda c: StripePaymentGateway(api_key), singleton=True)
container.register(OrderService,
    lambda c: OrderService(
        c.resolve(OrderRepository),
        c.resolve(PaymentGateway)
    ))

# Uzycie
service = container.resolve(OrderService)

Architektura warstwowa z DIP

BEZ DIP — zaleznosci plyna w dol:
  Presentation  -->  Business Logic  -->  Data Access  -->  DB

Z DIP — abstrakcje naleza do warstwy biznesowej:
  Presentation  -->  Business Logic  <--  Infrastructure
                     (definiuje           (implementuje
                      interfejsy)          interfejsy)

Struktura katalogow:
src/
  domain/                  // ZERO zaleznosci zewnetrznych
    entities/Order.ts
    repositories/OrderRepository.ts    // interfejs
    services/OrderService.ts

  infrastructure/          // implementuje interfejsy z domain/
    persistence/PostgresOrderRepository.ts
    payments/StripePaymentGateway.ts
    notifications/SendGridNotificationService.ts

  application/             // kompozycja — laczy warstwy
    config/container.ts

Testowanie dzieki DIP

class InMemoryOrderRepository implements OrderRepository {
    private orders = new Map<string, Order>();
    save(order: Order): void { this.orders.set(order.id, order); }
    findById(id: string): Order {
        const o = this.orders.get(id);
        if (!o) throw new NotFoundError(id);
        return o;
    }
}

class FakePaymentGateway implements PaymentGateway {
    public lastCharge?: { amount: Money; method: PaymentMethod };
    charge(amount: Money, method: PaymentMethod): PaymentResult {
        this.lastCharge = { amount, method };
        return PaymentResult.success('fake-tx-123');
    }
}

Kiedy DIP jest zbedne?

  • Proste skrypty — warstwa abstrakcji to przerost formy
  • Stabilne zaleznosci — String, Math, standardowa biblioteka
  • Value Objects — Money, Email, Address moga byc uzywane bezposrednio
// NIE potrzebujesz interfejsu dla wszystkiego
class OrderService {
    // Money to Value Object — stabilna, nie potrzebuje abstrakcji
    calculateDiscount(total: Money, pct: number): Money {
        return total.multiply(pct / 100);
    }
}
