CQRS

Command Query Responsibility Segregation — rozdzielenie modelu zapisu od modelu odczytu dla lepszej skalowalnosci i czytelnosci.

Czym jest CQRS?

CQRS to wzorzec architektoniczny polegajacy na rozdzieleniu modelu odczytu (Query) od modelu zapisu (Command). Zamiast jednego modelu obslugujacego oba zadania, tworzymy dwa niezalezne modele, kazdy zoptymalizowany pod katem swoich wymagan.

Tradycyjne podejscie (CRUD):

┌─────────┐     ┌──────────────┐     ┌──────┐
│ Klient  │────►│  Jeden model │────►│  BD  │
│         │◄────│  (CRUD)      │◄────│      │
└─────────┘     └──────────────┘     └──────┘

CQRS:

┌─────────┐  Command  ┌──────────────┐     ┌─────────┐
│ Klient  │──────────►│ Write Model  │────►│ Write   │
│         │           └──────────────┘     │ Store   │
│         │                                └────┬────┘
│         │                                     │ sync
│         │  Query    ┌──────────────┐     ┌────▼────┐
│         │◄──────────│ Read Model   │◄────│ Read    │
└─────────┘           └──────────────┘     │ Store   │
                                           └─────────┘

Dlaczego CQRS?

Problem jednego modelu

W typowej aplikacji CRUD jeden model musi obsluzuc: walidacje i reguly biznesowe (zapis), zlozone zapytania raportowe (odczyt), wyszukiwanie pelnotekstowe (odczyt) i agregacje (odczyt). To prowadzi do kompromisow — model jest zbyt zlozony dla zapisu i zbyt wolny dla odczytu.

Asymetria odczyt/zapis

W wiekszosci systemow:

Odczyty:  ████████████████████████ 90%
Zapisy:   ████                     10%

Wymagania odczytu:           Wymagania zapisu:
- Szybkosc                   - Walidacja
- Denormalizacja             - Reguly biznesowe
- Wiele widokow              - Spojnosc transakcyjna
- Stronicowanie              - Audyt
- Cache-friendly             - Idempotentnosc

Command Model (strona zapisu)

Struktura komendy i handlera

// Komenda = intencja zmiany stanu
interface CreateOrderCommand {
    type: "CreateOrder";
    customerId: string;
    items: Array<{
        productId: string;
        quantity: number;
    }>;
    shippingAddress: Address;
}

// Command Handler = logika biznesowa
class CreateOrderHandler {
    constructor(
        private readonly orderRepo: OrderRepository,
        private readonly inventory: InventoryService,
        private readonly eventBus: EventBus
    ) {}

    async handle(cmd: CreateOrderCommand): Promise<OrderId> {
        // 1. Walidacja biznesowa
        await this.inventory.checkAvailability(cmd.items);

        // 2. Utworzenie agregatu
        const order = Order.create(
            cmd.customerId, cmd.items, cmd.shippingAddress
        );

        // 3. Zapis
        await this.orderRepo.save(order);

        // 4. Publikacja zdarzen
        await this.eventBus.publish(order.domainEvents);

        return order.id;
    }
}

Walidacja komend

Komenda --► [Walidacja strukturalna] --► [Walidacja biznesowa] --► [Wykonanie]
              (format danych)              (reguly domeny)          (zapis)

Poziomy walidacji:
1. Strukturalna: czy pola sa wypelnione, typy poprawne?
2. Biznesowa:    czy klient istnieje? czy produkt jest dostepny?
3. Autoryzacja:  czy uzytkownik ma prawo wykonac te operacje?

Implementacja projekcji

// Projekcja nasluchuje na zdarzenia i aktualizuje Read Model
class OrderProjection {
    constructor(private readonly readDb: ReadDatabase) {}

    async onOrderCreated(event: OrderCreated): Promise<void> {
        await this.readDb.insert("order_views", {
            order_id: event.orderId,
            customer_name: event.customerName,
            status: "created",
            total: event.total,
            items_count: event.items.length,
            items_json: JSON.stringify(event.items),
            created_at: event.timestamp
        });
    }

    async onOrderShipped(event: OrderShipped): Promise<void> {
        await this.readDb.update("order_views",
            { order_id: event.orderId },
            {
                status: "shipped",
                shipped_at: event.timestamp,
                tracking_number: event.trackingNumber
            }
        );
    }
}

// Query Handler — prosty odczyt bez logiki biznesowej
class GetOrderQueryHandler {
    constructor(private readonly readDb: ReadDatabase) {}

    async handle(query: GetOrderQuery): Promise<OrderView> {
        return this.readDb.findOne("order_views", {
            order_id: query.orderId
        });
    }
}

Synchronizacja modeli

Synchroniczna

Command
  --► Write DB
  --► [Sync Update]
  --► Read DB

W tej samej transakcji
(strong consistency)

Proste, ale ogranicza skalowanie.

Asynchroniczna

Command
  --► Write DB
  --► [Event]
  --► Broker
  --► [Projection]
  --► Read DB

Eventual consistency

Skalowalne, wymaga obslugi opoznien.

AspektSynchronicznaAsynchroniczna
SpojnoscNatychmiastowaEventual
WydajnoscNizszaWyzsza
ZlozonoscNizszaWyzsza
SkalowalnoscOgraniczonaWysoka
NiezawodnoscZapis i projekcja powiazaneNiezalezne

CQRS + Event Sourcing

Naturalne polaczenie — Event Store jako zrodlo prawdy, projekcje jako modele odczytu:

┌─────────┐  Command   ┌──────────────┐
│ Klient  │───────────►│   Command    │
│         │            │   Handler    │
│         │            └──────┬───────┘
│         │                   │ append event
│         │            ┌──────▼───────┐
│         │            │  Event Store │ (zrodlo prawdy)
│         │            └──────┬───────┘
│         │                   │ events
│         │            ┌──────▼───────┐
│         │            │  Projection  │
│         │            │  Builder     │
│         │            └──────┬───────┘
│         │  Query     ┌──────▼───────┐
│         │◄───────────│  Read Model  │
└─────────┘            └──────────────┘

Wiele Read Models z jednego Event Store

Wzorzec Mediator (MediatR)

// Rejestracja (C#/.NET)
services.AddMediatR(cfg =>
    cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));

// Command
public record CreateOrderCommand(
    string CustomerId,
    List<OrderItemDto> Items
) : IRequest<OrderId>;

// Command Handler
public class CreateOrderHandler
    : IRequestHandler<CreateOrderCommand, OrderId>
{
    public async Task<OrderId> Handle(
        CreateOrderCommand request, CancellationToken ct)
    {
        var order = Order.Create(request.CustomerId, request.Items);
        await _repository.Save(order);
        return order.Id;
    }
}

// Query
public record GetOrderQuery(string OrderId)
    : IRequest<OrderView>;

// Controller
[HttpPost]
public async Task<ActionResult> Create(CreateOrderRequest req)
{
    var id = await _mediator.Send(
        new CreateOrderCommand(req.CustomerId, req.Items));
    return CreatedAtAction(nameof(Get), new { id }, null);
}

[HttpGet("{id}")]
public async Task<OrderView> Get(string id)
{
    return await _mediator.Send(new GetOrderQuery(id));
}

Kiedy stosowac CQRS?

Idealny dla

  • Systemow z asymetria odczyt/zapis
  • Zlozonych widokow raportowych
  • Pelnotekstowego wyszukiwania
  • Systemow z wieloma modelami odczytu
  • Aplikacji event-driven + Event Sourcing

Nie stosowac gdy

  • Proste CRUD bez zlozonej logiki
  • Maly zespol bez doswiadczenia
  • Symetryczny odczyt/zapis
  • Natychmiastowa spojnosc krytyczna
  • Ograniczony budzet na infrastrukture

Zalety i wady

ZaletyWady
Niezalezna optymalizacja odczytu i zapisuZwiekszona zlozonosc kodu i infrastruktury

Wiele widokow z jednego zrodla danychWiecej kodu do utrzymania (dwa modele)
Lepsze separation of concernsDuplikacja danych
Naturalnie wspolgra z Event SourcingWymaga dyscypliny zespolu

Podsumowanie

CQRS to wzorzec, ktory rozwiazuje realny problem asymetrii odczytu i zapisu. Nie jest uniwersalnym rozwiazaniem — stosuj go tam, gdzie jeden model nie wystarcza. Najlepiej sprawdza sie w polaczeniu z Event Sourcing i architektura event-driven, ale mozna go wdrozyc rowniez samodzielnie z synchroniczna projekcja.
