Authorization Code Flow (+ PKCE)

Najbezpieczniejszy flow — zalecany dla aplikacji webowych i mobilnych. PKCE chroni przed przechwyceniem kodu autoryzacyjnego.

1. Klient generuje code_verifier i code_challenge
   code_verifier  = losowy_string(43-128 znakow)
   code_challenge = BASE64URL(SHA256(code_verifier))

2. Przekierowanie do Authorization Server:
   GET /authorize?
     response_type=code
     &client_id=my-app
     &redirect_uri=https://myapp.com/callback
     &scope=openid profile email
     &state=random_csrf_token
     &code_challenge=E9Melhoa2OwvFrEMTJ...
     &code_challenge_method=S256

3. Uzytkownik loguje sie i wyrazenia zgode

4. Redirect z kodem:
   GET /callback?code=AUTH_CODE_xyz&state=random_csrf_token

5. Wymiana kodu na token (server-side):
   POST /token
   { "grant_type": "authorization_code",
     "code": "AUTH_CODE_xyz",
     "code_verifier": "original_code_verifier" }

6. Odpowiedz:
   { "access_token": "eyJhbG...",
     "refresh_token": "dGhpc...",
     "expires_in": 3600,
     "id_token": "eyJhbG..." }

Client Credentials Flow

Dla komunikacji server-to-server (bez uzytkownika):

POST /token
{
  "grant_type": "client_credentials",
  "client_id": "order-service",
  "client_secret": "super_secret_key",
  "scope": "inventory:read orders:write"
}

Odpowiedz:
{
  "access_token": "eyJhbGciOi...",
  "token_type": "Bearer",
  "expires_in": 3600
}

Uzycie:
GET /api/inventory
Authorization: Bearer eyJhbGciOi...

Device Authorization Flow

Dla urzadzen bez przegladarki (Smart TV, CLI, IoT):

1. Urzadzenie prosi o kod:
   POST /device/code → { "user_code": "WDJB-MJHT",
     "verification_uri": "https://auth.example.com/device" }

2. Uzytkownik wchodzi na URL i wpisuje kod na telefonie

3. Urzadzenie polluje co 5s az dostanie token

Struktura JWT

JWT sklada sie z trzech czesci: HEADER.PAYLOAD.SIGNATURE

Header

{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-2025-03"
}

Algorytmy: HS256 (symetryczny), RS256 (asymetryczny, zalecany), ES256 (ECDSA, mniejsze tokeny).

Payload (Claims)

{
  "sub": "user-123",
  "name": "Jan Kowalski",
  "role": "admin",
  "permissions": ["orders:read", "orders:write"],
  "iss": "https://auth.example.com",
  "aud": "https://api.example.com",
  "iat": 1709816000,
  "exp": 1709819600,
  "jti": "unique-token-id"
}
ClaimOpis
subSubject — identyfikator uzytkownika
issIssuer — kto wydal token
audAudience — dla kogo przeznaczony
expExpiration — czas wygasniecia
iatIssued At — czas wydania
jtiJWT ID — unikalny identyfikator

Walidacja JWT

const jwt = require('jsonwebtoken');
const jwksClient = require('jwks-rsa');

const client = jwksClient({
  jwksUri: 'https://auth.example.com/.well-known/jwks.json',
  cache: true,
  cacheMaxAge: 600000
});

async function validateToken(token) {
  const decoded = jwt.decode(token, { complete: true });
  if (!decoded) throw new Error('Invalid token');

  const key = await client.getSigningKey(decoded.header.kid);
  const publicKey = key.getPublicKey();

  return jwt.verify(token, publicKey, {
    algorithms: ['RS256'],
    issuer: 'https://auth.example.com',
    audience: 'https://api.example.com'
  });
}

Checklist walidacji

  1. Weryfikacja podpisu kluczem publicznym
  2. Sprawdzenie exp — czy token nie wygasl
  3. Sprawdzenie iss — czy wydawca jest zaufany
  4. Sprawdzenie aud — czy token jest dla tego serwisu
  5. Sprawdzenie nbf — czy token jest juz wazny
  6. Sprawdzenie wymaganych claims (role, permissions)

Rotacja kluczy (JWKS)

JWKS Endpoint: /.well-known/jwks.json
{
  "keys": [
    { "kid": "key-2025-03", ... },  // aktualny
    { "kid": "key-2025-01", ... }   // poprzedni
  ]
}

Procedura rotacji:
1. Wygeneruj nowy klucz
2. Dodaj do JWKS obok starego
3. Podpisuj nowe tokeny nowym kluczem
4. Poczekaj az stare tokeny wygasna
5. Usun stary klucz z JWKS

Refresh Tokens

Access Token:  krotki zycia (15 min), w kazdym requeście
Refresh Token: dlugi zycia (7 dni), tylko do odswiezenia

1. Login → access_token (15 min) + refresh_token (7 dni)
2. API request → Authorization: Bearer access_token
3. 401 Unauthorized (token wygasl)
4. POST /token { grant_type: "refresh_token", ... }
5. Nowy access_token + nowy refresh_token

Refresh Token Rotation

Kazde uzycie generuje nowy refresh token — stary jest uniewazniany. Ponowne uzycie starego tokena = wykrycie kradziezi.

async function refreshTokens(refreshToken) {
  const stored = await db.refreshTokens.findOne({
    token: refreshToken
  });

  if (!stored) throw new Error('Token not found');
  if (stored.revoked) {
    // Ponowne uzycie — uniewaznij cala rodzine!
    await db.refreshTokens.revokeFamily(stored.familyId);
    throw new Error('Refresh token reuse detected');
  }

  await db.refreshTokens.revoke(stored.id);
  const newAccess = generateAccessToken(stored.userId);
  const newRefresh = generateRefreshToken(
    stored.userId, stored.familyId
  );
  return { accessToken: newAccess, refreshToken: newRefresh };
}

Bezpieczenstwo JWT — czeste bledy

  1. Brak weryfikacji podpisu — zawsze weryfikuj!
  2. Algorytm "none" — nigdy nie akceptuj alg: none
  3. Zbyt dlugi czas zycia — max 15-30 minut dla access token
  4. Wrazliwe dane w payload — JWT jest base64, nie zaszyfrowany
  5. Brak walidacji iss/aud — umozliwia cross-service token reuse

Kluczowe wnioski

  1. Authorization Code + PKCE to zalecany flow dla web i mobile
  2. Client Credentials dla komunikacji server-to-server
  3. RS256 > HS256 — asymetryczne klucze bezpieczniejsze w systemach rozproszonych
  4. Access token krotki (15 min), refresh token z rotacja
  5. httpOnly cookies lub BFF pattern do przechowywania w przegladarce
  6. Rotacja kluczy przez JWKS — utrzymuj stary klucz do wygasniecia tokenow
