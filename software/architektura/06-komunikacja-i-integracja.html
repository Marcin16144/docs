Komunikacja i integracja

Jak serwisy rozmawiaja ze soba — synchronicznie i asynchronicznie.

Aktualizacja: 2026 — uwzglednia gRPC, GraphQL Federation v2, tRPC, Server-Sent Events, WebTransport, OpenTelemetry jako standard observability.

Komunikacja synchroniczna

REST API

  • Najpopularniejszy styl komunikacji
  • Zasoby identyfikowane przez URL
  • Metody HTTP: GET, POST, PUT, PATCH, DELETE
  • Bezstanowy (stateless)

Dobre praktyki: wersjonowanie API, spojne nazewnictwo zasobow, wlasciwe kody HTTP, paginacja, idempotentnosc.

gRPC

  • Wydajny protokol binarny (Protocol Buffers)
  • Silne typowanie i generowanie kodu
  • Obsluga streamingu (unary, server, client, bidirectional)
  • Dobry do komunikacji wewnetrznej miedzy serwisami
  • Pozostaje silnym wyborem w 2026 — niskie opoznienia, maly payload
  • gRPC-Web pozwala uzywac z przegladarki

GraphQL

  • Klient definiuje ksztalt odpowiedzi
  • Jeden endpoint dla wielu zapytan
  • Unika problemu over/under-fetching
  • Dobry dla zlozonych frontendow
  • GraphQL Federation v2 dojrzala — komponowanie wielu subgrafow w jeden supergraph (Apollo Router, Hot Chocolate, GraphQL Yoga)
  • Wzorce: persisted queries, APQ, defer/stream

tRPC (TypeScript-first)

  • Kontrakty typowane end-to-end bez generowania kodu (monorepo TS)
  • Idealny dla full-stack TypeScript (Next.js + Node)
  • Zerowy boilerplate — popularny w 2026 w ekosystemie TS

Server-Sent Events (SSE)

  • Jednokierunkowy streaming serwer → klient po HTTP
  • Prostsze niz WebSockets — automatyczny reconnect, dziala przez HTTP/2
  • Dobry dla powiadomien, live update'ow, streamingu LLM (token po tokenie)

WebTransport

  • Nowoczesny nastepca WebSocket oparty o HTTP/3 i QUIC
  • Obsluga wielu strumieni, datagramow (unreliable), niskie opoznienia
  • Dojrzaly w 2026 — gry, real-time collaboration, low-latency streaming

Komunikacja asynchroniczna

Message Queue (Kolejka wiadomosci)

Wiadomosc dostarczana do jednego konsumenta.

Narzedzia: RabbitMQ, Amazon SQS, Azure Service Bus

Publish/Subscribe (Pub/Sub)

Wiadomosc dostarczana do wielu subskrybentow.

Narzedzia: Apache Kafka, Google Pub/Sub, Redis Streams

Wzorce integracji

API Gateway

Pojedynczy punkt wejscia dla klientow zewnetrznych. Obsluguje routing, rate limiting, uwierzytelnianie, agregacje odpowiedzi.

Service Mesh

Warstwa infrastruktury obslugujaca komunikacje miedzy serwisami.

Narzedzia (2026): Istio (lider), Linkerd, Cilium Service Mesh (rosnie — eBPF, brak sidecara), Kuma, Consul Connect.

Saga Pattern

Zarzadzanie transakcjami rozproszonymi jako sekwencja lokalnych transakcji z kompensacjami.

1. Serwis zamowien  → Utworz zamowienie
2. Serwis platnosci → Pobierz platnosc
   (jesli blad → Kompensacja: Anuluj zamowienie)
3. Serwis magazynu  → Zarezerwuj towar
   (jesli blad → Kompensacja: Zwroc platnosc, Anuluj zamowienie)

Typy:

  • Choreografia — serwisy reaguja na zdarzenia
  • Orkiestracja — centralny koordynator zarzadza krokami

Circuit Breaker

Ochrona przed kaskadowymi awariami — po serii bledow zaprzestaje prob polaczenia.

Stany: Closed → Open → Half-Open

Retry z Exponential Backoff

Ponowne proby z rosnacym opoznieniem: 1s → 2s → 4s → 8s

Bulkhead Pattern

Izolacja zasobow — awaria jednego komponentu nie wplywa na reszte (jak grodzie na statku).

Observability komunikacji (2026)

OpenTelemetry (OTel) to de facto standard dla telemetrii (traces, metrics, logs) — zastepuje fragmentaryczne API poszczegolnych vendorow.

  • Kontekst tracingu propaguje sie przez naglowki HTTP (W3C Trace Context: traceparent, tracestate)
  • Dla gRPC kontekst przenoszony jest w metadanych
  • Dla wiadomosci asynchronicznych (Kafka, SQS) — w naglowkach wiadomosci
  • Backendy: Datadog, Honeycomb, Grafana Tempo, Jaeger, AWS X-Ray, New Relic
  • OpenTelemetry Collector jako uniwersalny przekaznik telemetrii (eliminuje vendor lock-in)
