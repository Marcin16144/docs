Bounded Context

Wyrazne granice modelu domenowego — klucz do zarzadzania zlozonoscia duzych systemow.

Czym jest Bounded Context?

Bounded Context (kontekst ograniczony) to wyrazna granica, wewnatrz ktorej dany model domenowy ma spojne, jednoznaczne znaczenie. Poza ta granica te same slowa moga oznaczac zupelnie co innego.

Kontekst Sprzedazy:
  Klient = potencjalny nabywca z budzetem, historia zakupow, segmentem

Kontekst Wysylki:
  Klient = adres dostawy, preferencje doreczenia, telefon kontaktowy

Kontekst Rozliczen:
  Klient = NIP, dane do faktury, historia platnosci, limit kredytowy

Kontekst Obslugi:
  Klient = historia zgloszen, poziom SLA, preferowany kanal kontaktu

Proba stworzenia jednej klasy Klient z wszystkimi tymi polami prowadzi do "God Object" — klasy, ktora wie i robi za duzo.

Definiowanie granic kontekstow

Sygnaly, ze potrzebujesz osobnych kontekstow

  • Ten sam termin ma rozne znaczenia w roznych czesciach systemu
  • Rozne zespoly pracuja nad roznymi aspektami domeny
  • Zmiany w jednej czesci nie powinny wymuszac zmian w innej
  • Rozne modele danych lepiej pasuja do roznych czesci systemu
  • Rozne wymagania niefunkcjonalne (np. wysoka dostepnosc vs spojnosc)

Context Mapping — wzorce relacji

Konteksty nie zyja w izolacji — musza ze soba wspolpracowac. Context Map opisuje relacje miedzy kontekstami.

Anti-Corruption Layer (ACL)

Warstwa tlumaczaca miedzy kontekstami. Chroni Twoj model przed "zanieczyszczeniem" przez zewnetrzny model.

class InventoryAntiCorruptionLayer {
    constructor(private inventoryClient: InventoryServiceClient) {}

    async checkAvailability(
        productId: ProductId, quantity: number
    ): Promise<ProductAvailability> {
        // Wywolanie do zewnetrznego kontekstu
        const stockData = await this.inventoryClient
            .getStockLevel(productId.value);

        // Tlumaczenie na nasz model domenowy
        return new ProductAvailability({
            productId,
            isAvailable: stockData.qty_on_hand >= quantity,
            availableQuantity: stockData.qty_on_hand,
            estimatedRestockDate: stockData.next_delivery_date
                ? new Date(stockData.next_delivery_date)
                : null,
        });
    }
}

// Nasz kontekst uzywa SWOJEGO modelu, nie modelu magazynu
class OrderService {
    constructor(private inventoryACL: InventoryAntiCorruptionLayer) {}

    async placeOrder(request: PlaceOrderRequest): Promise<Order> {
        for (const item of request.items) {
            const availability = await this.inventoryACL
                .checkAvailability(item.productId, item.quantity);
            if (!availability.isAvailable) {
                throw new ProductUnavailableError(item.productId);
            }
        }
        // ... reszta logiki zamowienia
    }
}

Shared Kernel

Wspolna czesc modelu, dzielona przez dwa konteksty. Musi byc mala i stabilna — zmiany wplywaja na oba konteksty.

// Shared Kernel — wspoldzielone Value Objects
class Money {
    constructor(
        readonly amount: number,
        readonly currency: Currency,
    ) {}

    add(other: Money): Money {
        this.ensureSameCurrency(other);
        return new Money(this.amount + other.amount, this.currency);
    }

    subtract(other: Money): Money {
        this.ensureSameCurrency(other);
        return new Money(this.amount - other.amount, this.currency);
    }

    private ensureSameCurrency(other: Money): void {
        if (this.currency !== other.currency)
            throw new CurrencyMismatchError(this.currency, other.currency);
    }
}

class Address {
    constructor(
        readonly street: string,
        readonly city: string,
        readonly postalCode: string,
        readonly country: CountryCode,
    ) {}
}

Open Host Service

Kontekst udostepnia dobrze zdefiniowane API (protokol) dla innych kontekstow. Konsumenci dostosowuja sie do tego protokolu.

// Kontekst Magazynu udostepnia Open Host Service
interface InventoryAPI {
    // Queries
    getStockLevel(sku: string): Promise<StockLevelResponse>;
    getStockLevels(skus: string[]): Promise<StockLevelResponse[]>;

    // Commands
    reserveStock(req: StockReservationRequest): Promise<ReservationId>;
    releaseReservation(reservationId: string): Promise<void>;

    // Events (webhooks lub message bus)
    onStockDepleted(handler: (e: StockDepletedEvent) => void): void;
    onStockReplenished(handler: (e: StockReplenishedEvent) => void): void;
}

// Published Language — wspolny format wymiany danych
interface StockLevelResponse {
    sku: string;
    quantityAvailable: number;
    quantityReserved: number;
    warehouse: string;
    updatedAt: string; // ISO 8601
}

Mapowanie kontekstow na zespoly

Bounded Contexts naturalnie mapuja sie na strukture zespolow (zgodnie z prawem Conwaya). Kazdy kontekst powinien miec jeden wlascicielski zespol.

Relacja zespolowWzorzec kontekstowyCharakterystyka
Bliska wspolpracaPartnershipDwa zespoly wspolpracuja, zmiany koordynowane
Wspolny mikroserwisShared KernelMaly, wspolny modul — wymaga dyscypliny
Dostawca-konsumentCustomer-SupplierDostawca priorytetyzuje potrzeby konsumenta
Bez wplywuConformistKonsument dostosowuje sie lub buduje ACL
IzolacjaSeparate WaysZespoly nie integruja sie — duplikacja OK

Typowe bledy

  • Zbyt duze konteksty — jesli kontekst ma setki encji, prawdopodobnie powinien byc rozbity
  • Zbyt male konteksty — jeden agregat to za malo na osobny kontekst; prowadzi do nadmiernej komunikacji
  • Brak ACL — bezposrednie uzycie modelu innego kontekstu "zanieczyszcza" Twoj model
  • Shared Kernel jako smietnik — do Shared Kernel trafia wszystko, co "wydaje sie wspolne"
  • Konteksty techniczne zamiast domenowych — podzial na "frontend", "backend", "baza danych" to nie Bounded Contexts
