Mikroserwisy

Niezalezne, male serwisy skupione na jednej funkcji biznesowej — architektura dla duzych systemow i zespolow.

Czym sa mikroserwisy?

Architektura mikroserwisowa to podejscie, w ktorym system jest budowany jako zbior malych, niezaleznych serwisow, z ktorych kazdy realizuje jedna, dobrze zdefiniowana funkcje biznesowa. Kazdy mikroserwis jest wdrazany, skalowany i rozwijany niezaleznie.

Kluczowe cechy

  1. Niezalezny deployment — kazdy serwis ma wlasny pipeline CI/CD
  2. Wlasna baza danych — Database per Service (brak wspoldzielonej BD)
  3. Autonomia zespolu — zespol odpowiada za serwis od A do Z
  4. Polyglot — kazdy serwis moze uzywac innej technologii
  5. Odpornosc na awarie — awaria jednego serwisu nie zatrzymuje systemu
  6. Niezalezne skalowanie — kazdy serwis skaluje sie osobno

Wzorce komunikacji

Synchroniczna (Request-Response)

Serwis A ──HTTP/gRPC──► Serwis B
           │
           ◄── odpowiedz ───┘

Zalety: prosty model mentalny, natychmiastowy wynik

Wady: temporal coupling, kaskadowe awarie

Asynchroniczna (Event-Driven)

Serwis A ──event──►
  [Message Broker]
    ──event──► Serwis B
    ──event──► Serwis C

Zalety: luzne powiazanie, odpornosc na awarie

Wady: eventual consistency, trudniejszy debug

Kiedy stosowac mikroserwisy?

Wymagane warunki wstepne

  1. Dojrzale DevOps — automatyzacja CI/CD, Infrastructure as Code
  2. Konteneryzacja — Docker, Kubernetes
  3. Monitoring — centralne logowanie, distributed tracing
  4. Wystarczajaco duzy zespol — minimum 20-30 deweloperow
  5. Zrozumienie domeny — dobrze poznane granice kontekstow

Sygnaly, ze potrzebujesz mikroserwisow

  • Rozne moduly wymagaja roznych cykli wdrozen
  • Jeden modul wymaga 100x wiecej zasobow niz inne
  • Zespoly blokuja sie nawzajem przy deploymencie
  • Potrzebujesz roznych technologii dla roznych problemow
  • Chcesz niezalezne skalowanie poszczegolnych funkcji

Podsumowanie

Mikroserwisy to potezny wzorzec, ale nie darmowy. Rozwiazuja problemy skali organizacyjnej i technicznej, ale wprowadzaja zlozonosc operacyjna. Zasada: zacznij od monolitu (najlepiej modularnego) i rozdzielaj na mikroserwisy dopiero gdy masz ku temu uzasadnione powody i wystarczajaca infrastrukture.
