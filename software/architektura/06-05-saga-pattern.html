Saga Pattern

Zarzadzanie transakcjami rozproszonymi jako sekwencja lokalnych transakcji z kompensacjami.

Problem transakcji rozproszonych

W monolicie transakcja bazodanowa zapewnia ACID. W mikroserwisach kazdy serwis ma wlasna baze — nie ma jednej transakcji obejmujacej wiele serwisow.

Zamowienie online — 3 serwisy, kazdy z wlasna baza:

1. Serwis zamowien  → Utworz zamowienie  ✓
2. Serwis platnosci → Pobierz platnosc   ✓
3. Serwis magazynu  → Zarezerwuj towar   ✗ BLAD!

System jest w niespolnym stanie!
Zamowienie istnieje, platnosc pobrana, ale brak towaru.

Dlaczego nie 2PC?

Two-Phase Commit (2PC) to klasyczne rozwiazanie, ale w mikroserwisach ma powazne wady:

  • Blokujacy — uczestnicy trzymaja locki do decyzji koordynatora
  • Single point of failure — awaria koordynatora blokuje wszystkich
  • Nie skaluje sie — wielu uczestnikow dramatycznie obniza wydajnosc
  • Wymaga dostepnosci — wszyscy musza byc online

Saga — rozwiazanie

Sekwencja lokalnych transakcji z kompensacjami. Jesli krok sie nie powiedzie, transakcje kompensujace wykonywane sa w odwrotnej kolejnosci.

Saga "Zloz zamowienie":

Krok 1: Utworz zamowienie (PENDING)
  ↓ sukces
Krok 2: Zarezerwuj srodki
  ↓ sukces
Krok 3: Zarezerwuj towar
  ↓ BLAD!

Kompensacja (odwrotna kolejnosc):
  ← Krok 2: Zwolnij zarezerwowane srodki
  ← Krok 1: Anuluj zamowienie (CANCELLED)

Choreografia (Choreography Saga)

Kazdy serwis reaguje na zdarzenia i publikuje nowe. Brak centralnego koordynatora — serwisy "tancza" samodzielnie.

Przeplyw sukcesu

[Serwis zamowien]
  → publikuje: OrderCreated
       ↓
[Serwis platnosci]
  slucha: OrderCreated
  → rezerwuje srodki
  → publikuje: PaymentReserved
       ↓
[Serwis magazynu]
  slucha: PaymentReserved
  → rezerwuje towar
  → publikuje: StockReserved
       ↓
[Serwis zamowien]
  slucha: StockReserved
  → potwierdza zamowienie (CONFIRMED)

Przeplyw kompensacji

[Serwis magazynu]
  brak towaru! → publikuje: StockReservationFailed
       ↓
[Serwis platnosci]
  slucha: StockReservationFailed
  → zwalnia srodki → publikuje: PaymentReleased
       ↓
[Serwis zamowien]
  slucha: PaymentReleased
  → anuluje zamowienie (CANCELLED)

Implementacja choreografii

# Serwis zamowien
class OrderService:
    def create_order(self, order_data):
        order = Order.create(status="PENDING", **order_data)
        event_bus.publish("OrderCreated", {
            "orderId": order.id,
            "userId": order.user_id,
            "total": order.total
        })
        return order

    @event_handler("StockReserved")
    def on_stock_reserved(self, event):
        order = Order.find(event["orderId"])
        order.update(status="CONFIRMED")

    @event_handler("PaymentReleased")
    def on_payment_released(self, event):
        order = Order.find(event["orderId"])
        order.update(status="CANCELLED")

# Serwis platnosci
class PaymentService:
    @event_handler("OrderCreated")
    def on_order_created(self, event):
        try:
            payment = Payment.reserve(
                userId=event["userId"],
                amount=event["total"])
            event_bus.publish("PaymentReserved", {
                "orderId": event["orderId"],
                "paymentId": payment.id})
        except InsufficientFundsError:
            event_bus.publish("PaymentFailed", {
                "orderId": event["orderId"]})

Zalety choreografii

  • Proste serwisy (reaguja na zdarzenia)
  • Brak single point of failure
  • Luzne powiazanie
  • Latwe dodawanie nowych krokow

Wady choreografii

  • Trudne sledzenie przeplywu
  • Ryzyko cyklicznych zaleznosci
  • Brak centralnego widoku stanu
  • Skomplikowane testowanie

Orkiestracja (Orchestration Saga)

Centralny koordynator (orchestrator) zarzadza przeplywem — mowi kazdemu serwisowi, co ma zrobic.

             [Orchestrator (Saga Manager)]
                 |           |           |
           (1) Create    (2) Reserve   (3) Reserve
           Order         Payment       Stock
                 |           |           |
        [Serwis zam.]  [Serwis plat.] [Serwis mag.]

Orchestrator utrzymuje stan sagi:
  Step 1: CREATE_ORDER  → SUCCESS
  Step 2: RESERVE_PAY   → SUCCESS
  Step 3: RESERVE_STOCK → FAILED → kompensacja!

Implementacja orchestratora

class OrderSagaOrchestrator:
    def __init__(self):
        self.steps = [
            SagaStep("create_order",
                action=self.create_order,
                compensation=self.cancel_order),
            SagaStep("reserve_payment",
                action=self.reserve_payment,
                compensation=self.release_payment),
            SagaStep("reserve_stock",
                action=self.reserve_stock,
                compensation=self.release_stock),
            SagaStep("confirm_order",
                action=self.confirm_order,
                compensation=None),
        ]

    def execute(self, order_data):
        saga_state = SagaState(data=order_data)
        completed_steps = []

        for step in self.steps:
            try:
                result = step.action(saga_state)
                saga_state.update(step.name, result)
                completed_steps.append(step)
            except Exception as e:
                self.compensate(completed_steps, saga_state)
                raise SagaFailedError(
                    f"Saga failed at {step.name}: {e}")
        return saga_state

    def compensate(self, completed_steps, saga_state):
        for step in reversed(completed_steps):
            if step.compensation:
                try:
                    step.compensation(saga_state)
                except Exception as e:
                    log.error(f"Compensation failed: {e}")
                    self.schedule_retry(step, saga_state)

Zalety orkiestracji

  • Czytelny przeplyw (jedno miejsce)
  • Latwe testowanie
  • Centralny widok stanu sagi
  • Prostsza obsluga bledow

Wady orkiestracji

  • Single point of failure
  • Ryzyko "god service"
  • Wieksze powiazanie
  • Orchestrator musi byc niezawodny

Transakcje kompensujace

Kompensacja to logiczne cofniecie efektu, nie rollback. Dane mogly sie zmienic od oryginalnej operacji.

Oryginalna transakcjaKompensacja
Utworz zamowienieAnuluj zamowienie (nie DELETE!)
Pobierz platnoscZwroc platnosc (refund)
Zarezerwuj towarZwolnij rezerwacje
Wyslij email z potwierdzeniemWyslij email z anulowaniem
Dodaj punkty lojalnoscioweOdejmij punkty

Zasady: kompensacja musi byc idempotentna, musi sie w koncu udac (retry), kolejnosc odwrotna, nie wszystko da sie skompensowac (np. wyslany SMS).

Idempotentnosc w sagach

Saga moze ponowic dowolny krok. Kazda operacja MUSI byc idempotentna.

# ZLE — nie idempotentne
def reserve_payment(order_id, amount):
    payment = Payment.create(
        order_id=order_id, amount=amount)
    return payment
    # Ponowne wywolanie = druga platnosc!

# DOBRZE — idempotentne
def reserve_payment(order_id, amount):
    existing = Payment.find_by_order(order_id)
    if existing:
        return existing  # juz zarezerwowana
    payment = Payment.create(
        order_id=order_id, amount=amount)
    return payment
    # Ponowne wywolanie = zwraca istniejaca

Frameworki do sag

Temporal

Platforma do orkiestracji workflow, obslugujaca dlugotrwale procesy, retry, kompensacje.

// Temporal — definicja workflow (Go)
func OrderSagaWorkflow(ctx workflow.Context,
    order OrderData) error {

    var orderResult OrderResult
    err := workflow.ExecuteActivity(ctx,
        CreateOrderActivity, order).Get(ctx, &orderResult)
    if err != nil { return err }

    var paymentResult PaymentResult
    err = workflow.ExecuteActivity(ctx,
        ReservePaymentActivity, orderResult).Get(ctx, &paymentResult)
    if err != nil {
        // Kompensacja kroku 1
        workflow.ExecuteActivity(ctx,
            CancelOrderActivity, orderResult)
        return err
    }

    err = workflow.ExecuteActivity(ctx,
        ReserveStockActivity, order.Items).Get(ctx, nil)
    if err != nil {
        // Kompensacja krokow 2 i 1
        workflow.ExecuteActivity(ctx,
            ReleasePaymentActivity, paymentResult)
        workflow.ExecuteActivity(ctx,
            CancelOrderActivity, orderResult)
        return err
    }
    return nil
}

MassTransit (.NET)

Framework komunikacji asynchronicznej z wbudowana obsluga sag jako state machines.

// MassTransit — State Machine Saga
public class OrderSagaStateMachine :
    MassTransitStateMachine<OrderSagaState>
{
    public State OrderCreated { get; private set; }
    public State PaymentReserved { get; private set; }
    public State Completed { get; private set; }
    public State Failed { get; private set; }

    public OrderSagaStateMachine()
    {
        InstanceState(x => x.CurrentState);

        Initially(
            When(OrderSubmitted)
                .TransitionTo(OrderCreated)
                .Publish(ctx =>
                    new ReservePayment(ctx.Saga.OrderId))
        );

        During(OrderCreated,
            When(PaymentReservedEvent)
                .TransitionTo(PaymentReserved)
                .Publish(ctx =>
                    new ReserveStock(ctx.Saga.OrderId)),
            When(PaymentFailedEvent)
                .TransitionTo(Failed)
                .Publish(ctx =>
                    new CancelOrder(ctx.Saga.OrderId))
        );
    }
}

Dobre praktyki

  1. Zacznij od choreografii — prostsze przypadki (2-4 kroki), migruj do orkiestracji gdy sie komplikuje
  2. Kazdy krok idempotentny — saga MUSI bezpiecznie ponawiac kroki
  3. Kompensacja musi sie udac — retry z backoff, alertowanie, reczna interwencja
  4. Monitoruj stan sag — dashboard ze statusem kazdej sagi
  5. Timeout na kazdym kroku — nie czekaj w nieskonczonosc
  6. Correlation ID — propaguj przez wszystkie kroki
  7. Testuj awarie — kazda mozliwa kombinacja bledow
  8. Unikaj sag w sagach — zagniezdzone sagi to koszmar
