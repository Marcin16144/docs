Architecture Decision Records

Dokumentowanie decyzji architektonicznych — szablony, cykl zycia, narzedzia i proces review.

Dlaczego ADR?

Bez ADR:
  "Dlaczego uzywamy MongoDB?" → "Nie wiem, ktos zdecydowal"
  → Powtarzanie dyskusji, brak kontekstu

Z ADR:
  "Dlaczego uzywamy MongoDB?" → Czyta ADR-007
  → Kontekst, alternatywy, uzasadnienie
  → Swiadoma decyzja czy zmieniac

Przyklad: Wybor bazy danych

ADR-007: PostgreSQL jako glowna baza

Status: Zaakceptowany | Data: 2025-01-20

Kontekst:
  System e-commerce — transakcje finansowe,
  relacje, full-text search, elastyczny schemat.

Rozwazone opcje:
  PostgreSQL — ACID, JSONB, full-text search, darmowy
  MongoDB    — elastyczny schemat, ale brak ACID miedzy kol.
  MySQL      — prosty, ale slabsze typy danych

Decyzja: PostgreSQL
  1. ACID krytyczne dla transakcji finansowych
  2. JSONB rozwiazuje elastyczny schemat
  3. Full-text search eliminuje Elasticsearch
  4. Zespol ma doswiadczenie

Konsekwencje (+):
  Jedna baza zamiast dwoch, silna spojnosc
Konsekwencje (-):
  Skalowanie horyzontalne trudniejsze

Przyklad: Komunikacja miedzy serwisami

ADR-012: RabbitMQ do komunikacji async

Status: Zaakceptowany | Data: 2025-02-10

Kontekst:
  5 serwisow, utrata wiadomosci niedopuszczalna,
  loose coupling, opoznienie < 1s.

Rozwazone: REST (tight coupling), RabbitMQ, Kafka (overeng.)

Decyzja: RabbitMQ — niezawodna dostawa bez
  zlozonosci Kafki.

(+) Loose coupling, odpornosc na awarie
(-) Brak replayability, dodatkowa infrastruktura

Cykl zycia ADR

PROPOSED → ACCEPTED → DEPRECATED / SUPERSEDED

Przyklad:
  ADR-007: PostgreSQL (Status: Zastapiony przez ADR-025)
  ADR-025: Migracja na CockroachDB (Status: Zaakceptowany)
    "ADR-007 zaklada wertykalne skalowanie,
     ale osiagnelismy limit jednego serwera..."

log4brains

log4brains build       # statyczna strona

Proces review

  1. Autor tworzy ADR jako PR — wypelnia szablon, status: Proposed
  2. Zespol reviewuje — kontekst kompletny? Alternatywy uczciwe? Konsekwencje realistyczne?
  3. Decyzja — akceptacja (merge), odrzucenie lub zmiana
  4. Implementacja — ADR jako referencja, link w kodzie i ticketach

Kiedy pisac ADR?

Pisz gdyNie pisz gdy
Wybierasz technologieDecyzja trywialna (formatowanie)
Zmieniasz architektureOdwracalne w minuty
Dlugoterminowe konsekwencjeStandard branzy (HTTPS)
Decyzja kontrowersyjna
Wplywa na wiele zespolow

Dobre praktyki

  1. Jeden ADR = jedna decyzja
  2. Krotkie i konkretne — 1-2 strony
  3. Pisz dla kogos kto dolacza za rok
  4. Uczciwie opisuj alternatywy — wady i zalety
  5. ADR niemutowalne — nie edytuj zaakceptowanych, tworzz nowe
  6. Linkuj w kodzie — komentarze: // patrz ADR-007
  7. Review jak kod — PR, dyskusja, merge

Kluczowe wnioski

  1. ADR zachowuje kontekst — "dlaczego" wazniejsze niz "co"
  2. Szablon Nygarda wystarcza — kontekst, decyzja, konsekwencje
  3. Cykl zycia — proposed → accepted → deprecated/superseded
  4. adr-tools lub log4brains — automatyzacja
  5. Review jak kod — PR, dyskusja, merge
  6. Niemutowalne — nowe zastepuja stare
  7. Linkuj w kodzie — ADR blisko decyzji, nie w zapomnianym wiki
