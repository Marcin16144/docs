SQL vs NoSQL

Porownanie modeli danych, gwarancji spojnosci i scenariuszy zastosowania relacyjnych i nierelacyjnych baz danych.

Modele danych

SQL (relacyjne)

Dane zorganizowane w tabelach z wierszami i kolumnami. Relacje miedzy tabelami przez klucze obce. Schema jest scisle zdefiniowana (schema-on-write).

CREATE TABLE users (
  id UUID PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  name VARCHAR(100) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE orders (
  id UUID PRIMARY KEY,
  user_id UUID REFERENCES users(id),
  total DECIMAL(10,2) NOT NULL,
  status VARCHAR(20) DEFAULT 'pending'
);

SELECT u.name, o.total, o.status
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 'abc-123';

NoSQL — Document (MongoDB)

Dane przechowywane jako dokumenty JSON/BSON. Schema elastyczna (schema-on-read). Zagniezdzanie powiazanych danych.

// Kolekcja: users
{
  "_id": "abc-123",
  "email": "jan@example.com",
  "name": "Jan Kowalski",
  "orders": [
    {
      "id": "ord-1",
      "total": 299.99,
      "status": "delivered",
      "items": [
        { "product": "Laptop Stand", "qty": 1 }
      ]
    }
  ]
}

NoSQL — Key-Value (Redis)

Najprostszy model — klucz mapowany na wartosc. Ekstremalnie szybki odczyt/zapis.

SET user:abc-123 '{"name":"Jan","email":"jan@example.com"}'
GET user:abc-123

SET session:token-xyz '{"userId":"abc-123"}'
EXPIRE session:token-xyz 3600

NoSQL — Column-Family (Cassandra)

Dane zorganizowane w rodziny kolumn. Zoptymalizowane do zapisu duzych wolumenow danych czasowych.

CREATE TABLE events (
  sensor_id TEXT,
  event_time TIMESTAMP,
  temperature DOUBLE,
  humidity DOUBLE,
  PRIMARY KEY (sensor_id, event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);

NoSQL — Graph (Neo4j)

Dane jako wezly i krawedzie. Naturalny model dla relacji wielokierunkowych — sieci spolecznosciowe, rekomendacje, fraud detection.

CREATE (jan:User {name: "Jan"})
CREATE (anna:User {name: "Anna"})
CREATE (jan)-[:FOLLOWS]->(anna)

MATCH (u:User {name: "Jan"})-[:FOLLOWS]->()-[:FOLLOWS]->(fof)
WHERE fof <> u
RETURN DISTINCT fof.name

ACID vs BASE

ACID (typowe dla SQL)

WlasciwoscOpis
AtomicityTransakcja jest niepodzielna — albo wszystko, albo nic
ConsistencyDane po transakcji sa w spojnym stanie
IsolationRownolegle transakcje nie wplywaja na siebie
DurabilityZatwierdzone dane przetrwaja awarie
 
BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
  -- Jesli cokolwiek sie nie powiedzie — oba cofniete
COMMIT;

BASE (typowe dla NoSQL)

WlasciwoscOpis
Basically AvailableSystem zawsze odpowiada (moze byc nieaktualna odpowiedz)
Soft stateStan systemu moze sie zmieniac z czasem
Eventually consistentDane beda spojne po pewnym czasie
 
Zapis do Node A --> Replikacja --> Node B (opoznienie ~ms)
                                   Node C (opoznienie ~ms)

Klient czyta z Node B zaraz po zapisie do Node A
--> Moze dostac stara wartosc (eventual consistency)
--> Po chwili wartosc bedzie aktualna

Twierdzenie CAP

Rozproszony system moze gwarantowac tylko 2 z 3 wlasciwosci: Consistency, Availability, Partition Tolerance.

         Consistency
           /     \
          /       \
    CA (SQL)    CP (MongoDB)
        |         |
   Availability  Partition Tolerance
        |         |
   AP (Cassandra, DynamoDB)
  • CP (MongoDB, HBase) — preferuj spojnosc, akceptuj niedostepnosc
  • AP (Cassandra, DynamoDB) — preferuj dostepnosc, akceptuj chwilowa niespojnosc
  • CA (tradycyjny SQL) — nie toleruje partycji sieciowych

Polyglot Persistence

Uzywanie roznych baz danych do roznych celow w jednym systemie:

┌──────────────────────────────────────────────┐
│           System e-commerce                   │
│                                               │
│  Uzytkownicy  → PostgreSQL (ACID)            │
│  Zamowienia   → PostgreSQL (ACID)            │
│  Sesje/Cache  → Redis (szybkosc)             │
│  Katalog      → MongoDB (elastyczny schemat) │
│  Wyszukiwanie → Elasticsearch (full-text)    │
│  Rekomendacje → Neo4j (graf relacji)         │
│  Analityka    → ClickHouse (OLAP)            │
│  Logi         → Elasticsearch                │
└──────────────────────────────────────────────┘

Sciezki migracji

SQL → NoSQL

  1. Zidentyfikuj wzorce dostepu — jakie zapytania sa najczestsze
  2. Zaprojektuj model pod zapytania — w NoSQL model wynika z zapytan
  3. Denormalizuj dane — zaakceptuj redundancje dla szybkosci
  4. Migruj inkrementalnie — zacznij od jednego serwisu
  5. Utrzymuj podwojny zapis (dual write) w okresie przejsciowym

NoSQL → SQL

  1. Zidentyfikuj relacje miedzy danymi
  2. Znormalizuj dane — usun redundancje
  3. Zdefiniuj schema i constrainty
  4. Migruj dane z transformacja
  5. Zweryfikuj integralnosc po migracji

Kluczowe wnioski

  1. Nie ma uniwersalnej bazy — kazda ma swoje mocne strony
  2. Zacznij od wymagan — wzorce dostepu determinuja wybor
  3. ACID nie zawsze potrzebny — eventual consistency czesto wystarczy
  4. Polyglot persistence to sila, ale i koszt operacyjny
  5. PostgreSQL to czesto najlepszy punkt startu — relacyjna z cechami NoSQL
