Architektura Event-Driven

Zdarzenia jako glowny mechanizm komunikacji — reaktywne systemy o luznych powiazaniach.

Czym jest architektura zdarzeniowa?

Architektura Event-Driven (EDA) to wzorzec, w ktorym zdarzenia (events) sa glownym mechanizmem komunikacji miedzy komponentami systemu. Zamiast bezposrednich wywolan, komponenty publikuja zdarzenia i reaguja na zdarzenia innych komponentow.

┌──────────┐  event   ┌──────────────┐  event   ┌──────────┐
│ Producent │────────►│ Event Broker  │────────►│ Konsument │
│           │         │ (Kafka/RMQ)   │────────►│ B         │
└──────────┘         └──────────────┘  event   └──────────┘
                                       ────────►┌──────────┐
                                                │ Konsument │
                                                │ C         │
                                                └──────────┘

Rodzaje zdarzen

1. Event Notification

Informacja, ze cos sie stalo — minimalny payload. Konsument musi pobrac szczegoly z serwisu zrodlowego.

{
  "type": "OrderCreated",
  "orderId": "abc-123",
  "timestamp": "2024-01-15T10:30:00Z"
}

2. Event-Carried State Transfer

Zdarzenie zawiera pelne dane potrzebne konsumentowi — jest samowystarczalny.

{
  "type": "OrderCreated",
  "orderId": "abc-123",
  "customerId": "cust-456",
  "items": [
    { "productId": "prod-1", "quantity": 2, "price": 29.99 },
    { "productId": "prod-2", "quantity": 1, "price": 49.99 }
  ],
  "totalAmount": 109.97,
  "timestamp": "2024-01-15T10:30:00Z"
}

3. Domain Event

Zdarzenie z kontekstu domenowego (DDD) — opisuje istotny fakt biznesowy:

{
  "type": "PaymentFailed",
  "aggregateId": "order-abc-123",
  "reason": "INSUFFICIENT_FUNDS",
  "attemptNumber": 3,
  "occurredAt": "2024-01-15T10:35:00Z"
}

Event Sourcing

Zamiast przechowywac biezacy stan, zapisujemy sekwencje wszystkich zdarzen:

Tradycyjne podejscie (CRUD):
┌─────────────────────────────────────┐
│ Order #123                          │
│ status: shipped                     │
│ total: 109.97                       │
│ updated_at: 2024-01-16              │
└─────────────────────────────────────┘

Event Sourcing:
┌─────────────────────────────────────┐
│ 1. OrderCreated    { total: 109.97 }│
│ 2. PaymentReceived { amount: 109.97}│
│ 3. OrderApproved   { approver: "A" }│
│ 4. ItemShipped     { tracking: "X" }│
└─────────────────────────────────────┘
Stan = replay wszystkich zdarzen

Implementacja Event Store

class EventStore:
    def __init__(self):
        self.events = []  # w produkcji: baza danych

    def append(self, aggregate_id: str, event: dict):
        self.events.append({
            "aggregate_id": aggregate_id,
            "event_type": event["type"],
            "data": event,
            "version": self._next_version(aggregate_id),
            "timestamp": datetime.utcnow()
        })

    def get_events(self, aggregate_id: str) -> list:
        return [e for e in self.events
                if e["aggregate_id"] == aggregate_id]

class Order:
    def __init__(self):
        self.status = None
        self.items = []
        self.total = 0

    @staticmethod
    def rebuild(events: list) -> "Order":
        """Odbuduj stan z sekwencji zdarzen"""
        order = Order()
        for event in events:
            order.apply(event)
        return order

    def apply(self, event: dict):
        match event["type"]:
            case "OrderCreated":
                self.status = "created"
                self.items = event["data"]["items"]
                self.total = event["data"]["total"]
            case "PaymentReceived":
                self.status = "paid"
            case "OrderShipped":
                self.status = "shipped"

Eventual Consistency

W systemach event-driven dane moga byc przejsciowo niespojne:

Czas ────────────────────────────────────────────►

Serwis A:  [Zamowienie zlozone]
                    │
                    ▼ (event)
Serwis B:          ···[Platnosc zainicjowana]
                              │
                              ▼ (event)
Serwis C:                    ···[Magazyn zaktualizowany]

Okno niespojnosci: │◄────────►│
(milisekundy do sekund)

Strategie radzenia sobie

  1. UI Optimistic Updates — pokaz uzytkownikowi oczekiwany stan
  2. Polling / WebSocket — odswiez widok po potwierdzeniu
  3. Saga Pattern — koordynacja i kompensacja
  4. Idempotencja — bezpieczne ponowne przetworzenie eventu

Event Storming

Technika warsztatowa sluzaca odkrywaniu procesow biznesowych w formie zdarzen:

Tablica Event Storming:

┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Klient   │  │ Zamowie. │  │ Platnosc │  │Zamowienie│
│ zlozyl   │─►│ utworzone │─►│ otrzymana│─►│ wyslane  │
│zamowienie│  │          │  │          │  │          │
│(pomaranc)│  │(pomaranc)│  │(pomaranc)│  │(pomaranc)│
└──────────┘  └──────────┘  └──────────┘  └──────────┘
     ↑              ↑             ↑             ↑
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Zloz     │  │ Utworz    │  │ Przyjmij │  │ Wyslij   │
│zamowienie│  │zamowienie│  │ platnosc │  │zamowienie│
│(niebieski)│ │(niebieski)│ │(niebieski)│ │(niebieski)│
└──────────┘  └──────────┘  └──────────┘  └──────────┘
  Komendy        Komendy       Komendy       Komendy

Kolory kartek w Event Storming

  • Pomaranczowy = Domain Event (co sie stalo)
  • Niebieski = Command (polecenie)
  • Zolty = Aggregate / Actor
  • Rozowy = Hotspot / Problem
  • Zielony = Read Model / View

Choreografia vs Orkiestracja

Choreografia

Serwisy samodzielnie reaguja na zdarzenia — brak centralnego koordynatora.

OrderCreated
  --► PaymentService
PaymentCompleted
  --► InventoryService
InventoryReserved
  --► ShippingService

Zalety: luzne powiazanie, latwe dodawanie konsumentow

Wady: trudne sledzenie procesu

Orkiestracja

Centralny koordynator (Saga) zarzadza procesem.

[Order Saga]
1. ReserveInventory
2. ProcessPayment
3. ArrangeShipping
4. SendConfirmation

OnFailure:
- CompensatePayment
- ReleaseInventory

Zalety: jasny przeplyw, latwy debug

Wady: centralny punkt, silniejsze powiazania

Podsumowanie

Architektura zdarzeniowa to potezny wzorzec dla systemow wymagajacych luznych powiazan, skalowalnosci i asynchronicznego przetwarzania. Wymaga dojrzalego zespolu, dobrego monitoringu i swiadomego podejscia do eventual consistency. Event Storming jest swietnym narzedziem do odkrywania zdarzen i granic kontekstow domenowych.
