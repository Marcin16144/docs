Migracje baz danych

Kontrolowane, wersjonowane zmiany schematu bazy — zero-downtime, expand-contract i narzedzia.

Dlaczego migracje sa wazne?

  • Powtarzalnosc — ten sam schemat na kazdym srodowisku
  • Historia zmian — kto, kiedy i dlaczego zmienil schemat
  • Automatyzacja — migracje w pipeline CI/CD
  • Wspolpraca — wielu developerow bez konfliktow
  • Rollback — mozliwosc cofniecia zmian

-- V001__create_users_table.sql
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(100) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);

-- V002__add_email_to_users.sql
ALTER TABLE users ADD COLUMN email VARCHAR(255);
UPDATE users SET email = 'unknown@example.com'
  WHERE email IS NULL;
ALTER TABLE users ALTER COLUMN email SET NOT NULL;
ALTER TABLE users ADD CONSTRAINT users_email_unique
  UNIQUE(email);

Zero-Downtime Migrations

Migracje bez przerwy w dzialaniu systemu. Glowna zasada: nigdy nie lamiemy kompatybilnosci wstecznej w jednym kroku.

Problem

Scenariusz 1:
  Deploy nowego kodu (uzywa nowej kolumny)
  Migracja bazy (dodaje kolumne)
  BLAD! Kod szuka kolumny, ktorej jeszcze nie ma

Scenariusz 2:
  Migracja bazy (usuwa stara kolumne)
  Deploy nowego kodu (nie uzywa starej kolumny)
  BLAD! Stary kod szuka kolumny, ktora usunieto

Expand-Contract Pattern

Kazda niebezpieczna zmiana rozbita na bezpieczne kroki:

Faza 1: EXPAND (rozszerzenie)
  Dodaj nowa kolumne/tabele
  Stary kod dziala bez zmian

Faza 2: MIGRATE (migracja danych)
  Przepisz dane do nowej struktury
  Nowy kod pisze do obu miejsc (dual write)

Faza 3: CONTRACT (skurcz)
  Usun stara kolumne/tabele
  Tylko po pelnym przejsciu na nowy kod

Przyklad: zmiana nazwy kolumny

-- ZLE: lamie kompatybilnosc
ALTER TABLE users RENAME COLUMN name TO full_name;

-- DOBRZE: 3 bezpieczne kroki

-- Krok 1: EXPAND
ALTER TABLE users ADD COLUMN full_name VARCHAR(100);
UPDATE users SET full_name = name;
CREATE TRIGGER sync_name_to_fullname
  BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION sync_columns();

-- Krok 2: DEPLOY nowy kod (uzywa full_name)
-- stary kod dalej dziala — kolumna name istnieje

-- Krok 3: CONTRACT
DROP TRIGGER sync_name_to_fullname ON users;
ALTER TABLE users DROP COLUMN name;

Przyklad: zmiana typu kolumny

-- Krok 1: EXPAND
ALTER TABLE orders ADD COLUMN total_v2 BIGINT;
UPDATE orders SET total_v2 = CAST(total * 100 AS BIGINT);

-- Krok 2: DEPLOY nowy kod (pisze do obu kolumn)
-- INSERT INTO orders (total, total_v2)
--   VALUES (19.99, 1999);

-- Krok 3: CONTRACT
ALTER TABLE orders DROP COLUMN total;
ALTER TABLE orders RENAME COLUMN total_v2 TO total;

Backward Compatible Changes

ZmianaBezpieczna?Uwagi
Dodanie tabeliTakNie wplywa na istniejacy kod
Dodanie kolumny nullableTakStary kod ignoruje nowa kolumne
Dodanie indeksu CONCURRENTLYTakNie blokuje tabeli
Zmiana nazwy kolumnyNieWymaga expand-contract
Usuwanie kolumnyNieWymaga expand-contract
Dodanie NOT NULLNieStary kod moze nie wysylac wartosci
Zmiana typu kolumnyNieWymaga expand-contract

Indeksy bez downtime

-- ZLE: blokuje tabele na czas tworzenia
CREATE INDEX idx_users_email ON users(email);

-- DOBRZE: nie blokuje tabeli (PostgreSQL)
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);

-- Uwaga: CONCURRENTLY nie dziala w transakcji
-- Flyway: ustaw executeInTransaction=false

Narzedzia do migracji

Flyway

# Zastosuj migracje
flyway migrate

# Sprawdz status
flyway info

# Waliduj migracje
flyway validate

Zalety: Prosty, SQL-native, szeroka adopcja.
Wady: Brak automatycznego rollbacka (community edition).

Liquibase

# changelog.yaml
databaseChangeLog:
  - changeSet:
      id: 001
      author: jan
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: id
                  type: UUID
                  constraints:
                    primaryKey: true
              - column:
                  name: email
                  type: VARCHAR(255)
                  constraints:
                    unique: true
      rollback:
        - dropTable:
            tableName: users

Zalety: Wiele formatow, automatyczny rollback, diff miedzy bazami.
Wady: Bardziej skomplikowany niz Flyway.

Prisma Migrate

npx prisma migrate dev --name init     # tworzenie
npx prisma migrate deploy              # produkcja
npx prisma migrate reset               # reset (dev)
npx prisma migrate status              # status

Zalety: Integracja z Prisma ORM, deklaratywny model, TypeScript.
Wady: Tylko ekosystem Prisma, mniejsza kontrola nad SQL.

Dobre praktyki

  1. Jedna migracja = jedna zmiana — latwiejszy rollback i debugging
  2. Migracje sa niezmienne — raz zastosowanej nigdy nie edytuj
  3. Testuj na kopii produkcji — nie na pustej bazie
  4. Monitoruj czas — dlugie migracje moga blokowac tabele
  5. Backupuj przed migracja — szczegolnie na produkcji
  6. Uzywaj transakcji — jesli baza to wspiera
  7. Code review migracji — traktuj jak kazdy inny kod

Kluczowe wnioski

  1. Migracje to wersjonowanie schematu — traktuj je jak kod
  2. Zero-downtime wymaga expand-contract — nigdy nie lam kompatybilnosci w jednym kroku
  3. Backward compatible changes sa zawsze bezpieczne
  4. CONCURRENTLY dla indeksow — unikaj lockow na duzych tabelach
  5. Wybor narzedzia zalezy od ekosystemu — Flyway, Liquibase, Prisma
