# CI/CD Pipelines

## Czym jest CI/CD?

**Continuous Integration (CI)** — automatyczne budowanie i testowanie kodu po kazdym uaktualnieniu. Kazdy commit uruchamia pipeline, ktory weryfikuje jakosc kodu.

**Continuous Delivery (CD)** — automatyczne przygotowanie artefaktu do wdrozenia. Po przejsciu pipeline kod jest gotowy do deploy na produkcje (reczne zatwierdzenie).

**Continuous Deployment** — automatyczne wdrozenie na produkcje bez recznej interwencji. Kazdy commit ktory przejdzie testy laduje na produkcji.

```
CI                          CD (Delivery)        CD (Deployment)
Code → Build → Test → ──→ Stage → Approval → ──→ Production
                          (artefakt gotowy)       (automatycznie)
```

## Etapy pipeline

### 1. Source (Checkout)

```yaml
# Pobranie kodu z repozytorium
- name: Checkout
  uses: actions/checkout@v4
  with:
    fetch-depth: 0  # pelna historia (dla wersjonowania)
```

### 2. Build

```yaml
- name: Setup Node.js
  uses: actions/setup-node@v4
  with:
    node-version: '20'
    cache: 'npm'

- name: Install dependencies
  run: npm ci  # deterministyczna instalacja

- name: Build
  run: npm run build

- name: Upload build artifact
  uses: actions/upload-artifact@v4
  with:
    name: build-output
    path: dist/
```

### 3. Test

```yaml
- name: Unit tests
  run: npm test -- --coverage

- name: Integration tests
  run: npm run test:integration

- name: E2E tests
  run: npx playwright test

- name: Upload coverage
  uses: actions/upload-artifact@v4
  with:
    name: coverage-report
    path: coverage/
```

### 4. Quality Gates

```yaml
- name: Lint
  run: npm run lint

- name: Type check
  run: npx tsc --noEmit

- name: Security audit
  run: npm audit --audit-level=high

- name: SonarQube analysis
  uses: sonarqube-quality-gate-action@v1
  with:
    scanMetadataReportFile: .scannerwork/report-task.txt
```

### 5. Deploy

```yaml
- name: Deploy to staging
  run: |
    aws ecs update-service \
      --cluster staging \
      --service my-app \
      --force-new-deployment

- name: Smoke tests on staging
  run: npm run test:smoke -- --base-url=https://staging.example.com
```

## Kompletny przyklad — GitHub Actions

```yaml
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  NODE_VERSION: '20'
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ─── CI: Build & Test ───────────────────────
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      - run: npm ci
      - run: npm run build
      - run: npm test -- --coverage
      - run: npm run lint

      - uses: actions/upload-artifact@v4
        with:
          name: build
          path: dist/

  # ─── Security ───────────────────────────────
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm audit --audit-level=high
      - uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}

  # ─── Docker Build ───────────────────────────
  docker:
    needs: [build, security]
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    permissions:
      contents: read
      packages: write

    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ─── Deploy Staging ─────────────────────────
  deploy-staging:
    needs: docker
    runs-on: ubuntu-latest
    environment: staging

    steps:
      - name: Deploy to staging
        run: |
          kubectl set image deployment/my-app \
            my-app=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

      - name: Smoke tests
        run: |
          curl -f https://staging.example.com/healthz || exit 1

  # ─── Deploy Production ─────────────────────
  deploy-prod:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://example.com

    steps:
      - name: Deploy to production
        run: |
          kubectl set image deployment/my-app \
            my-app=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

      - name: Verify deployment
        run: |
          kubectl rollout status deployment/my-app --timeout=300s
```

## Quality Gates

Quality gates to progi jakosci, ktore musi spelniac kod, aby przejsc dalej w pipeline.

| Quality Gate | Prog | Narzedzie |
|-------------|------|-----------|
| Pokrycie testami | >= 80% | Jest, Vitest |
| Brak bledow lint | 0 errors | ESLint, Prettier |
| Type safety | 0 errors | TypeScript |
| Brak podatnosci | 0 high/critical | npm audit, Snyk |
| Brak regresji | Wszystkie testy pass | Test framework |
| Zlozonosc cyklomatyczna | <= 15 | SonarQube |
| Duplikacja kodu | <= 3% | SonarQube |

## Zarzadzanie artefaktami

```
Pipeline Build
  ↓
Artefakt (Docker image, JAR, ZIP)
  ↓
Container Registry / Artifact Repository
  ↓
Deploy (staging → production)

Zasady:
- Buduj artefakt RAZ, wdrazaj WIELOKROTNIE
- Taguj artefakty (git SHA, semver, timestamp)
- Nigdy nie buduj ponownie na staging/prod
- Przechowuj artefakty z retencja (np. 90 dni)
```

### Wersjonowanie artefaktow

```bash
# Git SHA (dokladny commit)
ghcr.io/org/app:a1b2c3d4

# Semantic versioning
ghcr.io/org/app:1.2.3

# Environment tags
ghcr.io/org/app:latest        # najnowszy build
ghcr.io/org/app:staging       # aktualnie na staging
ghcr.io/org/app:production    # aktualnie na prod
```

## Environment Promotion

```
Feature Branch → PR → main
                       ↓
                    Build & Test
                       ↓
                   Docker Image
                       ↓
               ┌───────┴───────┐
               ↓               ↓
           Staging          Production
        (auto-deploy)     (manual approval)
               ↓               ↓
         Smoke Tests      Canary → Full
```

### Strategie wdrozeniowe

| Strategia | Opis | Ryzyko |
|-----------|------|--------|
| **Rolling** | Stopniowa podmiana instancji | Niskie |
| **Blue-Green** | Dwie identyczne infrastruktury | Niskie (szybki rollback) |
| **Canary** | Nowa wersja na malym % ruchu | Najnizsze |
| **Recreate** | Zatrzymaj stara, uruchom nowa | Downtime |

## Dobre praktyki

1. **Pipeline jako kod** — YAML w repozytorium, wersjonowany razem z kodem
2. **Szybki feedback** — pipeline powinien trwac < 10 minut (cache, rownolegle joby)
3. **Fail fast** — najszybsze testy najpierw (lint → unit → integration → e2e)
4. **Immutable artifacts** — buduj raz, wdrazaj wielokrotnie
5. **Sekrety w secret manager** — nigdy w kodzie ani w YAML
6. **Branch protection** — main wymaga przejscia pipeline + code review
7. **Rollback plan** — zawsze miej mozliwosc szybkiego powrotu

## Kluczowe wnioski

1. **CI** = automatyczne testy po kazdym uaktualnieniu — szybki feedback
2. **CD** = automatyczne wdrozenie — staging automatycznie, prod z zatwierdzeniem
3. **Quality gates** zapewniaja minimalny standard jakosci
4. **Artefakt budowany raz** — ten sam obraz na staging i produkcji
5. **Pipeline jako kod** w repozytorium — wersjonowanie i przeglad zmian
6. **Canary/Blue-Green** minimalizuja ryzyko wdrozenia
