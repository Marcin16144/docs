Zarzadzanie ryzykiem technicznym

Identyfikacja, ocena i mitygacja ryzyk technicznych w projektach programistycznych.

Czym jest ryzyko techniczne?

Ryzyko techniczne to potencjalne zdarzenie, ktore moze negatywnie wplynac na projekt, system lub organizacje. Nie chodzi o eliminowanie ryzyka — to niemozliwe — ale o swiadome zarzadzanie nim.

Ryzyko = Prawdopodobienstwo x Wplyw

Wysokie prawdopodobienstwo + Wysoki wplyw = Krytyczne ryzyko
Niskie prawdopodobienstwo + Wysoki wplyw  = Wymaga planu awaryjnego
Wysokie prawdopodobienstwo + Niski wplyw  = Wymaga monitorowania
Niskie prawdopodobienstwo + Niski wplyw   = Akceptowalne

Burza mozgow strukturalna

Przejdz przez kazda kategorie i zadaj pytania:

LUDZIE:
  - Czy mamy bus factor = 1 w jakims obszarze?
  - Czy zespol ma wymagane kompetencje?
  - Czy kluczowe osoby planuja odejscie?
  - Czy zespol jest przeciazony?

TECHNOLOGIA:
  - Czy uzywamy technologii bliskich EOL?
  - Czy zalezymy od unmaintained libraries?
  - Czy mamy single points of failure?
  - Czy architektura sie skaluje?

PROCES:
  - Czy mamy testy automatyczne?
  - Czy deployment jest zautomatyzowany?
  - Czy mamy procedury disaster recovery?
  - Czy robimy regularne security audyty?

ZEWNETRZNE:
  - Czy zalezymy od jednego dostawcy?
  - Czy nadchodza zmiany regulacyjne?
  - Czy kontrakty SLA sa odpowiednie?
  - Czy mamy plany na awarie dostawcow?

Pre-mortem

Technika "wyobraz sobie, ze projekt sie nie udal":

Scenariusz: Jest 6 miesiecy po wdrozeniu. Projekt okazal sie katastrofa.

Kazdy czlonek zespolu (niezaleznie!) pisze: "Projekt sie nie udal, poniewaz..."

  • "...nie przetestowalismy pod obciazeniem i system padl w Black Friday"
  • "...integracja z systemem platnosci zajela 3x dluzej niz zakladalismy"
  • "...nie uwzglednilismy migracji danych ze starego systemu"
  • "...kluczowy programista odszedl po 2 miesiacach"
  • "...nie zdefiniowalismy jasnych kryteriow akceptacji"

Nastepnie: kazde ryzyko trafia do rejestru ryzyk.

Ocena liczbowa

Prawdopodobienstwo (1-5):
  1 = Bardzo niskie (< 10%)
  2 = Niskie (10-25%)
  3 = Srednie (25-50%)
  4 = Wysokie (50-75%)
  5 = Bardzo wysokie (> 75%)

Wplyw (1-5):
  1 = Pomijalny (< 1 dzien opoznienia)
  2 = Niski (1-5 dni opoznienia)
  3 = Sredni (1-4 tygodnie opoznienia)
  4 = Wysoki (1-3 miesiace opoznienia)
  5 = Krytyczny (projekt zagrozony)

Risk Score = P x I

Krytyczne: 15-25 → Natychmiastowe dzialanie
Wysokie:   10-14 → Plan mitygacji wymagany
Srednie:    5-9  → Monitorowanie i plan awaryjny
Niskie:     1-4  → Akceptacja z monitorowaniem

Strategie zarzadzania ryzykiem

Cztery strategie (4T)

1. TERMINATE (Unikaj / Avoid)
   → Eliminuj ryzyko zmieniajac podejscie
   Przyklad: Zamiast budowac wlasny system auth,
   uzyj Auth0/Keycloak

2. TRANSFER (Przenies)
   → Przenies ryzyko na kogos innego
   Przyklad: SLA od cloud providera,
   ubezpieczenie, outsourcing specjalistyczny

3. TREAT (Mityguj / Mitigate)
   → Zmniejsz prawdopodobienstwo lub wplyw
   Przyklad: Regularne backupy, testy obciazeniowe,
   redundancja, monitoring

4. TOLERATE (Akceptuj / Accept)
   → Swiadomie zaakceptuj ryzyko
   Przyklad: Ryzyko przestoju < 5 min/rok
   przy koszcie eliminacji $100K

Przyklady strategii dla typowych ryzyk

RYZYKO: Bus factor = 1 (jeden programista zna krytyczny modul)
  Avoid:    Przepisanie modulu w prostszej technologii
  Transfer: Outsource wiedzy do zewnetrznego konsultanta
  Mitigate: Pair programming, dokumentacja, code review
  Accept:   Ryzyko niskie, modul sie nie zmienia

RYZYKO: Awaria bazy danych
  Avoid:    Multi-master setup (brak single point of failure)
  Transfer: Managed database (AWS RDS, Cloud SQL) — SLA 99.95%
  Mitigate: Automatyczny failover, replikacja, backupy co godzine
  Accept:   Dla systemu dev/staging — akceptowalne

RYZYKO: Zmiana regulacji (np. nowe wymagania GDPR)
  Avoid:    Nie zbieraj danych osobowych (rzadko mozliwe)
  Transfer: Konsultant prawny + DPO
  Mitigate: Privacy by design, audyty kwartalne, elastyczna architektura
  Accept:   Monitoruj zmiany, reaguj gdy sie pojawia

Zarzadzanie dlugiem technicznym

Typy dlugu technicznego

1. Celowy (Deliberate):
   "Wiemy, ze to hack, ale musimy zdazyc na deadline.
    Naprawimy w nastepnym sprincie."
   → Akceptowalny jesli udokumentowany i zaplanowany

2. Niecelowy (Inadvertent):
   "Nie wiedzielismy, ze to jest zle podejscie."
   → Wynik braku wiedzy, wymaga edukacji

3. Bit rot:
   "Kiedys to bylo OK, ale technologia poszla do przodu."
   → Naturalny proces, wymaga regularnego refactoringu

Regula "15%"

Przeznacz 15-20% capacity zespolu na spłate dlugu technicznego:

Sprint capacity: 100 story points
  → 80 SP na features
  → 15 SP na dlug techniczny
  → 5 SP na spike/research

Bez tej reguly dlug rosnie eksponencjalnie:
  Kwartal 1: "mamy troche dlugu, ale damy rade"
  Kwartal 2: "development trwa dluzej niz powinien"
  Kwartal 3: "polowa czasu idzie na obchodzenie problemow"
  Kwartal 4: "musimy przepisac system od nowa" (Big Rewrite)

Spike Solutions i Prototypowanie

Spike Solution

Timeboxowane badanie majace na celu redukcje ryzyka technicznego:

Spike: Weryfikacja wydajnosci Elasticsearch dla full-text search

Kontekst:
  - 50M dokumentow, srednio 5KB kazdy
  - Wymaganie: search < 200ms at p99
  - Aktualnie: PostgreSQL full-text, 2s przy 50k docs

Timebox: 2 dni

Plan:
  Dzien 1:
    - Setup klastra ES (3 wezly)
    - Import sample danych (5M dokumentow)
    - Konfiguracja analizerow i mapowan
  Dzien 2:
    - Benchmark z realistycznymi zapytaniami
    - Test przy 50M dokumentow
    - Dokumentacja wynikow

Rezultat:
  ✓ ES: 45ms at p99 dla 50M docs
  ✓ Spelnia wymaganie z duzym zapasem
  ✗ Wymaga 3x wiecej RAM niz zakladalismy
  → Rekomendacja: TAK, ale z budzetem na infra

Architecture Runway

Architecture Runway to istniejaca infrastruktura techniczna, ktora umozliwia dostarczanie features bez duzych zmian architektonicznych.

Runway wystarczajacy:
  ✓ Zespol moze dostarczac features bez zmian w architekturze
  ✓ Infrastruktura wspiera planowany wzrost przez 6+ miesiecy
  ✓ Narzedzia i procesy nie blokuja developmentu

Runway wyczerpany:
  ✗ Kazda nowa feature wymaga zmian w infrastrukturze
  ✗ Wydajnosc degraduje przy rosnacym ruchu
  ✗ Deployment trwa godziny zamiast minut
  ✗ Testy przechodza tylko "na szczescie"

Planowanie Runway

Kwartal Q1 (Runway Building):
  - Migracja CI/CD na GitHub Actions
  - Setup Kubernetes z auto-scaling
  - Implementacja distributed tracing
  - Standaryzacja API contracts (OpenAPI)

Kwartal Q2-Q3 (Feature Delivery):
  - Zespoly moga dostarczac features bez blokad
  - Runway wspiera nowe serwisy bez dodatkowej pracy infra
  - Monitoring i alerting dzialaja automatycznie

Kwartal Q4 (Runway Refresh):
  - Przeglad i aktualizacja runway
  - Nowe wymagania (np. multi-region)
  - Splata dlugu technicznego

Chaos Engineering

Proaktywne testowanie odpornosci systemu:

Zasady Chaos Engineering:

1. Zdefiniuj "steady state" (normalne zachowanie)
   → p99 < 200ms, error rate < 0.1%, CPU < 60%

2. Sformuluj hipoteze
   → "System obsluzy awarie jednego wezla bazy danych
      bez widocznego wplywu na uzytkownikow"

3. Wprowadz zmienna (eksperyment)
   → Wylacz primary database node

4. Obserwuj roznice miedzy steady state a eksperymentem
   → Zmierz: latency, error rate, recovery time

5. Wyciagnij wnioski
   → Failover zadzialal w 15s (cel: < 30s) ✓
   → 3 requesty zwrocily 500 w trakcie failover ✗
   → Action: retry logic na kliencie

Eksperymenty Chaos — poziomy ryzyka

Poziom 1 (bezpieczne):
  - Kill random pod w Kubernetes
  - Zwieksz latencje sieciowa o 100ms
  - Zablokuj polaczenie do cache

Poziom 2 (srednie ryzyko):
  - Wylacz caly serwis
  - Symuluj wyczerpanie dysku
  - Zablokuj DNS

Poziom 3 (produkcja, ostroznie):
  - Kill losowy node w klastrze
  - Symuluj awarie AZ (Availability Zone)
  - Ogranicz bandwidth miedzy serwisami

Kluczowe zasady zarzadzania ryzykiem

  1. Ryzyko to nie problem — problem juz wystapil, ryzyko to potencjalne zdarzenie
  2. Identyfikuj wczesnie — koszt reakcji rosnie wykladniczo z czasem
  3. Kwantyfikuj — "duze ryzyko" to za malo, potrzebujesz liczb
  4. Przypisuj wlascicieli — ryzyko bez wlasciciela to ryzyko nieskutecznie zarzadzane
  5. Regularnie przegladaj — ryzyka sie zmieniaja, rejestr musi byc zywy
  6. Akceptacja to tez strategia — nie kazde ryzyko wymaga dzialania
  7. Komunikuj — interesariusze musza znac ryzyka i ich status
  8. Ucz sie z porazek — post-mortem po incydencie to najlepsza lekcja
