Circuit Breaker i wzorce odpornosci

Ochrona przed kaskadowymi awariami — circuit breaker, retry, bulkhead, timeout i fallback.

Problem kaskadowych awarii

Klient → Serwis A → Serwis B (awaria!)
                      ↑ timeout 30s
          Serwis A czeka... watki sie koncza...
          Serwis A tez pada!

Klient → Serwis C → Serwis A (nie odpowiada!)
          Serwis C tez pada!

Efekt domina — jedna awaria paralizuje caly system.

Circuit Breaker — 3 stany

Wzorzec inspirowany bezpiecznikiem elektrycznym — przerywa komunikacje z niestabilnym serwisem.

                   sukces
    ┌──────────── CLOSED ←──────────┐
    │  (normalny ruch)               │
    │                                │
    │ prog bledow                    │ proba
    │ przekroczony                   │ udana
    ↓                                │
   OPEN ──── timeout ────→ HALF-OPEN
(blokuje ruch)         (przepuszcza probne zadania)
    ↑                        │
    │     proba              │
    └──── nieudana ──────────┘

CLOSED (zamkniety — normalny)

Zadania przechodza normalnie. Circuit breaker liczy bledy.

failureThreshold: 5, failureWindow: 60s

Zadanie 1: sukces  (failures: 0)
Zadanie 2: sukces  (failures: 0)
Zadanie 3: BLAD    (failures: 1)
Zadanie 5: BLAD    (failures: 2)
Zadanie 6: BLAD    (failures: 3)
Zadanie 7: BLAD    (failures: 4)
Zadanie 8: BLAD    (failures: 5) → OTWORZ circuit!

OPEN (otwarty — blokujacy)

Zadania natychmiast odrzucane bez proby polaczenia. Chroni zasoby i daje serwisowi czas na regeneracje.

Zadanie 9:  → natychmiast odrzucone
Zadanie 10: → natychmiast odrzucone
Zadanie 11: → natychmiast odrzucone

Po uplywie openTimeout (np. 30s) → HALF-OPEN

HALF-OPEN (pol-otwarty — testowy)

Przepuszcza ograniczona liczbe zadan testowych.

successThreshold: 3

Zadanie testowe 1: sukces  → (1/3)
Zadanie testowe 2: sukces  → (2/3)
Zadanie testowe 3: sukces  → (3/3) → CLOSED!

LUB:
Zadanie testowe 1: sukces  → (1/3)
Zadanie testowe 2: BLAD    → Powrot do OPEN

Implementacja (pseudokod)

class CircuitBreaker:
    def __init__(self, failure_threshold=5,
                 open_timeout=30, success_threshold=3):
        self.state = "CLOSED"
        self.failure_count = 0
        self.success_count = 0

    def call(self, func, *args, **kwargs):
        if self.state == "OPEN":
            if self._timeout_expired():
                self.state = "HALF_OPEN"
                self.success_count = 0
            else:
                raise CircuitBreakerOpenError(
                    "Circuit is OPEN")

        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise e

    def _on_success(self):
        if self.state == "HALF_OPEN":
            self.success_count += 1
            if self.success_count >= self.success_threshold:
                self.state = "CLOSED"
                self.failure_count = 0

    def _on_failure(self):
        self.failure_count += 1
        if self.state == "HALF_OPEN":
            self.state = "OPEN"
        elif self.failure_count >= self.failure_threshold:
            self.state = "OPEN"

Retry z Exponential Backoff

Automatyczne ponawianie zadan z rosnacym opoznieniem.

Natychmiastowy retry (zle):
Proba 1: BLAD → retry → BLAD → retry → BLAD...
Serwer przeciazony, a my go bombardujemy!

Exponential backoff (dobrze):
Proba 1: BLAD → czekaj 1s
Proba 2: BLAD → czekaj 2s
Proba 3: BLAD → czekaj 4s
Proba 4: BLAD → czekaj 8s
Proba 5: sukces!

Z jitter (losowe odchylenie):
Proba 1: BLAD → czekaj 1s + random(0, 500ms)
Jitter zapobiega thundering herd.

Ktore bledy ponawiac?

PONAWIAJ (transient)

  • 429 Too Many Requests
  • 500 Internal Server Error
  • 502 Bad Gateway
  • 503 Service Unavailable
  • 504 Gateway Timeout
  • Connection timeout
  • Network error

NIE PONAWIAJ (permanent)

  • 400 Bad Request
  • 401 Unauthorized
  • 403 Forbidden
  • 404 Not Found
  • 422 Validation Error

Bulkhead Pattern (wzorzec grodzi)

Izoluj zasoby — awaria jednego komponentu nie wplywa na reszte (jak grodzie na statku).

Problem: jedna pula watkow (100):
  → Serwis B (wolny!) — 80 watkow zablokowanych
  → Serwis C (OK)     — brak wolnych watkow!
  → Serwis D (OK)     — brak wolnych watkow!

Rozwiazanie: osobne pule
  Pula dla B: [30 watkow] → max 30 zablokowanych
  Pula dla C: [30 watkow] → dziala normalnie!
  Pula dla D: [30 watkow] → dziala normalnie!

Thread Pool Isolation

Osobna pula watkow per dependency.

// Resilience4j
BulkheadConfig config =
  BulkheadConfig.custom()
    .maxConcurrentCalls(30)
    .maxWaitDuration(
      Duration.ofMillis(500))
    .build();

Bulkhead bulkhead =
  Bulkhead.of("serviceB", config);

Semaphore Isolation

Ograniczenie rownoleglych wywolan bez osobnej puli.

# Python asyncio
semaphore = asyncio.Semaphore(30)

async def call_service_b():
    async with semaphore:
        return await http_client.get(
            "http://service-b/api")
    # 30 w toku — nastepne czekaja

Timeout Pattern

Maksymalny czas oczekiwania na odpowiedz. Prosty, ale krytyczny wzorzec.

import httpx

response = httpx.get("http://service-b/api/data",
    timeout=httpx.Timeout(
        connect=2.0,    # max 2s na polaczenie
        read=5.0,       # max 5s na odczyt
        write=5.0,      # max 5s na zapis
        pool=10.0       # max 10s na polaczenie z puli
    )
)

Zasada timeoutow w lancuchu

Klient → Serwis A → Serwis B → Serwis C

Timeout klienta:  10s
Timeout A → B:     5s  (mniejszy niz klienta!)
Timeout B → C:     2s  (mniejszy niz A → B!)

WAZNE: Timeout w lancuchu musi malec!

Polly (.NET)

Biblioteka odpornosci dla .NET — obsluguje wszystkie omawiane wzorce.

// Circuit Breaker + Retry + Timeout + Bulkhead
var retryPolicy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(3,
        attempt => TimeSpan.FromSeconds(
            Math.Pow(2, attempt)));  // 2s, 4s, 8s

var circuitBreaker = Policy
    .Handle<HttpRequestException>()
    .CircuitBreakerAsync(
        exceptionsAllowedBeforeBreaking: 5,
        durationOfBreak: TimeSpan.FromSeconds(30));

var timeout = Policy
    .TimeoutAsync(TimeSpan.FromSeconds(5));

var bulkhead = Policy
    .BulkheadAsync(maxParallelization: 30);

// Zlozenie polityk
var policy = Policy.WrapAsync(
    retryPolicy,      // zewnetrzna: retry
    circuitBreaker,   // circuit breaker
    bulkhead,         // bulkhead
    timeout           // wewnetrzna: timeout
);

var result = await policy.ExecuteAsync(async () =>
    await httpClient.GetAsync("http://service-b/api"));

Resilience4j (Java)

// Circuit Breaker
CircuitBreakerConfig cbConfig = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)
    .slowCallDurationThreshold(Duration.ofSeconds(2))
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .permittedNumberOfCallsInHalfOpenState(5)
    .slidingWindowSize(10)
    .build();

CircuitBreaker cb = CircuitBreaker.of("serviceB", cbConfig);

// Retry
RetryConfig retryConfig = RetryConfig.custom()
    .maxAttempts(3)
    .waitDuration(Duration.ofMillis(500))
    .retryExceptions(IOException.class)
    .build();

Retry retry = Retry.of("serviceB", retryConfig);

// Zlozenie dekoratorow
Supplier<String> decorated = Decorators
    .ofSupplier(() -> serviceB.call())
    .withCircuitBreaker(cb)
    .withRetry(retry)
    .withFallback(Arrays.asList(
        CallNotPermittedException.class),
        e -> "Fallback response")
    .decorate();

String result = decorated.get();

Spring Boot + Resilience4j

@Service
public class ProductService {

    @CircuitBreaker(name = "inventory",
        fallbackMethod = "fallback")
    @Retry(name = "inventory")
    @Bulkhead(name = "inventory")
    public CompletableFuture<Product> getProduct(String id) {
        return CompletableFuture.supplyAsync(
            () -> inventoryClient.getProduct(id));
    }

    public CompletableFuture<Product> fallback(
            String id, Throwable t) {
        return CompletableFuture.completedFuture(
            Product.defaultProduct(id));
    }
}

Dobre praktyki

  1. Zawsze ustawiaj timeout — brak timeoutu = ryzyko wyczerpania zasobow
  2. Circuit breaker per dependency — osobny breaker dla kazdego serwisu
  3. Retry tylko dla transient errors — nie ponawiaj 400/404
  4. Jitter w backoff — zapobiegaj thundering herd
  5. Fallback zawsze dostepny — nawet jesli to domyslna wartosc
  6. Monitoruj stany — dashboard ze stanem circuit breakerow
  7. Chaos Engineering — symuluj awarie (Chaos Monkey, Toxiproxy)
  8. Lacz wzorce madrze — retry wewnatrz circuit breakera, nie odwrotnie
  9. Nie ukrywaj bledow — fallback loguj, alertuj, analizuj
  10. Dostosuj progi — za niski threshold otwiera zbyt latwo, za wysoki za pozno
