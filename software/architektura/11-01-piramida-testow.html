Klasyczna piramida

Typy testow

Unit Tests

Testuja pojedyncza funkcje w izolacji. Szybkie (~ms), stabilne.

describe('calculateDiscount', () => {
  it('applies 20% discount for VIP', () => {
    expect(calculateDiscount(100, 'vip')).toBe(80);
  });

  it('applies 5% discount for regular', () => {
    expect(calculateDiscount(100, 'regular')).toBe(95);
  });

  it('no discount for unknown type', () => {
    expect(calculateDiscount(100, 'guest')).toBe(100);
  });
});

Integration Tests

Testuja wspolprace miedzy komponentami — aplikacja + baza, API.

describe('OrderService', () => {
  beforeEach(() => db.truncateAll());

  it('creates order and updates inventory', async () => {
    await db.products.insert({ id: 'p1', stock: 10 });

    const order = await orderService.create({
      items: [{ productId: 'p1', quantity: 2 }]
    });

    expect(order.status).toBe('created');
    const product = await db.products.findById('p1');
    expect(product.stock).toBe(8);
  });
});

E2E Tests

Testuja caly system z perspektywy uzytkownika.

test('user can place an order', async ({ page }) => {
  await page.goto('/login');
  await page.fill('[name=email]', 'jan@example.com');
  await page.fill('[name=password]', 'password123');
  await page.click('button[type=submit]');

  await page.goto('/products');
  await page.click('[data-testid=product-1] >> text=Dodaj');
  await page.click('text=Zamow');

  await expect(page.locator('[data-testid=order-status]'))
    .toHaveText('Zamowienie przyjete');
});

Alternatywne modele

Testing Trophy (Kent C. Dodds)

Nacisk na testy integracyjne — najlepsza rownowaga pewnosci i kosztu.

Static Analysis (TS, ESLint) — podstawa
Unit          — srednia ilosc
Integration   — NAJWIECEJ (tu wartosc)
E2E           — malo

Testing Diamond

Dla mikroserwisow — nacisk na testy kontraktowe i integracyjne.

E2E             — malo
Contract + Integ — NAJWIECEJ
Unit            — srednia ilosc

Anti-pattern: Ice Cream Cone

Duzo E2E (wolne, kruche)      ← ZLE
Duzo manualnych testow        ← ZLE
Malo integration
Bardzo malo unit

Problemy:
- Pipeline 45+ minut
- Testy losowo failuja (flaky)
- Debugging trudny
- Developerzy omijaja testy

Co testowac na kazdym poziomie

Unit:
  ✓ Logika biznesowa, kalkulacje, walidacja
  ✓ Transformacje danych, edge cases
  ✗ Baza danych, API, system plikow

Integration:
  ✓ Endpointy HTTP (request → response)
  ✓ Zapytania do bazy (CRUD)
  ✓ Integracje z zewnetrznymi API

E2E:
  ✓ Krytyczne sciezki (happy path)
  ✓ Onboarding, checkout, platnosc
  ✗ Edge cases (testuj na nizszych poziomach)

Unikanie flaky tests

  1. Nie uzywaj sleep — uzywaj waitFor
  2. Izoluj dane — kazdy test ma wlasne dane
  3. Niezaleznosc testow — test B nie wymaga danych z A
  4. Retry z umiarem — max 1 raz, potem napraw

Kluczowe wnioski

  1. Piramida to punkt wyjscia — dostosuj do projektu
  2. Testing Trophy lepsza dla typowych aplikacji webowych
  3. Ice Cream Cone to anti-pattern — unikaj za wszelka cene
  4. Integracyjne daja najlepsza wartosc za zainwestowany czas
  5. Testuj zachowanie, nie szczegoly implementacji
  6. Flaky tests — naprawiaj natychmiast lub usuwaj
  7. Pokrycie 80% to dobry cel — 100% czesto nie jest warte kosztu
