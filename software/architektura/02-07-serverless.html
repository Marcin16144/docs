Architektura Serverless

Funkcje uruchamiane na zadanie, automatyczne skalowanie i platnosc za uzycie — architektura bez zarzadzania serwerami.

Czym jest Serverless?

Serverless to model architektury, w ktorym zarzadzanie serwerami jest w pelni delegowane do dostawcy chmury. Deweloper pisze wylacznie kod funkcji biznesowych, a infrastruktura (serwery, skalowanie, patching) jest zarzadzana automatycznie. Placisz tylko za faktyczne wykorzystanie zasobow.

Tradycyjne podejscie:                Serverless:

┌──────────────────────┐             ┌──────────────┐
│  Twoj serwer 24/7    │             │  Funkcja A   │ <-- na zadanie
│  (placisz za czas)   │             └──────────────┘
│                      │             ┌──────────────┐
│  ┌────────────────┐  │             │  Funkcja B   │ <-- na zadanie
│  │  Twoja         │  │             └──────────────┘
│  │  aplikacja     │  │             ┌──────────────┐
│  └────────────────┘  │             │  Funkcja C   │ <-- na zadanie
│                      │             └──────────────┘
│  OS, runtime,        │
│  patching, scaling   │             Placisz: per wywolanie
└──────────────────────┘
  Placisz: zawsze

Anatomia funkcji serverless

AWS Lambda — Python

import json
import boto3

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('Orders')

def handler(event, context):
    """
    event   — dane wejsciowe (HTTP request, SQS message, etc.)
    context — metadane runtime (timeout, memory, request ID)
    """

    # Parsowanie requestu z API Gateway
    body = json.loads(event['body'])

    # Logika biznesowa
    order_id = create_order(body)

    # Zapis do DynamoDB
    table.put_item(Item={
        'orderId': order_id,
        'customerId': body['customerId'],
        'items': body['items'],
        'status': 'created'
    })

    return {
        'statusCode': 201,
        'body': json.dumps({'orderId': order_id}),
        'headers': {'Content-Type': 'application/json'}
    }

Azure Functions — C#

[Function("CreateOrder")]
public async Task<HttpResponseData> CreateOrder(
    [HttpTrigger(AuthorizationLevel.Function, "post")]
    HttpRequestData req)
{
    var body = await req.ReadFromJsonAsync<CreateOrderRequest>();

    var order = new Order(body.CustomerId, body.Items);
    await _orderRepository.Save(order);

    var response = req.CreateResponse(HttpStatusCode.Created);
    await response.WriteAsJsonAsync(new { order.Id });
    return response;
}

Cold Start — problem zimnego startu

Pierwsze wywolanie (Cold Start):
┌─────────┐  ┌───────────┐  ┌──────────┐  ┌──────────┐
│ Download│─►│ Init      │─►│ Bootstrap│─►│ Execute  │
│ code    │  │ container │  │ runtime  │  │ function │
│ ~50ms   │  │ ~200ms    │  │ ~300ms   │  │ ~100ms   │
└─────────┘  └───────────┘  └──────────┘  └──────────┘
                                          Total: ~650ms

Kolejne wywolania (Warm Start):
                                         ┌──────────┐
                               ─────────►│ Execute  │
                                         │ function │
                                         │ ~100ms   │
                                         └──────────┘
                                          Total: ~100ms

Typowe czasy Cold Start

RuntimeCold StartWarm

Strategie minimalizacji Cold Start

  1. Provisioned Concurrency (AWS) — instancje zawsze gotowe
  2. Warmup triggers — cykliczne pingowanie funkcji
  3. Mniejsze pakiety — mniej kodu = szybszy start
  4. Lazy initialization — polaczenia inicjalizowane gdy potrzebne
  5. SnapStart (Java/AWS) — snapshot JVM po inicjalizacji
  6. Lekkie runtime'y — Go, Rust zamiast Java, .NET

Limity wykonania

Typowe limity FaaS (AWS Lambda):

Timeout:           max 15 min
Pamiec:            128 MB — 10 GB
Payload:           6 MB sync, 256 KB async
Concurrent:        1000 domyslnie (zwiekszalne)
Temp storage:      512 MB — 10 GB (/tmp)
Deploy package:    50 MB (zip), 250 MB (unzipped)

Implikacje: dlugie procesy wymagaja Step Functions, duze pliki — streaming do S3, stan — w DynamoDB/Redis, polaczenia DB — przez RDS Proxy.

Model kosztow

Koszt = (Liczba wywolan x Cena/wywolanie)
      + (GB-sekundy x Cena/GB-s)

Przyklad AWS Lambda:
- $0.20 / milion wywolan
- $0.0000166667 / GB-sekunda

Obliczenie (1 mln wywolan/mies, 256 MB, 200ms):
Koszt = $0.20 + (1M x 0.256GB x 0.2s x $0.0000166667)
      = $0.20 + $0.85
      = ~$1.05 / miesiac

vs EC2 t3.micro: ~$7.50 / miesiac (zawsze wlaczony)
Koszt vs ruch:

  Koszt
    ↑
    │        ╱ EC2 / Kontenery (staly + rosnie wolniej)
    │       ╱
    │      ╱    ╱ Serverless (brak stalego, rosnie liniowo)
    │     ╱   ╱
    │    ╱  ╱
    │   ╱ ╱
    │  ╱╱
    │ ╱
    └──────────────────────────► Ruch

Niski ruch: Serverless wygrywa
Wysoki staly ruch: EC2/kontenery wygrywaja

Event Triggers — zrodla zdarzen

Zrodla zdarzen (AWS):

HTTP:        API Gateway --► Lambda
Queue:       SQS --► Lambda
Stream:      Kinesis / DynamoDB Streams --► Lambda
Storage:     S3 (upload/delete) --► Lambda
Schedule:    EventBridge (cron) --► Lambda
Database:    DynamoDB --► Lambda
Auth:        Cognito triggers --► Lambda
IoT:         IoT Core --► Lambda
CDN:         CloudFront (Lambda@Edge)

Przykladowe scenariusze

1. Przetwarzanie obrazow:
   S3 upload --► Lambda (resize) --► S3 (thumbnails)

2. Webhook processing:
   API Gateway --► Lambda --► DynamoDB + SQS

3. Scheduled reports:
   EventBridge (cron: 0 8 * * MON) --► Lambda --► SES (email)

4. Real-time stream:
   Kinesis --► Lambda --► Elasticsearch + S3

5. API backend:
   API Gateway --► Lambda --► DynamoDB / RDS Proxy

Vendor Lock-in

Problem:
Twoj kod ──► AWS Lambda API
                │
                ├── event format (specyficzny AWS)
                ├── context object (specyficzny AWS)
                ├── IAM permissions (specyficzny AWS)
                ├── DynamoDB SDK (specyficzny AWS)
                └── S3 integration (specyficzny AWS)

Migracja do Azure/GCP = przepisanie znacznej czesci kodu

Strategie minimalizacji lock-in

  1. Architektura heksagonalna — izolacja logiki biznesowej od providerow
  2. Serverless Framework / SST — abstrakcja nad providerami
  3. Kontenery — AWS Fargate, Cloud Run jako middle-ground
  4. Standardy — CloudEvents format dla zdarzen

Kiedy stosowac Serverless?

Idealny dla

  • Nieregularnego ruchu (spiky traffic)
  • API z niskim/srednim ruchem
  • Przetwarzania zdarzen (event processing)
  • Automatyzacji (scheduled tasks, cron)
  • MVP i prototypow
  • Microservices z prosta logika

Nieodpowiedni dla

  • Stalego, wysokiego ruchu (drozszy)
  • Ultra-niskiej latencji (cold start)
  • Dlugotrwalych procesow (> 15 min)
  • Aplikacji wymagajacych duzego RAM/CPU
  • Systemow z stalymi polaczeniami (WebSocket)

Podsumowanie

Serverless to potezny model dla scenariuszy z nieregularnym ruchem, event processing i szybkim prototypowaniem. Kluczowe jest zrozumienie limitow (cold start, timeout, vendor lock-in) i swiadome projektowanie — izolacja logiki biznesowej od providerow (architektura heksagonalna) znaczaco ulatwia przyszla migracje i testowanie.
