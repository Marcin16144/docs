Zarzadzanie Dockerem

Narzedzia, GUI, monitoring i self-hosted PaaS — Portainer, Dockge, Arcane, Coolify, Beszel, Lazydocker

Po co narzedzia do zarzadzania?

Samo CLI docker wystarcza do wszystkiego, ale przy wielu kontenerach, stackach i hostach wygodniej jest miec panel: podglad statusu, logi na zywo, metryki, restart jednym klikiem, deploy stacka z compose.yaml, a nawet deploy aplikacji prosto z gita. Narzedzia dziela sie na kilka kategorii:

  • Web GUI — pelny panel w przegladarce (Portainer, Dockge, Arcane, Yacht)
  • Self-hosted PaaS — deploy aplikacji jak na Heroku/Vercel, na wlasnym serwerze (Coolify, Dokploy, CapRover)
  • Home server / all-in-one — "app store" do domowego serwera (CasaOS, Cosmos, Komodo)
  • TUI — panel w terminalu, bez przegladarki (Lazydocker, ctop, Oxker)
  • Logi — przegladarka logow na zywo (Dozzle)
  • Metryki / monitoring — CPU/RAM/sieci, alerty (Beszel, Netdata, Glances, cAdvisor + Prometheus + Grafana, Uptime Kuma)
  • Auto-update — aktualizacja obrazow / powiadomienia (Watchtower, Diun, What's up Docker)
  • Narzedzia pomocnicze — analiza obrazow (Dive)
  • Desktop — aplikacje natywne (Docker Desktop, Podman Desktop, VS Code, JetBrains)

Zanim podlaczysz cokolwiek do docker.sock

Niemal kazde z tych narzedzi montuje /var/run/docker.sock. Dostep do tego socketu to de facto root na hoscie — kto steruje Dockerem, ten moze uruchomic uprzywilejowany kontener i przejac maszyne. Nie wystawiaj tych paneli do internetu bez uwierzytelnienia. Szczegoly w sekcji Bezpieczenstwo zarzadzania.

Portainer — flagowy panel web

Portainer to najpopularniejszy panel web do Dockera. Wersja Community Edition (CE) jest darmowa i open source; Business Edition (BE) dodaje RBAC, integracje z LDAP/OAuth, wsparcie. Obsluguje kontenery, obrazy, wolumeny, sieci, stacki (compose), szablony aplikacji oraz wiele srodowisk (zdalne hosty, Swarm, Kubernetes) przez agenta.

Instalacja (Linux / macOS / WSL2)

# Wolumen na dane Portainera (konfiguracja, uzytkownicy)
docker volume create portainer_data

docker run -d \
  --name portainer \
  --restart=always \
  -p 9443:9443 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v portainer_data:/data \
  portainer/portainer-ce:lts

# Panel: https://localhost:9443
# Pierwsze wejscie: ustaw haslo admina (masz ~5 min, potem trzeba restartowac kontener)

Wersja compose

# compose.yaml
services:
  portainer:
    image: portainer/portainer-ce:lts
    container_name: portainer
    restart: always
    ports:
      - "9443:9443"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - portainer_data:/data
volumes:
  portainer_data:
docker compose up -d

Windows (Docker Desktop + WSL2)

Najprosciej uruchomic powyzszy compose.yaml z poziomu WSL2 (terminal Ubuntu) — sciezka socketu /var/run/docker.sock dziala wtedy normalnie. Jesli odpalasz docker run bezposrednio z PowerShell, dodaj wiodacy ukosnik, zeby PowerShell nie psul sciezki:

docker run -d --name portainer --restart=always -p 9443:9443 `
  -v //var/run/docker.sock:/var/run/docker.sock `
  -v portainer_data:/data `
  portainer/portainer-ce:lts

Panel dostepny pod https://localhost:9443 z przegladarki Windows (Docker Desktop forwarduje port z WSL2).

Wiele hostow — Portainer Agent

Aby zarzadzac zdalnym hostem z jednego panelu, na tamtej maszynie uruchamiasz agenta, a w panelu dodajesz srodowisko (Environments → Add → Agent):

# Na zdalnym hoscie
docker run -d \
  --name portainer_agent \
  --restart=always \
  -p 9001:9001 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /var/lib/docker/volumes:/var/lib/docker/volumes \
  portainer/agent:lts

Obrazy: hub.docker.com/r/portainer/portainer-ce · agent: portainer/agent

Dockge — lekki menedzer stackow compose

Dockge (autor Louis Lam, tworca Uptime Kuma) to lekki panel skupiony na stackach Docker Compose. Edytujesz compose.yaml w przegladarce, widzisz logi na zywo, konwertujesz docker run na compose. Pliki stackow trzyma w zwyklym katalogu na hoscie (/opt/stacks), wiec sa czytelne i przenosne — nie sa zamkniete w bazie aplikacji. Bez skanowania, RBAC czy OIDC — po prostu czysty panel do stackow.

# Przygotuj katalogi
mkdir -p /opt/dockge/data /opt/stacks
cd /opt/dockge

# compose.yaml
services:
  dockge:
    image: louislam/dockge:1
    container_name: dockge
    restart: unless-stopped
    ports:
      - "5001:5001"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - ./data:/app/data
      - /opt/stacks:/opt/stacks
    environment:
      - DOCKGE_STACKS_DIR=/opt/stacks
docker compose up -d
# Panel: http://localhost:5001

Obraz: hub.docker.com/r/louislam/dockge · repo: github.com/louislam/dockge

Arcane — nowoczesny panel web z GitOps

Arcane to mlody (2025), szybko zyskujacy popularnosc panel web. Napisany w Go, dziala jako pojedynczy kontener z malym zuzyciem pamieci. Laczy zarzadzanie kontenerami/obrazami/wolumenami/sieciami z silna obsluga Compose (szablony stackow), web-terminalem, logami na zywo i GitOps (deploy stackow z repo). Czysty interfejs (SvelteKit) i prosty update przez docker compose pull.

# compose.yaml
services:
  arcane:
    image: ghcr.io/getarcaneapp/manager:latest
    container_name: arcane
    restart: unless-stopped
    ports:
      - "3552:3552"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - arcane-data:/app/data
    environment:
      - APP_URL=http://localhost:3552
      - PUID=1000
      - PGID=1000
      - ENCRYPTION_KEY=WSTAW_32_BAJTOWY_SEKRET
      - JWT_SECRET=WSTAW_32_BAJTOWY_SEKRET
volumes:
  arcane-data:
# Wygeneruj sekrety
openssl rand -hex 32   # do ENCRYPTION_KEY
openssl rand -hex 32   # do JWT_SECRET
# Panel: http://localhost:3552

Obraz: ghcr.io/getarcaneapp/manager · repo: github.com/getarcaneapp/arcane · docs: getarcane.app

Self-hosted PaaS — deploy jak Heroku, na wlasnym serwerze

To wyzsza polka niz "panel do kontenerow". Self-hosted PaaS daje workflow w stylu Heroku/Vercel/Render: git push → build → deploy, automatyczny HTTPS (Let's Encrypt), bazy danych jednym klikiem, podglad logow i rollback — ale na Twoim VPS, bez rachunków za chmurę. Pod spodem i tak siedzi Docker (czesto + Traefik jako reverse proxy).

Coolify

Najbardziej kompletny i dopracowany. Najwiekszy katalog szablonow, ladny UI, pelna obsluga Docker Compose, bazy danych, podglad. W zamian nieco wyzsze zuzycie zasobow na idle (rzedu kilku % CPU).

# Instalacja (skrypt oficjalny)
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | bash
# Panel: http://<ip-serwera>:8000

Dokploy

Lzejszy i prostszy — czysty UI, mniej opcji, niskie zuzycie na idle. Oparty o Traefik. Swietny, gdy wdrazasz kilka aplikacji i nie potrzebujesz zaawansowanych funkcji.

# Instalacja (skrypt oficjalny)
curl -sSL https://dokploy.com/install.sh | sh
# Panel: http://<ip-serwera>:3000
# Obraz: dokploy/dokploy

CapRover

Najstarszy i bardzo konfigurowalny, oparty o Docker Swarm, sporo aplikacji "one-click". Minus: slabe wsparcie Compose (zorientowany na pojedyncze kontenery) i nieco przestarzaly interfejs.

docker run -d -p 80:80 -p 443:443 -p 3000:3000 \
  -e ACCEPTED_TERMS=true \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /captain:/captain \
  caprover/caprover
# Dalej konfiguracja przez CLI: npm i -g caprover && caprover serversetup

Ktore PaaS wybrac?

  • Coolify — najwiecej funkcji, najlepszy dla wiekszosci; warto, jesli chcesz "wszystko w jednym".
  • Dokploy — gdy zalezy Ci na lekkosci i prostocie (2–5 aplikacji na malym VPS).
  • CapRover — gdy chcesz Swarm i maksimum kontroli, akceptujesz slabszy Compose i UI.

PaaS vs Portainer/Dockge: PaaS to deploy aplikacji z kodu (zastepuje Heroku); Portainer/Dockge to zarzadzanie istniejacymi kontenerami. Czesto uzywa sie obu, ale uwazaj, by nie zarzadzac tych samych kontenerow dwoma narzedziami naraz.

Obrazy/strony: Coolify · Dokploy · CapRover

Lazydocker — panel w terminalu (TUI)

Lazydocker (autor Jesse Duffield) to szybki panel tekstowy: lista kontenerow, logi, statystyki CPU/RAM, restart/stop/usun, czyszczenie — wszystko z klawiatury, bez przegladarki. Idealny na serwer SSH.

# macOS / Linux (Homebrew)
brew install lazydocker

# Windows (Scoop)
scoop install lazydocker

# Skrypt (Linux/macOS)
curl https://raw.githubusercontent.com/jesseduffield/lazydocker/master/scripts/install_update_linux.sh | bash

# Go
go install github.com/jesseduffield/lazydocker@latest

# Uruchom
lazydocker

Bez instalacji, jako kontener:

docker run --rm -it \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v ~/.config/lazydocker:/.config/jesseduffield/lazydocker \
  lazyteam/lazydocker

Skroty: x menu, d usun, s stop, r restart, Enter logi, [ / ] zakladki. Repo: github.com/jesseduffield/lazydocker

ctop i Oxker — metryki kontenerow w terminalu

ctop to "top dla kontenerow" — lista z CPU, RAM, siecia i I/O na zywo. Tylko podglad metryk, lekki.

docker run --rm -ti \
  --name ctop \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  quay.io/vektorlab/ctop:latest

Oxker to nowsza alternatywa napisana w Rust — minimalna, szybka, z logami i podstawowym sterowaniem kontenerami (start/stop/restart) z poziomu TUI.

docker run --rm -it \
  -v /var/run/docker.sock:/var/run/docker.sock \
  mrjackwills/oxker

Repo: ctop · oxker

Dozzle — logi na zywo w przegladarce

Dozzle to lekka przegladarka logow w czasie rzeczywistym — bez bazy, bez gromadzenia historii (czyta logi Dockera w locie). Swietne do szybkiego debugowania. Obsluguje tez wiele hostow (tryb agenta) i wyszukiwanie.

docker run -d \
  --name dozzle \
  --restart=unless-stopped \
  -p 8080:8080 \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  amir20/dozzle:latest

# Panel: http://localhost:8080

Socket podpiety jako :ro (read-only) — Dozzle tylko czyta logi, nie potrzebuje zapisu. Obraz: hub.docker.com/r/amir20/dozzle

Logi na zywo vs archiwizacja: Dozzle pokazuje strumien "tu i teraz". Jesli potrzebujesz przechowywac i przeszukiwac historie logow, zbuduj stack Grafana Loki + Promtail/Alloy + Grafana — to logowy odpowiednik Prometheusa.

Glances — monitoring hosta i kontenerow

Glances pokazuje pelny obraz systemu (CPU, RAM, dyski, siec, procesy) oraz kontenery Dockera. Dziala w terminalu albo jako serwer web.

docker run -d \
  --name glances \
  --restart=unless-stopped \
  -p 61208:61208 \
  -e GLANCES_OPT="-w" \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  --pid host \
  nicolargo/glances:latest

# Panel web: http://localhost:61208

Obraz: hub.docker.com/r/nicolargo/glances

Pelny monitoring: cAdvisor + Prometheus + Grafana

Standardowy, produkcyjny stack metryk. cAdvisor (Google) zbiera metryki kontenerow, Prometheus je przechowuje i odpytuje, Grafana rysuje dashboardy i wysyla alerty.

# compose.yaml
services:
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:latest
    container_name: cadvisor
    restart: unless-stopped
    ports:
      - "8081:8080"
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro

  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    restart: unless-stopped
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prometheus_data:/prometheus

  grafana:
    image: grafana/grafana:latest
    container_name: grafana
    restart: unless-stopped
    ports:
      - "3000:3000"
    volumes:
      - grafana_data:/var/lib/grafana

volumes:
  prometheus_data:
  grafana_data:
# prometheus.yml — skad zbierac metryki
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: cadvisor
    static_configs:
      - targets: ["cadvisor:8080"]

Grafana na http://localhost:3000 (login admin / admin). Dodaj zrodlo Prometheus (http://prometheus:9090) i zaimportuj gotowy dashboard (np. ID 193 "Docker monitoring"). Obrazy: cAdvisor · Prometheus · Grafana

Lzejszy monitoring: Beszel i Netdata

Pelny stack Prometheus+Grafana bywa przerostem formy dla kilku serwerow. Dwie popularne alternatywy w 2026:

Beszel — ultralekki (homelab)

Beszel to lekki monitor: jeden binarny hub (dashboard web) + agent na kazdym hoscie. Agent zuzywa ~10 MB RAM (dla porownania Netdata 200–500 MB, Prometheus 300 MB+). Zbiera CPU, RAM, dysk, siec i statystyki kontenerow Docker, ma alerty i historie. Idealny dla 1–20 serwerow.

# Hub (dashboard) — compose.yaml
services:
  beszel:
    image: henrygd/beszel
    container_name: beszel
    restart: unless-stopped
    ports:
      - "8090:8090"
    volumes:
      - ./beszel_data:/beszel_data
# Panel: http://localhost:8090 (gotowy compose agenta skopiujesz z UI przy dodawaniu hosta)
# Agent na monitorowanym hoscie
services:
  beszel-agent:
    image: henrygd/beszel-agent
    container_name: beszel-agent
    restart: unless-stopped
    network_mode: host
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    environment:
      LISTEN: 45876
      KEY: "ssh-ed25519 AAAA...."   # klucz z hub UI

Obrazy: henrygd/beszel · henrygd/beszel-agent · beszel.dev

Netdata — pelna obserwowalnosc

Netdata to bogata platforma: rozdzielczosc 1 sekundy, 2000+ metryk out-of-the-box, wykrywanie anomalii (ML), gotowe dashboardy — przy wiekszym zuzyciu zasobow. Dobry dla zlozonej infrastruktury i gdy chcesz natychmiast "wszystko widziec" bez budowania dashboardow.

docker run -d \
  --name netdata \
  --restart=unless-stopped \
  -p 19999:19999 \
  --cap-add SYS_PTRACE --cap-add SYS_ADMIN \
  --security-opt apparmor=unconfined \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  -v netdataconfig:/etc/netdata \
  -v netdatalib:/var/lib/netdata \
  netdata/netdata
# Panel: http://localhost:19999

Obraz: hub.docker.com/r/netdata/netdata

Uptime i status: Uptime Kuma

Uptime Kuma (tez autorstwa Louisa Lama) monitoruje dostepnosc: HTTP(s), TCP, ping, DNS, kontenery Docker. Wysyla alerty (90+ kanalow: e-mail, Telegram, Discord, ntfy...) i publikuje publiczne status pages. Uzupelnia metryki (Beszel/Netdata) o pytanie "czy usluga w ogole odpowiada?".

docker run -d \
  --name uptime-kuma \
  --restart=unless-stopped \
  -p 3001:3001 \
  -v uptime-kuma:/app/data \
  louislam/uptime-kuma:1
# Panel: http://localhost:3001

Obraz: hub.docker.com/r/louislam/uptime-kuma

Analiza obrazow: Dive

Dive nie zarzadza kontenerami — analizuje warstwy obrazu: co kazda warstwa dodaje, gdzie marnujesz miejsce, jaka jest "efficiency". Nieoceniony przy optymalizacji rozmiaru obrazow (zobacz tez rozdzial 06. Dockerfile).

docker run --rm -it \
  -v /var/run/docker.sock:/var/run/docker.sock \
  wagoodman/dive:latest \
  <obraz-do-analizy>            # np. node:20-alpine

Repo: github.com/wagoodman/dive

Automatyczne aktualizacje obrazow

Wazne (2026): oryginalny Watchtower (containrrr/watchtower) zostal zarchiwizowany 17.12.2025 — repozytorium jest tylko-do-odczytu, brak nowych poprawek i lat bezpieczenstwa. Aktywnie utrzymywany fork spolecznosci to nickfedor/watchtower (Nicholas Fedor) — drop-in replacement: w compose.yaml wystarczy zmienic nazwe obrazu, konfiguracja zostaje ta sama.

Watchtower (fork) — auto-update kontenerow

Watchtower sprawdza co jakis czas, czy jest nowsza wersja obrazu i podmienia kontener automatycznie (z zachowaniem tych samych opcji uruchomienia).

docker run -d \
  --name watchtower \
  --restart=unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock \
  nickfedor/watchtower \
  --interval 86400        # sprawdzaj raz na dobe (w sekundach)

# Tylko powiadom, nie aktualizuj automatycznie:
#   --monitor-only
# Aktualizuj wybrane kontenery: dodaj label na kontenerze
#   com.centurylinklabs.watchtower.enable=true  + flaga --label-enable

Uwaga — auto-update w produkcji. Watchtower podmieni obraz bez Twojej wiedzy — jesli upstream wypusci zepsuta wersje, polozy Ci usluge. W produkcji wybieraj raczej kontrolowany deploy przez CI/CD i pinowane wersje (:1.27.3 zamiast :latest). Auto-update zostaw dla homelabu albo polacz z trybem --monitor-only + powiadomienia.

Diun — tylko powiadomienia

Diun (Docker Image Update Notifier) nic nie aktualizuje — tylko sledzi obrazy i wysyla powiadomienie (e-mail, Discord, Telegram, Slack, ntfy...), gdy pojawi sie nowy tag. Bezpieczniejsze niz auto-update.

docker run -d \
  --name diun \
  --restart=unless-stopped \
  -e "TZ=Europe/Warsaw" \
  -e "DIUN_WATCH_SCHEDULE=0 */6 * * *" \
  -e "DIUN_PROVIDERS_DOCKER=true" \
  -v /var/run/docker.sock:/var/run/docker.sock:ro \
  -v diun_data:/data \
  crazymax/diun:latest

Obraz: hub.docker.com/r/crazymax/diun · alternatywa z UI: What's up Docker (github.com/getwud/wud)

Konfiguracja per platforma

Wszystkie narzedzia laczace sie z daemonem potrzebuja socketu Dockera. Jego sciezka zalezy od platformy i backendu:

Platforma / backendSciezka socketuUwagi
Linux (root)/var/run/docker.sockStandard. Dodaj usera do grupy docker
Linux (rootless)$XDG_RUNTIME_DIR/docker.sock
(np. /run/user/1000/docker.sock)		Bezpieczniejsze. Ustaw DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
Windows + Docker Desktop (WSL2)/var/run/docker.sock (w WSL2)
//var/run/docker.sock (w PowerShell)		Kontenery narzedzi uruchamiaj z WSL2
macOS + Docker Desktop/var/run/docker.sockSymlink do socketu w VM
macOS + Colima~/.colima/default/docker.sockUzyj docker context use colima lub ustaw DOCKER_HOST
macOS + OrbStack/var/run/docker.sockPodpiety automatycznie; ma tez wlasny natywny panel

Windows

  • Uruchamiaj kontenery narzedzi z terminala WSL2 — socket dziala natywnie, a dane trzymaj w named volumes (nie bind z C:\ — wolne).
  • W docker run z PowerShell uzyj //var/run/docker.sock (podwojny ukosnik) i backticka ` do lamania linii.
  • Panele otwierasz w przegladarce Windows pod localhost — Docker Desktop forwarduje porty z WSL2.
  • Dodaj --restart=always, zeby panel wstawal po restarcie Docker Desktop.

macOS

  • Docker Desktop i OrbStack: socket pod /var/run/docker.sock — komendy jak na Linux.
  • Colima: socket jest w ~/.colima/.... Jesli narzedzie montuje sztywno /var/run/docker.sock, ustaw kontekst (docker context use colima) albo zrob symlink.
  • Bind mounty na macOS sa wolne (VM) — dane paneli trzymaj w named volumes.

Linux

  • Najprostsza i najszybsza platforma — daemon dziala natywnie.
  • Tryb rootless: socket w /run/user/<uid>/docker.sock; w compose podaj go w volumes i ustaw DOCKER_HOST.
  • Przy SELinux (Fedora/RHEL) dodaj sufiks :z lub :ro,z do montowanego socketu/wolumenu.
  • Uzyj --restart=unless-stopped + ewentualnie jednostki systemd, zeby panel startowal z systemem.

Bezpieczenstwo zarzadzania

Socket Dockera = root na hoscie. Kontener z /var/run/docker.sock moze uruchomic uprzywilejowany kontener montujacy caly system plikow hosta — czyli przejac maszyne. Traktuj kazdy panel z dostepem do socketu jak konto root.

  • Nie wystawiaj paneli do internetu bez uwierzytelnienia. Domyslnie binduj do 127.0.0.1 (np. -p 127.0.0.1:9443:9443) i wchodz przez VPN/SSH tunnel.
  • Reverse proxy + auth — Traefik/Caddy/Nginx z HTTPS, a przed panelem warstwa logowania (Authelia, Authentik) i najlepiej 2FA.
  • Montuj socket read-only tam, gdzie narzedzie tylko czyta (Dozzle, ctop, Diun, Glances, Beszel): /var/run/docker.sock:/var/run/docker.sock:ro. Uwaga: :ro ogranicza ryzyko, ale nie jest pelna izolacja — przez Docker API i tak da sie sporo.
  • Socket proxy — zamiast dawac surowy socket, wystaw tylko potrzebne endpointy przez docker-socket-proxy (blokujac np. POST, exec):
# compose.yaml — proxy filtrujace Docker API
services:
  dockerproxy:
    image: tecnativa/docker-socket-proxy:latest
    container_name: dockerproxy
    restart: unless-stopped
    environment:
      CONTAINERS: 1      # pozwol czytac liste kontenerow
      IMAGES: 1
      NETWORKS: 1
      VOLUMES: 1
      POST: 0            # zablokuj operacje zapisu (start/stop/exec/create)
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    ports:
      - "127.0.0.1:2375:2375"

  dozzle:
    image: amir20/dozzle:latest
    environment:
      - DOZZLE_REMOTE_HOST=tcp://dockerproxy:2375
    ports:
      - "127.0.0.1:8080:8080"
    depends_on:
      - dockerproxy
  • Silne haslo admina przy pierwszym uruchomieniu (Portainer wymusza to w ~5 min od startu — nie zwlekaj).
  • Aktualizuj same panele — to oprogramowanie wystawione na ruch; trzymaj je na biezaco i obserwuj CVE. Nie uzywaj zarchiwizowanych projektow (jak stary containrrr/watchtower) do zadan bezpieczenstwa.
  • Wiecej o utwardzaniu Dockera (rootless, capabilities, secrets, skanowanie obrazow) w rozdziale 10. Bezpieczenstwo Docker.

Co wybrac? — rekomendacje 2026

  • Pojedynczy host, chce wygodny panel web → Portainer CE
  • Glownie stacki compose, lekko i przenosnie → Dockge
  • Nowoczesny panel web z GitOps → Arcane
  • Deploy aplikacji prosto z gita (jak Heroku) → Coolify (najwiecej funkcji) lub Dokploy (lekko)
  • Domowy serwer "all-in-one" → CasaOS lub Cosmos
  • Build + deploy + wiele hostow → Komodo lub Portainer Business
  • Szybki podglad z terminala / SSH → Lazydocker (zarzadzanie) lub ctop/Oxker (metryki)
  • Tylko logi na zywo → Dozzle (historia logow → Grafana Loki)
  • Lekki monitoring homelabu → Beszel
  • Pelna obserwowalnosc / metryki / alerty → Netdata lub cAdvisor + Prometheus + Grafana
  • Status i uptime uslug + alerty → Uptime Kuma
  • Powiadomienia o aktualizacjach → Diun (homelab auto-update: nickfedor/watchtower; produkcja: CI/CD)
  • Optymalizacja rozmiaru obrazu → Dive
  • Praca w IDE → VS Code Container Tools lub zakladka Services w JetBrains
