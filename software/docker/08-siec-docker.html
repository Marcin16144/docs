Siec Docker

Network drivers, custom bridges, port publishing, DNS

Sterowniki sieci

DriverCel
bridgeDomyslny — izolowana siec na hoscie z NAT
hostBrak izolacji — kontener uzywa stosu sieciowego hosta
overlayMulti-host — sieci rozproszone (Docker Swarm, K8s)
macvlanKontener z wlasnym MAC, widoczny w sieci LAN jak fizyczny host

Bridge (default)

Po instalacji Docker tworzy bridge0 (zwykle 172.17.0.0/16). Kazdy kontener bez explicit network ma interfejs na tym moscie.

docker network ls
# NETWORK ID     NAME      DRIVER    SCOPE
# 7d2f3a1b...    bridge    bridge    local
# 8e3a2c1d...    host      host      local
# 9f4b3d2e...    none      null      local

docker network inspect bridge
# pokazuje IPAM, kontenery, opcje

# Default bridge wada:
# - DNS NIE dziala miedzy kontenerami (tylko po IP, --link to deprecated)
# - Wszystkie kontenery widzia sie nawzajem — brak izolacji

Custom bridge networks — rekomendowane

Twoja wlasna siec uzytkownika ma automatyczny DNS — kontenery widza sie po nazwie. To powinien byc default.

# Stworz
docker network create mynet
docker network create --driver bridge --subnet 172.30.0.0/16 mynet

# Uzyj
docker run -d --name db --network mynet postgres:16
docker run -it --name app --network mynet alpine sh

# Wewnatrz "app"
ping db                    # dziala! DNS rozwiazuje na IP db
nslookup db
# Server:    127.0.0.11
# Address:   127.0.0.11:53
# Name:      db
# Address:   172.30.0.2

# W Compose — auto network ze service names jako DNS
services:
  app:
    # connect to db:5432, redis:6379 — DNS dziala

Default bridge vs custom bridge

  • Default bridge — brak DNS miedzy kontenerami, wszyscy widzia siebie, brak izolacji
  • Custom bridge — auto DNS po nazwie, izolacja per siec, mozna wiele sieci
  • Zawsze uzywaj custom bridge dla aplikacji wielokontainerowych
  • Compose automatycznie tworzy custom bridge per projekt

Host network

Kontener nie ma wlasnego stosu sieciowego — uzywa hosta. Brak NAT, brak port mapping. Najszybszy ale najmniej izolowany.

docker run --network host nginx
# Nginx slucha na port 80 hosta — bez -p

Use cases: networking-heavy apps (load balancery, monitoring), gdzie performance jest krytyczne. Uwaga: konflikt portow z hostem!

Overlay (multi-host)

Polaczenie kontenerow miedzy roznymi hostami. Wymaga Docker Swarm lub K8s.

# Init swarm na pierwszym hoscie
docker swarm init --advertise-addr 10.0.0.1

# Dolacz kolejne hosty (token z initu)
docker swarm join --token SWMTKN-1-... 10.0.0.1:2377

# Tworz overlay network
docker network create --driver overlay --attachable mynet

# Kontener moze byc na hoscie A, drugi na B — widza sie po DNS

Macvlan

Kontener dostaje wlasny MAC i jest widoczny bezposrednio w LAN — jak osobny komputer. Uzyteczne dla legacy app oczekujacych zycie w "prawdziwej sieci".

docker network create -d macvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 \
  iot-net

docker run --network iot-net --ip 192.168.1.50 -d nginx
# Nginx ma wlasny IP 192.168.1.50 w LAN

Limitacje: domyslnie host nie moze sie polaczyc z kontenerem na macvlan (kernel separation).

None

docker run --network none alpine
# Tylko loopback — zero zewnetrznej sieci

Use case: ekstremalna izolacja, batch processing, security-sensitive workloads.

Port publishing (-p)

# host:container
docker run -p 8080:80 nginx                       # 0.0.0.0:8080 -> 80

# Tylko localhost
docker run -p 127.0.0.1:8080:80 nginx             # tylko z hosta

# Konkretny IP hosta (przy multiple NIC)
docker run -p 10.0.0.5:8080:80 nginx

# UDP
docker run -p 53:53/udp dns-server

# Range
docker run -p 9000-9010:9000-9010 myapp

# Random port (publishall)
docker run -P nginx
docker port nginx                                  # zobacz mapping
# 80/tcp -> 0.0.0.0:32768

DNS rozwiazywanie

Wewnatrz custom bridge, Docker uruchamia embedded DNS na 127.0.0.11.

# Test DNS w kontenerze
docker network create test
docker run -d --network test --name a alpine sleep 1000
docker run -d --network test --name b alpine sleep 1000

docker exec a nslookup b
# Address: 172.30.0.3 (IP kontenera b)

docker exec a ping b              # dziala
docker exec a getent hosts b      # 172.30.0.3 b

Niestandardowe DNS

docker run --dns 1.1.1.1 --dns 8.8.8.8 alpine
docker run --dns-search example.com alpine

# Globalnie w /etc/docker/daemon.json
{
  "dns": ["1.1.1.1", "8.8.8.8"],
  "dns-search": ["example.com"]
}

Wiele sieci na jednym kontenerze

docker network create frontend
docker network create --internal backend       # bez wyjscia na internet

docker run -d --name api --network backend api:latest
docker network connect frontend api            # api ma teraz dwa interfejsy

# Caddy moze byc tylko na frontend, db tylko na backend, api jest pomostem
docker run -d --name caddy --network frontend -p 443:443 caddy
docker run -d --name db --network backend postgres
# api widzi i caddy, i db
# caddy nie widzi db — bezpieczne

Compose — sieci

services:
  caddy:
    image: caddy
    networks: [frontend]
    ports: ["443:443"]

  api:
    build: ./api
    networks: [frontend, backend]

  db:
    image: postgres
    networks: [backend]

networks:
  frontend:
  backend:
    internal: true              # brak NAT do internetu

iptables i firewall

UWAGA — Docker omija UFW

Docker domyslnie modyfikuje iptables i moze obchodzic regulki UFW na Ubuntu. Kontener z -p 80:80 bedzie publicznie dostepny nawet jesli UFW blokuje port 80.

Rozwiazania:

  • Bind tylko localhost: -p 127.0.0.1:80:80 (gdy reverse proxy)
  • Wylacz iptables w Docker: "iptables": false w daemon.json (i recznie zarzadzaj)
  • Uzywaj ufw-docker tool
# Zablokuj wszystko, wybiorczo otworz
docker run -d -p 127.0.0.1:8080:80 nginx
# Reverse proxy (Caddy/Nginx) na hoscie sluga jako frontend
# UFW ma kontrole tylko nad portami hosta
sudo ufw allow 443/tcp

Praktyki

Zalecenia 2026

  • Custom bridge zawsze — auto DNS, izolacja
  • Nie uzywaj default bridge w produkcji
  • Internal networks dla DB / cache — brak NAT do swiata
  • Port binding na 127.0.0.1 + reverse proxy (Caddy, Traefik) na publicznym
  • Jeden kontener — wiele sieci dla segregacji (frontend / backend)
  • Nie uzywaj --link — deprecated
  • K8s zamiast Swarm dla powaznych klastrow
  • Service mesh dla wiekszych mikroserwisowych aplikacji
