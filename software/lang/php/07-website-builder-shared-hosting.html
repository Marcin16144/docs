1. Kontekst — co to jest creator stron i kiedy go pisać samemu

Creator stron (website / page builder) to aplikacja, w której nie-programista układa stronę z gotowych bloków (drag & drop), zmienia treść w edytorze WYSIWYG i publikuje stronę bez znajomości HTML/CSS. Przykłady komercyjne: WordPress + Elementor, Webflow, Wix, Squarespace, nazwa.pl Kreator.

Kiedy ma sens pisać własny creator zamiast kupić gotowy?

SytuacjaPisz własnyUżyj gotowego
Klienci mają już hosting na nazwa.pl / home.pl i nie chcą migrować✅❌
Tworzysz strony stylizowane (np. tylko branża X — restauracje, fryzjerzy, salony)✅WordPress + custom theme też OK
Potrzebujesz integracji z polskim systemem (Allegro, InPost, P24, Subiekt, Comarch)✅❌ (lub WP + plugin)
Standardowy landing dla firmy / blog❌✅ WordPress / Webflow / Framer
Sklep — chcesz unikalny UX❌✅ Shopify, PrestaShop, WooCommerce
Chcesz SaaS (klient wynajmuje konto, ty hostujesz)✅❌ (whitelabel WordPress to ból)
💡 Realny scenariusz w 2026: agencja web obsługująca 50–500 stron lokalnych firm. Klienci są na nazwa.pl/home.pl bo "tak ich kuzyn poradził 10 lat temu". Własny creator pozwala wyceniać tańsze pakiety i mieć kontrolę nad UX.

Inne hostingi — nie tylko nazwa.pl i home.pl

nazwa.pl i home.pl to najpopularniejsze, ale wcale nie najlepsze dla developera. Rynek 2026 oferuje hostingi, które mają dokładnie to, czego brakuje „klasykom" — SSH, Composer, Git, a czasem nawet Node.js. Warto je znać, bo wybór hostingu zmienia architekturę całego projektu (rozdziały 3 i 10 zakładają najgorszy przypadek — brak SSH).

VPS jako alternatywa dla shared

Jeśli creator ma być SaaS-em multi-tenant (rozdział 9) albo potrzebuje queue workerów, Redisa czy WebSocketów — shared hosting zawsze będzie kompromisem. Tani VPS rozwiązuje to raz na zawsze:

⚠️ VPS = sam administrujesz serwerem (aktualizacje, firewall, backupy, certyfikaty). To dodatkowa praca i odpowiedzialność. Na shared hostingu robi to za Ciebie dostawca. Jeśli nie czujesz się pewnie w Linuksie — zostań na shared developer-friendly (MyDevil/zenbox) albo użyj panelu (CloudPanel, aaPanel, Coolify) na VPS.
📋 Jak wybrać — szybka decyzja:
  • Klient już ma nazwa.pl/home.pl i nie chce migrować → akceptujesz ograniczenia, build lokalnie + FTP (reszta przewodnika).
  • Klient jest elastyczny, chcesz wygody dev → MyDevil.net lub zenbox.pl (SSH + Composer + Git).
  • Budujesz SaaS multi-tenant, potrzebujesz workerów/Redis/WS → VPS (Hetzner Cloud / mikr.us na start).
  • Liczy się głównie cena dla wielu małych stron → Hostinger albo pakiet reseller u polskiego dostawcy.

⚠️ Najboleśniejsze: brak Node.js i brak Composera na podstawowych pakietach. Konsekwencja: całość buildujesz lokalnie (npm run build, composer install --no-dev) i wgrywasz przez FTP. To zmienia architekturę pipeline.

Co z tego wynika dla architektury

  • ❌ Nie ma sensu używać frameworków wymagających Node-server (Next.js, Nuxt, SvelteKit z SSR) jako BACKENDU — możesz tylko ich static export.
  • ✅ Backend MUSI być PHP (klasyczny request → response, bez long-running processów).
  • ✅ Frontend admin może być SPA (Vue/React) bundlowane statycznie na Twojej maszynie.
  • ✅ Frontend public lepiej server-side rendered w PHP (SEO, szybkość) + drobne JS-y inline lub jako jeden mały bundle.
  • ⚠️ Cron jest, ale ograniczony — co 1 minutę u niektórych, co 15 min u innych. Sprawdź panel.
  • ⚠️ Brak Redis/Memcached — cache musi być plikowy lub w MySQL.
  • ⚠️ Brak WebSocketów (Apache nie proxy). Long-polling lub Server-Sent Events maks.

4. Architektura creatora — moduły i odpowiedzialności

┌─────────────────────────────────────────────────────────────┐
│                    SHARED HOSTING (Apache + PHP-FPM)         │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│   /public_html/                                              │
│       index.php   ────────►  routing front: site renderer    │
│       admin/                                                 │
│           index.php  ─────►  SPA shell (HTML + JS bundle)    │
│           api/      ──────►  REST: bloki, strony, media      │
│       uploads/    (writable)                                 │
│       assets/     (CSS/JS skompilowane lokalnie)             │
│       .htaccess   (mod_rewrite, security headers)            │
│                                                              │
│   /private/    (poza public_html)                            │
│       src/       (PHP code)                                  │
│       vendor/    (Composer dependencies)                     │
│       cache/     (writable, PHP file cache)                  │
│       config/    (env, secrets — poza document root!)        │
│                                                              │
│   MySQL DB:                                                  │
│       sites, pages, blocks, blocks_data,                     │
│       users, sessions, media, settings                       │
└─────────────────────────────────────────────────────────────┘

Główne moduły

  1. Router (PHP) — rozdziela ruch na frontend (renderer) i admin (API).
  2. Renderer — pobiera definicję strony z DB i renderuje HTML po stronie serwera.
  3. Block library — katalog bloków (Hero, Text+Image, Gallery, Pricing, Contact, Map). Każdy blok = klasa PHP + szablon Twig + schemat propsów (JSON Schema lub konfiguracja).
  4. Admin API — REST endpoints: CRUD pages, blocks, media. JWT lub session-based auth.
  5. Admin SPA (Vue) — edytor drag-drop, preview, media library.
  6. Media manager — upload, resize (Intervention Image), thumbnails.
  7. Cache layer — file-based, klucz = page_id + version.
  8. Asset compiler — uruchamiany LOKALNIE: Tailwind/Sass → CSS, Vue → JS bundle.

Przepływ "user edytuje stronę"

  1. Admin loguje się przez /admin/login (session cookie).
  2. SPA pobiera GET /admin/api/pages/{id} → JSON z listą bloków + ich propsami.
  3. Edytor renderuje bloki w iframe preview (osobne URL /preview/{token}).
  4. Zmiana props → debounce 500ms → PUT /admin/api/blocks/{id}.
  5. Po "Publikuj" → backend invaliduje cache i wersjonuje stronę.
  6. Public user wchodzi na /uslugi → PHP czyta z cache (pominięcie DB jeśli świeże) → render Twig → odpowiedź.

Opcja B: Alpine.js (no-build, idealne dla mniejszych edytorów)

<!-- admin/dashboard.php — renderowane przez PHP -->
<script src="https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js" defer></script>
<script src="https://cdn.jsdelivr.net/npm/sortablejs@1.15.0/Sortable.min.js"></script>

<div x-data="editor()" x-init="load()">
    <button @click="addBlock('hero')">+ Hero</button>
    <button @click="addBlock('text')">+ Tekst</button>

    <div id="blocks-list">
        <template x-for="block in blocks" :key="block.id">
            <div class="block" :data-id="block.id">
                <input x-model="block.props.title" @input.debounce.500ms="save(block)">
                <button @click="remove(block)">Usuń</button>
            </div>
        </template>
    </div>
</div>

<script>
function editor() {
    return {
        blocks: [],
        sortable: null,
        async load() {
            const r = await fetch('/admin/api/pages/<?= $pageId ?>');
            this.blocks = (await r.json()).blocks;
            this.$nextTick(() => this.initSortable());
        },
        initSortable() {
            this.sortable = Sortable.create(document.getElementById('blocks-list'), {
                animation: 150,
                onEnd: () => this.reorderSave()
            });
        },
        async addBlock(type) {
            const r = await fetch('/admin/api/blocks', {
                method: 'POST',
                headers: { 'Content-Type': 'application/json' },
                body: JSON.stringify({ type, page_id: <?= $pageId ?> })
            });
            this.blocks.push(await r.json());
        },
        async save(block) {
            await fetch(`/admin/api/blocks/${block.id}`, {
                method: 'PUT',
                headers: { 'Content-Type': 'application/json' },
                body: JSON.stringify({ props: block.props })
            });
        },
        async reorderSave() {
            const ids = [...document.querySelectorAll('.block')].map(e => +e.dataset.id);
            await fetch('/admin/api/blocks/reorder', {
                method: 'POST',
                headers: { 'Content-Type': 'application/json' },
                body: JSON.stringify({ ids })
            });
        },
        async remove(block) {
            await fetch(`/admin/api/blocks/${block.id}`, { method: 'DELETE' });
            this.blocks = this.blocks.filter(b => b.id !== block.id);
        }
    }
}
</script>
💡 Alpine + Sortable.js + Tailwind z CDN to zero buildu — wgrywasz FTP-em pliki PHP i działa. Idealne dla MVP i klienta, który nie ma git/npm.

6. Frontend strony publicznej — jak nie zabić wydajności

Złota zasada: strona publiczna to generowany HTML, nie SPA. Powody:

  • SEO — Google indeksuje SSR HTML lepiej i szybciej niż SPA.
  • Core Web Vitals — LCP < 2.5s wymaga pierwszego paint bez JS.
  • Konwersja — landing z 1s vs 4s ładowania = 2× konwersji (Google research).

Stack frontu publicznego (rekomendowany)

1. PHP renderuje HTML (Twig template).
2. CSS: jeden plik site.css (~30KB gzip), Tailwind precompiled.
3. JS: jeden plik site.js (~5-15KB) z Alpine.js + custom kod.
4. Obrazy: lazy loading native (loading="lazy"), <picture> + WebP/AVIF.
5. Fonty: woff2 z preload, font-display: swap.
6. Cache: HTTP cache headers + PHP file cache HTML.

Tailwind bez Node na hostingu

# Lokalnie:
npx tailwindcss -i src/site.css -o dist/site.css --minify

# tailwind.config.js — content scanning, żeby nie wygenerować całego Tailwind

        './public_html/**/*.php',
        './src/Blocks/**/*.twig',
        './src/Blocks/**/*.php'

7. Schemat bazy danych dla page builder

-- Konta klientów (multi-tenant)
CREATE TABLE sites (
    id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    domain       VARCHAR(190) NOT NULL UNIQUE,
    name         VARCHAR(190) NOT NULL,
    theme        VARCHAR(64)  DEFAULT 'default',
    settings     JSON,                                     -- kolory, fonty, logo
    plan         ENUM('basic','pro','agency') DEFAULT 'basic',
    created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_domain (domain)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Użytkownicy (admin / klient)
CREATE TABLE users (
    id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    site_id       BIGINT UNSIGNED NOT NULL,
    email         VARCHAR(190) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    role          ENUM('owner','admin','editor','viewer') NOT NULL,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_site_email (site_id, email),
    FOREIGN KEY (site_id) REFERENCES sites(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Strony
CREATE TABLE pages (
    id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    site_id      BIGINT UNSIGNED NOT NULL,
    slug         VARCHAR(190) NOT NULL,                    -- /uslugi
    title        VARCHAR(255) NOT NULL,                    -- <title>
    meta_desc    VARCHAR(160),
    og_image     VARCHAR(255),
    status       ENUM('draft','published') DEFAULT 'draft',
    published_at DATETIME NULL,
    version      INT UNSIGNED DEFAULT 1,                   -- inwalidacja cache
    updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_site_slug (site_id, slug),
    INDEX idx_status (site_id, status),
    FOREIGN KEY (site_id) REFERENCES sites(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Bloki (instancje na stronach)
CREATE TABLE blocks (
    id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    page_id      BIGINT UNSIGNED NOT NULL,
    type         VARCHAR(64) NOT NULL,                     -- 'hero', 'text', 'gallery'
    props        JSON NOT NULL,                            -- treść bloku
    position     INT UNSIGNED NOT NULL,                    -- kolejność
    visible      TINYINT(1) DEFAULT 1,
    created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_page_pos (page_id, position),

Page renderer

<?php
namespace App\Renderer;

use Twig\Environment;

class PageRenderer
{
    public function __construct(
        private BlockRegistry $registry,
        private Environment $twig,
        private Cache $cache,
        private MediaResolver $media
    ) {}

    public function render(int $pageId): string
    {
        $cacheKey = "page_{$pageId}";

        // 1. Cache hit?
        if ($html = $this->cache->get($cacheKey)) {
            return $html;
        }

        // 2. Pobierz stronę + bloki
        $page = Page::find($pageId);                    // ORM lub PDO
        if (!$page || $page->status !== 'published') {
            throw new NotFoundException();
        }

        $blocks = Block::where('page_id', $pageId)
            ->where('visible', 1)
            ->orderBy('position')
            ->get();

        // 3. Renderuj każdy blok
        $html = '';
        $context = ['media_resolver' => fn($id, $size) => $this->media->url($id, $size)];

        foreach ($blocks as $block) {
            $class = $this->registry->getClass($block->type);
            if (!$class) continue;                       // unknown type — skip

            $instance = new $class();
            $props = $instance->prepare($block->props, $context);

            $html .= $this->twig->render($class::template(), $props);
        }

        // 4. Owin layoutem (head/header/footer)
        $full = $this->twig->render('layout.twig', [
            'title'      => $page->title,
            'meta_desc'  => $page->meta_desc,
            'og_image'   => $page->og_image,
            'content'    => $html
        ]);

        // 5. Zapisz w cache (5 minut)
        $this->cache->set($cacheKey, $full, 300);
        return $full;
    }
}

File-based cache (bo brak Redis na shared)

<?php
namespace App\Renderer;

class FileCache implements Cache
{
    public function __construct(private string $dir) {
        if (!is_dir($dir)) mkdir($dir, 0755, true);
    }

    public function get(string $key): ?string
    {
        $file = $this->path($key);
        if (!is_file($file)) return null;

        $data = file_get_contents($file);
        $payload = unserialize($data);
        if ($payload['expires'] < time()) {
            @unlink($file);
            return null;
        }
        return $payload['value'];
    }

    public function set(string $key, string $value, int $ttl): void
    {
        $payload = ['expires' => time() + $ttl, 'value' => $value];
        $tmp = $this->path($key) . '.tmp';
        file_put_contents($tmp, serialize($payload), LOCK_EX);
        rename($tmp, $this->path($key));                 // atomowo
    }

    public function delete(string $key): void { @unlink($this->path($key)); }

    public function invalidatePage(int $pageId): void { $this->delete("page_{$pageId}"); }

    private function path(string $key): string
    {
        return $this->dir . '/' . hash('xxh3', $key);   // xxh3 szybsze niż md5
    }
}

Ładowanie i rejestracja pluginów

Rdzeń ma PluginManager: skanuje katalog plugins/, czyta manifesty, sprawdza zgodność wersji i ładuje aktywne pluginy. Komunikacja przez system hooków (event bus) — plugin nie modyfikuje rdzenia, tylko „podpina się" do zdarzeń.

<?php
// Kontrakt każdego pluginu
interface PluginInterface {
    public function register(HookBus $hooks): void;  // podpięcie pod zdarzenia
    public function activate(): void;                 // jednorazowo: migracje, kopiowanie assetów
    public function deactivate(): void;               // sprzątanie
}

// Prosty event bus — zero zależności, działa wszędzie
class HookBus {
    private array $listeners = [];
    public function on(string $event, callable $cb): void {
        $this->listeners[$event][] = $cb;
    }
    public function emit(string $event, mixed $payload = null): mixed {
        foreach ($this->listeners[$event] ?? [] as $cb) {
            $payload = $cb($payload) ?? $payload;   // filtry mogą zmieniać payload
        }
        return $payload;
    }
}

// Manager — skanuje, waliduje, ładuje
class PluginManager {
    public function __construct(
        private string $dir,           // ścieżka do plugins/
        private string $coreVersion,   // np. "2.3.1"
        private array  $enabled        // sluginy aktywne (z DB)
    ) {}

    public function loadAll(HookBus $hooks): void {
        foreach (glob($this->dir.'/*/plugin.json') as $manifestPath) {
            $m = json_decode(file_get_contents($manifestPath), true);
            if (!$m || !in_array($m['slug'], $this->enabled, true)) continue;

            // Walidacja wymagań
            if (!$this->satisfies($this->coreVersion, $m['requires']['core'] ?? '*')) {
                error_log("Plugin {$m['slug']}: wymaga core {$m['requires']['core']}");
                continue;
            }
            if (version_compare(PHP_VERSION, ltrim($m['requires']['php'] ?? '0', '>=v'), '<')) {
                continue;
            }

            require_once dirname($manifestPath).'/'.$m['entry'];
            /** @var PluginInterface $plugin */
            $plugin = new $m['class']();
            $plugin->register($hooks);
        }
    }

    private function satisfies(string $version, string $constraint): bool {
        // uproszczone: obsługa ">=X.Y.Z" i "*"
        if ($constraint === '*') return true;
        if (str_starts_with($constraint, '>=')) {
            return version_compare($version, trim(substr($constraint, 2)), '>=');
        }
        return $version === $constraint;
    }
}

Bezpieczeństwo pluginów

⚠️ Na shared hostingu nie ma realnego sandboxa. Plugin to PHP wykonywany z pełnymi prawami Twojej aplikacji — może czytać DB, pliki, wysyłać maile. disable_functions coś ogranicza, ale to nie izolacja.

Model zaufania w praktyce:

  • Pluginy tylko od Ciebie / zweryfikowanych autorów — żadnego „marketplace" z kodem od obcych, jeśli nie robisz review.
  • Podpisuj pakiety (sekcja o aktualizacjach niżej) — instalujesz tylko podpisane.
  • Code review przed dodaniem do repozytorium pluginów — szukaj eval, system, base64_decode, dynamicznych require z URL.
  • Manifest deklaruje uprawnienia (np. "permissions": ["db", "mail", "http"]) — przynajmniej widać, co plugin robi.
  • Multi-tenant: plugin jednego klienta nie może widzieć danych innego — patrz rozdział 9.

Automatyczna aktualizacja — wyzwanie shared hostingu

Masz 200 stron klientów na 200 hostingach. Wychodzi krytyczna poprawka bezpieczeństwa. Ręczny FTP do każdej = kilka dni pracy. Potrzebujesz auto-update — modelu, który zna każdy użytkownik WordPressa.

Ograniczenia z rozdziału 2 utrudniają sprawę:

  • ❌ Brak SSH / Composera → aktualizacja musi działać z poziomu PHP (sam się aktualizuje).
  • ❌ Brak git pull → pobierasz spakowany pakiet (ZIP) po HTTPS.
  • ⚠️ Cron jest, ale rzadki → sprawdzanie wersji co kilka godzin, nie co minutę.
  • ⚠️ Prawa do plików → PHP musi mieć prawo nadpisać własne pliki (zwykle ma, bo właściciel ten sam).

Mechanizm self-update krok po kroku

Serwer aktualizacji (Twój — np. updates.twojadomena.pl) wystawia dwa zasoby: endpoint wersji (JSON) i pakiety ZIP. Aplikacja klienta odpytuje go z crona.

KrokCo się dziejeZabezpieczenie
1. SprawdzenieCron odpytuje /version?current=2.3.1&key=LICENCJAKlucz licencyjny — tylko klienci dostają update
2. PobranieJest nowsza → pobierz core-2.4.0.zip + core-2.4.0.zip.sigHTTPS (TLS) — brak MITM
3. WeryfikacjaSprawdź podpis pakietu kluczem publicznym wbudowanym w aplikacjęPodpis cyfrowy — sednem bezpieczeństwa
4. BackupSpakuj obecne pliki + dump DB do storage/backups/Rollback jeśli coś padnie
5. MaintenanceWłącz tryb serwisowy (plik-flaga → strona pokazuje „chwilowa przerwa")Brak ruchu w trakcie podmiany
6. RozpakowanieRozpakuj ZIP do katalogu tymczasowego, potem podmień plikiAtomowo na ile się da
7. MigracjeUruchom nowe pliki migrations/*.sqlWersjonowane, idempotentne

<?php
// Uruchamiane z crona: php cron/update.php
class SelfUpdater {
    private string $updateServer = 'https://updates.twojadomena.pl';

    public function run(string $currentVersion, string $licenseKey): void {
        // 1. Sprawdź dostępność nowej wersji
        $info = json_decode(file_get_contents(
            "{$this->updateServer}/version?current={$currentVersion}&key={$licenseKey}"
        ), true);
        if (!$info || version_compare($info['latest'], $currentVersion, '<=')) {
            return; // aktualny
        }

        $tmp = sys_get_temp_dir().'/update_'.$info['latest'];
        @mkdir($tmp, 0755, true);

        // 2. Pobierz pakiet + podpis
        $zip = $tmp.'/core.zip';
        file_put_contents($zip, file_get_contents($info['package_url']));
        $sig = file_get_contents($info['signature_url']);

        // 3. Weryfikacja podpisu (klucz publiczny wbudowany w aplikację)
        if (!$this->verifySignature($zip, $sig)) {
            error_log('UPDATE: zły podpis pakietu — przerwano!');
            return;
        }

        // 4. Backup (pliki + baza)
        $this->backup();

        // 5. Tryb serwisowy
        touch(__DIR__.'/../storage/MAINTENANCE');

        try {
            // 6. Rozpakuj i podmień
            $archive = new ZipArchive();
            $archive->open($zip);
            $archive->extractTo($tmp.'/files');
            $archive->close();
            $this->replaceFiles($tmp.'/files', __DIR__.'/..');

            // 7. Migracje DB
            $this->runMigrations($tmp.'/files/migrations');

            // 8. Finał
            file_put_contents(__DIR__.'/../storage/version', $info['latest']);
            $this->clearCache();
        } catch (\Throwable $e) {
            error_log('UPDATE failed: '.$e->getMessage());
            $this->rollback();          // przywróć z backupu
        } finally {
            @unlink(__DIR__.'/../storage/MAINTENANCE');  // wyłącz serwis
        }
    }

    private function verifySignature(string $file, string $sig): bool {
        $pubKey = file_get_contents(__DIR__.'/update_public.pem');
        return openssl_verify(
            file_get_contents($file), base64_decode($sig), $pubKey,
            OPENSSL_ALGO_SHA256
        ) === 1;
    }
    // backup(), replaceFiles(), runMigrations(), rollback(), clearCache() — analogicznie
}
💡 Tryb serwisowy = jeden plik. Front-controller na starcie sprawdza if (file_exists('storage/MAINTENANCE')) { http_response_code(503); echo '...'; exit; }. Zero zależności, działa na każdym hostingu.

Aktualizacja pluginów

Ten sam mechanizm, ale per-plugin. Każdy plugin.json ma update_url — manager okresowo sprawdza wersje i pokazuje w panelu admina „Dostępne aktualizacje (3)", jak w WordPressie. Aktualizacja pluginu = pobranie ZIP-a, weryfikacja podpisu, podmiana katalogu plugins/<slug>/, uruchomienie jego migracji.

Bezpieczeństwo aktualizacji — krytyczne

❌ Auto-update bez podpisu cyfrowego to backdoor. Jeśli ktoś przejmie Twój serwer aktualizacji albo podmieni DNS — wgra dowolny kod na 200 stron klientów naraz. HTTPS chroni transmisję, ale nie źródło. Podpis (klucz prywatny u Ciebie, publiczny w aplikacji) jest obowiązkowy.
  • Podpisuj każdy pakiet kluczem prywatnym trzymanym offline (nie na serwerze update!).
  • Klucz publiczny wbudowany w aplikację — aktualizacja odrzucana, gdy podpis się nie zgadza.
  • Zawsze backup przed — i przetestowany rollback. Update, który się wywali w połowie, nie może zostawić martwej strony.
  • Wersjonuj migracje i rób je idempotentnymi (CREATE TABLE IF NOT EXISTS, sprawdzaj kolumny przed ALTER).
  • Kanał stabilny vs beta — nie wypychaj wszystkim naraz; najpierw 5% stron, obserwuj logi, potem reszta.
  • Log aktualizacji — kto, kiedy, z jakiej na jaką wersję; przy problemie wiesz gdzie szukać.
📋 Minimalna wersja na start: nie buduj od razu marketplace pluginów i kanałów beta. Wystarczy: (1) pluginy-bloki ładowane z katalogu, (2) self-update rdzenia z podpisem i backupem, uruchamiany z crona raz dziennie. Resztę dołożysz, gdy liczba klientów to uzasadni.

Krytyczne ustawienia .htaccess

# /public_html/.htaccess
RewriteEngine On

    </FilesMatch>

# Security headers
<IfModule mod_headers.c>

    Header always set X-Frame-Options "SAMEORIGIN"
    Header always set Referrer-Policy "strict-origin-when-cross-origin"

    Header always set Content-Security-Policy "default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; font-src 'self' data:;"
</IfModule>

# Brotli/Gzip

    AddOutputFilterByType DEFLATE text/html text/css text/javascript application/javascript application/json
</IfModule>

# Cache statyków
<IfModule mod_expires.c>
    ExpiresActive On
    ExpiresByType image/jpeg "access plus 1 year"
    ExpiresByType image/webp "access plus 1 year"
    ExpiresByType text/css "access plus 1 month"
    ExpiresByType application/javascript "access plus 1 month"
</IfModule>

Lista must-have

  • Hasła: password_hash($pwd, PASSWORD_ARGON2ID) — nie bcrypt, nie SHA.
  • Sesje: session.cookie_httponly=1, session.cookie_secure=1, session.cookie_samesite=Strict w .user.ini
  • CSRF w każdym formularzu admin (token w sesji).
  • SQL Injection: tylko prepared statements (PDO z ? placeholders).
  • XSS: escapuj na output (Twig robi automatycznie, raw PHP — htmlspecialchars($x, ENT_QUOTES, 'UTF-8')).
  • Upload: walidacja MIME przez finfo_file(), nigdy nie ufaj $_FILES['type'].
  • Rate limiting: tabela rate_limits (ip, action, count, window_start) — bez Redis się da.
  • Cloudflare przed hostingiem — darmowy WAF, DDoS, cache.
  • Backup: cron 1× dzień mysqldump + zip do /private/backups/ + przekazanie na S3/Backblaze.

Backup script (działa na nazwa.pl/home.pl)

#!/usr/bin/env php
<?php
// scripts/backup.php — uruchamiany z crona
$config = require __DIR__ . '/../config/config.php';

$date = date('Y-m-d-Hi');
$dir = __DIR__ . '/../backups';
if (!is_dir($dir)) mkdir($dir, 0700, true);

// 1. mysqldump
$sql = "$dir/db-$date.sql.gz";
$cmd = sprintf(
    'mysqldump --single-transaction -u%s -p%s %s | gzip > %s',
    escapeshellarg($config['db']['user']),
    escapeshellarg($config['db']['pass']),
    escapeshellarg($config['db']['name']),
    escapeshellarg($sql)
);
shell_exec($cmd);

// 2. uploads tarball
shell_exec("tar czf $dir/uploads-$date.tar.gz public_html/uploads");

// 3. Wyślij do Backblaze B2 (curl, brak SDK potrzebny)
// ...

// 4. Usuń starsze niż 30 dni
foreach (glob("$dir/*-{*-*-*}.{sql.gz,tar.gz}", GLOB_BRACE) as $f) {
    if (filemtime($f) < strtotime('-30 days')) unlink($f);
}
⚠️ Na nazwa.pl/home.pl shell_exec() czasem jest disabled w php.ini (sprawdź disable_functions). Zamiennik: PHP-only mysqldump — gotowa biblioteka ifsnop/mysqldump-php.
