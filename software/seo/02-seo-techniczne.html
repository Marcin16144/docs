SEO techniczne

Szybkość, mobile-first, HTTPS, architektura URL, crawl budget, robots.txt, sitemap, canonical, hreflang i renderowanie JS

Aktualizacja: 2026-06

SEO techniczne to fundament, na którym opierają się wszystkie inne działania. Nawet najlepsza treść nie zaindeksuje się poprawnie, jeśli Googlebot ma problemy z dostępem, strona ładuje się wolno lub struktura URL jest chaotyczna. Problemy techniczne rozwiązuj przed inwestowaniem w treść i linki.

Szybkość i wydajność

Szybkość strony wpływa zarówno na rankingi (poprzez Core Web Vitals), jak i na doświadczenie użytkownika. Google używa danych z Chrome User Experience Report (CrUX) — prawdziwych danych od użytkowników Chrome, nie pomiarów laboratoryjnych.

  • Kompresja Gzip/Brotli — zmniejsza rozmiar transferowanych plików HTML/CSS/JS o 60–80%.
  • Minifikacja CSS/JS — usuwa białe znaki i komentarze. Narzędzia: esbuild, Terser, LightningCSS.
  • Lazy loading obrazów — <img loading="lazy"> opóźnia ładowanie obrazów poza ekranem.
  • Formaty nowej generacji — WebP, AVIF zamiast JPEG/PNG; mniejsze o 30–50%.
  • CDN — treść serwowana z węzła geograficznie bliskiego użytkownikowi.
  • Cache HTTP — nagłówki Cache-Control i ETag redukują ponowne pobieranie zasobów.
  • Preload / preconnect — <link rel="preload"> na czcionki i krytyczne zasoby.
💡 Szczegóły Core Web Vitals (LCP, INP, CLS) i ich optymalizacja znajdziesz na stronie 08 — Core Web Vitals.

Mobile-first indexing

Od 2019 roku Google domyślnie indeksuje i rankuje wersję mobilną strony (Googlebot Smartphone). Jeśli twoja strona ma oddzielną wersję m.dot lub różną treść w wersji mobilnej vs desktopowej — Googlebot zobaczy wersję mobilną i to ona będzie rankować.

  • Używaj responsywnego designu — jeden URL, CSS zmienia layout przez media queries.
  • Upewnij się, że treść na mobile jest identyczna z desktopem (nie ukrywaj treści za hamburgerami bez konieczności).
  • Sprawdź test Mobile-Friendly w Google Search Console → Narzędzia → Test optymalizacji mobilnej.
  • Czcionka min. 16px, przyciski min. 48×48px, brak poziomego scrollowania.

HTTPS i bezpieczeństwo

HTTPS to minimalny wymóg — Google traktuje go jako słaby, ale realny sygnał rankingowy. Ważniejszy jest wpływ na zaufanie użytkownika: przeglądarka oznacza HTTP jako „Niezabezpieczone".

  • Certyfikat SSL/TLS — darmowe rozwiązanie: Let's Encrypt (automatyczne odnowienie przez Certbot).
  • Przekieruj HTTP → HTTPS przez 301 (permanentne).
  • Przekieruj www → non-www (lub odwrotnie) — wybierz jedną wersję i trzymaj się jej.
  • Nagłówek Strict-Transport-Security (HSTS) — wymusza HTTPS w przeglądarce.
  • Sprawdź mieszaną zawartość (mixed content) — obrazy lub skrypty przez HTTP na stronie HTTPS blokują ikonę kłódki.

Architektura URL

Dobra struktura URL ułatwia Googlebotowi zrozumienie hierarchii serwisu i pomaga użytkownikom orientować się, gdzie są.

Zasady dobrego URL

  • Krótkie i czytelne: /oferta/strony-internetowe zamiast /?page_id=142&cat=3
  • Słowo kluczowe w URL — pomocne, ale nie upychaj ich na siłę.
  • Małe litery — URL jest case-sensitive; /Oferta i /oferta to różne adresy.
  • Myślniki jako separatory — strony-internetowe, nie strony_internetowe ani stronyinternetowe.
  • Bez parametrów dla treści SEO — parametry (?sort=, ?color=) mnożą duplikaty; użyj canonical lub filtrowania po stronie serwera.
  • Stabilność — zmiana URL = konieczność przekierowania 301. Planuj strukturę z wyprzedzeniem.

Przykłady: dobry vs zły URL

Dobry URLZły URLProblem ze złym

/sklep/buty/meskie/sklep/cat/12/sub/34/itemsNieczytelna hierarchia
/kontakt/index.php?module=contactRozszerzenie i parametry
/uslugi/UslugiWielka litera — ryzyko duplikatu

robots.txt

Plik robots.txt w katalogu głównym domeny instruuje roboty, których sekcji serwisu nie crawlować. Ważne: Disallow blokuje crawling, ale nie indeksowanie — strona może wciąż pojawić się w wynikach, jeśli linki do niej istnieją.

User-agent: *
Disallow: /admin/
Disallow: /koszyk/
Disallow: /checkout/
Disallow: /wyszukiwanie?
Allow: /

User-agent: Googlebot
Disallow: /tmp/

Sitemap: https://example.pl/sitemap.xml
⚠ Nie blokuj przez robots.txt plików CSS i JS — Googlebot musi je pobrać, żeby poprawnie wyrenderować stronę i ocenić jej wygląd oraz treść.

Sitemap XML

Sitemap to plik XML z listą URL twojego serwisu — wskazówka dla Googlebota, co warto zaindeksować i kiedy było ostatnio aktualizowane.

<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://example.pl/</loc>
    <lastmod>2026-06-01</lastmod>
    <changefreq>weekly</changefreq>
    <priority>1.0</priority>
  </url>
  <url>
    <loc>https://example.pl/oferta</loc>
    <lastmod>2026-05-15</lastmod>
    <priority>0.8</priority>
  </url>
</urlset>
  • Zgłoś sitemap w Google Search Console → Indeksowanie → Mapy witryn.
  • Umieść ścieżkę do sitemapy w robots.txt (linia Sitemap:).
  • Dla dużych serwisów — sitemap index (plik wskazujący na wiele sitemapów, maks. 50 000 URL / plik).
  • Nie umieszczaj stron z noindex ani zablokowanych przez robots.txt.

Linki kanoniczne (canonical)

Gdy ta sama treść jest dostępna pod wieloma URL (np. /produkt, /produkt?color=red, /produkt/), Google może nie wiedzieć, którą wersję rankować. Tag canonical rozwiązuje ten problem.

<!-- W <head> wersji kanonicznej i wszystkich duplikatów: -->
<link rel="canonical" href="https://example.pl/produkt">
  • Canonical to wskazówka, nie dyrektywa — Google może ją zignorować, jeśli nie jest spójna z innymi sygnałami.
  • Wzmocnij canonical przez: konsekwentne linkowanie wewnętrzne do wersji kanonicznej, sitemap zawierający tylko kanoniczne URL, przekierowania 301 zamiast canonical tam, gdzie to możliwe.
  • Cross-domain canonical — możesz wskazać kanoniczną wersję na innej domenie (np. syndykacja treści).

Przekierowania i kody HTTP

Kod statusu HTTP informuje przeglądarkę i boty, co stało się z żądanym zasobem.

2xx
Sukces — strona istnieje i jest dostępna. 200 OK to standard.
3xx
Przekierowanie. 301 = trwałe (przekazuje PageRank), 302 = tymczasowe (nie przekazuje).
4xx
Błąd klienta. 404 = nie znaleziono, 410 = usunięto trwale, 403 = brak dostępu.
5xx
Błąd serwera. 500 = ogólny błąd, 503 = serwer niedostępny (Google czeka, nie usuwa z indeksu).
KodNazwaSEO konsekwencja
200OKStrona crawlowana i indeksowana normalnie
301Moved PermanentlyPrzekazuje ~90–99% wartości linkowej; używaj przy trwałych zmianach URL
302Found (tymczasowe)Nie przekazuje PageRank; oryginalny URL pozostaje w indeksie
404Not FoundStrona wypadnie z indeksu; strata wartości linków do niej
410GoneSygnalizuje trwałe usunięcie — Google szybciej usuwa z indeksu niż 404
503Service UnavailableGoogle rozumie przerwy techniczne i nie usuwa od razu z indeksu
canonicalizedSoft 404Pusta strona zwracająca 200 — Google traktuje jak 404, ale z opóźnieniem
✅ Sprawdzaj łańcuchy przekierowań (redirect chains): A→B→C. Każde przekierowanie to utrata frakcji wartości linkowej i dodatkowy czas ładowania. Skracaj do jednego skoku: A→C.

Renderowanie JavaScript

Wiele nowoczesnych stron (React, Vue, Angular) renderuje treść po stronie klienta przez JavaScript. To stwarza wyzwanie: Googlebot musi dwuetapowo indeksować takie strony — najpierw pobiera HTML, potem (z opóźnieniem) uruchamia JS i analizuje wyrenderowany DOM.

  • SSR (Server-Side Rendering) — strona renderuje się na serwerze i bot dostaje gotowy HTML. Najlepsze rozwiązanie dla SEO.
  • SSG (Static Site Generation) — strony generowane przy buildzie jako statyczny HTML. Idealne dla blogów, dokumentacji.
  • Hydration — SSR + interaktywność po stronie klienta (Next.js, Nuxt, Astro).
  • Dynamic rendering — serwer wykrywa bota i serwuje mu pre-renderowany HTML (obejście, nie rekomendowane przez Google od 2023).
⚠ Treść ładowana przez AJAX na żądanie użytkownika (np. po kliknięciu przycisku) może NIE być zaindeksowana — Googlebot nie kliknie. Upewnij się, że kluczowa treść jest w pierwotnym DOM lub ładowana automatycznie.

Hreflang — wersje językowe

Jeśli strona istnieje w wielu wersjach językowych lub regionalnych, użyj atrybutu hreflang, żeby Google wiedział, którą wersję pokazać użytkownikowi z danego kraju.

<!-- W <head> każdej wersji językowej: -->
<link rel="alternate" hreflang="pl" href="https://example.pl/oferta">
<link rel="alternate" hreflang="en" href="https://example.com/offer">
<link rel="alternate" hreflang="de" href="https://example.de/angebot">
<link rel="alternate" hreflang="x-default" href="https://example.pl/oferta">
  • x-default wskazuje wersję domyślną (gdy żaden język nie pasuje).
  • Hreflang musi być wzajemny — każda wersja musi wskazywać na wszystkie pozostałe.
  • Alternatywa: zapis w sitemapie XML lub nagłówku HTTP (dla plików PDF).
