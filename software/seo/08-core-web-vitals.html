Core Web Vitals

LCP, INP, CLS — definicje, progi Google, pomiar i optymalizacja wydajności

Aktualizacja: 2026-06

Core Web Vitals (CWV) to zestaw trzech metryk wydajności zdefiniowanych przez Google, które mierzą realne doświadczenie użytkownika na stronie: szybkość ładowania, responsywność na interakcje i stabilność wizualną. Od maja 2021 roku są oficjalnym sygnałem rankingowym Google (Page Experience signal).

💡 CWV to tie-breaker — przy podobnej jakości treści i autorytecie strona z lepszymi Core Web Vitals będzie rankować wyżej. Nie zastąpi świetnej treści, ale może decydować o kilku pozycjach w silnej konkurencji.

LCP — Largest Contentful Paint

LCP mierzy czas od nawigacji (kliknięcia linku / wczytania strony) do momentu, gdy największy element widoczny w oknie przeglądarki zostaje w pełni wyrenderowany. Typowo jest to hero image, duże zdjęcie w tle, wideo lub duży blok tekstu.

LCP — skala czasu
0s2.5s — dobry4s — wymaga pracy4s+

Najczęstsze przyczyny słabego LCP

  • Niespriorytetyzowany obraz hero — brak <link rel="preload"> lub fetchpriority="high" na LCP image.
  • Lazy loading na LCP image — loading="lazy" celowo opóźnia ładowanie; usuń go z LCP elementu.
  • Wolny serwer / TTFB — jeśli Time To First Byte wynosi > 600ms, poprawa LCP zaczyna się od hostingu lub CDN.
  • CSS blokujący render — wielkie pliki CSS ładowane synchronicznie w <head>.
  • Czcionki webfont bez font-display: swap — tekst niewidoczny, dopóki czcionka nie dotrze.
  • Ciężki obraz bez kompresji — JPEG 2 MB zamiast WebP 200 KB.

Jak poprawić LCP

  • Dodaj <link rel="preload" as="image" href="hero.webp" fetchpriority="high"> w <head>.
  • Używaj fetchpriority="high" bezpośrednio na tagu <img> LCP elementu.
  • Zoptymalizuj TTFB: szybszy hosting, cache HTTP, CDN (Cloudflare, Bunny CDN).
  • Przenieś krytyczny CSS inline do <head> i opóźnij resztę przez <link rel="stylesheet" media="print" onload>.
  • Kompresja obrazów: WebP / AVIF, rozmiary srcset.
  • Włącz Brotli / Gzip na serwerze.

INP — Interaction to Next Paint

INP (zastąpiło FID w marcu 2024) mierzy opóźnienie wszystkich interakcji użytkownika ze stroną (kliknięcia, dotknięcia, naciśnięcia klawiszy) w czasie całej wizyty — od interakcji do momentu, gdy przeglądarka wyrenderuje wizualną odpowiedź. Raportuje najgorzej wypadającą interakcję (z odjęciem pewnego percentyla górnego, żeby ignorować aberracje).

Przyczyny wysokiego INP

  • Długie zadania JavaScript (Long Tasks > 50ms) blokujące główny wątek przeglądarki.
  • Event handlery synchroniczne — duże obliczenia w obsłudze kliknięcia bez podziału na mniejsze części.
  • Przeładowanie DOM — tysiące węzłów DOM spowalniają operacje layoutu i renderowania.
  • Duże Third-Party scripts — Google Tag Manager z 20 tagami, reklamy, chatboty.
  • Animacje CSS/JS blokujące main thread — zamiast kompozytora GPU.

Jak poprawić INP

  • Rozbij długie zadania JS: setTimeout(fn, 0), scheduler.yield(), requestIdleCallback.
  • Użyj Web Workers dla obliczeń CPU-intensive poza głównym wątkiem.
  • Ogranicz rozmiar DOM — mniej węzłów = szybszy layout recalculation.
  • Audytuj third-party scripts w Chrome DevTools → Performance → Bottom-Up.
  • Preferuj animacje CSS transform i opacity (GPU compositor) zamiast top/left/width (main thread).

CLS — Cumulative Layout Shift

CLS mierzy nieoczekiwane przesunięcia elementów na stronie podczas ładowania i użytkowania. Wartość CLS to suma impact fraction × distance fraction dla każdego przesunięcia. Użytkownik klika w przycisk, reklama się ładuje i przesuwa layout — klika w nieodpowiednie miejsce. To jest CLS.

Najczęstsze przyczyny wysokiego CLS

PrzyczynaRozwiązanie
Obrazy bez zdefiniowanego wymiaru width/heightZawsze podaj width i height w tagu <img> — przeglądarka zarezerwuje miejsce
Reklamy / embedy bez zdefiniowanego rozmiaru konteneraZarezerwuj min-height dla kontenera reklamy

Pomiar Core Web Vitals

Dane Field (RUM) vs. Lab

TypŹródłoDo czego
Field data (RUM)Chrome UX Report (CrUX) — prawdziwi użytkownicy ChromeTo Google używa do rankowania. Zmiany widoczne po 28 dniach zbierania danych.
Lab dataLighthouse, WebPageTest — symulowany pomiarSzybkie debugowanie i testowanie zmian — wyniki natychmiastowe.

Narzędzia pomiarowe

  • PageSpeed Insights (pagespeed.web.dev) — łączy dane field (CrUX) i lab (Lighthouse). Punkt wyjścia dla audytu.
  • Google Search Console → Kluczowe wskaźniki → Core Web Vitals — raport dla całego serwisu, segmentacja mobile/desktop.
  • Lighthouse — wbudowany w Chrome DevTools (F12 → Lighthouse). Lab data, szczegółowe rekomendacje.
  • Chrome DevTools → Performance — głęboka analiza: Long Tasks, main thread blocking, layout shifts.
  • WebPageTest (webpagetest.org) — zaawansowane testy z różnych lokalizacji i urządzeń, filmik z ładowania.
  • web-vitals.js — biblioteka JS do mierzenia CWV po stronie klienta i wysyłania do własnej analityki.
✅ Zacznij od PageSpeed Insights dla reprezentatywnej podstrony (nie tylko strony głównej!) — stron produktowych, artykułów blogowych, stron kategorii. To one generują ruch i mają zazwyczaj gorsze CWV niż strona główna.
✅ Google Search Console → Core Web Vitals wskazuje konkretne URL z problemami, pogrupowane według typu błędu. To najszybsza ścieżka do ustalenia priorytetów napraw na dużym serwisie.

Priorytety optymalizacji

  1. LCP jako pierwszy — najczęściej krytyczny, największy wpływ na postrzeganie szybkości.
  2. CLS jako drugi — frustrujące dla użytkownika, często proste do naprawy (wymiary obrazów).
  3. INP jako trzeci — trudniejsze do optymalizacji, wymaga analizy JS.
  4. Nie optymalizuj tylko dla Lighthouse — sprawdź field data z Search Console.
  5. Mierz na prawdziwym urządzeniu mobilnym w sieci 4G — nie na desktopie przez fiber.
