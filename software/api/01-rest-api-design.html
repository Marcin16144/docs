REST API Design

Zasady projektowania interfejsow REST, konwencje, metody HTTP i kody statusow.

Richardson Maturity Model

Model Richardsona opisuje cztery poziomy dojrzalosci API REST. Im wyzszy poziom, tym bardziej "prawdziwie" RESTful jest interfejs.

Poziom 0 — The Swamp of POX

Pojedynczy punkt koncowy, wszystkie operacje realizowane przez POST. Brak rozroznienia zasobow. Przyklad: stare API SOAP lub XML-RPC. Nie ma tu mowy o REST — to po prostu HTTP jako transport.

Poziom 1 — Zasoby (Resources)

Kazdy zasob ma swoj URL, ale wciaz uzywa sie tylko jednej metody HTTP (zazwyczaj POST). Rozrozniamy juz /users od /orders, lecz semantyka HTTP nie jest wykorzystywana.

Poziom 2 — Metody HTTP

Stosujemy odpowiednie metody: GET do odczytu, POST do tworzenia, PUT/PATCH do aktualizacji, DELETE do usuwania. Kody statusow HTTP sa znaczace (200, 201, 404, 422). To poziom, na ktorym dziala wiekszosc wspolczesnych API.

Poziom 3 — HATEOAS

Odpowiedzi zawieraja hiperlinki do powiazanych operacji. Klient nie musi znac z gory struktury URL — odkrywa mozliwe akcje dynamicznie z odpowiedzi serwera. Rzadko stosowany w praktyce, ale teoretycznie najwyzszy poziom REST.

Naming Conventions

Dobra konwencja nazewnictwa URL jest kluczem do czytelnego i przewidywalnego API.

  • Rzeczowniki, nie czasowniki — /users zamiast /getUsers
  • Liczba mnoga — /articles, /products, /orders
  • Lowercase z myslnikami — /user-profiles, nie /UserProfiles
  • Hierarchia zasobow — /users/42/orders/7 dla zasobow zagniezdonych
  • Brak rozszerzenia pliku — /users, nie /users.json
  • Filtry jako query params — /products?category=books&sort=price

Zasada jednolitosci

Stosuj te same wzorce we wszystkich zasobach. Jesli jeden endpoint uzywa /kebab-case, wszystkie powinny. Niespojnosc to najczestszy blad w projektowaniu API.

Metody HTTP

Kazda metoda HTTP ma okreslona semantyke i powinna byc stosowana zgodnie z przeznaczeniem.

Metoda Operacja Idempotentna Safe Przyklad uzycia
GET Odczyt zasobu Tak Tak Pobierz liste uzytkownikow lub jednego uzytkownika
POST Tworzenie zasobu Nie Nie Utworz nowego uzytkownika, zamowienie
PUT Pelna aktualizacja Tak Nie Zamien caly dokument uzytkownika
PATCH Czesciowa aktualizacja Nie* Nie Zmien tylko email uzytkownika
DELETE Usuniecie zasobu Tak Nie Usun uzytkownika o danym ID

* PATCH moze byc idempotentny, jezeli implementacja tego nie wymaga (np. SET field=value vs INCREMENT field).

CRUD Endpoints — przyklad

# Kolekcja zasobow
GET    /api/v1/users          # lista uzytkownikow (z paginacja)
POST   /api/v1/users          # utworz nowego uzytkownika

# Pojedynczy zasob
GET    /api/v1/users/{id}     # pobierz uzytkownika
PUT    /api/v1/users/{id}     # pelna aktualizacja
PATCH  /api/v1/users/{id}     # czesciowa aktualizacja
DELETE /api/v1/users/{id}     # usun uzytkownika

# Zagniezdzone zasoby
GET    /api/v1/users/{id}/orders          # zamowienia uzytkownika
POST   /api/v1/users/{id}/orders          # nowe zamowienie
GET    /api/v1/users/{id}/orders/{oid}    # konkretne zamowienie

Kod Nazwa Kiedy uzywac

400Bad RequestNiepoprawna skladnia, brakujace pole, zla wartosc.
401UnauthorizedBrak lub nieważny token uwierzytelniania.
403ForbiddenUwierzytelniony, ale brak uprawnien do zasobu.

500Internal Server ErrorNieoczekiwany blad serwera.
503Service UnavailableSerwer tymczasowo niedostepny (maintenance, przeciazenie).

Paginacja

Dla duzych kolekcji zawsze stosuj paginacje. Popularne podejscia to cursor-based (najlepsza wydajnosc) i offset-based (prostota implementacji).

# Offset paginacja — query params
GET /api/v1/products?page=2&limit=20&sort=created_at&order=desc

# Odpowiedz z metadanymi
{
  "data": [...],
  "meta": {
    "total": 1543,
    "page": 2,
    "limit": 20,
    "pages": 78
  },
  "links": {
    "self":  "/api/v1/products?page=2&limit=20",
    "first": "/api/v1/products?page=1&limit=20",
    "prev":  "/api/v1/products?page=1&limit=20",
    "next":  "/api/v1/products?page=3&limit=20",
    "last":  "/api/v1/products?page=78&limit=20"
  }
}

# Naglowki paginacji (alternatywnie)
X-Total-Count: 1543
X-Page: 2
X-Per-Page: 20
Link: </products?page=3>; rel="next", </products?page=78>; rel="last"

HATEOAS

Hypermedia As The Engine Of Application State — klient odkrywa mozliwe akcje z odpowiedzi serwera, bez hardkodowania URL-i. Spelnia najwyzszy poziom modelu Richardsona.

{
  "id": 42,
  "name": "Jan Kowalski",
  "status": "active",
  "_links": {
    "self":    { "href": "/api/v1/users/42" },
    "orders":  { "href": "/api/v1/users/42/orders" },
    "disable": { "href": "/api/v1/users/42/disable", "method": "POST" },
    "delete":  { "href": "/api/v1/users/42", "method": "DELETE" }
  }
}

Idempotency

Idempotentne operacje moga byc wykonane wielokrotnie z tym samym rezultatem. GET, PUT, DELETE sa idempotentne. POST — nie.

Dla POST mozna implementowac idempotency key: klient generuje unikalny klucz i dolacza go do naglowka. Serwer zapamietuje wynik i przy ponownym zadaniu z tym samym kluczem zwraca ten sam rezultat bez duplikowania operacji.

POST /api/v1/payments
Idempotency-Key: a8098c1a-f86e-11da-bd1a-00112444be1e

{
  "amount": 9900,
  "currency": "PLN",
  "recipient": "acc_xyz123"
}

Versioning — przeglad strategii

Wersjonowanie API pozwala wprowadzac zmiany bez zrywania kompatybilnosci z istniejacymi klientami.

  • URL versioning — /api/v1/users, /api/v2/users. Najczytelniejszy, najlatiwejszy do routowania i cachowania.
  • Header versioning — Accept: application/vnd.myapi+json;version=2. Czysty URL, ale mniej oczywisty.
  • Content-Type negotiation — Content-Type: application/vnd.myapi.v2+json. Stosowany przez GitHub API.

Dobry vs zly REST design

Wzorzec Zle Dobrze
Nazwy zasobow /getUser, /deleteOrder /users/{id}, /orders/{id}
Metody HTTP POST do wszystkiego GET/POST/PUT/PATCH/DELETE wg semantyki
Kody odpowiedzi Zawsze 200, blad w body 200/201/400/404/422 wg sytuacji
Bledy {"status": "error", "msg": "not found"} RFC 7807 Problem Details lub spojny schemat
Paginacja Zwracaj wszystko bez limitu Cursor lub offset z metadanymi
Wersjonowanie Brak wersjonowania, breaking changes w produkcji URL versioning z polityka deprecacji
Walidacja 500 przy blednych danych wejsciowych 422 z lista bledow per pole
Filtry POST body z filtrami do GET Query params: ?status=active&page=2

Najczestsze bledy w REST API

  • Uzycie czasownikow w URL (/createUser) zamiast rzeczownikow (/users + POST)
  • Ignorowanie kodow statusow HTTP — zawsze 200, blad w body JSON
  • Brak paginacji na kolekcjach — zwracanie tysiecy rekordow naraz
  • Niespojny format odpowiedzi — inne pola bledu w roznych endpointach
  • Brak wersjonowania — breaking changes bez ostrzezenia
