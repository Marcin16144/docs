Deployment Rust API

Optymalizacja binarki, cross-compilation, minimalne obrazy Docker, Kubernetes, fly.io i graceful shutdown — wszystko co potrzebne do produkcji.

cargo build --release — optymalizacje

Domyslny profil release jest juz znacznie szybszy od debug, ale mozna go dalej optymalizowac w Cargo.toml. Kluczowe ustawienia to LTO (Link Time Optimization) i codegen-units=1 — powoduja dluzsza kompilacje, ale generuja znacznie szybszy i mniejszy binarny.

# Cargo.toml
[profile.release]
opt-level = 3          # maksymalna optymalizacja (domyslne dla release)
lto = true             # link-time optimization (wolniejszy build, szybszy runtime)
codegen-units = 1      # jeden jednostka kodowania (lepsze LTO, wolniejszy build)
strip = true           # usun symbole debug z binarki (mniejszy plik)
panic = "abort"        # mniejszy binarny (bez unwind tables)

# Profil dla szybkiego CI (bez LTO, ale z optymalizacjami)
[profile.ci]
inherits = "release"
lto = false
codegen-units = 16

# Sprawdzenie rozmiaru binarki
# cargo build --release
# ls -lh target/release/my-api
# Typowy rozmiar: 5-15 MB (przed stripem), 2-8 MB (po stripie)

Cross-compilation — narzedzie cross

Crate cross uzywa Docker do cross-kompilacji bez konfigurowania lokalnego toolchainu. Wystarczy zainstalowac i wywolac jak cargo — reszta dzieje sie w kontenerze.

# Instalacja
cargo install cross --git https://github.com/cross-rs/cross

# Kompilacja dla Linux x86_64 (musl — statyczny binarny)
cross build --release --target x86_64-unknown-linux-musl

# Kompilacja dla ARM64 (np. AWS Graviton, Apple M1 serwery)
cross build --release --target aarch64-unknown-linux-musl

# Kompilacja dla ARM32 (Raspberry Pi)
cross build --release --target armv7-unknown-linux-musleabihf

# Wynikowy binarny jest statycznie zlinkowany — nie wymaga glibc na serwerze
# Mozna go uruchomic na scratch/distroless bez zadnych zaleznosci systemowych

Multi-stage Dockerfile — minimalny obraz

Multi-stage build pozwala uzyc pelnego obrazu do kompilacji, a nastepnie skopiowac tylko binarny do minimalnego obrazu bazowego. Obraz scratch ma 0 MB — idealny dla statycznie zlinkowanych binarow musl.

# Dockerfile
# ---- Etap budowania ----
FROM rust:1.78-slim AS builder

WORKDIR /app

# Cache zaleznosci (osobna warstwa)
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo 'fn main(){}' > src/main.rs
RUN cargo build --release --locked
RUN rm src/main.rs

# Kompilacja wlasciwego kodu
COPY src ./src
COPY migrations ./migrations
RUN touch src/main.rs && cargo build --release --locked

# Stripowanie symboli debug
RUN strip target/release/my-api

# ---- Obraz produkcyjny (distroless) ----
FROM gcr.io/distroless/cc-debian12 AS runtime

# distroless zawiera minimalne biblioteki C (libc, libssl)
# Alternatywa: FROM scratch  (tylko dla musl/statycznych binarow)

WORKDIR /app
COPY --from=builder /app/target/release/my-api ./my-api
COPY --from=builder /app/migrations ./migrations

# Bezpieczenstwo: uruchom jako non-root
USER nonroot:nonroot

EXPOSE 8080
ENTRYPOINT ["./my-api"]

Graceful shutdown — tokio signal

Aplikacja produkcyjna musi obsluzyc sygnaly SIGTERM/SIGINT i zakonczyc aktywne polaczenia zanim sie wylacy. Axum wspiera graceful shutdown przez .with_graceful_shutdown().

use tokio::signal;

async fn shutdown_signal() {
    let ctrl_c = async {
        signal::ctrl_c().await.expect("Nie mozna zainstalowac handlera Ctrl+C");
    };

    #[cfg(unix)]
    let terminate = async {
        signal::unix::signal(signal::unix::SignalKind::terminate())
            .expect("Nie mozna zainstalowac handlera SIGTERM")
            .recv()
            .await;
    };

    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        _ = ctrl_c    => { tracing::info!("Otrzymano Ctrl+C"); },
        _ = terminate => { tracing::info!("Otrzymano SIGTERM"); },
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let listener = tokio::net::TcpListener::bind("0.0.0.0:8080").await?;
    tracing::info!("Serwer startuje na :8080");

    axum::serve(listener, app)
        .with_graceful_shutdown(shutdown_signal())
        .await?;

    tracing::info!("Serwer zakonczyl dzialanie");
    Ok(())
}

Kubernetes — health probes

Kubernetes wymaga endpointow liveness i readiness. Liveness sprawdza czy aplikacja zyje (restart jesli nie), readiness czy jest gotowa do ruchu (usun z load balancera jesli nie).

// Health check handlery
async fn liveness() -> impl IntoResponse {
    StatusCode::OK
}

async fn readiness(State(state): State<Arc<AppState>>) -> impl IntoResponse {
    // Sprawdz polaczenie z baza
    match sqlx::query("SELECT 1").execute(&state.db).await {
        Ok(_) => StatusCode::OK,
        Err(_) => StatusCode::SERVICE_UNAVAILABLE,
    }
}

Konfiguracja — config crate i dotenvy

// Cargo.toml [dependencies]
// config = "0.14"
// dotenvy = "0.15"
// serde = { version = "1", features = ["derive"] }

use config::{Config, ConfigError, Environment, File};
use serde::Deserialize;

#[derive(Debug, Deserialize, Clone)]
pub struct AppConfig {
    pub database_url: String,
    pub listen_addr: String,
    pub jwt_secret: String,
    pub log_level: String,
    pub max_connections: u32,
}

impl AppConfig {
    pub fn load() -> Result<Self, ConfigError> {
        dotenvy::dotenv().ok();

        Config::builder()
            // Domyslne wartosci
            .set_default("listen_addr", "0.0.0.0:8080")?
            .set_default("log_level", "info")?
            .set_default("max_connections", 20)?
            // Plik konfiguracyjny (opcjonalny)
            .add_source(File::with_name("config/default").required(false))
            .add_source(File::with_name("config/local").required(false))
            // Zmienne srodowiskowe maja najwyzszy priorytet
            // APP_DATABASE_URL -> database_url
            .add_source(Environment::with_prefix("APP").separator("_"))
            .build()?
            .try_deserialize()
    }
}

fly.io — szybki deployment

# fly.toml
app = "my-rust-api"
primary_region = "waw"   # Warsaw

[build]
  dockerfile = "Dockerfile"

[env]
  RUST_LOG = "info"
  PORT = "8080"

[http_service]
  internal_port = 8080
  force_https = true
  auto_stop_machines = true
  auto_start_machines = true
  min_machines_running = 1

  [http_service.concurrency]
    type = "requests"
    hard_limit = 500
    soft_limit = 200

[[vm]]
  cpu_kind = "shared"
  cpus = 1
  memory_mb = 256

# Deployment:
# fly launch                          # pierwsza konfiguracja
# fly secrets set DATABASE_URL="..."  # sekrety (nie w fly.toml!)
# fly deploy                          # deployment
# fly logs                            # logi produkcyjne
# fly status                          # status maszyn
Typowy rozmiar obrazu Docker dla Rust API: Binarny release (~5 MB po stripie) + distroless/cc (~20 MB) = obraz ~25 MB. Dla porownania: Node.js API to zwykle 200-500 MB, Python FastAPI to 150-300 MB. Mniejszy obraz to szybszy pull, mniejsza powierzchnia ataku i nizsze koszty storage.
CI/CD tip: Uzyj GitHub Actions z cache Cargo — actions/cache dla ~/.cargo i target/. Bez cache kompilacja release trwa 5-10 min, z cache — 1-2 min. W monorepo workspace dodaj --package my-api do cargo build aby nie kompilowac wszystkiego.
