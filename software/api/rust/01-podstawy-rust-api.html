Podstawy Rust dla API dev

Cargo, tokio, ownership, serde, error handling i structured logging — fundament kazdego projektu API w Rust.

Cargo i struktura projektu

Cargo to oficjalny menedzer pakietow i system budowania w Rust. W projektach API kluczowe sa pliki Cargo.toml oraz opcjonalnie Cargo.lock (zawsze commituj dla aplikacji, pomijaj dla bibliotek).

Cargo.toml — typowy plik dla API

Sekcja [dependencies] zawiera zaleznosci runtime, a [dev-dependencies] — narzedzia uzywane tylko podczas testow. Sekcja [profile.release] pozwala na agresywna optymalizacje binariow produkcyjnych.

[package]
name = "my-api"
version = "0.1.0"
edition = "2021"

[dependencies]
tokio = { version = "1", features = ["full"] }
axum = "0.7"
serde = { version = "1", features = ["derive"] }
serde_json = "1"
sqlx = { version = "0.7", features = ["runtime-tokio", "postgres", "macros"] }
thiserror = "1"
anyhow = "1"
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
dotenvy = "0.15"

[dev-dependencies]
tokio = { version = "1", features = ["full", "test-util"] }

[profile.release]
lto = true
codegen-units = 1
strip = true

Workspace (monorepo)

Gdy projekt sklada sie z wielu skrzyni (crates), np. api, core, migrations, uzyj workspace w glownym Cargo.toml:

[workspace]
members = [
    "api",
    "core",
    "migrations",
]
resolver = "2"

[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["full"] }

Dzieki temu kazda skrzynia w members moze dziedziczyc zaleznosci z workspace za pomoca serde.workspace = true zamiast powielac wersje.

Features — warunkowa kompilacja

Features pozwalaja wlaczac fragmenty kodu lub opcjonalne zaleznosci. Przyklad: sqlx = { version = "0.7", features = ["runtime-tokio", "postgres"] }. Mozna tez definiowac wlasne features w [features].

Tokio runtime — async/await

Rust sam w sobie nie ma wbudowanego runtime dla asynchronicznosci. Tokio to najpopularniejszy wybor dla API — zapewnia reaktor I/O, pule watkow i prymitywy synchronizacyjne.

Punkt wejscia aplikacji

Makro #[tokio::main] transformuje funkcje main tak, by uruchomila runtime Tokio i wykonala cialo funkcji jako future:

use tokio::net::TcpListener;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // inicjalizacja loggera
    tracing_subscriber::fmt()
        .with_env_filter("info,my_api=debug")
        .init();

    dotenvy::dotenv().ok();
    let addr = std::env::var("LISTEN_ADDR")
        .unwrap_or_else(|_| "0.0.0.0:8080".to_string());

    let listener = TcpListener::bind(&addr).await?;
    tracing::info!("Serwer nasluchuje na {addr}");

    // axum::serve(listener, app).await?;
    Ok(())
}

Slowo kluczowe async fn zamienia funkcje w funkcje zwracajaca impl Future. Operator .await zawiesza wykonanie do momentu gotowosci future — bez blokowania watku OS.

Ownership w kontekscie API

String vs &str

W API czesto pojawia sie pytanie: kiedy String, a kiedy &str? Prosta zasada: jesli wartosc musi zyc dluzej niz biezacy scope lub jest budowana dynamicznie — uzyj String. Jesli jedynie czytasz — &str.

TypOwnershipTypowe uzycie w APIUwagi
Stringwlascicelpola struct, zwracane wartoscialokacja na stercie
&strpozyczenieparametry funkcji, literalzero-copy, ograniczony lifetime
&'static strpozyczenie statycznestale komunikaty bleduzyje przez caly czas dzialania
Cow<'_, str>zalezyelastyczne APIunika klonowan gdy niepotrzebne

Clone i Arc dla wspoldzielonego stanu

Handlery w Axum/Actix sa uruchamiane wspolbieznie, wiec wspoldzelony stan musi byc thread-safe. Standardowy wzorzec to Arc<T> — licznik referencji atomowy:

use std::sync::Arc;
use tokio::sync::RwLock;

#[derive(Clone)]
struct AppState {
    db: sqlx::PgPool,
    config: Arc<Config>,
    cache: Arc<RwLock<std::collections::HashMap<String, String>>>,
}

// przekazywanie stanu do handlera:
// State(state): State<Arc<AppState>>
// state.db.fetch_one(...).await?;

Clone na AppState jest tani — klonuje tylko Arc, nie wewnetrzne dane. RwLock z Tokio (nie std) nie blokuje watku OS — zawiesza future.

Serde — serializacja i deserializacja

Crate serde z features = ["derive"] generuje implementacje Serialize i Deserialize dla twoich struct przy uzyciu makr proceduralnych:

use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct CreateUserRequest {
    pub first_name: String,
    pub last_name: String,
    pub email: String,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub phone: Option<String>,
}

#[derive(Debug, Serialize)]
pub struct UserResponse {
    pub id: i64,
    #[serde(rename = "fullName")]
    pub full_name: String,
    #[serde(with = "chrono::serde::ts_seconds")]
    pub created_at: chrono::DateTime<chrono::Utc>,
}

Atrybuty serde: rename_all = "camelCase" zmienia nazwy pol (snake_case -> camelCase), skip_serializing_if pomija pole gdy predykat jest spelniony, with umozliwia uzywanie niestandardowych funkcji (de)serializacji.

Error handling — thiserror i anyhow

Dobre API wymaga czytelnego obslugi bledow. Rust wyraza bledy przez typ Result<T, E>. Dwie popularne biblioteki uzupelniaja sie nawzajem:

thiserror — do definiowania wlasnych typow bledow bibliotecznych/domenowych. Generuje implementacje Display, Error i opcjonalnie konwersje From.
anyhow — do kodu aplikacyjnego. anyhow::Result<T> przyjmuje dowolny blad implementujacy std::error::Error. Operator ? dziala ze wszystkim. 
use thiserror::Error;

#[derive(Debug, Error)]
pub enum AppError {
    #[error("Zasob nie znaleziony: {0}")]
    NotFound(String),

    #[error("Nieautoryzowany dostep")]
    Unauthorized,

    #[error("Blad bazy danych: {0}")]
    Database(#[from] sqlx::Error),

    #[error("Blad walidacji: {0}")]
    Validation(String),
}

// implementacja IntoResponse dla Axum (patrz 02-axum.html)

Operator #[from] generuje automatyczna konwersje sqlx::Error -> AppError::Database, wiec ? dziala bez .map_err().

Tracing — structured logging

Crate tracing zastepuje klasyczne log — umozliwia structured logging (klucz-wartosc), spans (kontekst czasowy) i jest kompatybilny z Tokio.

use tracing::{info, warn, error, instrument, Span};

#[instrument(skip(db), fields(user_id = %id))]
async fn get_user(id: i64, db: &sqlx::PgPool) -> anyhow::Result<User> {
    info!("Pobieranie uzytkownika");

    let user = sqlx::query_as!(User, "SELECT * FROM users WHERE id = $1", id)
        .fetch_optional(db)
        .await?;

    match user {
        Some(u) => {
            info!(email = %u.email, "Uzytkownik znaleziony");
            Ok(u)
        }
        None => {
            warn!("Uzytkownik nie istnieje");
            Err(AppError::NotFound(format!("user {id}")).into())
        }
    }
}

Makro #[instrument] automatycznie tworzy span z nazwa funkcji i argumentami. skip wyklucza parametry, ktore nie powinny byc logowane (np. pool polaczen). fields dodaje dodatkowe pola do spana.

Inicjalizacja subscribera: Uzyj tracing-subscriber z EnvFilter, by kontrolowac poziom logow przez zmienna RUST_LOG=info,my_api=debug. W produkcji rozwaz tracing-bunyan-formatter lub tracing-opentelemetry dla eksportu do Grafana Loki / Jaeger.
