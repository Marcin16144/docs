Gunicorn + Uvicorn workers

Na produkcji nie uruchamiaj Uvicorna bezposrednio — uzyj Gunicorn jako process managera z workerami Uvicorn. Gunicorn zarzadza procesami (restart po awarii, graceful shutdown), Uvicorn obsluguje ASGI w kazdym workerze.

Podstawowe uruchomienie produkcyjne

gunicorn main:app \
  -w 4 \
  -k uvicorn.workers.UvicornWorker \
  --bind 0.0.0.0:8000 \
  --timeout 120 \
  --keepalive 5 \
  --access-logfile - \
  --error-logfile -
Parametr Wartosc / opis Rekomendacja
-w / --workers Liczba procesow worker 2 * CPU + 1 (np. 4 CPU = 9 workers)
-k / --worker-class Klasa workera uvicorn.workers.UvicornWorker
--timeout Max czas requestu (sekundy) 30-120s, 0 = bez limitu
--keepalive Keep-alive dla polaczen 2-5s przy uzyciu load balancera
--max-requests Restart workera co N requestow 1000-2000 (zapobiega wyciekom pamieci)
--preload Zaladuj aplikacje przed forkiem Oszczedza pamiec (copy-on-write)

Docker — multi-stage build

Multi-stage build pozwala na stworzenie malego obrazu produkcyjnego — etap build instaluje zaleznosci, etap final kopiuje tylko to co potrzebne. Uzycie uv drastycznie przyspiesza instalacje pakietow.

# Dockerfile
# ================================
# ETAP 1: Builder — instalacja zaleznosci
# ================================
FROM python:3.12-slim AS builder

# Instalacja uv
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

WORKDIR /app

# Kopiuj pliki konfiguracji zaleznosci
COPY pyproject.toml uv.lock ./

# Instalacja zaleznosci do oddzielnego katalogu
RUN uv sync --frozen --no-dev --no-install-project

# ================================
# ETAP 2: Final — obraz produkcyjny
# ================================
FROM python:3.12-slim AS final

# Uzytkownik bez uprawnien root (bezpieczenstwo)
RUN groupadd --gid 1001 appuser && \
    useradd --uid 1001 --gid appuser --shell /bin/bash appuser

WORKDIR /app

# Kopiuj zainstalowane pakiety z buildera
COPY --from=builder /app/.venv /app/.venv

# Kopiuj kod aplikacji
COPY --chown=appuser:appuser . .

# Aktywacja venv przez PATH
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PYTHONPATH=/app

USER appuser

EXPOSE 8000

# Health check
HEALTHCHECK --interval=30s --timeout=10s --start-period=5s --retries=3 \
    CMD python -c "import httpx; httpx.get('http://localhost:8000/health').raise_for_status()"

CMD ["gunicorn", "main:app", \
     "-w", "4", \
     "-k", "uvicorn.workers.UvicornWorker", \
     "--bind", "0.0.0.0:8000", \
     "--timeout", "120", \
     "--access-logfile", "-"]

# docker-compose.yml
services:
  api:
    build:
      context: .
      target: final
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql+asyncpg://postgres:tajne@db:5432/mojabaza
      SECRET_KEY: ${SECRET_KEY}
      REDIS_URL: redis://redis:6379/0
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started

      POSTGRES_USER: postgres

      test: ["CMD-SHELL", "pg_isready -U postgres"]

Platformy PaaS — Railway, Render, Fly.io

Dla mniejszych projektow i MVP warto rozwazyc platformy PaaS zamiast samodzielnie zarzadzac serwerami. Porownanie popularnych opcji:

  • Railway — najprostszy deploy z GitHub, auto-detect Dockerfile lub Procfile, PostgreSQL w jednym kliknieciu, darmowy tier (500h/mies.)
  • Render — podobny do Railway, dobre wsparcie dla background workers i cron jobs, darmowy tier z usspiaciem po nieaktywnosci
  • Fly.io — bardziej zaawansowany, maszyny VM w wybranych regionach, dobry dla aplikacji wymagajacych niskich opoznienia lub globalnej dystrybucji

AWS Lambda z Mangum

Mangum to adapter ASGI dla AWS Lambda — pozwala uruchamiac FastAPI (i inne ASGI) jako serverless funkcje za API Gateway bez zadnych zmian w kodzie aplikacji.

Konfiguracja — pydantic-settings

pydantic-settings to oficjalne rozszerzenie Pydantic do zarzadzania konfiguracja przez zmienne srodowiskowe i pliki .env. Oferuje automatyczna walidacje typow i szyfrowanie sekretow.

# settings.py
from pydantic_settings import BaseSettings, SettingsConfigDict
from pydantic import PostgresDsn, RedisDsn, field_validator
from typing import Literal
import secrets

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        case_sensitive=False,
        extra="ignore",
    )

    # Serwer
    APP_NAME: str = "Moje API"
    APP_VERSION: str = "1.0.0"
    DEBUG: bool = False
    ENVIRONMENT: Literal["development", "staging", "production"] = "development"
    ALLOWED_HOSTS: list[str] = ["*"]

    # Baza danych
    DATABASE_URL: PostgresDsn
    DB_POOL_SIZE: int = 10
    DB_MAX_OVERFLOW: int = 20

    # Redis
    REDIS_URL: RedisDsn = "redis://localhost:6379/0"  # type: ignore

    # Bezpieczenstwo
    SECRET_KEY: str = secrets.token_urlsafe(32)
    JWT_ALGORITHM: str = "HS256"
    ACCESS_TOKEN_EXPIRE_MINUTES: int = 30
    REFRESH_TOKEN_EXPIRE_DAYS: int = 7

    # Zewnetrzne serwisy
    SMTP_HOST: str = "localhost"
    SMTP_PORT: int = 587
    SMTP_USER: str = ""
    SMTP_PASSWORD: str = ""

    @field_validator("SECRET_KEY")
    @classmethod
    def sprawdz_secret_key(cls, v: str) -> str:
        if len(v) < 32:
            raise ValueError("SECRET_KEY musi miec min. 32 znaki")
        return v

    @property
    def jest_produkcja(self) -> bool:
        return self.ENVIRONMENT == "production"

# Singleton — jeden obiekt w calej aplikacji
settings = Settings()  # type: ignore

# Uzycie w aplikacji FastAPI
# from .settings import settings
# DATABASE_URL = str(settings.DATABASE_URL)

# ================================
# Health check endpoint
# ================================
from fastapi import FastAPI
from fastapi.responses import JSONResponse
from datetime import datetime
import sys

app = FastAPI()

@app.get("/health", tags=["monitoring"])
async def health_check() -> JSONResponse:
    """
    Endpoint health check dla load balancerów i kontenerów.
    Zwraca 200 jesli aplikacja dziala poprawnie.
    """
    return JSONResponse(
        status_code=200,
        content={
            "status": "healthy",
            "timestamp": datetime.utcnow().isoformat(),
            "version": settings.APP_VERSION,
            "environment": settings.ENVIRONMENT,
            "python": sys.version,
        }
    )

@app.get("/health/ready", tags=["monitoring"])
async def readiness_check() -> JSONResponse:
    """Sprawdza gotowosci: polaczenie z DB i Redis."""
    checks: dict[str, str] = {}
    overall_ok = True

    # Sprawdz baze danych
    try:
        # await db.execute("SELECT 1")
        checks["database"] = "ok"
    except Exception as e:
        checks["database"] = f"error: {e}"
        overall_ok = False

    # Sprawdz Redis
    try:
        # await redis.ping()
        checks["redis"] = "ok"
    except Exception as e:
        checks["redis"] = f"error: {e}"
        overall_ok = False

    return JSONResponse(
        status_code=200 if overall_ok else 503,
        content={"status": "ready" if overall_ok else "not_ready", "checks": checks},
    )

# Handler dla AWS Lambda / API Gateway

    lifespan="off",        # Lambda nie obsluguje lifespan
    api_gateway_base_path="/prod",  # prefix stage API Gateway
)

Liczba workers Gunicorn

Zalecana formula: workers = 2 * CPU_cores + 1. Dla maszyny 2 CPU = 5 workers, dla 4 CPU = 9 workers. Nie przekraczaj dostepnej pamieci RAM — kazdy worker FastAPI z asyncpg moze zuzyc 50-150 MB. Monitoruj uzycie pamieci i dostosowuj.

Procfile dla Railway i Render

Jesli nie uzywasz Dockerfile, platformy PaaS wykrywaja Procfile:
web: gunicorn main:app -w 4 -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:$PORT
Zmienna $PORT jest automatycznie ustawiana przez platforme.
