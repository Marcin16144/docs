Typy testow API

Efektywna strategia testowania API opiera sie na kilku warstwach — kazda ma inny cel, koszt i szybkosc wykonania.

Typ testu Co sprawdza Szybkosc Koszt utrzymania Narzedzia
Unit Logika biznesowa, validatory, transformacje danych Bardzo szybkie (<1ms) Niski Jest, Vitest, pytest
Integration Endpointy z prawdziwa baza, cache, zewnetrznymi serwisami Srednie (sekundy) Sredni Testcontainers, Supertest
Contract Zgodnosc kontraktu miedzy producentem a konsumentem Szybkie Sredni Pact, Spring Cloud Contract

Security OWASP Top 10, podatnosci, nieautoryzowany dostep Zmienne Wysoki OWASP ZAP, Burp Suite

Integration Tests z Testcontainers

Testcontainers uruchamia prawdziwe kontenery Docker (PostgreSQL, Redis, Kafka) na czas testow. Eliminuje problem "works on my machine" i roznice miedzy mockiem a prawdziwym serwisem.

// api.integration.test.ts (Node.js + Testcontainers + Supertest)
import { PostgreSqlContainer } from '@testcontainers/postgresql';
import { RedisContainer }      from '@testcontainers/redis';
import request                  from 'supertest';
import { createApp }            from '../src/app';
import { runMigrations }        from '../src/db/migrations';

describe('Users API — integration tests', () => {
  let pgContainer:    Awaited<ReturnType<typeof PostgreSqlContainer.prototype.start>>;
  let redisContainer: Awaited<ReturnType<typeof RedisContainer.prototype.start>>;
  let app:            ReturnType<typeof createApp>;

  // Uruchom kontenery raz dla calego suite
  beforeAll(async () => {
    pgContainer = await new PostgreSqlContainer('postgres:16-alpine')
      .withDatabase('testdb')
      .withUsername('test')
      .withPassword('test')
      .start();

    redisContainer = await new RedisContainer('redis:7-alpine').start();

    app = createApp({
      databaseUrl: pgContainer.getConnectionUri(),
      redisUrl:    redisContainer.getConnectionUrl(),
    });

    await runMigrations(pgContainer.getConnectionUri());
  }, 60_000);  // timeout 60s na start kontenerow

  afterAll(async () => {
    await pgContainer.stop();
    await redisContainer.stop();
  });

  beforeEach(async () => {
    // Czysc dane miedzy testami
    await app.db.user.deleteMany();
  });

  describe('POST /v1/users', () => {
    it('tworzy uzytkownika i zwraca 201', async () => {
      const res = await request(app)
        .post('/v1/users')
        .send({ name: 'Jan Kowalski', email: 'jan@test.com', password: 'secret123' })
        .expect(201);

      expect(res.body).toMatchObject({
        id:    expect.any(String),
        name:  'Jan Kowalski',
        email: 'jan@test.com',
        role:  'user',
      });
      expect(res.headers.location).toMatch(/\/v1\/users\//);
      expect(res.body).not.toHaveProperty('password');  // nigdy nie zwracaj hasla
    });

    it('zwraca 409 przy duplikacie emaila', async () => {
      await request(app)
        .post('/v1/users')
        .send({ name: 'Jan', email: 'dup@test.com', password: 'pass123' });

      const res = await request(app)
        .post('/v1/users')
        .send({ name: 'Jan2', email: 'dup@test.com', password: 'pass456' })
        .expect(409);

      expect(res.body.error.code).toBe('EMAIL_ALREADY_EXISTS');
    });

    it('zwraca 422 przy niepoprawnym emailu', async () => {
      const res = await request(app)
        .post('/v1/users')
        .send({ name: 'Jan', email: 'not-an-email', password: 'pass123' })
        .expect(422);

      expect(res.body.error.details).toEqual(
        expect.arrayContaining([
          expect.objectContaining({ field: 'email' })
        ])
      );
    });
  });

  describe('GET /v1/users/:id', () => {
    it('zwraca uzytkownika po ID', async () => {
      const created = await request(app)
        .post('/v1/users')
        .send({ name: 'Anna', email: 'anna@test.com', password: 'pass123' })
        .expect(201);

      await request(app)
        .get(`/v1/users/${created.body.id}`)
        .set('Authorization', `Bearer ${await getTestToken('admin')}`)
        .expect(200)
        .expect(res => {
          expect(res.body.email).toBe('anna@test.com');
        });
    });

    it('zwraca 404 dla nieistniejacego ID', async () => {
      await request(app)
        .get('/v1/users/nonexistent-id')
        .set('Authorization', `Bearer ${await getTestToken('admin')}`)
        .expect(404);
    });
  });
});

Contract Testing z Pact

Pact pozwala testowac zgodnosc kontraktu miedzy konsumentem (klient API) a producentem (serwer API). Konsument definiuje oczekiwania (interactions), Pact generuje pact file, ktory producent weryfikuje w swoich testach. Eliminuje potrzebe wspoldzielonego srodowiska testowego.

Consumer-Driven Contract Testing

W odroznieniu od testow producenta (gdzie producent definiuje kontrakt), Consumer-Driven Contract Testing pozwala konsumentom wyrazic swoje oczekiwania. Producent musi spelniac oczekiwania wszystkich konsumentow — zapobiega regression breaking changes.

// consumer.pact.test.ts — test po stronie konsumenta
import { PactV3, MatchersV3 } from '@pact-foundation/pact';
import { UserApiClient }      from '../src/user-api-client';
import path                    from 'path';

const { like, string, integer, datetime } = MatchersV3;

const provider = new PactV3({
  consumer: 'OrderService',
  provider: 'UserService',
  dir:      path.resolve(__dirname, '../pacts'),
  port:     8080,
});

describe('UserService contract', () => {
  it('GET /users/:id — pobiera uzytkownika', async () => {
    await provider
      .given('user with id usr_123 exists')
      .uponReceiving('a request for user usr_123')
      .withRequest({
        method:  'GET',
        path:    '/v1/users/usr_123',
        headers: { Authorization: like('Bearer token') },
      })
      .willRespondWith({
        status:  200,
        headers: { 'Content-Type': 'application/json' },
        body: {
          id:        string('usr_123'),
          name:      string('Jan Kowalski'),
          email:     string('jan@example.com'),
          role:      string('user'),
          createdAt: datetime("yyyy-MM-dd'T'HH:mm:ssXXX"),
        },
      })
      .executeTest(async (mockServer) => {
        const client = new UserApiClient(mockServer.url);
        const user   = await client.getUser('usr_123');

        expect(user.id).toBe('usr_123');
        expect(user.name).toBeTruthy();
      });
  });
});

// producer.pact.test.ts — weryfikacja po stronie producenta
import { Verifier } from '@pact-foundation/pact';

describe('Pact verification — UserService', () => {
  it('verifies consumer contracts', async () => {
    const verifier = new Verifier({
      provider:              'UserService',
      providerBaseUrl:       'http://localhost:3000',
      pactBrokerUrl:         process.env.PACT_BROKER_URL,
      pactBrokerToken:       process.env.PACT_BROKER_TOKEN,
      publishVerificationResult: true,
      providerVersion:       process.env.GIT_SHA,
      stateHandlers: {
        'user with id usr_123 exists': async () => {
          await testDb.user.upsert({
            where:  { id: 'usr_123' },
            create: { id: 'usr_123', name: 'Jan Kowalski', email: 'jan@example.com', role: 'user' },
            update: {},
          });
        },
      },
    });

    await verifier.verifyProvider();
  });
});

Load Testing — k6

// load-test.js (k6)
import http    from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

// Metryki customowe
const errorRate      = new Rate('error_rate');
const createUserTime = new Trend('create_user_duration', true);

export const options = {
  stages: [
    { duration: '1m',  target: 50   },   // ramp-up do 50 VU
    { duration: '3m',  target: 50   },   // utrzymaj 50 VU
    { duration: '2m',  target: 200  },   // spike do 200 VU
    { duration: '2m',  target: 200  },   // utrzymaj spike
    { duration: '1m',  target: 0    },   // ramp-down
  ],
  thresholds: {
    http_req_duration:    ['p(95)<500', 'p(99)<1000'],  // 95% < 500ms
    http_req_failed:      ['rate<0.01'],                // <1% bledow
    error_rate:           ['rate<0.02'],
    create_user_duration: ['p(95)<800'],
  },
};

const BASE_URL = __ENV.BASE_URL || 'https://api.staging.example.com';

export default function () {
  // Test 1 — GET lista uzytkownikow
  const listRes = http.get(`${BASE_URL}/v1/users?limit=20`, {
    headers: { Authorization: `Bearer ${__ENV.API_TOKEN}` },
  });

  check(listRes, {
    'list: status 200':       (r) => r.status === 200,
    'list: has data array':   (r) => Array.isArray(JSON.parse(r.body).data),
    'list: response time ok': (r) => r.timings.duration < 500,
  });

  errorRate.add(listRes.status !== 200);

  sleep(0.5);

  // Test 2 — POST nowy uzytkownik
  const payload = JSON.stringify({
    name:     `User ${Math.random()}`,
    email:    `test${Date.now()}@example.com`,
    password: 'TestPass123!',
  });

  const startCreate = Date.now();
  const createRes = http.post(`${BASE_URL}/v1/users`, payload, {
    headers: {
      'Content-Type': 'application/json',
      Authorization:  `Bearer ${__ENV.API_TOKEN}`,
    },
  });

  createUserTime.add(Date.now() - startCreate);

  check(createRes, {
    'create: status 201':       (r) => r.status === 201,
    'create: has id':           (r) => JSON.parse(r.body).id !== undefined,
    'create: location header':  (r) => r.headers['Location'] !== undefined,
  });

  errorRate.add(createRes.status !== 201);

  sleep(1);
}

// Uruchomienie:
// k6 run --env BASE_URL=https://api.staging.example.com \
//         --env API_TOKEN=sk_test_... \
//         load-test.js

API Mocking

Mockowanie pozwala testowac klientow API bez uruchamiania prawdziwego serwera. Przydatne do testow frontend, testow izolowanych i development bez backendu.

  • WireMock — Java, standalone server lub JUnit rule, bogaty DSL, record & replay
  • Mockoon — desktop app i CLI, drag&drop interface, latwy start
  • MSW (Mock Service Worker) — interceptuje fetch/XHR w przegladarce i Node.js, idealny dla React/Next.js
  • Prism — generuje mock serwer automatycznie z OpenAPI spec
// MSW — setupowanie handlerow w testach
import { http, HttpResponse } from 'msw';
import { setupServer }         from 'msw/node';

const server = setupServer(
  http.get('https://api.example.com/v1/users/:id', ({ params }) => {
    if (params.id === 'not-found') {
      return HttpResponse.json(
        { error: { code: 'NOT_FOUND', message: 'User not found' } },
        { status: 404 }
      );
    }
    return HttpResponse.json({
      id:    params.id,
      name:  'Jan Kowalski',
      email: 'jan@example.com',
      role:  'user',
    });
  }),

  http.post('https://api.example.com/v1/users', async ({ request }) => {
    const body = await request.json() as any;
    return HttpResponse.json(
      { id: 'new-id', ...body },
      { status: 201, headers: { Location: '/v1/users/new-id' } }
    );
  }),
);

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

// Nadpisanie handlera dla konkretnego testu
it('obsluguje blad serwera', async () => {
  server.use(
    http.get('https://api.example.com/v1/users/:id', () => {
      return HttpResponse.json(null, { status: 500 });
    })
  );
  // ... test
});

Chaos Engineering i fault injection

Chaos engineering to celowe wprowadzanie awarii do systemu w kontrolowanych warunkach, aby odkryc slabe punkty zanim zrobi to produkcja. Dla API testujemy: opoznienia, bledy HTTP, timeouty, utrate polaczen.

Test data management

Izoluj dane testowe od produkcyjnych. Uzyj dedykowanej bazy per test suite (Testcontainers). Stosuj factory functions lub biblioteki (fishery, faker) do generowania danych testowych. Nigdy nie uzywaj produkcyjnych danych osobowych w testach — RODO/GDPR.

Checklist — testy przed deploymentem

  • Testy jednostkowe: 100% przejscie, coverage >80% dla logiki biznesowej
  • Testy integracyjne: wszystkie endpointy pokryte happy path i error cases
  • Testy kontraktu: Pact broker zielony dla wszystkich konsumentow
  • Load test na staging: p95 latency < SLA, error rate < 1%
  • Security scan: OWASP ZAP baseline scan, brak krytycznych podatnosci
