Podstawy PHP API

PSR-7, PSR-15, Composer, PHP 8.3, JSON handling i standardy PHP-FIG

PHP-FIG i standardy PSR

PHP-FIG (PHP Framework Interoperability Group) to organizacja odpowiedzialna za tworzenie standardow PSR (PHP Standards Recommendations). Standardy te umozliwiaja interoperacyjnosc miedzy roznymy frameworkami i bibliotekami PHP. Dla budowniczych API najwazniejsze sa PSR-7 (interfejsy HTTP) i PSR-15 (middleware).

Stosowanie standardow PSR sprawia, ze kod jest bardziej przenosny — biblioteka napisana z uzyciem interfejsow PSR-7 dziala z dowolnym frameworkiem implementujacym ten standard, niezaleznie od tego czy to Slim, Laravel, Symfony czy inny.

PSR-7: HTTP Message Interfaces

PSR-7 definiuje interfejsy dla wiadomosci HTTP: RequestInterface, ResponseInterface, ServerRequestInterface i StreamInterface. Wszystkie obiekty PSR-7 sa immutable — kazda modyfikacja zwraca nowy obiekt zamiast mutowac istniejacy.

Dlaczego immutability ma znaczenie?

Immutable HTTP messages eliminuja subtelne bledy wynikajace z przypadkowej mutacji obiektow w lancuchu middleware. Kazdy handler dostaje gwarancje, ze obiekt Request, ktory otrzymal, nie zostal zmodyfikowany przez poprzedni handler.

Najpopularniejsze implementacje PSR-7 to Guzzle/psr7 oraz Nyholm/psr7 (lekka, wysoka wydajnosc). Nyholm jest rekomendowana dla nowych projektow ze wzgledu na minimalistyczna implementacje i brak dodatkowych zaleznosci.

<?php
// Instalacja przez Composer
// composer require nyholm/psr7 nyholm/psr7-server

use Nyholm\Psr7\Factory\Psr17Factory;
use Nyholm\Psr7Server\ServerRequestCreator;

$factory = new Psr17Factory();

$creator = new ServerRequestCreator(
    $factory, // ServerRequestFactory
    $factory, // UriFactory
    $factory, // UploadedFileFactory
    $factory  // StreamFactory
);

// Tworzenie ServerRequest z superglobals
$request = $creator->fromGlobals();

// Odczyt danych z requestu (PSR-7 API)
$method  = $request->getMethod();          // GET, POST, PUT ...
$uri     = $request->getUri();             // UriInterface
$path    = $uri->getPath();                // /api/users
$headers = $request->getHeaders();        // ['Content-Type' => ['application/json']]
$body    = (string) $request->getBody(); // raw body string

// Tworzenie Response (immutable — kazda zmiana = nowy obiekt)
$response = $factory->createResponse(200)
    ->withHeader('Content-Type', 'application/json')
    ->withBody($factory->createStream(json_encode(['status' => 'ok'])));

echo $response->getStatusCode(); // 200

PSR-15: HTTP Server Request Handlers i Middleware

PSR-15 definiuje dwa interfejsy: RequestHandlerInterface (obsluguje request i zwraca response) oraz MiddlewareInterface (przetwarza request i przekazuje go dalej lub zwraca response bezposrednio). Middleware tworzy lancuch — kazdy element moze modyfikowac request przed przekazaniem go dalej lub response przed zwroceniem go klientowi.

Przyklad middleware PSR-15

<?php
use Psr\Http\Message\ResponseInterface;
use Psr\Http\Message\ServerRequestInterface;
use Psr\Http\Server\MiddlewareInterface;
use Psr\Http\Server\RequestHandlerInterface;

// Middleware logujace czas wykonania requestu
class TimingMiddleware implements MiddlewareInterface
{
    public function process(
        ServerRequestInterface $request,
        RequestHandlerInterface $handler
    ): ResponseInterface {
        $start = microtime(true);

        // Przekazanie requestu do kolejnego handlera
        $response = $handler->handle($request);

        $elapsed = round((microtime(true) - $start) * 1000, 2);

        // Dodanie headera X-Response-Time do odpowiedzi
        return $response->withHeader('X-Response-Time', $elapsed . 'ms');
    }
}

// Middleware weryfikujace token Bearer
class AuthMiddleware implements MiddlewareInterface
{
    public function process(
        ServerRequestInterface $request,
        RequestHandlerInterface $handler
    ): ResponseInterface {
        $authHeader = $request->getHeaderLine('Authorization');

        if (!str_starts_with($authHeader, 'Bearer ')) {
            // Przerwanie lancucha — zwrocenie 401 bez wywolania handlera
            return (new Psr17Factory())->createResponse(401)
                ->withHeader('Content-Type', 'application/json')
                ->withBody((new Psr17Factory())->createStream(
                    json_encode(['error' => 'Unauthorized'])
                ));
        }

        $token = substr($authHeader, 7);
        // Dodanie tokenu do atrybutow requestu (immutable)
        $request = $request->withAttribute('token', $token);

        return $handler->handle($request);
    }
}

Composer i PSR-4 Autoloading

Composer to menedzer zaleznosci PHP, ktory obsluguje rowniez autoloading klas. PSR-4 to standard mapowania namespace'ow na struktury katalogow. Prawidlowo skonfigurowane autoloading eliminuje potrzebe recznego require kazdego pliku.

Konfiguracja PSR-4 w composer.json 
{
  "name": "myapp/api",
  "require": {
    "php": "^8.3",
    "nyholm/psr7": "^1.8",
    "nyholm/psr7-server": "^1.1",
    "psr/http-message": "^2.0",
    "psr/http-server-middleware": "^1.0"
  },
  "autoload": {
    "psr-4": {
      "App\\": "src/"
    }
  },
  "autoload-dev": {
    "psr-4": {
      "Tests\\": "tests/"
    }
  }
}

PHP 8.3 — nowosci istotne dla API

PHP 8.3 wprowadzil kilka ulepszonych funkcji, ktore bezposrednio przydaja sie przy budowie API.

Typed Class Constants

Stale klasowe moga teraz miec zadeklarowany typ, co zwieksza bezpieczenstwo typow i eliminuje przypadkowe nadpisania z blednym typem.

Readonly Properties i Readonly Classes

Wlasciwosci readonly mozna ustawic tylko raz (w konstruktorze). PHP 8.2 wprowadzil readonly classes — wszystkie promowane wlasciwosci sa automatycznie readonly. PHP 8.3 udoskonalil klonowanie readonly obiektow.

Named Arguments

Named arguments pozwalaja przekazywac argumenty do funkcji po nazwie, co zwieksza czytelnosc kodu i umozliwia pominiecie opcjonalnych parametrow posrednich.

JSON Handling w PHP

PHP oferuje json_encode() i json_decode() do serializacji i deserializacji JSON. Krytyczne znaczenie ma flaga JSON_THROW_ON_ERROR — bez niej bledy JSON sa cicho ignorowane, co moze prowadzic do trudnych do debugowania bledow w produkcji.

OPcache — optymalizacja wydajnosci

OPcache kompiluje skrypty PHP do bytecode i przechowuje je w pamieci wspoldzielonej. Przy kazdym kolejnym zadaniu PHP nie musi parsowac i kompilowac plikow — bezposrednio wykonuje bytecode. Dla API z wieloma requestami na sekunde OPcache jest absolutnie konieczny.

Rekomendowana konfiguracja OPcache dla produkcji (php.ini) 
opcache.enable=1
opcache.memory_consumption=256
opcache.interned_strings_buffer=16
opcache.max_accelerated_files=20000
opcache.validate_timestamps=0   ; wylacz na produkcji!
opcache.save_comments=1
opcache.enable_cli=0
; PHP 8.x — preloading (ladowanie klas przy starcie FPM)
opcache.preload=/var/www/app/preload.php
opcache.preload_user=www-data

Ustawienie validate_timestamps=0 na produkcji eliminuje sprawdzanie, czy pliki na dysku zostaly zmodyfikowane — cache jest zawsze wazny i OPcache nie musi wykonywasc operacji I/O. Przy deploymencie nalezy zresetowac OPcache (opcache_reset() lub restart PHP-FPM).

Preloading (PHP 7.4+)

Preloading to funkcja, ktora laduje klasy do OPcache przy starcie PHP-FPM, zanim zostanie obsluzony jakikolwiek request. Klasy zaladowane przez preloading sa dostepne dla wszystkich requestow bez potrzeby ponownego ladowania. Idealnie nadaje sie dla frameworkow takich jak Laravel czy Symfony.

Podsumowanie dobrych praktyk

  • Zawsze uzywaj JSON_THROW_ON_ERROR przy pracy z JSON
  • Implementuj interfejsy PSR-7 i PSR-15 dla interoperacyjnosci
  • Uzywaj readonly dla Data Transfer Objects (DTO)
  • Wlacz OPcache na kazdym srodowisku (w tym staging)
  • Konfiguruj validate_timestamps=0 tylko na produkcji
  • Uzywaj PSR-4 autoloading — zero recznych require
  • Typuj wszystko: parametry, zwracane wartosci, stale, wlasciwosci
