GraphQL

Jezyk zapytan dla API — schema, resolvery, federacja i bezpieczenstwo.

Schema Definition Language (SDL)

SDL to jezyk opisu schematu GraphQL. Definiuje typy, pola, zapytania i mutacje. Schema jest kontraktem miedzy klientem a serwerem — wszystko, co nie jest w schemacie, nie istnieje w API.

# schema.graphql

# Typy skalarne wbudowane: Int, Float, String, Boolean, ID
# Wlasny skalar
scalar DateTime
scalar JSON

# Interfejs — wspolne pola dla wielu typow
interface Node {
  id: ID!
}

# Typ obiektowy
type User implements Node {

  name:      String!
  email:     String!
  role:      UserRole!

  id:        ID!

type OrderItem {
  product:  Product!
  quantity: Int!
  price:    Float!
}

type Product implements Node {
  id:    ID!
  name:  String!
  price: Float!

# Glowne operacje
type Query {
  user(id: ID!): User
  users(
    first:  Int = 20
    after:  String
    filter: UserFilterInput

  me: User
}

type Mutation {
  createUser(input: CreateUserInput!): CreateUserPayload!
  updateUser(id: ID!, input: UpdateUserInput!): UpdateUserPayload!
  deleteUser(id: ID!): DeleteUserPayload!
}

type Subscription {
  orderStatusChanged(orderId: ID!): Order!

}

  endCursor:       String

type CreateUserPayload {
  user:   User

}

type UserError {
  field:   String
  message: String!
  code:    String!
}

Query, Mutation, Subscription

GraphQL definiuje trzy typy operacji. Query to odpowiednik GET — odczyt danych. Mutation zmienia stan serwera. Subscription otwiera polaczenie WebSocket do otrzymywania zdarzen w czasie rzeczywistym.

# Przykladowe query z fragmentem
fragment UserFields on User {
  id
  name
  email
  role
}

query GetUser($id: ID!) {
  user(id: $id) {
    ...UserFields
    orders {
      id
      status
      total
    }
  }
}

# Mutation z obsliga bledu
mutation CreateUser($input: CreateUserInput!) {
  createUser(input: $input) {
    user {
      ...UserFields
    }
    errors {
      field
      message
      code
    }
  }
}

# Subscription
subscription WatchOrder($orderId: ID!) {
  orderStatusChanged(orderId: $orderId) {
    id
    status
    updatedAt
  }
}

Resolvery

Resolver to funkcja, ktora zwraca dane dla konkretnego pola schematu. Kazde pole moze miec wlasny resolver. Jesli nie ma resolvera, GraphQL uzywa domyslnego, ktory zwraca pole o tej samej nazwie z obiektu rodzica.

// resolvers.ts (Node.js / TypeScript)
import { GraphQLResolveInfo } from 'graphql';
import { Context } from './context';

export const resolvers = {
  Query: {
    user: async (_: unknown, { id }: { id: string }, ctx: Context) => {
      return ctx.db.user.findUnique({ where: { id } });
    },
    users: async (_: unknown, { first, after, filter }: any, ctx: Context) => {
      const users = await ctx.db.user.findMany({
        take: first,
        cursor: after ? { id: after } : undefined,
        where: filter,
        orderBy: { createdAt: 'desc' },
      });
      return buildConnection(users, first);
    },
    me: async (_: unknown, __: unknown, ctx: Context) => {
      if (!ctx.userId) throw new AuthenticationError('Not authenticated');
      return ctx.db.user.findUnique({ where: { id: ctx.userId } });
    },
  },

  Mutation: {
    createUser: async (_: unknown, { input }: any, ctx: Context) => {
      try {
        const user = await ctx.db.user.create({ data: input });
        return { user, errors: [] };
      } catch (err) {
        return { user: null, errors: [{ message: err.message, code: 'CREATE_FAILED' }] };
      }
    },
  },

  User: {
    // Resolver pola zagniezdzonego — lazy loading
    orders: async (parent: any, _: unknown, ctx: Context) => {
      return ctx.db.order.findMany({ where: { userId: parent.id } });
    },
  },

  SearchResult: {
    // Resolver __resolveType dla Union
    __resolveType(obj: any) {
      if (obj.email)    return 'User';
      if (obj.price)    return 'Product';
      if (obj.status)   return 'Order';
      return null;
    },
  },
};

DataLoader i problem N+1

Problem N+1 to klasyczna pulapka GraphQL: dla listy 100 uzytkownikow resolver orders wykona 100 oddzielnych zapytan do bazy. DataLoader rozwiazuje to przez batching — zbiera wszystkie klucze z jednego ticku event loop i wykonuje jedno zapytanie zbiorcze.

Problem N+1 w praktyce

Query users { orders } bez DataLoadera: 1 zapytanie po uzytkownikow + N zapytan po zamowienia = N+1 zapytan do bazy. Przy N=100 to 101 zapytan zamiast 2.

// dataloader.ts
import DataLoader from 'dataloader';
import { db } from './db';

// Funkcja batch — dostaje tablice kluczy, zwraca tablice wynikow
const batchLoadOrders = async (userIds: readonly string[]) => {
  const orders = await db.order.findMany({
    where: { userId: { in: [...userIds] } },
  });

  // Mapuj wyniki z powrotem do kolejnosci kluczy
  const ordersByUserId = new Map();
  for (const order of orders) {
    if (!ordersByUserId.has(order.userId)) {
      ordersByUserId.set(order.userId, []);
    }
    ordersByUserId.get(order.userId)!.push(order);
  }

  return userIds.map(id => ordersByUserId.get(id) ?? []);
};

// Tworzenie loadera — jeden na request (NIE globalnie)
export const createLoaders = () => ({
  ordersByUserId: new DataLoader(batchLoadOrders),
  // Caching: domyslnie wlaczone — ten sam klucz = jeden fetch
  userById: new DataLoader(async (ids: readonly string[]) => {
    const users = await db.user.findMany({ where: { id: { in: [...ids] } } });
    const map = new Map(users.map(u => [u.id, u]));
    return ids.map(id => map.get(id) ?? null);
  }),
});

// Uzycie w resolverze
const User = {
  orders: (parent: any, _: unknown, ctx: Context) => {
    return ctx.loaders.ordersByUserId.load(parent.id);
  },
};

Federation v2 — Supergraph

Apollo Federation pozwala podzielic jeden schemat GraphQL na wiele niezaleznych serwisow (subgrafow). Router (Apollo Router lub Gateway) laczy je w jeden supergraf widoczny dla klientow.

# subgraph: users-service
extend schema
  @link(url: "https://specs.apollo.dev/federation/v2.3",
        import: ["@key", "@shareable", "@external"])

type User @key(fields: "id") {
  id:    ID!
  name:  String!
  email: String!
}

type Query {
  me: User
  user(id: ID!): User
}

# subgraph: orders-service
extend schema
  @link(url: "https://specs.apollo.dev/federation/v2.3",
        import: ["@key", "@external", "@requires"])

# Rozszerz typ z innego subgrafu
type User @key(fields: "id") {
  id:     ID! @external
  orders: [Order!]!
}

type Order @key(fields: "id") {
  id:     ID!
  status: String!
  total:  Float!
  user:   User!
}

Bezpieczenstwo — query depth i complexity

GraphQL jest podatny na ataki przez zlosliwe zapytania: glebokie zagniezdzone pola moga przeciazyc serwer, a skomplikowane zapytania zuzyc nadmierne zasoby. Nalezy wprowadzic limity depth i complexity.

Persisted Queries

Zamiast wysylac pelny tekst zapytania, klient wysyla tylko hash (ID) zapytania zarejestrowanego wczesniej na serwerze. Eliminuje ryzyko arbitralnych zapytan od niezaufanych klientow i zmniejsza payload.

// Apollo Server — limity bezpieczenstwa
import { ApolloServer } from '@apollo/server';
import depthLimit from 'graphql-depth-limit';
import { createComplexityLimitRule } from 'graphql-validation-complexity';

const server = new ApolloServer({
  typeDefs,
  resolvers,
  validationRules: [
    depthLimit(7),                          // max 7 poziomow zagniezdzen
    createComplexityLimitRule(1000, {       // max complexity score = 1000
      onCost: (cost) => console.log('Query cost:', cost),
      formatErrorMessage: (cost) =>
        `Query too complex: ${cost}. Max allowed: 1000`,
    }),
  ],
  plugins: [
    {
      async requestDidStart() {
        return {
          async didResolveOperation({ request, document }) {
            // Blokuj introspekcje na produkcji
            if (process.env.NODE_ENV === 'production') {
              const isIntrospection = document.definitions.some(
                def => def.kind === 'OperationDefinition' &&
                  def.selectionSet.selections.some(
                    sel => sel.kind === 'Field' &&
                      (sel.name.value === '__schema' || sel.name.value === '__type')
                  )
              );
              if (isIntrospection) throw new Error('Introspection disabled');
            }
          },
        };
      },
    },
  ],
});

GraphQL vs REST — kiedy co wybrac

Kryterium GraphQL REST
Pobieranie danych Klient okresla dokladnie co chce — brak over/under-fetchingu Serwer decyduje o ksztalcie odpowiedzi
Wiele zasobow naraz Jedno zapytanie pobiera dane z wielu typow Wymaga wielu requestow lub dedykowanych endpointow
Caching Trudniejszy — wszystko przez POST na /graphql Latwy — HTTP caching, CDN per URL
Krzywa uczenia Stroma — SDL, resolvery, DataLoader, N+1 Plaska — standardy HTTP wszystkim znane
Typowanie Mocne — schema jako kontrakt, generowanie typow OpenAPI/JSON Schema — opcjonalne
Real-time Subscriptions wbudowane w specyfikacje Wymaga SSE lub WebSocket poza standardem
Mikroserwisy Federation — jeden supergraf z wielu serwisow API Gateway lub BFF pattern
Kiedy wybrac Zlozony frontend, wiele klientow (web/mobile), szybka iteracja UI Proste API, publiczne API, silny caching, prostota
