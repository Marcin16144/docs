Deployment .NET API

Publikacja, AOT, Dockerfile, Docker Compose, IIS, Nginx, Azure App Service, Kubernetes i konfiguracja srodowiskowa

Typy publikacji

TypKomendaRozmiarWymaga runtimeKiedy
Framework-dependent dotnet publish -c Release Maly (~1 MB) Tak (.NET zainstalowany) Serwery z zainstalowanym .NET, Docker
Self-contained dotnet publish -c Release -r linux-x64 --self-contained Duzy (~70 MB) Nie Srodowiska bez .NET, edge deployment
Single file --self-contained -p:PublishSingleFile=true Jeden plik Nie Prostota dystrybucji, CLI tools
Native AOT -p:PublishAot=true Bardzo maly (~10 MB) Nie Mikrouslugi, minimalny cold start, serverless

Native AOT — .NET 8+

Native AOT kompiluje aplikacje do natywnego kodu maszynowego bez potrzeby JIT. Efekty: bardzo krotki czas startu (<50ms), mniejsze zuzycie pamieci i brak zaleznosci od runtime .NET.

<!-- .csproj — wlaczenie Native AOT -->
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>  <!-- mniejszy rozmiar -->
</PropertyGroup>

<!-- AOT wymaga JSON source generation zamiast refleksji -->
<ItemGroup>
  <PackageReference Include="Microsoft.AspNetCore.OpenApi" Version="9.*" />
</ItemGroup>
// Program.cs — Minimal API kompatybilne z AOT
var builder = WebApplication.CreateSlimBuilder(args);  // Slim = AOT-friendly

builder.Services.ConfigureHttpJsonOptions(options =>
{
    options.SerializerOptions.TypeInfoResolverChain.Insert(0,
        AppJsonSerializerContext.Default);
});

var app = builder.Build();
app.MapGet("/products", () => new[] { new Product(1, "Laptop", 3999m) });
app.Run();

// Source generation dla JSON (wymagane przez AOT)
[JsonSerializable(typeof(Product[]))]
[JsonSerializable(typeof(Product))]
[JsonSerializable(typeof(ProblemDetails))]
internal partial class AppJsonSerializerContext : JsonSerializerContext { }

record Product(int Id, string Name, decimal Price);

Dockerfile — multi-stage build

# Dockerfile — optimized multi-stage dla .NET 9
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src

# Kopiuj pliki projektow i przywroc zaleznosci (cache layer)
COPY ["src/MyApi/MyApi.csproj", "src/MyApi/"]
COPY ["src/MyApi.Infrastructure/MyApi.Infrastructure.csproj", "src/MyApi.Infrastructure/"]
RUN dotnet restore "src/MyApi/MyApi.csproj"

# Kopiuj caly kod i zbuduj
COPY . .
WORKDIR "/src/src/MyApi"
RUN dotnet build "MyApi.csproj" -c Release -o /app/build

# Publikacja
FROM build AS publish
RUN dotnet publish "MyApi.csproj" \
    -c Release \
    -r linux-x64 \
    --self-contained false \
    -o /app/publish \
    /p:UseAppHost=false

# Obraz finalny — minimalny runtime
FROM mcr.microsoft.com/dotnet/aspnet:9.0-alpine AS final
WORKDIR /app

# Bezpieczenstwo — nie uruchamiaj jako root
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# Health check
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
    CMD wget -qO- http://localhost:8080/health/live || exit 1

EXPOSE 8080
ENV ASPNETCORE_URLS=http://+:8080
ENV ASPNETCORE_ENVIRONMENT=Production

COPY --from=publish /app/publish .
ENTRYPOINT ["dotnet", "MyApi.dll"]

Docker Compose

# docker-compose.yml
version: "3.9"

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "8080:8080"
    environment:
      - ASPNETCORE_ENVIRONMENT=Development
      - ConnectionStrings__DefaultConnection=Host=postgres;Database=mydb;Username=myuser;Password=mypass
      - Redis__ConnectionString=redis:6379
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped
    networks:
      - app-network

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: mydb
      POSTGRES_USER: myuser
      POSTGRES_PASSWORD: mypass
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myuser -d mydb"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - app-network

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
    networks:
      - app-network

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/ssl:/etc/nginx/ssl:ro
    depends_on:
      - api
    networks:
      - app-network

volumes:
  postgres_data:
  redis_data:

networks:
  app-network:
    driver: bridge

Nginx — reverse proxy

# nginx/nginx.conf
events {
    worker_connections 1024;
}

http {
    upstream api {
        server api:8080;
        keepalive 32;
    }

    # Rate limiting
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/m;

    server {
        listen 80;
        server_name myapi.example.com;
        return 301 https://$server_name$request_uri;
    }

    server {
        listen 443 ssl http2;
        server_name myapi.example.com;

        ssl_certificate /etc/nginx/ssl/cert.pem;
        ssl_certificate_key /etc/nginx/ssl/key.pem;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_ciphers HIGH:!aNULL:!MD5;

        # Naglowki bezpieczenstwa
        add_header X-Content-Type-Options nosniff;
        add_header X-Frame-Options DENY;
        add_header Strict-Transport-Security
            "max-age=31536000; includeSubDomains" always;

        location / {
            limit_req zone=api_limit burst=20 nodelay;
            proxy_pass http://api;
            proxy_http_version 1.1;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection keep-alive;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_cache_bypass $http_upgrade;
            proxy_read_timeout 90s;
        }

        location /health {
            proxy_pass http://api;
            access_log off;
        }
    }
}

IIS — web.config

<!-- web.config dla IIS -->
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <location path="." inheritInChildApplications="false">
    <system.webServer>
      <handlers>
        <add name="aspNetCore" path="*" verb="*"
             modules="AspNetCoreModuleV2"
             resourceType="Unspecified" />
      </handlers>
      <aspNetCore processPath="dotnet"
                  arguments=".\MyApi.dll"
                  stdoutLogEnabled="false"
                  stdoutLogFile=".\logs\stdout"
                  hostingModel="inprocess">  <!-- inprocess = szybszy -->
        <environmentVariables>
          <environmentVariable name="ASPNETCORE_ENVIRONMENT"
                               value="Production" />
        </environmentVariables>
      </aspNetCore>
    </system.webServer>
  </location>
</configuration>

Konfiguracja per srodowisko

// Program.cs — ladowanie konfiguracji srodowiskowej
var builder = WebApplication.CreateBuilder(args);

// Kolejnosc ladowania (pozniejsze nadpisuja wczesniejsze):
// 1. appsettings.json
// 2. appsettings.{Environment}.json
// 3. User Secrets (Development)
// 4. Zmienne srodowiskowe
// 5. Argumenty wiersza polecen

// Azure Key Vault (produkcja)
if (builder.Environment.IsProduction())
{
    var keyVaultUri = builder.Configuration["KeyVault:Uri"];
    if (!string.IsNullOrEmpty(keyVaultUri))
    {
        builder.Configuration.AddAzureKeyVault(
            new Uri(keyVaultUri),
            new DefaultAzureCredential());
    }
}

// Mapowanie zmiennych srodowiskowych z prefixem
builder.Configuration.AddEnvironmentVariables(prefix: "MYAPI_");

Opcje deploymentu — kiedy co wybrac

OpcjaKiedy uzywacZaletyWady
IIS (Windows) Istniejaca infrastruktura Windows, integracja z AD Znany adminom Windows, integracja z WAS Tylko Windows, wymaga licencji serwera
Kestrel + Nginx Linux VPS, wlasna infrastruktura, microservices Wydajny, wieloplatformowy, latwy w konfiguracji Recznie zarzadzasz infrastruktura
Docker / Compose Lokalne testy produkcyjne, mala skala, CI/CD Reprodukowalnosc, izolacja, latwy rollback Naglowek zasobow, wymaga Docker runtime
Kubernetes (K8s) Duza skala, wiele usług, auto-scaling Auto-scaling, self-healing, rolling updates Wysoka zlozonosc operacyjna, koszty
Azure App Service Szybki deployment, brak ops, male/srednie projekty Managed, slots (blue/green), easy scaling Wyzsze koszty przy duzej skali, lock-in
Azure Container Apps Mikrouslugi, serverless containers, K8s bez ops Managed K8s, KEDA scaling, DAPR integration Mniejsza kontrola niz czysty K8s
Rekomendacja 2026 — nowe projekty:
  • Mikrouslugi / duza skala: Docker + Kubernetes (AKS/EKS/GKE) lub Azure Container Apps
  • Standardowe API / startup: Azure App Service z deployment slots (blue/green)
  • Edge / serverless z minimalnym startem: Native AOT + Azure Container Apps
  • On-premise Windows: IIS in-process lub Windows Service z Kestrel
