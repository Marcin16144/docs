Podstawy ASP.NET Core 9

Program.cs, middleware pipeline, DI container, konfiguracja, logowanie i health checks

Program.cs — top-level statements

Od .NET 6 plik Program.cs uzywa top-level statements — nie ma klasy Program ani metody Main. Kompilator generuje je automatycznie. Calkowity kod startowy aplikacji miesci sie w kilku-kilkunastu liniach.

Wzorzec WebApplication builder dzieli inicjalizacje na dwa etapy: rejestracje uslug (przed builder.Build()) i konfiguracje middleware (po Build()). Dzieki temu struktura jest jednoznaczna i latwiejsza do testowania.

// Program.cs — ASP.NET Core 9 minimal
var builder = WebApplication.CreateBuilder(args);

// --- rejestracja uslug ---
builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddOpenApi();
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddSingleton<ICacheService, MemoryCacheService>();

// --- konfiguracja logowania ---
builder.Logging.ClearProviders();
builder.Logging.AddConsole();
builder.Logging.AddDebug();

var app = builder.Build();

// --- pipeline middleware ---
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
    app.UseDeveloperExceptionPage();
}

app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
app.MapHealthChecks("/health");

app.Run();

Kolejnosc middleware — zasada FIFO

Middleware w ASP.NET Core tworzy potok (pipeline). Kazdy element odbiera zadanie (request), moze je przetworzyc, przekazac dalej i przetworzyc odpowiedz. Kolejnosc rejestracji ma kluczowe znaczenie — blad polega na przykladanie UseAuthorization przed UseAuthentication.

Poprawna kolejnosc middleware:
  1. UseExceptionHandler / UseDeveloperExceptionPage
  2. UseHttpsRedirection
  3. UseStaticFiles
  4. UseRouting
  5. UseCors
  6. UseAuthentication
  7. UseAuthorization
  8. UseOutputCache / UseResponseCaching
  9. MapControllers / MapEndpoints
// Przyklad niestandardowego middleware
public class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    public RequestTimingMiddleware(RequestDelegate next,
        ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        await _next(context);
        sw.Stop();
        _logger.LogInformation(
            "Request {Method} {Path} zakonczony w {Ms}ms",
            context.Request.Method,
            context.Request.Path,
            sw.ElapsedMilliseconds);
    }
}

// rejestracja
app.UseMiddleware<RequestTimingMiddleware>();

Dependency Injection — cykl zycia

ASP.NET Core ma wbudowany kontener DI. Kazda usluga rejestrowana jest z jednym z trzech cyklów zycia:

Cykl Metoda rejestracji Kiedy uzywac Uwagi
Singleton AddSingleton Cache, konfiguracja, polaczenia wspoldzielone Jedna instancja na caly czas zycia aplikacji. Uwazaj na thread-safety.
Scoped AddScoped DbContext, jednostki pracy (Unit of Work) Jedna instancja na zadanie HTTP. Domyslny wybor dla wiekszosci serwisow.
Transient AddTransient Lekkie, bezstanowe serwisy Nowa instancja przy kazdym pobraniu z kontenera. 
// Rejestracja roznych cyklow zycia
builder.Services.AddSingleton<IConfiguration>(builder.Configuration);
builder.Services.AddScoped<IUnitOfWork, UnitOfWork>();
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();

// Rejestracja z fabryke (factory)
builder.Services.AddScoped<IReportService>(sp =>
{
    var config = sp.GetRequiredService<IConfiguration>();
    var repo = sp.GetRequiredService<IReportRepository>();
    return new ReportService(repo, config["Reports:OutputPath"]!);
});

// Wstrzykiwanie przez konstruktor
public class ProductController : ControllerBase
{
    private readonly IProductRepository _repo;
    private readonly ILogger<ProductController> _logger;

    public ProductController(
        IProductRepository repo,
        ILogger<ProductController> logger)
    {
        _repo = repo;
        _logger = logger;
    }
}

Konfiguracja — appsettings.json i zmienne srodowiskowe

ASP.NET Core laduje konfiguracje z wielu zrodel w ustalonej kolejnosci (pozniejsze nadpisuja wczesniejsze):

  1. appsettings.json
  2. appsettings.{Environment}.json (np. appsettings.Development.json)
  3. User Secrets (tylko Development)
  4. Zmienne srodowiskowe
  5. Argumenty wiersza polecen
// appsettings.json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=localhost;Database=MyDb;Trusted_Connection=True;"
  },
  "Jwt": {
    "Secret": "ZMIEN_MNIE_W_PRODUKCJI",
    "Issuer": "https://myapi.example.com",
    "ExpiryMinutes": 60
  },
  "FeatureFlags": {
    "EnableNewCheckout": false
  }
}
// Silnie typowana konfiguracja — Options Pattern
public class JwtOptions
{
    public const string SectionName = "Jwt";
    public string Secret { get; set; } = string.Empty;
    public string Issuer { get; set; } = string.Empty;
    public int ExpiryMinutes { get; set; } = 60;
}

// rejestracja w Program.cs
builder.Services.Configure<JwtOptions>(
    builder.Configuration.GetSection(JwtOptions.SectionName));

// uzycie w serwisie
public class TokenService
{
    private readonly JwtOptions _opts;

    public TokenService(IOptions<JwtOptions> opts)
    {
        _opts = opts.Value;
    }
}

ILogger i structured logging

ASP.NET Core ma wbudowany system logowania przez ILogger<T>. Structured logging pozwala zapisywac dane jako pola, nie ciagi znakow, co ulatwia filtrowanie w Kibana / Seq / Grafana Loki.

// Logowanie strukturalne — prawidlowo
_logger.LogInformation(
    "Zamowienie {OrderId} zlozone przez {UserId} na kwote {Amount:C}",
    order.Id, order.UserId, order.TotalAmount);

// Logowanie z wyjatkiem
try { /* ... */ }
catch (Exception ex)
{
    _logger.LogError(ex,
        "Blad przetwarzania zamowienia {OrderId}", orderId);
    throw;
}

// Logowanie warunkowe (unikanie alokacji)
if (_logger.IsEnabled(LogLevel.Debug))
{
    _logger.LogDebug("Szczegoly: {Payload}", JsonSerializer.Serialize(data));
}

Serilog — konfiguracja

// dotnet add package Serilog.AspNetCore
// dotnet add package Serilog.Sinks.Console
// dotnet add package Serilog.Sinks.Seq

// Program.cs
builder.Host.UseSerilog((ctx, lc) => lc
    .ReadFrom.Configuration(ctx.Configuration)
    .Enrich.FromLogContext()
    .Enrich.WithMachineName()
    .WriteTo.Console(new JsonFormatter())
    .WriteTo.Seq("http://localhost:5341"));

// appsettings.json (Serilog sekcja)
{
  "Serilog": {
    "MinimumLevel": {
      "Default": "Information",
      "Override": {
        "Microsoft.AspNetCore": "Warning",
        "System": "Warning"
      }
    }
  }
}

Health Checks

Health checks pozwalaja Kubernetes, load balancerom i narzędziom monitorowania sprawdzac, czy aplikacja dziala prawidlowo. ASP.NET Core ma wbudowane wsparcie przez pakiet Microsoft.AspNetCore.Diagnostics.HealthChecks.

// rejestracja
builder.Services.AddHealthChecks()
    .AddSqlServer(
        connectionString: builder.Configuration.GetConnectionString("DefaultConnection")!,
        healthQuery: "SELECT 1",
        name: "sqlserver",
        tags: new[] { "database", "sql" })
    .AddRedis(
        redisConnectionString: builder.Configuration["Redis:ConnectionString"]!,
        name: "redis",
        tags: new[] { "cache" })
    .AddCheck<CustomDependencyCheck>("external-api");

// mapowanie endpointow
app.MapHealthChecks("/health", new HealthCheckOptions
{
    ResponseWriter = UIResponseWriter.WriteHealthCheckUIResponse
});

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false  // zawsze zwraca 200 jesli aplikacja chodzi
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = hc => hc.Tags.Contains("database")
});
// Niestandardowy health check
public class CustomDependencyCheck : IHealthCheck
{
    private readonly HttpClient _http;

    public CustomDependencyCheck(HttpClient http)
    {
        _http = http;
    }

    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context,
        CancellationToken cancellationToken = default)
    {
        try
        {
            var response = await _http.GetAsync("/ping", cancellationToken);
            return response.IsSuccessStatusCode
                ? HealthCheckResult.Healthy("Zewnetrzne API dostepne")
                : HealthCheckResult.Degraded("Zewnetrzne API odpowiada z bledem");
        }
        catch (Exception ex)
        {
            return HealthCheckResult.Unhealthy("Zewnetrzne API niedostepne", ex);
        }
    }
}
Wskazowka Kubernetes: Uzyj /health/live jako livenessProbe i /health/ready jako readinessProbe. Kubernetes zatrzyma ruch do poda, gdy readiness zwroci blad, ale nie zrestartuje go, dopoki liveness pozostaje OK.

Podsumowanie — dobre praktyki

  • Zawsze rejestruj DbContext jako Scoped — nigdy Singleton (problemy z wspolbieznoscia).
  • Unikaj ServiceLocator (pobieranie DI z IServiceProvider w logice biznesowej).
  • Separuj konfiguracje srodowisk — sekrety trzymaj w zmiennych srodowiskowych lub Azure Key Vault.
  • Uzywaj structured logging z nazwanymi parametrami, nie interpolacji stringow.
  • Rejestruj health checks dla kazdej zaleznosci zewnetrznej (baza, cache, API).
  • Nie ignoruj ostrzezen kompilatora o nullable — wlacz <Nullable>enable</Nullable> w .csproj.
