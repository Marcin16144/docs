Dokumentacja API

OpenAPI 3.1, narzedzia dokumentacji, contract-first vs code-first i zarzadzanie changelogiem.

OpenAPI 3.1 — co nowego vs 3.0

OpenAPI 3.1 (wydana w 2021) to pelna zgodnosc z JSON Schema Draft 2020-12, co rozwiazuje dlugotrwale niespojnosci miedzy OpenAPI a JSON Schema.

  • Pelna zgodnosc z JSON Schema — mozna uzyc dowolnego keywordu JSON Schema (np. unevaluatedProperties, prefixItems)
  • Webhooks — nowa sekcja webhooks obok paths do opisywania zdarzen wychodzacych
  • Deprecacja nullable — zamiast nullable: true uzywa sie type: [string, null]
  • Licencja SPDX — pole license.identifier przyjmuje identyfikatory SPDX
  • Shared Path Items — mozna referencjonowac Path Items z components

Przyklad openapi.yaml

openapi: "3.1.0"

info:
  title: Example API
  version: "2.1.0"
  description: |
    REST API dla platformy e-commerce.
    Autentykacja: Bearer JWT w naglowku Authorization.
  contact:
    name: API Support
    email: api@example.com
    url: https://developers.example.com
  license:
    name: Apache 2.0
    identifier: Apache-2.0

servers:
  - url: https://api.example.com/v2
    description: Production
  - url: https://api.staging.example.com/v2
    description: Staging
  - url: http://localhost:3000/v2
    description: Local development

security:
  - BearerAuth: []

tags:
  - name: users
    description: Zarzadzanie uzytkownikami
  - name: orders
    description: Zamowienia i platnosci

paths:
  /users:
    get:
      tags: [users]
      operationId: listUsers
      summary: Pobierz liste uzytkownikow
      description: Zwraca stronicowana liste uzytkownikow. Wymaga roli admin.
      parameters:
        - name: page
          in: query
          schema: { type: integer, minimum: 1, default: 1 }
        - name: limit
          in: query
          schema: { type: integer, minimum: 1, maximum: 100, default: 20 }
        - name: search
          in: query
          description: Filtruj po imieniu lub emailu
          schema: { type: string }
      responses:
        "200":
          description: Lista uzytkownikow
          headers:
            X-Total-Count:
              schema: { type: integer }
              description: Laczna liczba uzytkownikow
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/UserListResponse'
              examples:
                default:
                  $ref: '#/components/examples/UserListExample'
        "401": { $ref: '#/components/responses/Unauthorized' }
        "403": { $ref: '#/components/responses/Forbidden' }

    post:
      tags: [users]
      operationId: createUser
      summary: Utworz uzytkownika
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateUserRequest'
      responses:
        "201":
          description: Uzytkownik utworzony
          headers:
            Location:
              schema: { type: string, format: uri }
              description: URL nowo utworzonego zasobu
          content:
            application/json:
              schema: { $ref: '#/components/schemas/User' }
        "400": { $ref: '#/components/responses/BadRequest' }
        "409": { $ref: '#/components/responses/Conflict' }

  /users/{id}:
    parameters:
      - name: id
        in: path
        required: true
        schema: { type: string }
        description: Unikalny identyfikator uzytkownika

    get:
      tags: [users]
      operationId: getUser
      summary: Pobierz uzytkownika
      responses:
        "200":
          content:
            application/json:
              schema: { $ref: '#/components/schemas/User' }
        "404": { $ref: '#/components/responses/NotFound' }

components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

  schemas:
    User:
      type: object
      required: [id, name, email, role, createdAt]
      properties:
        id:
          type: string
          description: Unikalny ID uzytkownika
          example: usr_01HXYZ123
        name:
          type: string
          minLength: 1
          maxLength: 100
          example: Jan Kowalski
        email:
          type: string
          format: email
          example: jan@example.com
        role:
          type: string
          enum: [user, admin, moderator]
        createdAt:
          type: string
          format: date-time

    CreateUserRequest:
      type: object
      required: [name, email, password]
      properties:
        name:    { type: string, minLength: 1, maxLength: 100 }
        email:   { type: string, format: email }
        password:
          type: string
          minLength: 8
          writeOnly: true   # nie zwracaj w odpowiedzi
          description: Min. 8 znakow, co najmniej jedna cyfra

  responses:
    Unauthorized:
      description: Brak lub nieprawidlowy token uwierzytelniania
      content:
        application/json:
          schema: { $ref: '#/components/schemas/Error' }
    NotFound:
      description: Zasob nie istnieje
      content:
        application/json:
          schema: { $ref: '#/components/schemas/Error' }

webhooks:
  userCreated:
    post:
      summary: Zdarzenie tworzenia uzytkownika
      requestBody:
        content:
          application/json:
            schema:
              type: object
              properties:
                event: { type: string, example: user.created }
                data:  { $ref: '#/components/schemas/User' }

Contract-first vs Code-first

Contract-first (Design-first)

Najpierw piszesz specyfikacje OpenAPI, nastepnie generujesz szkielet kodu serwera i klienta. Wymusza przemyslenie API przed implementacja. Lepszy dla zespolow, gdzie frontend i backend pracuja rownolegle. Narzedzia: Stoplight Studio, openapi-generator, oapi-codegen.

Code-first

Piszesz kod serwera z adnotacjami/dekoratorami, a specyfikacja OpenAPI jest generowana automatycznie. Szybszy start dla malych projektow i prototypow. Ryzyko: generowana spec czesto gorszej jakosci — brak opisow, przykladow, zbyt ogolne typy. Narzedzia: tsoa, FastAPI, Springdoc.

Narzedzia dokumentacji

Narzedzie Typ Zalety Wady Cena
Swagger UI Renderer Wszechobecny standard, try-it-out, duza spolecznosc Przestarzaly wyglad, wolny na duzych specach Free / OSS
Redoc Renderer Elegancki wyglad, 3-kolumnowy layout, responsywny Brak try-it-out w darmowej wersji, komercyjna Redocly Free / OSS + Pro
Scalar Renderer + klient Nowoczesny UI, try-it-out, dark mode, szybki, OSS Mlodszy projekt, mniejsza spolecznosc Free / OSS
Stoplight Studio Design IDE Visual editor, mock server, walidacja, team collaboration Platny dla zespolow, vendor lock-in Free tier + Plany
Postman Klient + docs Testowanie, collections, mock servers, monitoring Przeladowany funkcjami, wolny desktop app Free + Enterprise

Postman Collections

Kolekcje Postman to plik JSON grupujacy endpointy, zmienne srodowiskowe i testy. Mozna je eksportowac i importowac, uzyc w CI/CD (Newman CLI) i opublikowac jako dokumentacje publiczna.

# Uruchomienie kolekcji Postman w CLI (Newman)
npm install -g newman newman-reporter-htmlextra

# Uruchom testy z kolekcji
newman run my-api.postman_collection.json \
  --environment production.postman_environment.json \
  --reporters cli,htmlextra \
  --reporter-htmlextra-export reports/test-results.html \
  --bail  # zatrzymaj przy pierwszym bledzie

# W CI/CD (GitHub Actions)
# - name: Run API tests
#   run: newman run collection.json -e staging.env.json

Changelog management

Dobry changelog API dokumentuje zmiany w sposob zrozumialy dla uzytkownikow API — nie dla dewelopera. Rozrozniaj: breaking changes, new features, deprecations, bug fixes.

# CHANGELOG.md — format Keep a Changelog

## [2.1.0] - 2025-05-08

### Dodano
- Endpoint GET /users/{id}/activity-log — historia aktywnosci uzytkownika
- Parametr `include` dla GET /orders — mozliwosc pobrania powiazanych zasobow
- Webhook `order.shipped` — powiadomienie o wysylce zamowienia

### Zmieniono
- GET /products zwraca teraz pole `stock` (poprzednio: `inventory_count`)
  DEPRECATION: `inventory_count` bedzie usuniety w v3.0 (2026-01-01)

### Naprawiono
- GET /users zwracal niepoprawne pole `lastLogin` przy braku aktywnosci

## [2.0.0] - 2025-02-01 — BREAKING CHANGES

### Usunieto (breaking)
- Usunieto parametr `api_key` z query string — uzywaj naglowka Authorization
- Usunieto endpoint POST /auth/login (zastapiony przez /auth/token)

### Zmieniono (breaking)
- Paginacja: parametr `offset`+`count` zastapiony przez `page`+`limit`
- Pole `user_id` przemianowane na `userId` (camelCase)

### Sunset header dla przestarzalych endpointow
# Sunset: Sat, 01 Jan 2026 00:00:00 GMT
# Deprecation: Mon, 01 Feb 2025 00:00:00 GMT
# Link: <https://docs.example.com/migration/v2>; rel="deprecation"

Zasady dobrego changelogu API

  • Pisz z perspektywy konsumenta API, nie implementacji
  • Wyraznie oznaczaj breaking changes — osobna sekcja, ostrzezenia
  • Zawsze podaj date i wersje semver
  • Dla deprecacji podaj date usuniecia i sciezke migracji
  • Dodaj naglowek Sunset do deprecowanych endpointow
