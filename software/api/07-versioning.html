Glowna/ API/ API Versioning

API Versioning

Strategie wersjonowania, polityka deprecacji, backward compatibility i naglowki Sunset.

Dlaczego wersjonowanie jest niezbedne

API jest kontraktem z klientami. Bez wersjonowania kazda zmiana lamia istniejace integracje. Wersjonowanie pozwala wprowadzac nowe funkcje i naprawiac bledy bez zrywania kompatybilnosci — klienci moga migrować we wlasnym tempie.

Breaking change vs Non-breaking change

Breaking: usuniecie pola, zmiana typu, usuniecie endpointu, zmiana semantyki, nowe wymagane pole w request. Non-breaking: dodanie opcjonalnego pola, nowy endpoint, nowy opcjonalny parametr, rozszerzenie enuma o nowe wartosci.

URL Versioning

Wersja jest czescia sciezki URL. Najpopularniejsza i najprostrza strategia. Jednoznaczna, latwa do routowania, dziala z cacheowaniem HTTP.

# Wersja jako segment sciezki
GET https://api.example.com/v1/users
GET https://api.example.com/v2/users

# Alternatywnie jako subdomena
GET https://v1.api.example.com/users
GET https://v2.api.example.com/users

# Routing w Express.js
import express from 'express';
import { v1Router } from './routes/v1';
import { v2Router } from './routes/v2';

const app = express();

app.use('/v1', v1Router);
app.use('/v2', v2Router);

// Przekierowanie bez wersji na aktualna
app.use('/api', (req, res) => {
  res.redirect(301, `/v2${req.path}`);
});

// Struktura katalogow
// src/routes/
//   v1/
//     users.ts      <- stara implementacja
//     orders.ts
//   v2/
//     users.ts      <- nowa implementacja
//     orders.ts
//     products.ts   <- nowy w v2

Header Versioning

Wersja jest przekazywana przez naglowek HTTP. URL pozostaje czysty. Stosowany przez GitHub API (X-GitHub-Api-Version).

# Custom header
GET /users
X-API-Version: 2
Accept: application/json

# Accept header z vendor media type (GitHub style)
GET /users
Accept: application/vnd.example.api+json;version=2

# Middleware Node.js — rozpoznawanie wersji
function versionMiddleware(req: any, res: any, next: any) {
  const version =
    req.headers['x-api-version'] ||
    parseAcceptVersion(req.headers['accept']) ||
    '1';   // domyslna wersja

  req.apiVersion = parseInt(version, 10);

  if (req.apiVersion > CURRENT_VERSION) {
    return res.status(400).json({
      error: `API version ${version} not supported. Latest: ${CURRENT_VERSION}`
    });
  }

  next();
}

function parseAcceptVersion(accept?: string): string | null {
  if (!accept) return null;
  const match = accept.match(/version=(\d+)/);
  return match ? match[1] : null;
}

Content-Type Negotiation

Wersja jest zakodowana w media type. Uzywany przez GitHub v3 API i niektore enterprise API. Najtrudniejszy w debugowaniu — wymaga znajomosci vendor media types.

# Request z wersjonowanym Content-Type
GET /users
Accept: application/vnd.example.v2+json

# Response
HTTP/1.1 200 OK
Content-Type: application/vnd.example.v2+json

# Routing na podstawie Accept header
app.get('/users', (req, res) => {
  const accept = req.headers.accept ?? '';

  if (accept.includes('vnd.example.v2')) {
    return usersV2Handler(req, res);
  }
  // domyslnie v1
  return usersV1Handler(req, res);
});

Semantic Versioning dla API

Semver (MAJOR.MINOR.PATCH) stosowany do API: MAJOR — breaking change (nowa wersja URL), MINOR — nowa funkcja wstecznie kompatybilna (nie wymaga nowej wersji URL), PATCH — poprawka bledu, zmiana dokumentacji.

# Przykladowy changelog z semver
## v2.3.1 (patch) — 2025-05-08
- Poprawka: GET /users zwracal bledny licznik totalCount przy filtrowaniu

## v2.3.0 (minor) — 2025-04-15
- Dodano: endpoint GET /users/{id}/activity
- Dodano: opcjonalny parametr `include` dla GET /orders
- Deprecacja: pole `phone` w User (uzyj `phoneNumber`)

## v2.0.0 (major) — 2025-01-01  — BREAKING
- Zmiana: paginacja przez `page`+`limit` zamiast `offset`+`count`
- Usunieto: endpoint POST /auth/login (zastapiony /auth/token)
- Zmiana: wszystkie ID sa teraz ULID zamiast auto-increment int

# Naglowek API-Version w odpowiedzi
HTTP/1.1 200 OK
API-Version: 2.3.1

Deprecation Policy i naglowek Sunset

RFC 8594 definiuje naglowek Sunset — date, po ktorej zasob przestanie byc dostepny. Naglowek Deprecation (RFC draft) informuje, kiedy zasob zostal uznany za przestarzaly. Klienci powinni monitorowac te naglowki.

# Naglowki deprecacji dla endpointu v1
HTTP/1.1 200 OK
Deprecation: Mon, 01 Jan 2025 00:00:00 GMT
Sunset: Wed, 01 Jan 2026 00:00:00 GMT
Link: <https://docs.example.com/migration/v1-to-v2>; rel="deprecation",
      <https://api.example.com/v2/users>; rel="successor-version"
Warning: 299 - "This endpoint is deprecated and will be removed 2026-01-01"

# Middleware dodajacy naglowki do przestarzalych endpointow
const deprecatedEndpoints: Record = {
  '/v1/users':  {
    sunset: 'Wed, 01 Jan 2026 00:00:00 GMT',
    migration: 'https://docs.example.com/migration/v1-to-v2#users',
  },
  '/v1/orders': {
    sunset: 'Wed, 01 Jan 2026 00:00:00 GMT',
    migration: 'https://docs.example.com/migration/v1-to-v2#orders',
  },
};

function deprecationMiddleware(req: any, res: any, next: any) {
  const info = deprecatedEndpoints[req.path];
  if (info) {
    res.set({
      'Deprecation': 'Mon, 01 Jan 2025 00:00:00 GMT',
      'Sunset':      info.sunset,
      'Link':        `<${info.migration}>; rel="deprecation"`,
    });
  }
  next();
}

Backward Compatibility — zasady

  • Dodawanie pol jest bezpieczne — klienci powinni ignorowac nieznane pola (Postel's Law)
  • Nie zmieniaj typow istniejacych pol — string na int to breaking change
  • Nie usuwaj pol bez deprecacji — minimum 6 miesiecy okresu ostrzegawczego
  • Nowe wymagane pola w request = breaking change — dodawaj z wartoscia domyslna
  • Rozszerzanie enum jest ryzykowne — klienci moga nie obslugiwac nowej wartosci
  • Nie zmieniaj semantyki bez zmiany wersji — zmiana zachowania to breaking change nawet bez zmiany kontraktu

Strategie wersjonowania — porownanie

Strategia Przyklad Zalety Wady
URL versioning /v1/users Oczywisty, latwy routing, dziala z CDN i cache, latwy do testowania w przegladarce URL nie jest "czysty" REST (wersja to nie zasob), trzeba utrzymywac wiele sciezek
Header versioning X-API-Version: 2 Czysty URL, jeden endpoint dla wszystkich wersji Niewidoczny w przegladarce, trudniejszy caching (Vary header), mniej oczywisty dla poczatkujacych
Content-Type negot. Accept: vnd.api.v2+json Zgodny z RFC HTTP content negotiation, czysty URL Najtrudniejszy w debugowaniu i dokumentowaniu, wymaga znajomosci vendor media types
Query param /users?version=2 Prosty, nie wymaga zmiany nagłowkow Anty-wzorzec — wersja w query params myli sie z filtrami, zly caching

Rekomendacja praktyczna

Dla wiekszosci API publicznych i wewnetrznych: URL versioning (/v1/, /v2/) to najlepszy wybor. Jest oczywisty, prosty w debugowaniu i dobrze wspolpracuje z narzędziami HTTP. Header versioning stosuj jesli masz specyficzne wymagania dotyczace "czystosci" URL lub wzorujac sie na GitHub API.
