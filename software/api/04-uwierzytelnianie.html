Uwierzytelnianie i autoryzacja API

JWT, OAuth 2.0, OpenID Connect, API Keys, mTLS, RBAC/ABAC i integracje z dostawcami identity.

JWT — JSON Web Token

JWT to otwarty standard (RFC 7519) reprezentowania claims miedzy dwiema stronami. Token sklada sie z trzech czesci oddzielonych kropkami: Header.Payload.Signature, kazda zakodowana w Base64URL.

Struktura JWT

# Header — algorytm i typ tokenu
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-id-2025-01"    # ID klucza publicznego (do rotacji kluczy)
}

# Payload — claims
{
  "sub":   "user_01HXYZ",          # Subject — ID uzytkownika
  "iss":   "https://auth.example.com",  # Issuer
  "aud":   ["https://api.example.com"], # Audience
  "exp":   1746705600,             # Expiry (Unix timestamp)
  "iat":   1746619200,             # Issued At
  "jti":   "jwt_unique_id_123",    # JWT ID — do blacklistingu
  "email": "jan@example.com",
  "roles": ["user", "editor"],
  "org":   "org_ABC"
}

# Signature (RS256)
RSA_SIGN(
  base64url(header) + "." + base64url(payload),
  PRIVATE_KEY
)

RS256 vs HS256

  • HS256 (HMAC-SHA256) — jeden wspolny sekret do podpisywania i weryfikacji. Prosty, ale kazda uslugi musi znac sekret. Przy wycieku mozna podrabiac tokeny.
  • RS256 (RSA-SHA256) — para kluczy: prywatny do podpisywania (tylko serwer auth), publiczny do weryfikacji (mozna udostepnic). Bezpieczniejszy dla architektury mikroserwisow.
  • ES256 (ECDSA-SHA256) — krotszy klucz niz RSA przy tym samym poziomie bezpieczenstwa. Zalecany dla nowych systemow.

Refresh Tokens

Access token ma krotki czas zycia (5-15 minut). Refresh token (dlugi — dni/tygodnie) sluzy do pobierania nowych access tokenow bez ponownego logowania. Przechowuj refresh tokeny w HttpOnly cookie, nigdy w localStorage.

// Weryfikacja JWT w Node.js (jose library)
import { jwtVerify, createRemoteJWKSet } from 'jose';

const JWKS = createRemoteJWKSet(
  new URL('https://auth.example.com/.well-known/jwks.json')
);

async function verifyToken(token: string) {
  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer:   'https://auth.example.com',
      audience: 'https://api.example.com',
    });
    return payload;
  } catch (err) {
    if (err.code === 'ERR_JWT_EXPIRED') throw new Error('Token expired');
    if (err.code === 'ERR_JWS_INVALID')  throw new Error('Invalid signature');
    throw err;
  }
}

// Middleware Express
export async function authMiddleware(req, res, next) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Missing Bearer token' });
  }

  const token = authHeader.slice(7);
  try {
    req.user = await verifyToken(token);
    next();
  } catch (err) {
    res.status(401).json({ error: err.message });
  }
}

OAuth 2.0 Flows

OAuth 2.0 (RFC 6749) to framework autoryzacji, nie uwierzytelniania. Definiuje kilka przepływow (flows/grants) dostosowanych do roznych scenariuszy.

Authorization Code + PKCE (aplikacje webowe i mobilne)

# Krok 1 — klient generuje code_verifier i code_challenge
code_verifier  = random_string(43-128 chars, URL-safe)
code_challenge = BASE64URL(SHA256(code_verifier))

# Krok 2 — redirect do authorization server
GET https://auth.example.com/authorize?
  response_type=code
  &client_id=my_app
  &redirect_uri=https://myapp.com/callback
  &scope=openid+profile+email+offline_access
  &state=random_csrf_token
  &code_challenge=BASE64URL_CHALLENGE
  &code_challenge_method=S256

# Krok 3 — exchange code na tokeny
POST https://auth.example.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=AUTH_CODE_FROM_CALLBACK
&redirect_uri=https://myapp.com/callback
&client_id=my_app
&code_verifier=ORIGINAL_VERIFIER

# Odpowiedz
{
  "access_token":  "eyJhbGci...",
  "token_type":    "Bearer",
  "expires_in":    900,
  "refresh_token": "rt_abc123...",
  "id_token":      "eyJhbGci..."  # OpenID Connect
}

Client Credentials (M2M)

# Dla komunikacji serwer-serwer bez uzytkownika
POST https://auth.example.com/token
Content-Type: application/x-www-form-urlencoded
Authorization: Basic BASE64(client_id:client_secret)

grant_type=client_credentials
&scope=read:users+write:orders
&audience=https://api.example.com

OpenID Connect

OpenID Connect (OIDC) to warstwa uwierzytelniania zbudowana na OAuth 2.0. Dodaje ID Token (JWT z informacjami o uzytkowniku) oraz endpoint /userinfo. Discovery document pod /.well-known/openid-configuration zawiera wszystkie endpointy i wspierane algorytmy.

OAuth 2.0 vs OpenID Connect

OAuth 2.0 odpowiada na pytanie "Co mozesz robic?" (autoryzacja). OpenID Connect odpowiada na "Kim jestes?" (uwierzytelnianie). Uzywaj OIDC gdy potrzebujesz wiedziec kto jest zalogowany, OAuth gdy chcesz tylko dostep do zasobu.

API Keys

Klucze API to proste tokeny do uwierzytelniania — glownie dla dostepow M2M, webhookow i integracji zewnetrznych. Nie zawieraja informacji o sesji jak JWT.

  • Format — uzyj prefiksu identyfikujacego produkt: sk_live_abc123..., pk_test_xyz...
  • Przechowywanie — przechowuj hash (bcrypt lub SHA-256), nigdy plaintext
  • Rotacja — umoz latwa rotacje bez przestojow (overlap period)
  • Zakres — ogranicz klucze do konkretnych zasobow lub operacji
  • Naglowek — Authorization: Bearer sk_live_... lub X-API-Key: sk_live_...
# Uzycie klucza API w request
GET /api/v1/users
Authorization: Bearer sk_live_abc123xyz456def789

# Alternatywny naglowek
GET /api/v1/users
X-API-Key: sk_live_abc123xyz456def789

# Nigdy w URL (pojawi sie w logach!)
# ZLE: GET /api/v1/users?api_key=sk_live_...

mTLS — Mutual TLS

W standardowym TLS tylko klient weryfikuje certyfikat serwera. W mTLS obydwie strony wymieniaja i weryfikuja certyfikaty. Stosowane w architekturach zero-trust i komunikacji miedzy mikroserwisami (service mesh: Istio, Linkerd).

RBAC vs ABAC

Kryterium RBAC (Role-Based) ABAC (Attribute-Based)
Zasada Uprawnienia przypisane do rol, role do uzytkownikow Decyzja na podstawie atrybutow: uzytkownik, zasob, srodowisko
Zlozonosc Prosta — latwa do zrozumienia i audytu Wysoka — elastyczna ale trudna w debugowaniu
Przyklad role=admin moze wszystko, role=viewer tylko GET Moze edytowac jezeli owner=true AND dept=same AND time=business_hours
Skalowalnosc Problem z eksplozja rol przy zlozonych wymaganiach Skaluje sie lepiej przy zlozonych politykach
Kiedy Wiekszosc aplikacji biznesowych, prostsze systemy Rzad, healthcare, fintech z regulacjami compliance

Integracje z dostawcami identity

Zamiast implementowac uwierzytelnianie od zera, skorzystaj z gotowych dostawcow:

  • Auth0 — elastyczny, bogaty ekosystem, Machine-to-Machine apps, Actions (webhooks)
  • Clerk — developer-first, swietny DX, wbudowane UI komponenty, organizacje/teams
  • Okta — enterprise, compliance (SOC2, HIPAA), zaawansowane polityki
  • Azure AD / Entra ID — integracja z Microsoft 365, enterprise SSO, B2C dla konsumentow
  • Keycloak — open-source, self-hosted, pelen kontrola danych
// Clerk — middleware Next.js
import { clerkMiddleware, createRouteMatcher } from '@clerk/nextjs/server';

const isPublicRoute = createRouteMatcher([
  '/sign-in(.*)', '/sign-up(.*)', '/api/webhooks(.*)'
]);

export default clerkMiddleware((auth, request) => {
  if (!isPublicRoute(request)) {
    auth().protect();
  }
});

// Pobranie uzytkownika w Server Component
import { currentUser } from '@clerk/nextjs/server';

export default async function Dashboard() {
  const user = await currentUser();
  if (!user) redirect('/sign-in');
  return <div>Hello, {user.firstName}!</div>;
}

Metody uwierzytelniania — kiedy co stosowac

Metoda Kiedy stosowac Zalety Wady
JWT (stateless) SPA, mobile, mikroserwisy, distributed systems Bezstanowy, skaluje sie bez sesji, self-contained Nie mozna uniewaźnic przed wygasniecia, rozmiar tokena
Session cookie Tradycyjne aplikacje webowe, SSR Latwa rewokacja, maly payload, HttpOnly cookie Wymaga sesji po stronie serwera (Redis), problemy z CORS
API Key M2M, CLI tools, webhooks, integracje zewnetrzne Prostosc, latwa do zrozumienia, dlugi czas zycia Brak info o uzytkownikach, trudny audyt, latwa do wycieku
OAuth 2.0 Delegowany dostep do zasobow stron trzecich Standard, nie udostepniasz hasla, granularny zakres Zlozonosc implementacji, wiele krokow flow
mTLS Zero-trust, service mesh, wewnetrzne mikroserwisy Bardzo silne uwierzytelnianie, bez tokenow w naglowkach Zarzadzanie certyfikatami, infrastruktura PKI

Security checklist dla API

  • Zawsze HTTPS — nigdy HTTP dla API produkcyjnych
  • Krotki TTL access tokenow (5-15 min), dlugi refresh (7-30 dni)
  • Przechowuj refresh tokeny w HttpOnly Secure SameSite=Strict cookie
  • Weryfikuj aud i iss claims w JWT
  • Rotuj klucze podpisujace (JWKS rotation) bez przestojow
  • Implementuj rate limiting na endpoint logowania (brute force)
  • Loguj wszystkie nieudane autentykacje z IP i user-agent
