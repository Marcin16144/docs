Deployment Go API

Statyczny binary, multi-stage Docker, Kubernetes, graceful shutdown i konfiguracja srodowiskowa

go build — statyczny binary

Jednym z najwiekszych atutow Go jest kompilacja do pojedynczego statycznego pliku wykonywalnego bez zewnetrznych zaleznosci. Binary zawiera wszystko — runtime, biblioteki standardowe i zaleznosci. To idealne dla kontenerow i deploymentu na serwery bez koniecznosci instalacji Go.

# Podstawowy build
go build -o bin/api ./cmd/api

# Produkcyjny build — mniejszy binary, wersja w metadanych
go build \
  -ldflags="-s -w \
    -X main.Version=1.2.3 \
    -X main.BuildTime=$(date -u +%Y-%m-%dT%H:%M:%SZ) \
    -X main.GitCommit=$(git rev-parse --short HEAD)" \
  -o bin/api \
  ./cmd/api

# -s  usuwa symbol table (mniejszy rozmiar)
# -w  usuwa DWARF debug info (mniejszy rozmiar)
# -X  wstrzykuje wartosci zmiennych w czasie kompilacji

# Cross-compilation — build dla Linuksa na Windows/Mac
GOOS=linux GOARCH=amd64 go build -o bin/api-linux ./cmd/api
GOOS=linux GOARCH=arm64 go build -o bin/api-arm64 ./cmd/api

# Weryfikacja: binary nie ma zewnetrznych zaleznosci
ldd bin/api-linux  # powinno zwrocic: not a dynamic executable

Multi-stage Dockerfile z obrazem scratch

Multi-stage build kompiluje aplikacje w obrazie z pelnym Go toolchainem, a nastepnie kopiuje tylko binary do minimalnego obrazu bazowego. Obraz scratch jest calkowicie pusty — zero OS, zero shellowych narzedzi, zero podatnosci systemowych. Wynikowy obraz ma typowo 10-20 MB.

# Dockerfile
# ---- Stage 1: budowanie ----
FROM golang:1.23-alpine AS builder

WORKDIR /app

# Cache zaleznosci (warstwa Cache Dockera)
COPY go.mod go.sum ./
RUN go mod download

# Kopiowanie kodu i build
COPY . .
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build \
    -ldflags="-s -w -X main.Version=${VERSION:-dev}" \
    -o /api \
    ./cmd/api

# ---- Stage 2: obraz produkcyjny ----
FROM scratch

# Certyfikaty TLS (konieczne dla HTTPS/OAuth2 wywolan wychodzacych)
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/

# Strefa czasowa (opcjonalnie)
COPY --from=builder /usr/share/zoneinfo /usr/share/zoneinfo

# Binary
COPY --from=builder /api /api

# Uzytkownik niepriwilegowany (UID 65532 = nonroot w distroless)
USER 65532:65532

EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD ["/api", "healthcheck"]

ENTRYPOINT ["/api"]

docker-compose.yml

Docker Compose sluzy do lokalnego developmentu i testow integracyjnych — uruchamia API razem z PostgreSQL, Redis i innymi zaleznosci.

# docker-compose.yml
services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      - DATABASE_URL=postgres://dev:dev@postgres:5432/myapp?sslmode=disable
      - REDIS_URL=redis://redis:6379
      - JWT_SECRET=local-dev-secret-not-for-production
      - LOG_LEVEL=debug
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: myapp
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U dev -d myapp"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

volumes:
  pgdata:

Kubernetes — Deployment i Service

Deployment Kubernetes zarzadza zestawem replik Pod. Service eksponuje Deployment wewnatrz klastra lub na zewnatrz. HorizontalPodAutoscaler skaluje liczbe replik na podstawie zuzycia CPU lub wlasnych metryk.

Health endpoints — /healthz i /readyz

Kubernetes sprawdza stan aplikacji przez dwa typy prob: liveness (czy app nie zawisnela — restart jesli nie odpowiada) i readiness (czy app jest gotowa na ruch — wylaczenie z load balancera jesli nie jest gotowa).

Konwencja endpointow zdrowia

  • /healthz (liveness) — zawsze odpowiada 200 jesli proces zyje. Nie sprawdza DB.
  • /readyz (readiness) — sprawdza wszystkie zaleznosci: DB, Redis, zewnetrzne API. Zwraca 503 jesli cos nie dziala.
  • /metrics — eksport metryk Prometheus (opcjonalnie)

Graceful shutdown

Graceful shutdown to poprawne zakonczenie pracy serwera: zatrzymanie przyjmowania nowych polaczyc, dokonczenie aktywnych zadan i zwolnienie zasobow (polaczenia DB, kolejki). Bez tego przy deployu mozna utracic aktywne zadania HTTP.

func main() {
    // Kontekst reagujacy na SIGINT i SIGTERM
    ctx, stop := signal.NotifyContext(context.Background(),
        syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    srv := &http.Server{
        Addr:    ":8080",
        Handler: router,
    }

    // Uruchomienie serwera w tle
    go func() {
        log.Println("Serwer startuje na :8080")
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatalf("ListenAndServe: %v", err)
        }
    }()

    // Czekaj na sygnal zakonczenia
    <-ctx.Done()
    stop()
    log.Println("Otrzymano sygnal zakonczenia, graceful shutdown...")

    // Daj aktywnym zadaniom max 30 sekund na zakonczenie
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Fatalf("Shutdown wymuszony: %v", err)
    }

    // Zamknij polaczenia z baza danych
    db.Close()
    log.Println("Serwer zatrzymany poprawnie")
}

Konfiguracja srodowiskowa

Aplikacje Go czytaja konfiguracje ze zmiennych srodowiskowych (os.Getenv) lub przez biblioteke github.com/spf13/viper obslugujaca pliki YAML/TOML, flagi CLI i env jednoczesnie z priorytetami.

Deployment na Fly.io i Railway

Fly.io i Railway to platformy PaaS idealne dla projektow Go bez koniecznosci zarzadzania Kubernetesem.

  • Fly.io: fly launch automatycznie wykrywa Dockerfile, fly deploy deployuje, fly secrets set KEY=val zarzadza sekretami. Wspiera wiele regionow i volumes dla danych trwalych.
  • Railway: automatyczny build z Dockerfile lub Nixpacks, wbudowany PostgreSQL i Redis jako uslugi, zmienne srodowiskowe przez GUI lub CLI.

Checklista przed deploymentem produkcyjnym

  • Skonfiguruj limity zasobow (CPU/memory requests i limits w K8s)
  • Wlacz graceful shutdown z timeoutem min. 30 sekund
  • Dodaj health endpointy /healthz i /readyz
  • Ustaw connection pool DB — MaxOpenConns odpowiedni do liczby replik
  • Skonfiguruj structured logging (slog lub zap) z poziomem INFO w prod
  • Eksportuj metryki Prometheus (goroutines, heap, request duration, error rate)
  • Ustaw PodDisruptionBudget w K8s aby nie zatrzymac wszystkich replik naraz
  • Uzyj Secrets managera (Vault, AWS SSM, K8s Secrets) — nie hardkoduj sekretow
