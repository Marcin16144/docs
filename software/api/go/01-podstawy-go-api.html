Podstawy Go API

net/http, goroutines, struktury, JSON — fundament kazdego serwisu w Go

Pakiet net/http — standardowa biblioteka

Go dostarcza w standardowej bibliotece pelny stos HTTP. Nie trzeba zewnetrznych pakietow, zeby uruchomic serwer produkcyjny. Pakiet net/http obsluguje routing, parsowanie zadan, kodowanie odpowiedzi i TLS.

Minimalny serwer HTTP wyglada nastepujaco — jedna funkcja main i dwa wyrazenia:

package main

import (
    "encoding/json"
    "fmt"
    "log"
    "net/http"
)

type Response struct {
    Message string `json:"message"`
    Status  int    `json:"status"`
}

func helloHandler(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodGet {
        http.Error(w, "Method not allowed", http.StatusMethodNotAllowed)
        return
    }
    resp := Response{Message: "Witaj w Go API", Status: 200}
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusOK)
    json.NewEncoder(w).Encode(resp)
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("/hello", helloHandler)
    mux.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, `{"status":"ok"}`)
    })

    server := &http.Server{
        Addr:    ":8080",
        Handler: mux,
    }
    log.Println("Serwer startuje na :8080")
    log.Fatal(server.ListenAndServe())
}

ServeMux vs gorilla/mux

Wbudowany http.ServeMux jest prosty i wydajny, ale ma ograniczenia: nie obsluguje parametrow sciezki (/user/:id), nie rozroznia metod HTTP na poziomie routera ani nie ma wbudowanego middleware. Do bardziej zlozonych API warto uzyc zewnetrznego routera.

Cecha http.ServeMux gorilla/mux chi
Parametry sciezki Brak Tak ({id}) Tak ({id})
Filtrowanie metod HTTP Reczne Wbudowane Wbudowane
Middleware Reczne owijanie Use() / Subrouter Use() / Group()

Goroutines i channels w kontekscie API

Kazde przychodzace zadanie HTTP jest obslugiwane w osobnej goroutine — Go robi to automatycznie. Goroutines sa lekkie (poczatkowy stos ~2 KB) i skaluja sie do setek tysiecy jednoczesnych polaczyc.

Channels sluza do komunikacji miedzy goroutines. W API uzywamy ich np. do ograniczania wspolbieznosci, zbierania wynikow z rownoleglych zapytan do zewnetrznych serwisow lub implementacji timeoutow.

// Rownolegla agregacja danych z kilku zrodel
func fetchAll(userID int) (map[string]any, error) {
    type result struct {
        key string
        val any
        err error
    }
    ch := make(chan result, 3)

    go func() {
        data, err := fetchProfile(userID)
        ch <- result{"profile", data, err}
    }()
    go func() {
        data, err := fetchOrders(userID)
        ch <- result{"orders", data, err}
    }()
    go func() {
        data, err := fetchPrefs(userID)
        ch <- result{"prefs", data, err}
    }()

    out := make(map[string]any)
    for i := 0; i < 3; i++ {
        r := <-ch
        if r.err != nil {
            return nil, fmt.Errorf("blad w %s: %w", r.key, r.err)
        }
        out[r.key] = r.val
    }
    return out, nil
}

defer, panic i recover

defer wykonuje wyrazenie po zakonczeniu funkcji — idealny do zamykania zasobow (polaczen DB, plikow). panic przerywa normalny przeplyw wykonania i jest uzywany do bledow krytycznych. recover lapie panic i pozwala na graceful recovery — typowo w middleware API.

Wzorzec middleware recovery

Kazdy serwer HTTP powinien miec middleware, ktory lapie niezaplanowane paniki i zwraca kod 500 zamiast zabijac caly proces. W Gin i Echo jest to wbudowane (Recovery()), w czystym net/http implementujemy recznie.

Go modules — go.mod

Od Go 1.11 zarzadzanie zaleznosci odbywa sie przez modul system. Plik go.mod definiuje nazwe modulu i wersje zaleznosci. Nie trzeba ustawiac GOPATH — modul moze znajdowac sie gdziekolwiek.

Podstawowe komendy

  • go mod init github.com/user/projekt — inicjalizuje nowy modul
  • go get github.com/gin-gonic/gin@v1.9.1 — dodaje zaleznosc
  • go mod tidy — usuwa nieuzywane zaleznosci, pobiera brakujace
  • go mod vendor — kopiuje zaleznosci do katalogu vendor/
  • go list -m all — lista wszystkich zaleznosci z wersjami

Struktury i interfejsy dla API

Go uzywa struktur jako modeli danych. Tagi JSON (`json:"pole"`) kontroluja serializacje. Interfejsy definiuja kontrakty — np. http.Handler jest interfejsem z jedna metoda ServeHTTP.

Wzorzec request/response DTO

Typowy projekt Go API rozdziela modele bazy danych od modeli HTTP — dzieki temu nie eksponuje wewnetrznych pol (np. hasla) i latwiej waliduje dane wejsciowe.

JSON marshal i unmarshal

Pakiet encoding/json serializuje struktury Go do JSON (Marshal) i deserializuje JSON do struktur (Unmarshal). Dla duzych ciagnosci i streamingu uzywamy json.Encoder / json.Decoder — unikamy buforowania calej odpowiedzi w pamieci.

Wskazowki dotyczace JSON

  • Uzyj omitempty, zeby pominac zerowe pola: `json:"name,omitempty"`
  • json:"-" wyklucza pole z serializacji (np. hasla, wewnetrzne ID)
  • Dla dynamicznych danych uzyj map[string]any lub json.RawMessage
  • json.Number zamiast float64 gdy potrzebujesz dokladnych liczb
  • Zaimplementuj json.Marshaler / json.Unmarshaler dla niestandardowej logiki

Obsuga bledow — idiomy Go

Go nie ma wyjatkow — bledy sa zwracanymi wartosciami. Funkcje zwracaja (wynik, error). Bledy nalezy obsluzyc natychmiast po otrzymaniu. Od Go 1.13 mozna owijac bledy przez fmt.Errorf("kontekst: %w", err) i rozwijac przez errors.Is / errors.As.

Centralna obsluga bledow HTTP

Wzorzec polega na zdefiniowaniu typu bledu API (APIError) zawierajacego kod statusu i komunikat, a nastepnie obsludze go w jednym miejscu — najczesciej w middleware lub funkcji pomocniczej respond().
