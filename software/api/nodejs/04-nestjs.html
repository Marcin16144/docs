NestJS

Framework enterprise-grade dla Node.js — modularna architektura, DI, dekoratory i pelna skalowalnosc

Filozofia NestJS

NestJS to framework zbudowany na Express (lub opcjonalnie Fastify), inspirowany Angularem. Wprowadza scisla strukture architektoniczna opartą na modulach, kontrolerach i serwisach — tzw. tryade MCS. Uzywa dekoratorow TypeScript intensywnie, a wbudowany kontener Dependency Injection (DI) zarzadza cyklem zycia zaleznosci.

NestJS jest szczegolnie polecany dla duzych zespolow i projektow enterprise, gdzie spójnosc kodu i testowalnosc sa priorytetem. Dla malych projektów moze byc nadmiarowy — wtedy lepszy bedzie Express lub Fastify.

Tryada Module / Controller / Service

// === users.module.ts ===
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { UsersController } from './users.controller';
import { UsersService } from './users.service';
import { User } from './entities/user.entity';

@Module({
  imports: [TypeOrmModule.forFeature([User])], // rejestracja encji w module
  controllers: [UsersController],
  providers: [UsersService],
  exports: [UsersService], // udostepnij innym modulom
})
export class UsersModule {}

// === users.controller.ts ===
import {
  Controller, Get, Post, Put, Delete,
  Param, Body, Query, HttpCode, HttpStatus,
  UseGuards, ParseUUIDPipe,
} from '@nestjs/common';
import { UsersService } from './users.service';
import { CreateUserDto } from './dto/create-user.dto';
import { UpdateUserDto } from './dto/update-user.dto';
import { JwtAuthGuard } from '../auth/jwt-auth.guard';

@Controller('users')          // prefix trasy: /users
@UseGuards(JwtAuthGuard)      // guard dla calego kontrolera
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get()
  findAll(@Query('page') page = 1, @Query('limit') limit = 20) {
    return this.usersService.findAll({ page: +page, limit: +limit });
  }

  @Get(':id')
  findOne(@Param('id', ParseUUIDPipe) id: string) {
    return this.usersService.findOne(id);
  }

  @Post()
  @HttpCode(HttpStatus.CREATED)
  create(@Body() createUserDto: CreateUserDto) {
    return this.usersService.create(createUserDto);
  }

  @Put(':id')
  update(@Param('id', ParseUUIDPipe) id: string, @Body() dto: UpdateUserDto) {
    return this.usersService.update(id, dto);
  }

  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  remove(@Param('id', ParseUUIDPipe) id: string) {
    return this.usersService.remove(id);
  }
}

DTO z class-validator i class-transformer

DTO (Data Transfer Object) definiuje ksztalt danych wejsciowych. class-validator dostarcza dekoratory walidacyjne, a class-transformer przeksztalca plain objects na instancje klas. NestJS laczy je przez globalny ValidationPipe.

// === dto/create-user.dto.ts ===
import {
  IsString, IsEmail, IsEnum, IsOptional,
  MinLength, MaxLength, IsInt, Min, Max,
  IsStrongPassword,
} from 'class-validator';
import { Transform, Type } from 'class-transformer';

export enum UserRole { ADMIN = 'admin', USER = 'user', MODERATOR = 'moderator' }

export class CreateUserDto {
  @IsString()
  @MinLength(2)
  @MaxLength(100)
  @Transform(({ value }) => value.trim()) // usun biale znaki
  name: string;

  @IsEmail()
  @Transform(({ value }) => value.toLowerCase())
  email: string;

  @IsStrongPassword({ minLength: 8, minNumbers: 1, minSymbols: 1 })
  password: string;

  @IsEnum(UserRole)
  @IsOptional()
  role?: UserRole = UserRole.USER;

  @IsInt()
  @Min(0)
  @Max(120)
  @IsOptional()
  @Type(() => Number) // konwersja stringa na liczbe (z query params)
  age?: number;
}

Dependency Injection w NestJS

Kontener DI NestJS zarzadza cyklem zycia dostawcow (providers). Domyslny zakres to Singleton — jedna instancja serwisu na caly modul. Dostepne sa tez zakresy REQUEST (nowa instancja na zapytanie) i TRANSIENT (nowa instancja przy kazdym wstrzyknieciu).

Dekorator Cel Zakres Przyklad uzycia
@Injectable() Oznacza klase jako dostawce DI Singleton (domyslnie) Serwisy, repozytoria, strategie
@Inject(TOKEN) Wstrzykuje przez token (nie klase) Dowolny Konfiguracja, wartosci prymitywne
@Optional() Zaleznosc opcjonalna (moze byc undefined) Dowolny Feature flags, opcjonalne integracje
@Global() Modul dostepny wszedie bez importu Singleton DatabaseModule, ConfigModule
useFactory Fabryczna inicjalizacja dostawcy Singleton / async Polaczenie z baza danych

ConfigModule i zmienne srodowiskowe

@nestjs/config integruje dotenv z systemem DI NestJS. ConfigService jest wstrzykiwany do serwisow i zapewnia typowane pobieranie zmiennych. Walidacje zmiennych srodowiskowych mozna zdefiniowac przy uzyciu Joi lub class-validator.

Guards, Interceptors, Pipes, Filters

Guards (CanActivate)

Guard decyduje, czy zapytanie moze dotrzec do handlera. Implementuje interfejs CanActivate z metoda canActivate(context): boolean | Promise | Observable. Uzywany do autentykacji i autoryzacji (RBAC).

Interceptors

Interceptor otacza handler — moze modyfikowac zapytanie PRZED i odpowiedz PO wykonaniu. Implementuje NestInterceptor. Uzywany do logowania czasu odpowiedzi, transformacji danych wyjsciowych, cache'owania.

Pipes

Pipe transformuje lub waliduje dane wejsciowe przed dotarciem do handlera. Wbudowane: ValidationPipe, ParseIntPipe, ParseUUIDPipe, DefaultValuePipe.

Exception Filters

Filter przechwytuje wyjatki i formatuje odpowiedz bledu. Wbudowany HttpExceptionFilter obsluguje HttpException. Mozna tworzyc wlasne filtry dla specyficznych typow bledow.

// === jwt-auth.guard.ts ===
import { Injectable, ExecutionContext, UnauthorizedException } from '@nestjs/common';
import { AuthGuard } from '@nestjs/passport';
import { Reflector } from '@nestjs/core';
import { IS_PUBLIC_KEY } from './decorators/public.decorator';

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private reflector: Reflector) { super(); }

  canActivate(context: ExecutionContext) {
    // Sprawdz metadane @Public() — jesli publiczny, pomijamy guard
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (isPublic) return true;
    return super.canActivate(context);
  }
}

// === Globalny filter wyjatkow ===
import { ExceptionFilter, Catch, ArgumentsHost, HttpException } from '@nestjs/common';

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse();
    const status = exception.getStatus();
    const exceptionResponse = exception.getResponse();

    response.status(status).json({
      statusCode: status,
      timestamp: new Date().toISOString(),
      error: typeof exceptionResponse === 'string'
        ? exceptionResponse
        : (exceptionResponse as any).message,
    });
  }
}

CQRS Module

Modul @nestjs/cqrs implementuje wzorzec Command Query Responsibility Segregation. Rozdziela operacje zapisu (Commands) od odczytu (Queries) i wprowadza Event Sourcing. Idealny dla zlozonych domen biznesowych.

NestJS + Prisma vs TypeORM

W 2025/2026 Prisma jest popularniejszym wyborem niz TypeORM dla nowych projektow NestJS. Prisma oferuje lepsze typowanie, migracje i Prisma Studio. TypeORM nadal dominuje w starszych projektach i gdy potrzebne sa zaawansowane relacje ORM (lazy loading, inheritance).

Pulapki DI — scope REQUEST

Uzycie Scope.REQUEST w serwisie powoduje, ze wszystkie serwisy wyzej w lancuchu DI TEZ staja sie REQUEST-scoped. Moze to znaczaco obnizyc wydajnosc. Uzywaj REQUEST scope tylko gdy naprawde potrzebujesz dostepu do obiektu request w serwisie.
