Deployment Node.js API

PM2, Docker, docker-compose, platformy chmurowe, graceful shutdown, health check i zarzadzanie env

Przeglad strategii deploymentu

Deployment aplikacji Node.js mozna zrealizowac na wiele sposobow — od prostego PM2 na VPS, przez kontenery Docker, po zarzadzane platformy chmurowe. Wybor zalezy od wymagan projektu: skalowalnosc, budzet, kontrola infrastruktury i wielkosc zespolu.

Strategia Kontrola Zlozonosc Koszt Kiedy stosowac
PM2 na VPS Pelna Srednia Niski Malezesne projekty, pelna kontrola OS
Docker + VPS Pelna Srednia-wysoka Niski-sredni Reprodukowalny deployment, izolacja
Railway / Render Ograniczona Niska Sredni Szybki start, brak DevOps w zespole
Fly.io Srednia Srednia Sredni Globalny deployment, edge regions
AWS/GCP/Azure (managed) Pelna Wysoka Wysoki Enterprise, compliance, duze zespoly

PM2 — Process Manager

PM2 to produkcyjny menadzer procesow dla Node.js. Zapewnia: automatyczny restart po awarii, tryb cluster (wiele procesow na wszystkich CPU), rotacje logow, monitorowanie oraz wbudowany load balancer. Konfiguracja przez plik ecosystem.config.js.

// ecosystem.config.js — konfiguracja PM2
module.exports = {
  apps: [
    {
      name: 'api-server',
      script: './dist/index.js',
      instances: 'max',           // uruchom tyle instancji ile CPU (cluster mode)
      exec_mode: 'cluster',       // load balancing miedzy instancjami
      watch: false,               // wylacz watch w produkcji
      max_memory_restart: '500M', // restart jesli proces przekroczy 500 MB RAM

      // Zmienne srodowiskowe
      env: {
        NODE_ENV: 'development',
        PORT: 3000,
      },
      env_production: {
        NODE_ENV: 'production',
        PORT: 3000,
      },

      // Rotacja logow
      log_date_format: 'YYYY-MM-DD HH:mm:ss',
      error_file: './logs/error.log',
      out_file: './logs/out.log',
      merge_logs: true,

      // Graceful shutdown — czekaj max 5 sekund na zakonczenie zapytan
      kill_timeout: 5000,
      wait_ready: true,           // czekaj na process.send('ready')
      listen_timeout: 10000,

      // Restart strategy
      max_restarts: 10,
      min_uptime: '30s',          // minimalna czas dzialania by nie uznac za crash loop
      restart_delay: 1000,
    }
  ],

  deploy: {
    production: {
      user: 'deploy',
      host: 'myserver.com',
      ref: 'origin/main',
      repo: 'git@github.com:user/repo.git',
      path: '/var/www/api',
      'post-deploy': 'npm install && npm run build && pm2 reload ecosystem.config.js --env production',
    }
  }
};

// Komendy PM2:
// pm2 start ecosystem.config.js --env production
// pm2 reload api-server          # zero-downtime reload (cluster mode)
// pm2 logs api-server --lines 100
// pm2 monit                      # interaktywny monitor
// pm2 save && pm2 startup        # autorestart po restarcie serwera

Docker — multi-stage Dockerfile

Multi-stage build redukuje rozmiar finalnego obrazu Docker przez oddzielenie etapu budowania (kompilacja TypeScript, instalacja devDependencies) od etapu produkcyjnego (tylko runtime i zaleznosci produkcyjne). Finalny obraz moze byc o 60-80% mniejszy.

# Dockerfile — multi-stage build dla Node.js 22
# ============ STAGE 1: Builder ============
FROM node:22-alpine AS builder

WORKDIR /app

# Kopiuj tylko package files — warstwa jest cachowana jesli nie zmienily sie zaleznosci
COPY package*.json ./
RUN npm ci --include=dev          # instaluj tez devDependencies (tsc, typy)

# Kopiuj kod zrodlowy i kompiluj
COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build                 # tsc -> dist/

# ============ STAGE 2: Production ============
FROM node:22-alpine AS production

# Bezpieczenstwo: nie uruchamiaj jako root
RUN addgroup -g 1001 -S nodejs && adduser -S nodeuser -u 1001 -G nodejs

WORKDIR /app

# Kopiuj tylko package files produkcyjne
COPY package*.json ./
RUN npm ci --omit=dev --ignore-scripts && npm cache clean --force

# Kopiuj skompilowany kod z buildera
COPY --from=builder /app/dist ./dist

# Zmien wlasciciela plikow
RUN chown -R nodeuser:nodejs /app
USER nodeuser

# Metadane obrazu
LABEL org.opencontainers.image.source="https://github.com/user/repo"
LABEL org.opencontainers.image.description="My API Server"

EXPOSE 3000

# Healthcheck wbudowany w Docker
HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/health', r => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"

CMD ["node", "dist/index.js"]

# --- Roznice alpine vs slim ---
# node:22-alpine  (~65 MB)  — minimalistyczny, musl libc, brak niektorych narzedzi
# node:22-slim    (~180 MB) — Debian bez zbednych paczek, glibc, lepsza kompatybilnosc
# node:22         (~950 MB) — pelny Debian — tylko do developmentu!

docker-compose — lokalne srodowisko

# docker-compose.yml — API + PostgreSQL + Redis
services:
  api:
    build: { context: ., dockerfile: Dockerfile, target: production }
    ports: ['3000:3000']
    environment:
      NODE_ENV: production
      DATABASE_URL: postgresql://postgres:secret@postgres:5432/mydb
      REDIS_URL: redis://redis:6379
      JWT_SECRET: ${JWT_SECRET}           # z pliku .env hosta
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_healthy }
    restart: unless-stopped
    networks: [app-network]

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: mydb
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres-data:/var/lib/postgresql/data
      - ./scripts/init.sql:/docker-entrypoint-initdb.d/init.sql
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U postgres -d mydb']
      interval: 10s
      timeout: 5s
      retries: 5
    networks: [app-network]

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes --requirepass ${REDIS_PASSWORD}
    volumes: [redis-data:/data]
    healthcheck:
      test: ['CMD', 'redis-cli', 'ping']
      interval: 10s
    networks: [app-network]

volumes: { postgres-data: {}, redis-data: {} }
networks: { app-network: { driver: bridge } }

Graceful Shutdown

Graceful shutdown to proces bezpiecznego zamkniecia aplikacji: zatrzymanie przyjmowania nowych polaczen, dokonczenie obslugi biezacych zapytan, zamkniecie polaczen z baza danych i innymi zasobami. Bez tego, zatrzymanie procesu moze przerwac aktywne transakcje i uszkodzic dane.

// graceful-shutdown.ts — implementacja dla Express + Prisma
import { Server } from 'http';
import { PrismaClient } from '@prisma/client';

export function setupGracefulShutdown(server: Server, prisma: PrismaClient) {
  let isShuttingDown = false;

  async function shutdown(signal: string) {
    if (isShuttingDown) return;
    isShuttingDown = true;

    console.log(`\n[Shutdown] Otrzymano ${signal} — rozpoczynam graceful shutdown...`);

    // 1. Zatrzymaj przyjmowanie nowych polaczen
    server.close(async (err) => {
      if (err) {
        console.error('[Shutdown] Blad zamkniecia serwera HTTP:', err);
        process.exit(1);
      }

      console.log('[Shutdown] Serwer HTTP zamkniety');

      try {
        // 2. Zamknij polaczenie z baza danych
        await prisma.$disconnect();
        console.log('[Shutdown] Polaczenie z baza danych zamkniete');

        // 3. Inne zasoby (Redis, kolejki, etc.)
        // await redisClient.quit();
        // await messageQueue.close();

        console.log('[Shutdown] Aplikacja zamknieta pomyslnie');
        process.exit(0);
      } catch (cleanupErr) {
        console.error('[Shutdown] Blad podczas czyszczenia zasobow:', cleanupErr);
        process.exit(1);
      }
    });

    // Wymuszony exit po 30 sekundach (deadline)
    setTimeout(() => {
      console.error('[Shutdown] Timeout! Wymuszone zamkniecie.');
      process.exit(1);
    }, 30_000).unref(); // .unref() — nie blokuje event loop
  }

  // Sygnaly systemowe
  process.on('SIGTERM', () => shutdown('SIGTERM')); // Docker stop, Kubernetes, PM2
  process.on('SIGINT',  () => shutdown('SIGINT'));  // Ctrl+C w terminalu

  // Niezlapane bledy — loguj i zamknij
  process.on('uncaughtException', (err) => {
    console.error('[FATAL] Niezlapany wyjatek:', err);
    shutdown('uncaughtException');
  });

  process.on('unhandledRejection', (reason) => {
    console.error('[FATAL] Niezlapane odrzucenie Promise:', reason);
    shutdown('unhandledRejection');
  });

  // Sygnalizacja gotowosci PM2 (wait_ready: true w ecosystem.config.js)
  if (process.send) process.send('ready');
  console.log('[App] Serwer gotowy, czeka na polaczenia');
}

Health Check Endpoint

Endpoint /health (lub /healthz) jest sprawdzany przez load balancery, Docker, Kubernetes i platformy PaaS. Powinien sprawdzic krytyczne zaleznosci (baza danych, cache) i odpowiedziec szybko.

Zarzadzanie zmiennymi srodowiskowymi

Zmienne srodowiskowe sa standardem dla konfiguracji aplikacji (12-factor app). Wazne zasady: nie commituj .env do repozytorium, uzyj .env.example z placeholderami, waliduj zmienne przy starcie aplikacji.

dotenv vs @dotenvx/dotenvx

dotenv to klasyczna biblioteka ladowania .env. @dotenvx/dotenvx (2024) rozszerza dotenv o: szyfrowanie plikow .env (mozna je commitowac!), wsparcie dla wielu srodowisk (.env.production, .env.staging) i CLI do zarzadzania sekretami.

Zero-downtime deployment z PM2

W trybie cluster, komenda pm2 reload app-name (nie restart) wykonuje rolling reload — restartuje instancje jedna po drugiej, zachowujac ciaglosc dzialania serwisu. Nowe zapytania trafiaja do juz zrestartowanych instancji podczas gdy pozostale konczą biezace zapytania.

node:alpine — potencjalne problemy

Alpine uzywa musl libc zamiast glibc. Niektore natywne moduly npm (np. bcrypt, sharp, canvas) moga nie dzialac lub wymagac kompilacji. Jesli uzywasz natywnych modulow — wybierz node:22-slim (Debian, glibc) lub dodaj do Dockerfile pakiety budujace: apk add --no-cache python3 make g++.

Walidacja zmiennych srodowiskowych przy starcie

Uzyj Zod lub envalid do walidacji process.env przy starcie aplikacji. Jesli brakuje wymaganej zmiennej — aplikacja powinna natychmiast sie zatrzymac z czytelnym komunikatem bledu, zamiast dzialac z nieprawidlowa konfiguracja i crashowac pozniej.
